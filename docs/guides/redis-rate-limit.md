# Совместные квоты через Redis/phpredis

Этот backend нужен, когда квоту должны совместно учитывать несколько workers или
экземпляров SDK. Обычный локальный режим не требует Redis. Общая настройка лимитов —
в [справочнике rate limit](client-config/rate-limit.md).

## Подключение

Требуется расширение phpredis >= 6.2 и Redis standalone >= 7.0. RedisCluster, Predis,
Sentinel orchestration и active-active в этом адаптере не поддерживаются. Установку
расширения/сервера обеспечивает приложение; ext-redis не входит в обязательный require SDK.

```php
use Brahmic\ApiSutra\Config\ClientConfig;
use Brahmic\ApiSutra\Config\RateLimitConfig;
use Brahmic\ApiSutra\RateLimiting\Backends\PhpRedisRateLimitBackend;

$redis = new Redis();
$redis->connect('127.0.0.1', 6379, 1.0);

$config = new ClientConfig(
    baseUrl: 'https://api.example',
    rateLimit: new RateLimitConfig(limit: 100, period: 60),
    rateLimitBackend: new PhpRedisRateLimitBackend(
        redis: $redis,
        scope: 'provider-example/account-42',
    ),
);
```

`scope` — стабильная группа совместного учёта, выбранная приложением или SDK провайдера.
Один аккаунт может иметь общую квоту у нескольких клиентов, разные аккаунты — разные
квоты. Ядро не угадывает это по URL/credentials. Не меняйте scope при каждом запросе
или ротации токена. Для объединения должны совпадать сервер/DB, scope и Redis prefix
соединений; технические ключи квот строит и хеширует SDK.

## Выделенное соединение и время

Соединение предназначено адаптеру; каждый worker открывает своё. Адаптер отключает
OPT_MAX_RETRIES, требует обычный режим без MULTI/pipeline и serializer/compression.
Redis prefix поддерживается. Не передавайте соединение, на котором другой код
одновременно меняет режим, транзакцию или options. Секреты соединения не логируются.

`ioTimeoutMs` по умолчанию 1000 ms. Перед I/O адаптер сокращает read timeout до минимума
своего лимита и оставшегося бюджета вызова. Положительный прежний read timeout затем
восстанавливается. При исходном read timeout <= 0 адаптер сначала задаёт выделенному
соединению конечный default: установка обратно нуля в phpredis 6.2 может нарушить
следующее чтение. Пользователю не нужно самостоятельно реализовывать этот обход.
Подключение приложения происходит до SDK-вызова; его connect timeout задаётся отдельно.

Redis желательно располагать близко по сети. Сетевое обращение и ожидание квоты входят
в RetryConfig.totalTimeoutMs, если он задан; ClientConfig.timeout ограничивает HTTP-попытку.
Без общего бюджета ожидание освобождения квоты может продолжаться, но каждое отдельное
обращение к Redis ограничено. SDK не обещает жёсткое завершение ровно в миллисекунду
при остановке процесса или системных задержках.

## Гарантии и доступность

Обычно один EVALSHA проверяет весь набор квот; после NOSCRIPT выполняется EVAL с тем
же постоянным script. Это безопасно, поскольку NOSCRIPT означает отсутствие исполнения.
Время окон задаёт серверный TIME. Отказ по квоте не изменяет счётчики и их окна.

Redis становится зависимостью доступности: его ошибка прекращает вызов **даже при
свободной квоте**. SDK не переключается в память и не повторяет неизвестное списание.
При потере ответа команда могла исполниться; HTTP не отправляется, разрешения могут
остаться потраченными. Повтор задания — решение приложения.

Для ключей квот требуется отсутствие eviction. Практический вариант — выделенный
Redis с maxmemory-policy=noeviction и контролем памяти. Отдельная logical DB не
защищает ключи от общей политики eviction сервера. При OOM запись может отказать;
это ошибка выполнения, а не разрешение запроса. Очистка данных, restart без сохранения
или откат реплики при failover могут обнулить счётчики. Строгая сохранность при любой
аварии не обещается.

Lua предварительно проверяет все состояния и записывает счётчики одной MSET, затем
устанавливает абсолютные TTL. Ошибка после MSET может оставить все разрешения списанными
и часть TTL неустановленными; HTTP не выполняется. Состояние содержит конец окна,
но корректное освобождение памяти при нарушенных ACL не гарантируется. Автоматического
rollback/refund нет. Приложение обеспечивает нужные права и эксплуатацию сервера.

## Laravel

Используйте тот же адаптер при сборке SDK-клиента в ServiceProvider. Отдельный
Laravel-адаптер или автоматическое включение Redis не нужны:

```php
use Brahmic\ApiSutra\RateLimiting\Backends\PhpRedisRateLimitBackend;
use Illuminate\Support\Facades\Redis;

$backend = new PhpRedisRateLimitBackend(
    redis: Redis::connection('apisutra')->client(),
    scope: $quotaScope,
);
```

`apisutra` — выделенное именованное соединение в config/database.php с драйвером
phpredis. Оно может использовать тот же подходящий Redis-сервер. `$quotaScope`
определяет приложение/SDK провайдера; в ClientConfig передаётся готовый `$backend`.
Соединения и backend не помещаются в config-файлы: там остаются сериализуемые значения,
а объекты создаёт контейнер после загрузки конфигурации. Это совместимо с config:cache.
Подробности общей интеграции — в [Laravel-гайде](laravel.md).

## Проверки

Реальные конкурентные workers, потеря подтверждения, ACL до/после записи, OOM,
NOSCRIPT, сетевой timeout и Laravel-рецепт проверяются отдельно от обычных unit tests.
Для локального Redis suite выполните `composer test:redis`: команда создаёт и очищает
изолированный стенд. Требования и ручной запуск Laravel-проверки — в
[гайде тестирования](testing.md#redis-rate-limit).
Нельзя направлять этот стенд на рабочий Redis: часть сценариев меняет ACL, script cache
и настройки памяти выделенного тестового сервера.
