# Сопровождение документации

Публичная документация обслуживает автора SDK и пользователя готового клиента.
Изменение ядра описывается отдельно в `docs/development/`. Инструкции checkout находятся
в [.agents/documentation.md](../../.agents/documentation.md); рабочие доказательства — в workflow.

## Владение содержанием

| Слой | Что хранить |
| --- | --- |
| `docs/start/` | Задача, исходные данные, порядок, критерии результата |
| `docs/guides/` | Практика со ссылками на контракт и исполняемый образец |
| `docs/reference/` | Один полный владелец параметров, приоритетов и ограничений |
| `docs/glossary/` | Короткое определение и ссылка на владельца |
| `docs/example/` | Поставляемые исходники, фикстуры и запуск |
| `docs/migration/` | Действия при смене версии |
| `docs/development/` | Общий вход разработчика ApiSutra, устройство ядра и проверки checkout |

Агент использует маршрут своей задачи: пользователь SDK — `docs/start/`,
разработчик ApiSutra — [docs/development/README.md](README.md).
`docs/start/agent.md` содержит передачу задания для SDK, а не отдельный набор контрактов.

## Изменить контракт

Сверьте декларацию с `src/` и поведение с целевым тестом. Измените тематического
владельца, затем примеры и короткие ссылки из остальных слоёв. Не копируйте таблицу
приоритетов в glossary, guide и attributes. Справочник атрибутов задаёт сигнатуру
декларации и ссылается на поведение в тематическом разделе.

Для публичных PHP-имён используйте явный реестр
[docs-api.json](../../tests/Support/docs-api.json). Проверка Reflection сверяет классы,
публичность, параметры и типы, не создавая пользовательские object-default значения.
Для атрибутов отдельно сравнивается текст конструктора и опубликованная сигнатура: default
не вычисляется, но изменение его выражения требует обновить документацию.
Этот реестр не доказывает семантику: побочные эффекты defaults с `new`, приоритеты и ограничения
подтверждаются исходниками и наблюдаемыми сценариями.

## Исполняемые примеры

Классы примера находятся в отдельных PSR-4 файлах с namespace. Руководство ссылается
на эти файлы. Smoke исполняет опубликованный файл, включая архив без require-dev;
копировать пример внутрь теста нельзя. Фрагмент справочника может показывать
отдельный вызов, но должен обозначать внешние переменные и требуемый контекст.

Laravel-пример выполняется с реальными зависимостями отдельно. Для обычной проверки
используйте fake: внешнее API и credentials не должны требоваться для чтения quickstart.

## Перенести страницу

При переносе сохраните полезное содержание и обновите ссылки текущего комплекта,
включая реестр деклараций. Удалите прежнюю страницу и неиспользуемые якоря.
При перемещении раздела разработки обновите исключения Git/Composer архивов
и классификацию документов в проверяющих инструментах.
Каждая опубликованная страница содержит актуальное руководство, справку или индекс.
Ссылки из `.workflow/` не требуют сохранять старые публичные адреса: история
доступна в Git, а рабочие отчёты относятся к зафиксированному в них состоянию.

Лимиты строк: корневой README с обзором пакета и тремя примерами 180, индекс 150,
маршрут 200, guide 300, reference 320, glossary 180,
development 220; дополнительно 24 KiB на файл. История изменений и версионные
release notes исключены. Если тема не помещается, разделите её по самостоятельным
задачам; не создавайте «часть 1/2».

## Проверки

```bash
composer check-docs
composer analyse-docs
python3 tests/Support/test-check-docs.py
git diff --check
python3 tests/Support/check-package.py --staged
```

`check-docs` проверяет локальные пути, якоря, reference-style ссылки, размер,
достижимость страниц, запрещённые зависимости публичного комплекта, страницы-переходы,
блоки прежних разделов, пустые определения словаря, реестр API и пять опубликованных
примера. `--report` сохраняет подробный JSON;
`--navigation-only` проверяет документацию распакованного архива.

В [Docs CI](../../.github/workflows/docs.yml) выполняются `composer check-docs` и
`composer analyse-docs` на PHP 8.4. Workflow запускается на push, pull request и
вручную; техническая ветка `badges` исключена из push. Изменения src тоже запускают
проверку соответствия документации API. Бейдж Docs CI в README показывает результат
push-проверки ветки master; бейдж docs ведёт к пользовательской документации.

Неблагоприятные случаи проверяющего инструмента закреплены отдельными тестами.
Внешние веб-страницы, содержательная полнота API, смысл SQL/JSON/команд и корректность
всех контекстных PHP-фрагментов автоматически не доказываются: для них нужна
редакционная сверка и целевые проверки. Совпадение числа файлов не заменяет эту работу.

`check-package` по умолчанию берёт HEAD, `--staged` — Git index. Поэтому перед приёмкой
изменённого дерева добавьте нужные файлы в index и зафиксируйте проверенный tree
в отчёте. Git и Composer архивы должны совпасть и установить runtime-зависимости.
