# Устройство атрибутов

Как ядро читает, кеширует и обрабатывает атрибуты. Публичные декларации находятся
в [справочнике атрибутов](../reference/attributes/README.md), а места вызова
обработчиков — в [пайплайне](pipeline.md#подключение-расширений).

## Роль атрибутов
Атрибуты — декларативный слой конфигурации запросов и DTO. Они позволяют описывать:
- HTTP‑метод и endpoint
- источники данных (query/body/path/header/file)
- правила валидации и трансформации
- поведение пайплайна (cache/retry/timeout/ratelimit)

## Где используются
- **RequestSpecResolver** — собирает метаданные запроса (HTTP, responseType, behavior).
- **Serializer** — применяет request‑атрибуты для сборки PreparedRequest.
- **Hydrator** — применяет DTO‑атрибуты при гидрации.
- **HookRunner** — исполняет hook‑атрибуты.
- **AttributeRegistry** — запускает кастомные обработчики атрибутов.

## Резолв и кеш
- Метаданные атрибутов читаются рефлексией.
- `AttributeMetadataCache` сохраняет описания, чтобы не сканировать класс повторно.
- В гидраторе и сериализаторах значения атрибутов с объектными аргументами создаются
  для текущего узла; scalar/enum и массивы значений позволяют переиспользовать шаблон.
  Defaults конструктора вычисляет PHP при пропущенном аргументе.
- Клиент отключает кеш в `Environment::Local/Testing` и включает в Production.
  `Hydrator::default()` работает без него, `Hydrator::forRules()` создаёт собственный
  включённый кеш. Результат изоляции объектов от режима кеша не зависит.

Момент вызова пользовательского конструктора различается для
[default DTO](../reference/dto/lifecycle.md#значения-по-умолчанию-и-изоляция-объектов) и
[аргумента атрибута](../reference/dto/lifecycle.md#объектные-аргументы-атрибутов).
Кеш метаданных не предназначен для общего изменяемого состояния.

## Кастомные атрибуты (AttributeRegistry)

[AttributeRegistry](../../src/Attributes/AttributeRegistry.php) регистрирует соответствия
«класс атрибута → класс обработчика». Resolver реестра создаёт обработчик при первом
обращении; затем его экземпляр переиспользуется. Данные текущего исполнения
передаются через контекст.

### Типы обработчиков
- **AttributeHandlerInterface** — простой обработчик:
  получает атрибут, Reflection‑цель и `PipelineContext`.
- **AttributeContextHandlerInterface** — контекстный обработчик:
  получает `AttributeContext` с `PipelineStage`, `type`, `data` и списком
  атрибутов класса; может вернуть модифицированные данные.

### Порядок обхода
1) Атрибуты класса
2) Атрибуты свойств
Порядок соответствует Reflection‑порядку объявления.

## AttributeContext
Контекст, который получает обработчик:
- `attribute` — инстанс атрибута
- `target` — ReflectionClass или ReflectionProperty
- `type` — Request/Dto
- `stage` — PipelineStage
- `context` — PipelineContext
- `data` — текущие данные (если обработчик работает со стадией)

## StageProcessor

`StageProcessor` связывает Pipeline с `AttributeRegistry::processStage()`.
Фактические точки вызова перечислены в [пайплайне](pipeline.md#подключение-расширений).
Контекстный обработчик может возвращать изменённые данные, которые передаются
следующему обработчику; вызывающая стадия определяет, как использовать итог.
Записи стадий в audit не запускают обработчики автоматически.

Регистрацию и передачу данных проверяет
[AttributeRegistryTest](../../tests/Unit/Attributes/AttributeRegistryTest.php).

## Ограничения
- Атрибуты не должны выполнять бизнес‑логику.
- Тяжёлые вычисления выносить в сервисы/хуки.
