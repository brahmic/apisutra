# Описать DTO

Начните с данных и требований, затем выберите способ декларации. PHPDoc `list<int>`
сам по себе не проверяет элементы массива при гидратации.

## Выбрать способ

| Условие | Маршрут |
| --- | --- |
| Модели должны оставаться обычными PHP-классами | [Внешние правила](../guides/dto/plain-models.md) |
| Модель принадлежит SDK и декларации удобно хранить на свойствах | [Атрибуты DTO](../guides/dto/attribute-models.md) |
| Одному классу нужны разные mapping/strict/extras у разных клиентов | [Набор клиента](../reference/dto/field-rules.md) |

Смешивание способов имеет явные [ограничения конфликтов](../reference/dto/field-rules.md).
Не добавляйте атрибуты к внешней модели только ради подключения набора.

## Порядок описания

1. Зафиксируйте [имена и пути](../reference/dto/profiles.md), включая fallback.
2. Решите [присутствие, null и defaults](../reference/dto/defaults.md).
3. Задайте [формы объектов и списков](../reference/dto/shapes.md),
   [варианты](../reference/dto/variants.md) и [строгие скаляры](../reference/dto/scalars.md).
4. Подключите casts только для нужных преобразований. Вложенная гидратация внутри
   пользовательского обработчика использует [HydrationScope](../reference/dto/scope.md).
5. Если нельзя терять неизвестные поля, объявите [receiver](../reference/dto/extras.md),
   например `_extra`. Это настраиваемое свойство, а не зарезервированный ключ ответа.
6. Проверьте [исходящее представление](../reference/serialization/README.md).
   `toArray()` для приложения и сериализация в запросе клиента имеют разные задачи.

## Проверка результата

По реальным обезличенным фикстурам проверьте обычное значение, missing, null,
ошибочный тип, пустой объект/список и неизвестные поля. Для nested проверьте
[путь ошибки](../reference/dto/diagnostics.md). Отдельно проверьте ручное создание
DTO и его отправку: receiver исключается по классу и набору клиента.

[Исполняемые примеры](../example/README.md) дают исходники для обоих способов.
