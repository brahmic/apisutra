# План тестов по рекомендованным проверкам

## Цель
Зафиксировать минимальный набор проверок, который гарантирует корректную работу пагинации и rate‑limit после рефакторингов, без изменения бизнес‑логики.

- Добавлен RequestSpecResolver::clearCache() (на всякий случай для тестов/локалки).

---

## 1. Пагинация: поведение по умолчанию и offset‑based

### 1.1. Page‑based по умолчанию
**Суть:** если `offsetBased` не задан, работает классическая page‑based пагинация.  
**Проверка:**
- Создать paginable‑запрос без явного `offsetBased` (или без атрибута `#[Pagination]`, чтобы использовались defaults).
- Вызвать `paginate()->pages(1)` без `limit`.
- Ожидание: без ошибок, страница = 1, параметр страницы берётся из defaults (`page` / `paginationConfig->pageParam`).

**Почему важно:** это «нормальный» режим по умолчанию для большинства API.

### 1.2. Offset‑based требует limit
**Суть:** при `offsetBased: true` должен быть `limit`, иначе ошибка.  
**Проверка:**
- Запрос с `#[Pagination(pageParam: 'offset', limitParam: 'limit', offsetBased: true)]`.
- Вызвать `paginate()->pages(1)` без `limit`.
- Ожидание: `ConfigurationException` с понятным сообщением.

**Почему важно:** без limit offset вычисляется некорректно.

---

## 2. Цепочки опций + пагинация (пункт 2.2)

**Суть:** цепочка `withCache()->withPage()` не должна терять опции кеша.  
**Проверка:**
- Создать запрос, вызвать `withCache(300)->withPage(2)->withLimit(10)`.
- Убедиться, что:
  - `RequestExecution::getOptions()->getCacheOverride()` содержит `mode=CacheMode::Enabled` и TTL=300;
  - `RequestExecution::getPaginationOptions()` содержит `page=2`, `limit=10`.
- (Интеграционно) прогнать через pipeline с фейковым транспортом и проверить, что:
  - query содержит page/limit,
  - кеш‑ключ строится с учётом опций (не опускаются).

**Почему важно:** типичный DX‑сценарий «опции + пагинация» не должен ломаться.

---

## 3. Rate limit key стабилен и уникален (пункт 2.3)

**Суть:** ключ rate‑limit должен быть детерминированным и разным для разных `baseUrl`.  
**Проверка:**
- Подменить `RateLimiter` на тестовый, который запоминает полученный `$key`.
- Два вызова `RateLimitApplier->apply()` с одинаковым `baseUrl` → ключи равны.
- Вызов с другим `baseUrl` → ключ отличается.

**Почему важно:** предотвращает коллизии между разными API и гарантирует повторяемость.
