# Вопрос: контракт обработчиков атрибутов

## Предварительный анализ кода (текущее состояние)
- `AttributeRegistry::process()` вызывает `AttributeHandlerInterface::handle(attribute, reflection, context)` и кеширует метаданные через `AttributeMetadataCache`.
- `Pipeline` вызывает обработку атрибутов для request в начале `execute()` и для DTO после `hydrate()`.
- Серилизация и гидрация используют атрибуты напрямую (не через `AttributeRegistry`).
- В enum `PipelineStage` нет отдельных стадий для “prepare/validation”, есть `Started/BeforeSend/HttpRequest/HttpResponse/BeforeHydrate/AfterHydrate/Completed/Failed`.

## Исследование требований (документация)
- `docs/features/attributes.md` описывает `AttributeContext` и обработчик `handle(AttributeContext $ctx): mixed`, а также стадийность (Validation/Prepare/Hydration).
- `docs/architecture/07-attributes.md` фиксирует, что обработка встроенных атрибутов разнесена по `Serializer`/`Hydrator`/`Validator`/`Pipeline`.
- `docs/architecture/03-pipeline.md` задаёт порядок стадий и точку, где допустима модификация `PreparedRequest` и DTO через хуки.

## Границы ответственности (чтобы не ломать бизнес‑логику)
- Встроенные атрибуты (`Path/Query/Body/Header/From/Nested/Cast/Validate`) остаются в `Serializer`/`Hydrator`/`Validator`.
- `AttributeRegistry` обрабатывает **только кастомные** атрибуты.
- Контекстные обработчики могут модифицировать только данные стадии (`PreparedRequest` / DTO), а не менять порядок pipeline.

## Договорённости
Поддерживаем оба режима обработки (контракт архитектуры и контекстный). Выбор режима — за разработчиком. Детальные рекомендации для разработчиков добавим после реализации.

## Согласовано (по спорным вопросам)
- Новые значения в `PipelineStage` **не добавляем**, маппим контекстные стадии на существующие.
- Контекстные обработчики выполняются **до** hooks на той же стадии.
- Возврат `null` из контекстного обработчика означает **без изменений**.
- Исключения из обработчиков **не перехватываем** (fail‑fast, как и сейчас).

## Что делать и в каком порядке
1) **Ввести контекстный режим**
   - Добавить `AttributeContext` (VO) и новый интерфейс `AttributeContextHandlerInterface`.
   - Контекст должен включать: инстанс атрибута, цель (класс/свойство), reflection, `PipelineContext`, текущий `PipelineStage`, данные (опционально, например `PreparedRequest`/DTO), тип контекста (Request/DTO).
   - Контекст и его поля — readonly, без скрытой мутабельности.

2) **Расширить `AttributeRegistry`**
   - Добавить метод `processStage(..., PipelineStage $stage, mixed $data = null): mixed`.
   - Если handler поддерживает контекстный интерфейс — вызывать его и возвращать обновлённые данные.
   - Если handler реализует старый интерфейс — вызывать как сейчас (поведение без изменений).
   - Использовать существующий `AttributeMetadataCache`.
   - Явно задокументировать порядок выполнения: class‑атрибуты → property‑атрибуты, порядок декларации сохраняется.

3) **Обновить `Pipeline` без поломки бизнес‑логики**
   - Вызов `processStage` для request до валидации (stage `Started`, data `null`).
    - После сериализации и **до аутентификации** — вызвать `processStage` со stage `BeforeSend` и data = `PreparedRequest`; применять возвращённые изменения.
   - После `hydrate()` — вызвать `processStage` со stage `AfterHydrate` и data = DTO; применять возвращённые изменения.
   - Сохранить порядок хуков и поведение кеша/ретраев.

4) **Проверки консистентности (минимум)**
   - Старые обработчики работают как раньше (без регрессий).
   - Модификации `PreparedRequest` происходят **до** расчёта cache key и отправки.
   - Модификации DTO происходят **до** `AfterHydrate` hooks.
   - Кастомные обработчики не должны обходить `Validator` и `Serializer`.

## Риски и что учесть при реализации
- **Стадийность**: в текущем enum нет `Validation/Prepare`. Нельзя вводить скрытые стадии без согласования.
- **Возвраты**: нужно определить правило — возвращаемое значение полностью заменяет данные стадии или является «патчем».
- **Обработка исключений**: сейчас исключения атрибутов не перехватываются и прерывают pipeline.
- **Порядок с хуками**: важно зафиксировать, идут ли контекстные обработчики до/после соответствующих hook‑стадий.

## Спорные вопросы для согласования
1) Добавляем новые значения в `PipelineStage` (`Validation`, `Prepare`) или маппим на существующие (`Started`, `BeforeSend`)?
2) Контекстные обработчики выполняются **до** хуков или **после**?
3) Если `AttributeContextHandlerInterface` возвращает `null`, данные остаются без изменений или считаем это явным обнулением?
4) Нужно ли ловить исключения обработчиков и превращать в `ExecutionResult`?

## Итог
Такой порядок сохраняет текущую бизнес‑логику и даёт новый режим без ломки, а специфику обоих режимов можно закрепить в документации после реализации.
