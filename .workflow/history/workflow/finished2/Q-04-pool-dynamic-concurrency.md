# Вопрос: динамический расчёт concurrency в Pool

## Проблема
В `PoolExecutor` поддерживается `ConcurrencyResolverInterface`, но текущая реализация вычисляет concurrency один раз на старт исполнения. Если ожидалась динамическая коррекция по мере выполнения, поведение расходится с ожиданиями.

## Влияние на бизнес-логику
Динамическая регулировка нужна для адаптации к rate limit и внешним ограничениям. При фиксированном значении возможны лишние ошибки или более низкая пропускная способность при высоком лимите.

## Принятое решение (вариант A)
Фиксированная concurrency: вычисляется один раз на старт исполнения и считается максимальным уровнем параллелизма на весь пул.

## Почему так
- Совпадает с текущей реализацией `PoolExecutor` и моделью `Utils::eachLimit`.
- Предсказуемость поведения для SDK‑разработчиков.
- Минимальные риски для текущей архитектуры и тестового покрытия.

## Вопросы
- Нужен ли пересчёт concurrency после каждой завершённой задачи?
- Должны ли `stopOnFailure` и `concurrency` координироваться для ранней остановки?
- Достаточно ли одного расчёта на запуск для текущих требований?

## Рекомендованное решение
Явно закрепить модель расчёта: либо динамический пересчёт на каждом шаге, либо фиксированное значение на всю итерацию.

## Аргументация
Динамика даёт гибкость, но усложняет реализацию и тестирование. Фиксированная модель проще и стабильнее. Выбор должен быть отражён в документации, чтобы клиенты могли рассчитывать на корректное поведение.

## Нюансы реализации (чтобы не сломать бизнес-логику)
- **Единый расчёт**: `ConcurrencyResolverInterface`/callable вызывается один раз с `(pending=count, completed=0)`.
- **stopOnFailure**: не отменяет уже запущенные задачи, а только прекращает дозапуск новых.
- **Порядок результатов**: сохранять исходный порядок запросов (как сейчас через `ksort`).
- **Исключения**: ошибки должны превращаться в `ExecutionResult` и не ломать весь pool.
- **Idempotency**: пул используется только для независимых запросов.
- **Rate limit**: контроль происходит внутри pipeline; pool не должен дублировать throttling.
