# План: авто‑резолвинг клиента для DI‑запросов

## Цель
Сделать так, чтобы запросы могли DI‑иться в контроллерах и **автоматически находили “свой” клиент** без ручной конфигурации в приложении.

## Принципы
- Клиент регистрируется **в своём composer‑пакете** через ServiceProvider.
- Запросы **жёстко привязаны** к своему клиенту (по namespace).
- Никакой ручной настройки в приложении — только auto‑discovery.

## Шаги реализации
1) **Registry/Resolver в apisutra**
   - Ввести `ClientRegistry` (namespace → client class/instance).
   - Ввести `ClientResolverInterface` и реализацию по умолчанию.
2) **Namespace‑правило**
   - По умолчанию: `RootNamespace\\Requests\\*` принадлежит клиенту `RootNamespace\\Client`.
   - Разрешить override через явный конфиг в провайдере клиента.
3) **Интеграция с контейнером**
   - В `SdkServiceProvider` при `resolving(AbstractRequest)` подставлять клиент через resolver.
4) **Защита от “чужого клиента”**
   - При `setClient()` и/или `send()` валидировать соответствие namespace → client.
   - Несоответствие → `ConfigurationException` с понятным сообщением.
5) **Документация и тесты**
   - Тесты: DI‑запрос резолвит клиент; неверный клиент → ошибка; два клиента с одинаковыми именами запросов, но разными namespace — работают независимо.

## Примеры / юзкейсы (лаконично)
- **DI в контроллере:**
  - `public function __invoke(GetOrder $request) { return $request->send(); }`
- **Один проект — несколько клиентов:**
  - `Kontur\Requests\GetOrder` → `KonturClient`
  - `Other\Requests\GetOrder` → `OtherClient`
- **Ручное создание запроса:**
  - `$request = new Kontur\Requests\GetOrder(); $request->send();` — клиент подставляется автоматически
- **Неверный клиент:**
  - `$request->setClient($otherClient)` → исключение

## Финальные ожидания
- DI‑запросы отправляются без ручной конфигурации клиента.
- Запрос **не может** быть отправлен чужим клиентом.
- Множественные клиенты в одном приложении работают изолированно.
- Механизм не требует изменения приложения (auto‑discovery провайдеров).
