# План: пагинация и совместимость с readonly‑запросами

## Проблема
Пагинация сейчас устанавливается через `RequestPaginationHelper` с использованием `ReflectionProperty::setValue()`.  
Это ломается для `readonly` классов (PHP 8.3+), т.к. свойства нельзя менять после конструктора.

## Риски
- Невозможность использовать `readonly` для запросов с пагинацией.
- Скрытые ошибки при runtime‑изменении page/limit/cursor.

## Варианты решения

### Вариант A (рекомендуемый): отдельные PaginationOptions
1. Ввести `PaginationOptions` (VO) с `page/limit/cursor`.
2. Хранить `PaginationOptions` в `RequestExecution` (рядом с `RequestOptions`).
3. `withPage/withLimit/withCursor` изменяют `PaginationOptions`, не трогая свойства запроса.
4. `RequestPaginationHelper` сначала смотрит `PaginationOptions`, потом — fallback к свойствам запроса.

**Плюсы:** совместим с readonly, сохраняет DX.  
**Минусы:** усложняет пайплайн и сериализацию (нужно учитывать в Serializer/Paginator).

### Вариант B: запрет readonly для paginated‑запросов
1. Явно зафиксировать в документации ограничение: запросы с пагинацией не должны быть readonly.
2. Добавить явную проверку и исключение при попытке пагинации на readonly.

**Плюсы:** просто и быстро.  
**Минусы:** противоречит общей политике “readonly по умолчанию”.

### Вариант C: конструкторное клонирование
1. Для paginated‑запросов обязать наличие конструктора с page/limit/cursor.
2. `withPage/withLimit/withCursor` создают новый экземпляр через конструктор (без Reflection).

**Плюсы:** чисто и типобезопасно.  
**Минусы:** жесткие требования к API запросов.

## Критерии приёмки
- Пагинация работает для readonly‑классов (или явно запрещена/документирована).
- DX не ухудшается для разработчика.
- Бизнес‑логика пагинации не меняется.
