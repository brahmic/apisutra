# План: наблюдения/опциональные улучшения и рекомендованные проверки

## Цели
- Сохранить бизнес‑логику и DX, улучшить консистентность архитектуры.
- Зафиксировать решения по опциональным улучшениям и набор проверок.

## 1) Наблюдения / опциональные улучшения

### 1.1. Применение RequestRole в `PoolExecutor`
**Контекст:**  
`BatchExecutor` при подготовке запросов всегда задаёт роль (`withRole($context->role)`), а `PoolExecutor` — нет. Это приводит к различному поведению контекста/аудита/логирования для одинаковых сценариев пакетного исполнения.

**Влияние:**  
Функционально запросы выполняются, но метаданные контекста различаются. Это ломает предсказуемость телеметрии и поведения, когда бизнес‑логика завязана на роль (`RequestRole`).

**Варианты:**
1) Ничего не делать (документировать различие).  
2) Ввести роль в `PoolExecutor` и применять её так же, как в `BatchExecutor`.

**Рекомендуемое решение:**  
Вариант 2. Добавить опциональную роль в `PoolExecutor` и при подготовке запросов применять `withRole(...)` к `RequestExecution`/`AbstractRequest` аналогично `BatchExecutor`.

**Аргументы:**
- Выравнивает поведение executors → меньше скрытых различий.
- Не меняет бизнес‑логику исполнения, затрагивает только метаданные контекста.
- Расширяет предсказуемость аудита/отладки для пользователя пакета.

**Нюансы реализации:**
- Добавить в `PoolExecutor` параметр `RequestRole $role = RequestRole::Nested` (или fluent `withRole()`), не ломая существующие вызовы конструктора.
- В `prepareRequest()` для `RequestExecutionInterface` применять `withRole($role)` через `RequestOptions`.
- Сохранять порядок и логику, как в `BatchExecutor`, чтобы не ломать семантику.

**Риски/совместимость:**  
Минимальные — это метаданные контекста. Если у пользователя уже явно задан `roleOverride`, стоит решить приоритет (рекомендуется как в `BatchExecutor`: контекст роли исполнителя выше пользовательского override).

### 1.2. Кэширование `RequestSpecResolver` с учётом окружения
**Контекст:**  
Сейчас у `RequestSpecResolver` статический кеш без инвалидации. В средах с разными окружениями/атрибутами может возникнуть несоответствие (особенно в тестах).

**Варианты:**
1) Оставить как есть, принять риски.  
2) Связать `RequestSpecResolver` с `AttributeMetadataCache` (окружение-aware).  
3) Добавить ручную инвалидацию кеша.

**Рекомендуемое решение:**  
Вариант 2 + (опционально) 3. Использовать `AttributeMetadataCache` как источник метаданных, а для тестов добавить метод сброса кеша.

**Аргументы:**
- Полное соответствие философии «окружения» и настройкам клиента.
- Управляемость в тестах без побочных эффектов.
- Не затрагивает бизнес‑логику, только оптимизацию метаданных.

**Нюансы реализации:**
- Придерживаться ранее согласованного плана `PLAN-REF-REQUESTSPEC-METADATACACHE.md`.
- Кешировать по ключу: `class + environment`.
- Добавить безопасный публичный способ сброса кеша (только для тестов).

## 2) Рекомендованные проверки (тесты/проверки поведения)

### 2.1. Offset‑based пагинация без `limit`
**Цель:** гарантировать корректный расчёт offset и явную ошибку при отсутствии `limit`.  
**Рекомендация:** тест, который вызывает `paginate()->pages()` для запроса с `offsetBased: true` и без `withLimit()` — ожидается `ConfigurationException`.

**Аргументы:**  
Без `limit` offset вычисляется некорректно → лучше явная ошибка, чем молчаливый 0.

---

### 2.2. Цепочка `withCache()->withPage()` сохраняет опции
**Цель:** убедиться, что опции кеша не теряются при добавлении пагинации.  
**Рекомендация:** тест, где запрос получает `withCache(300)->withPage(2)` и в `PipelineContext` присутствуют и `RequestOptions`, и `PaginationOptions`.

**Аргументы:**  
Это ключевой DX‑сценарий: конфигурация кеша и пагинации должна быть совместимой.

---

### 2.3. Rate limit key стабилен и уникален
**Цель:** ключ rate‑limit должен быть детерминированным и различаться для разных `baseUrl`.  
**Рекомендация:** тест, который сравнивает ключи для одинакового `baseUrl` (равны) и для разных (различаются).

**Аргументы:**  
Это предотвращает коллизии и «склеивание» лимитов между разными API.
