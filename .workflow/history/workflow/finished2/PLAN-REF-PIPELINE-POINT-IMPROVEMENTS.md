# План: точечные улучшения Pipeline (без большого рефакторинга)

## 1) Тайм‑контроль для retry при 429
**Анализ кода:** в `src/Pipeline/Transport/RetrySender.php` при `429` вызывается `sleep($retryAfter)`. Это обход `SleeperInterface`, в отличие от `AuthHandler`, где тайм‑контроль инъектируется.
**Рекомендуемое решение:** добавить `SleeperInterface` в `RetrySender` (опционально, с дефолтом `SystemSleeper`) и заменить `sleep()` на `$sleeper->sleepMs($retryAfter * 1000)`.
**Обоснование:** повышает тестируемость и делает управление временем единообразным.

## 2) Единый путь подготовки `PreparedRequest`
**Анализ кода:** `CacheManager::prepareForCache()` вручную сериализует запрос и применяет overrides, что дублирует `RequestPreparationStep::prepare()`. Риск расхождения логики при будущих изменениях.
**Рекомендуемое решение:** вынести общий helper `PreparedRequestFactory` и использовать его и в пайплайне, и в `CacheManager`.
**Обоснование:** один источник правды для подготовки запроса и меньший риск регрессий.

## 3) Убрать мутацию `$prepared` по ссылке
**Анализ кода:** `RequestFlowRunner::applyBeforeSendStages()` принимает `PreparedRequest &$prepared` и синхронизирует его через `syncPrepared()`. Поток данных неочевиден и зависит от побочных эффектов.
**Рекомендуемое решение:** возвращать `PreparedRequest` из `applyBeforeSendStages()` и обновлять переменную явно в вызывающем коде.
**Обоснование:** прозрачный flow данных, проще тестировать и поддерживать.

## 4) Семантика cache override для записи
**Анализ кода:** логика чтения/записи кеша должна управляться одним источником истины. Для этого нужен явный режим `CacheMode`.
**Рекомендуемое решение:** использовать `CacheMode::Disabled` как единый выключатель **и для чтения, и для записи**. Для редкого DX‑сценария «чисто, но записать» использовать `withCacheWriteOnly()` / `CacheMode::WriteOnly`.
**Обоснование и влияние на DX:** `withoutCache()` становится полностью предсказуемым (кеш не трогаем), а write‑only даёт осознанный сценарий «обновить кеш без чтения» и не конфликтует с атрибутами (override имеет приоритет).

## 5) Закрепить критичные инварианты тестами/чек‑листом
**Анализ кода:** есть неочевидные инварианты (validation до composite, refresh при 401 форсируется, `AfterResponse` вызывается и для кеш‑ответа), но они не закреплены отдельными тестами.
**Рекомендуемое решение:** добавить минимальные unit‑тесты и короткий чек‑лист инвариантов.
**Необходимые тесты (минимум):**
- `RetrySender`: при `429` вызывается `SleeperInterface::sleepMs()` с корректной длительностью.
- `CacheManager`: `withoutCache()` отключает и чтение, и запись.
- `RequestFlowRunner`: `AfterResponse` вызывается при cache hit.
- `Pipeline`: validation выполняется до composite/depends‑on.
- `AuthHandler/RetrySender`: при `authRetryOn401` refresh выполняется форсированно независимо от `shouldRefresh()`.
**Обоснование:** снижает риск регрессий при локальных правках.
