# План: унификация API под строго иммутабельный стиль

## Цель
Свести публичный API к консистентному `with*`‑стилю без мутабельных `set*`, сохранив бизнес‑логику.

## Область
- Публичные методы конфигурирования запросов и связанных объектов.
- **Исключение:** `Paginator` рассматривается как процессный builder и остаётся мутабельным по своей природе.
- Контракты (интерфейсы) и документация.

## Результаты аудита (классификация)
### Кандидаты для перевода на иммутабельный стиль (`with*`)
- `PoolExecutor`: `withResponseHandler()`, `withExceptionHandler()`, `withRole()`.
- `BatchExecutor`: `parallel()`, `sequential()`, `failStrategy()`, `concurrency()`.
- `AbstractRequest`: рассмотреть `withContext()` (вместо `setContext()`), `setClient()` — спорно (см. ниже).

### Должны остаться мутабельными (процессные/исполнительские)
- `AbstractClient::setTraceId()` — процессное состояние клиента.
- `Pipeline::setTraceId()` — процессное состояние пайплайна.
- `AbstractRequest::setContext()` — внутренний метод установки окружения пайплайна.
- `TokenAuthenticator::setCache()` — состояние аутентификатора.
- `RequestPaginationHelper::setPage/setLimit/setCursor()` — вспомогательные методы, мутируют внешний объект.
- `AuditLogger::addAudit()` — накопление по ссылке.
- `Paginator` — процессный builder (см. исключение выше).

### Спорные/зависят от жизненного цикла
- `AbstractRequest::setClient()` — **зафиксировано как внутренний инфраструктурный метод** и остаётся мутабельным (установка окружения исполнения).

## Критерии приёмки
- Нет публичных мутабельных `set*` там, где есть `with*`.
- Все контракты и доки соответствуют иммутабельной модели.
- Поведение бизнес‑логики не изменено.

## Шаги
1. Аудит API:
   - Найти публичные `set*`, `add*`, `push*` и прочие мутабельные методы.
   - Зафиксировать, какие из них относятся к конфигурации, а какие — к чистым действиям.
   - Отдельно отметить `Paginator` как процессный объект (builder), требующий явного закрепления мутабельного поведения.
2. Классификация:
   - Для конфигурационных методов подготовить `with*` аналоги.
   - Для методов‑действий оставить текущий стиль.
   - Зафиксировать исключения (процессные объекты и builder’ы).
3. Контракты:
   - Обновить интерфейсы (например, `PaginableInterface`) под `with*`.
4. Реализация:
   - Перевести реализации на `cloneWith()`/иммутабельные методы.
   - Удалить мутабельные аналоги, где это допустимо.
   - **Для `Paginator`: оставить мутабельность.** Рекомендуемый вариант — переименовать на `setPerPage/setFailStrategy/setRange`.
5. Документация:
   - Обновить разделы с примерами, глоссарий и контракты.
6. Проверка:
   - Пробежать по ключевым сценариям SDK (пагинация, retries, cache overrides).

## Риски
- Несогласованность примеров/доков с новым API.
- Скрытые мутабельные методы вне явных `set*`.
- Для `Paginator`: риск неочевидной мутабельности, если не закрепить явно (имена или документация).
