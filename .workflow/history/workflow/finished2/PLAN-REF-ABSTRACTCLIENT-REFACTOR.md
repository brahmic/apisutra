# План рефакторинга AbstractClient (без изменения бизнес‑логики)

## 1) Цель
Снизить объём обязанностей `AbstractClient`, убрать дублирование и изолировать тестовую инфраструктуру, сохранив текущий публичный API и поведение.

## 2) Границы (что не делаем)
- Не меняем бизнес‑логику выполнения запросов.
- Не меняем публичные сигнатуры методов клиента.
- Не ломаем формат результатов/ошибок/response.
- Не трогаем пайплайн и его семантику.

## 3) Критерии успеха
- Все существующие тесты проходят без изменений поведения.
- `__construct()` и `rebuildPipeline()` используют единый путь сборки.
- Убрано повторение кода и разбросанные `MockTransport`‑проверки.
- Тестовые методы остаются доступными, но вынесены в отдельный слой.

## 4) Ограничения
- Строгая типизация, PSR‑12, без FQN, комментарии на русском.
- Обратная совместимость по API.
- Минимальные изменения в зависимостях и wiring.

## 5) Сценарии и инварианты
### Сценарии
- Обычное выполнение запроса (sync/async).
- Batch/Pool, hooks/extensions, касты, кеш, retry.
- Тестовые сценарии: fake/record/playback/assert.

### Инварианты
- Пайплайн собирается одинаково при старте и при `rebuildPipeline()`.
- Mock‑транспорт используется строго в тестовых режимах.
- Регистрация кастов/расширений не меняет порядок и поведение.

## 6) Архитектурная декомпозиция (внутренняя)
### Кандидаты на выделение:
1. **PipelineBuilder** — сборка пайплайна и зависимостей.
2. **ClientBootstraper** — инициализация регистров (casts/extensions/hooks/attributes).
3. **TestingSupport** — fake/record/playback/assert, переключение транспорта.
4. **TransportGuard** — единый helper проверки/переключения транспорта.

## 6.1) Критичные инварианты (не сломать)
- Порядок регистрации **casts → extensions → hooks → attributes** сохраняется.
- `MockClient::hasGlobal()` остаётся единственной точкой глобального тест‑режима.
- `rebuildPipeline()` использует тот же путь сборки, что и `__construct()`.
- Любая смена транспорта сохраняет текущее поведение `record/playback/fake`.
- Публичные методы клиента не меняются по сигнатурам и семантике.

## 7) Последовательность реализации (без ломки)
### Шаг 1 — Единая сборка пайплайна
- Вынести логику сборки пайплайна в приватный метод `buildPipeline()` и использовать его в `__construct()` и `rebuildPipeline()`.
- Удалить дублирование `new RetryHandler(...)`.

### Шаг 2 — Выделить boot‑логику
- Вынести регистрацию casts/extensions/hooks/attributes в приватные методы:
  - `registerCasts()`, `registerExtensions()`, `buildRegistries()`.
- Сохранить порядок и логику как есть.

### Шаг 3 — Централизовать MockTransport‑логику
- Вынести повторяющиеся проверки `instanceof MockTransport` в helper:
  - `ensureMockTransport()` / `assertMockTransport()`.
- Использовать helper во всех тестовых методах.

### Шаг 4 — Тестовый слой без изменения API
- Вынести тестовые методы в `TestingClientTrait` или `TestingSupport` (композиция).
- Публичные методы остаются в `AbstractClient`, но делегируют.
 - Глобальный режим `MockClient::global()` не должен «размазываться» по коду.

### Шаг 5 — Мосты видимости (опционально)
- Оставить `hasRequestFailedInternal()` / `shouldRetryInternal()` / `getRequestExceptionInternal()` как есть.
- Отдельный рефакторинг политик — только отдельным планом.

## 8) Тестирование
- Прогон всего существующего набора.
- Дополнительный unit‑тест (при необходимости):
  - `rebuildPipeline()` не меняет поведение при одинаковом конфиге.

## 9) Риски
- Несовпадение пайплайна между `__construct()` и `rebuildPipeline()`.
- Неправильная изоляция тестовых методов может сломать DX.
- Изменение порядка регистрации extensions/casts.
- Глобальные тест‑состояния (record/playback/fake) могут «протечь» в боевой рантайм при неаккуратной декомпозиции.

## 10) Критерии приёмки
- Поведение не меняется.
- API не ломается.
- Дублирование устранено.
