# План: опциональная поддержка мегаклиента (архитектурный рефакторинг)

## Цель
Сделать поддержку мегаклиента первой‑классной возможностью, без оглядки на BC,
с приоритетом чистой архитектуры и предсказуемого DX.

## Архитектурные принципы
- **Сервис = отдельная конфигурация** (baseUrl/auth/pagination и пр.).
- **Фасад не смешивает конфиги**, а лишь маршрутизирует к нужному сервису.
- **Автоскан и DI** должны стабильно резолвить нужный клиент по namespace.
- **Zero‑config по умолчанию**, override только при необходимости.

## Текущее состояние
- `ClientConfig` глобален для клиента, часть параметров не разделима.
- Разные `baseUrl/auth/pagination` сейчас возможны только через per‑request override.
- Auto‑discovery сканирует один root‑namespace клиента.
- `ClientRegistry` резолвит клиента по «самому длинному совпадению namespace».

## Целевая модель
### A) Фасад над несколькими клиентами (основной путь)
- Для каждого сервиса свой `AbstractClient` + свой `ClientConfig`.
- Мегаклиент (`KonturClient`) держит сервисы и отдаёт ресурсы.
- Auto‑discovery регистрирует namespace‑ы каждого сервиса в `ClientRegistry`.

### B) Один клиент + per‑service overrides (доп. режим)
- Разрешён, но не поощряется из‑за смешивания глобальных параметров.
- Использовать только если сервисы гарантированно совместимы по глобальным настройкам.

## План работ
1) **Контракты и модель сервисов**
   - Ввести `MultiServiceClientInterface` (`services(): array`).
   - `services()` возвращает **только** клиентов (`ClientInterface` или class‑string).
   - Ввести опциональный контракт `RequestNamespaceProviderInterface`
     (например `requestNamespaces(): array`) для явного override.

2) **ServiceRegistrar (zero‑config по умолчанию)**
   - Новый сервис: принимает список клиентов.
   - Для каждого клиента:
     - если реализует `RequestNamespaceProviderInterface` → использовать явные namespace‑ы;
     - иначе → `RequestNamespaceDetector->detect($client)` (текущий авто‑детект).
   - Зарегистрировать найденные namespace‑ы в `ClientRegistry`.

3) **Laravel‑интеграция**
   - В `SdkServiceProvider` поддержать `MultiServiceClientInterface`
     и вызывать `ServiceRegistrar` при наличии мегаклиента.
   - Обычные клиенты не затрагиваются.

4) **Тесты**
   - Авто‑detector для каждого сервис‑клиента (default).
   - Override через `RequestNamespaceProviderInterface`.
   - DI‑разрешение Request → правильный сервис‑клиент.

5) **Документация**
   - Новый гайд: «Мегаклиент и мультисервисная архитектура».
   - Обновить auto‑discovery/Laravel интеграцию.
   - Явно сравнить A и B, с рекомендацией использовать A.

## Риски и ограничения
- При разных `namingStrategy/serializeNulls/queryArrayFormat` безопаснее A.
- При нескольких baseUrl нужен явный `RateLimitConfig::key`.

## Финальные ожидания
- Мегаклиент работает **опционально**, архитектура чистая.
- `services()` достаточно для zero‑config регистрации сервисов.
- Override namespaces возможен только при необходимости.
- Auto‑discovery/DI корректно резолвят нужный сервис‑клиент.

## Миграционный чек‑лист
- Контейнер регистрирует `MultiServiceClientInterface` (фасад мегаклиента).
- `ServiceRegistrar` вызывается при наличии мегаклиента.
- Все сервис‑клиенты доступны из контейнера (для DI и `services()`).
- Запросы лежат в корректных namespace (auto‑detect их находит).
- Ручные `setClient()` в коде не используются без нужды.
