# ADR-002: внешний набор правил гидратации DTO

- Дата создания: 2026-09-14
- Дата обновления: 2026-09-14
- Статус: принято владельцем пакета 2026-09-14

## Контекст

SDK внешних API хранит публичные модели обычными `final readonly` классами без
зависимости от ApiSutra. Требования [AS-1–AS-4](../issue/iss-002-apisutra-reuse/upstream-requirements.md)
и [аудит aud-006](../audit/aud-006-declarative-dto/aud-006-readme.md) показали,
что правила гидратации ядра задаются только атрибутами и профилями на самих классах.
Нет изолированного внешнего набора, строгих scalar-типов, приёмника дополнительных
полей и пути ошибки в исходных данных.

## Решение

- Правила задаются неизменяемым `HydrationRules` по точному class-string и подключаются
  через `ClientConfig::hydrationRules` или `Hydrator::forRules()`. Исполнитель — существующий
  Hydrator; второго общего mapper нет.
- Внешние правила и входные атрибуты одного поля, а также внешнее описание класса
  с DtoHydrate/профилем — ошибка конфигурации. Слияния источников в первой версии нет.
- Strict-политика запрещает неявные scalar-приведения, кроме точного расширения int → float
  в диапазоне ±2^53. Элементы списков и форма контейнеров описываются явно.
- Обработчики описываются классом и scalar-аргументами. Повторная гидратация идёт
  через передаваемый `HydrationScope`.
- Остаток данных вычисляется по реально потреблённым путям; остаток проекции списка —
  плотный список записей `sourceKey/remainder`.
- Receiver — механизм чтения: в запросах клиента с набором он не сериализуется,
  в DX-представлении остаётся обычным свойством. Непрозрачные преобразования значения
  с receiver в первой версии отклоняются, чтобы гарантия исключения не зависела от обработчика.
- Literal default и аргументы обработчиков содержат только значения; новые объекты
  создаёт provider.
- Ошибки сохраняют DTO-путь и получают `sourcePath` в формате JSON Pointer с признаком
  точности; автоматический лог использует отдельный маскированный контекст.

Точные сигнатуры и таблицы — в [контракте 028](../current/pln-028-declarative-dto/contracts.md),
альтернативы — в [dsc-005](../discussion/dsc-005-declarative-dto-contracts/dsc-005-readme.md).

## Последствия

- Без набора поведение базовой версии не меняется. Модели SDK остаются независимыми от ApiSutra.
- Запрет пересечений позволяет позже разрешить отдельные сочетания без смены уже выпущенных
  приоритетов.
- `HydrationException` получает необязательные поля происхождения. Автоматические логгеры
  переходят на `logContext()`.
- Предпосылки: изоляция значений metadata — [план 031](../completed/pln-031-metadata-value-isolation/pln-031-readme.md);
  await получает гидратор клиента по [ADR-001](adr-001-continuation-readiness.md).
- Сериализатор клиента получает тот же набор правил, чтобы исключать receiver из запросов.
  Явное включение receiver можно добавить позже как opt-in без смены поведения по умолчанию.

## Отклонённые альтернативы

- **Семиуровневое слияние внешних правил, атрибутов и профилей.** Требует закрепить
  результат каждого пересечения и затрудняет развитие API.
- **Инъекция произвольного HydratorInterface.** Даёт замену алгоритма, но не решает AS-1–AS-4.
- **Чтение `list<T>` из PHPDoc.** Вводит второй язык контракта и зависимость от комментариев.
- **Единственный строковый путь для DTO и источника.** Неоднозначен для произвольных ключей.
- **Отправлять receiver под своим именем или разворачивать в корень.** API получает незнакомый
  ключ либо серверные и read-only поля; остатки проекций однозначно не разворачиваются.
