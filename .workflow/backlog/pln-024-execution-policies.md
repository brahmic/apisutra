## Проблема и конкретный объём

При востребованности сохранить механизм политик в SDK: приложение выбирает значения,
SDK правильно применяет defaults/ограничения. Оценить отдельно группировку конфигурации
и необязательную динамику. Ни отказ от всего 024, ни система управления профилями/БД
внутри SDK не являются итоговым решением. Ниже сохранён подготовленный вариант объёма;
типы, цена динамики и точная поставка подлежат уточнению до начала реализации.

Приложение хочет централизованно менять настройки нескольких SDK и исключения для
сценариев. ClientConfig неизменяем, а его defaults можно переопределить; пересоздание
клиента при каждом чтении БД сбрасывает локальное состояние. Основание:
[аудит N1–N2, N5](../audit/aud-004-policies-admission-assembly/aud-004-readme.md),
[модель, инвентаризация и сценарии](../audit/aud-004-policies-admission-assembly/configuration-model.md).

Первая поставка: optional ExecutionPolicyProviderInterface + callable adapter,
immutable ExecutionPolicy/ExecutionDefaults/ExecutionLimits с allowlist из модели.
Управляем timeout/connectTimeout, budget, ordinary retry attempts/delays/jitter,
logLevel/debug и усилением redaction. Политика определяется на логическое выполнение.
Существующие поля ClientConfig не переносятся и не становятся обязательными группами.

Cache TTL/eligibility, rateLimit, pool, maxPages, delay, auth retry и wire/auth settings
не становятся динамическими в этом плане. Их границы уже описаны в модели;
включение потребует отдельного объёма. Никакой БД, административной UI, очереди или
языка scopes SDK не реализует: приложение возвращает одну разрешённую политику.

После [рецензии](../audit/aud-004-policies-admission-assembly/peer-review.md) внутри
плана принят рекомендуемый порядок: **таймауты/budget → ordinary retry → диагностика**.
Каждый этап получает профильные проверки; незавершённая диагностика не объявляется
поддерживаемой. Отсрочка всего этапа требует явного изменения объёма, а не тихого пропуска.
Это этапы выполнения одного плана, не автоматическое разрешение отдельных публичных
релизов с уже объявленными, но ещё не работающими полями policy.

## Шаги реализации

1. Зафиксировать ответы В2–В4. Рекомендуются failure без HTTP при сбое источника,
   неизменяемый снимок на начатую операцию и явные caps поверх текущих overrides.
2. Добавить типы defaults/limits/provider/adapter, валидацию значений и optional
   executionPolicyProvider в конец ClientConfig; поддержать with/fromLaravel.
   Не использовать непроверенный массив произвольных config overrides.
   Обязательные тесты: оба handler сохраняют identity после with(), смены постороннего
   поля и fromLaravel; замена и null работают независимо. Не рефакторить все поля config.
3. Использовать область выполнения из 023 для одного снимка после допуска.
   Наличие handler допуска не обязательно: provider может работать самостоятельно.
   Учитывать время чтения provider в budget с исходного момента начала; ошибку
   источника доставлять через execution_error/reason=policy_resolution_failed без retry.
   Причину именовать ExecutionControlReason; строковый context.reason не менять.
   Измерять duration шага policy_resolution и сохранять stage при timeout/ошибке;
   использовать существующую диагностику, без новой tracing-системы/enum cases PipelineStage.
4. Реализовать чистое разрешение defaults → текущие атрибуты/runtime → caps.
   null означает отсутствие override, нулевой timeout не обходит cap;
   withoutRetry/safe/replay/auth и текущие semantics Retry-атрибута сохраняются.
5. Перевести TimeoutResolver, RetryConfigResolver/RetrySender и создание ExecutionBudget
   на effective значения выполнения. Ordinary attempts не считать общим числом auth
   и зависимых HTTP. Существующие budgets страниц/batch/await не объединять скрыто.
6. Провести диагностические значения через AuditLogger, внутренние вызовы логирования,
   ExecutionResultBuilder/DebugInfo/безопасные экспорты, включая ошибки до подготовки
   запроса. Маскировку объединять, размер диагностического тела только ограничивать.
   Статические protocol consumers сохраняют ClientConfig; logger/limiter/store/transport
   не пересоздаются и не получают mutable «последнюю политику».
   RecordingTransport получает дополнительную маскировку конкретного исполнения через
   его options, включая сохранение при копировании; полные fixtures не обрезаются
   по диагностическому maxBodyBytes и сохраняют атомарность записи.
7. Добавить полноценные сценарии шести клиентов, отчёта, retry cap и обновления debug
   при частично израсходованной квоте. Проверить две одновременно действующие revisions.
8. Документировать defaults/caps, сроки жизни и единицы, null/0, ошибки источника,
   отсутствие обязательной настройки и пример источника приложения. Отдельно пояснить
   ordinary/auth attempts. Обновить changelog без ссылок на workflow.

В документации явно различить SDK и приложение: без provider клиент не зависит от
административного store. Приложение может обработать сбой и вернуть выбранную policy;
пустая policy подходит только если допустимо снять динамические caps/redaction.
Для обязательных ограничений — явный безопасный снимок либо отказ. SDK не добавляет
failureMode/fallback/cache. Пример request/job-scoped снимка исходных настроек в приложении
показывает сокращение I/O для batch; 500 элементов всё равно вызывают provider 500 раз.
Этот snapshot не кеширует допуск и не обещает изменения административных settings
внутри уже зафиксированного job. Чувствительный к свежести сценарий перечитывает источник.

Основные области: Config, Execution (новые типы и scope), Pipeline/Preparation,
Pipeline/Transport, Pipeline/Diagnostics, Pipeline/Flow, Diagnostics, RecordingTransport,
данные options/PreparedRequest, диагностические
вызовы Pipeline/Cache, RequestResolver/Paginator и результат. Полный список потребителей
из модели перепроверить при реализации, чтобы не оставить захваченный статичный debug.
Делать это механически: сохранить список найденных чтений управляемых полей и точечные
обоснования оставшихся static fallback (file/method/field), повторить поиск после этапов.
Использовать существующие rg/PHP-инструменты, не новую AST-зависимость и не тест на
точные номера строк. Поиск дополняется сценариями разных revisions: alias/helper может
скрыть чтение от текстового шаблона. Snapshot доступен явно через scope/PipelineContext.

## Приёмка

- Старый клиент без provider проходит существующие тесты без новых defaults.
  Пустая policy эквивалентна отсутствию override. Handler допуска и provider независимы.
- Все четыре сценария модели реализованы через реальные клиенты и transport doubles.
  В частности, config=2/attribute=5/runtime=7/cap=3 даёт максимум три обычные попытки;
  это не разрешение повторять небезопасный POST.
- Default/attribute/runtime/cap, null/0, невалидные значения, budget независимо от retry,
  его уменьшение родителем и время получения policy проверены явно.
- Изменение debug/logLevel между вызовами видно на живом клиенте; лимитер сохраняет
  израсходованную квоту, store/key и реестры — identity. Не создаётся новый pipeline.
- Retry/страницы/зависимости согласованы в одной revision, другой клиент независим;
  новый внешний элемент/poll получает свежую policy. Нет утечки между вложенными вызовами.
- Дополнительная маскировка не удаляет стандартную/provider redaction; snapshots
  не меняют wire bytes, cache identity, raw response или исходный поток.
- Ошибка provider не вызывает HTTP/auth/cache, сохраняет previous безопасно и не
  повторяется через SDK. Не обещается принудительное прерывание блокирующего provider.
- Клиент без provider работает при падении чужого источника. Для подключённого provider
  проверяются stage/duration сбоя и отсутствие обязательного logger; допускается только
  явно реализованное приложением восстановление, без SDK-переключателя failureMode.
- Callback counts: без provider — ноль, новый элемент batch — один, retry/page — без
  повторного чтения. Зафиксировать локальное сравнение времени/памяти mock workload,
  не добавляя нестабильный CI-тест на процент производительности.

После целевых policy/timing/retry/diagnostics/rate-limit/entry-point тестов выполнить
`composer test`, `composer lint`, `composer analyse`, `composer check-docs`, `composer check-package`.
Для standalone и Laravel binding проверить отсутствие новых обязательных зависимостей
и сериализации closures через config:cache.

## Зависимости и завершение

Рекомендуется после 023: повторно используется определённая там область выполнения.
022 ранее рекомендован после функциональных поставок; сейчас очередь отложена.
Сборщик не отвечает за приоритет политик. В2–В4 пока открыты;
план конкретен по предлагаемому объёму, но продуктовая реализация ожидает ответов.

Совместимость сохраняется без opt-in. С provider defaults намеренно меняют настройки,
caps ограничивают даже атрибут/runtime. Новые runtime-зависимости не требуются.
Завершение — согласованный объём реализован, все потребители согласованы со snapshot,
проверки записаны, документация/changelog обновлены, план перенесён в completed.
