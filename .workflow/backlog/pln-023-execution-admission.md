## Проблема и объём

Приложению нужна ручная пауза выбранного подключения. Существующий BeforeSend запускается
слишком поздно для запрета auth/cache/зависимых действий. Основание:
[аудит N3–N4](../audit/aud-004-policies-admission-assembly/aud-004-readme.md),
[контракт и полная матрица](../audit/aud-004-policies-admission-assembly/admission-contract.md).
Функция и zero-config поддержаны, точная продуктовая семантика В1–В3 ожидает ответа.

Добавить один ExecutionAdmissionInterface, immutable descriptor/decision и адаптер
callback. ClientConfig.executionAdmission по умолчанию null; поле в конце конструктора,
поддержка config.with. Отказ — execution_error/reason=execution_denied, ошибка handler —
admission_check_failed, типизированные исключения и прежний throwOnErrors/Promise-контракт.
Не добавлять case в ErrorCode, очередь, circuit breaker, fallback и обязательные connectionId.
Причины именовать общим ExecutionControlReason: string; context.reason остаётся строкой.
Уточнения проверены в [рецензии](../audit/aud-004-policies-admission-assembly/peer-review.md).

## Шаги реализации

1. Зафиксировать ответы В1–В3 в аудите и актуализировать контракт. Рекомендации:
   запрет cache hit, отказ при ошибке проверки, продолжение начатой логической операции.
2. Добавить типы допуска, адаптер и конфигурацию; проверить старые ClientConfig/fromLaravel/
   with и типы callback. Пустая конфигурация не вызывает дополнительных обработчиков.
   Обязательные тесты: идентичность executionAdmission после with(), with(timeout: ...),
   fromLaravel; отдельные случаи замены handler и явного сброса через null.
3. Ввести внутреннюю область выполнения с владельцем и явной передачей/завершением.
   В AbstractClient/RequestResolver/Pipeline обеспечить проверку до Started, composite,
   подготовки тела, cache и auth. В прямом Pipeline не доверять одному parent/role/traceId.
   Проверять владельца и срок жизни области, исключать случайное наследование допуска.
   Способ передачи области выбрать по минимальной достаточной сложности; не вводить
   обязательный registry ради защиты от намеренного обхода пользовательским кодом.
4. Провести область через RequestExecution/Paginator, включая путь без executor closure,
   lazy iteration и повторный запуск. Сохранять её на retries и вложенных вызовах того же
   клиента; другой клиент открывает свою. Не использовать mutable «текущее разрешение».
5. Покрыть BatchContext/стратегии и PoolExecutor: внешние элементы проверяются отдельно,
   внутренние элементы composite наследуют область. Сохранить FailAll/Partial/stopOnError.
6. Доставить локальные ошибки через ExecutionResultBuilder, mapper/result-first и throw;
   исключить retry/refresh/продолжение polling для отказа, даже при специальном token extractor.
   Сохранить реальный отказ зависимости, не присваивать ей response родителя.
   Формировать безопасное событие отказа с traceId/reason; внешний лог — через заданный
   logger с учётом logLevel, без автоматического sink. Ошибка logger не подменяет отказ.
   Измерять admission_check монотонными часами; stage/duration доступны при ошибке/timeout.
7. Обновить документацию client-config, pipeline, ошибки, batch/pagination и добавить
   короткие standalone/Laravel примеры подключения handler. В changelog — пользовательское
   поведение без внутренних ссылок.

## Матрица приёмки

Контракт содержит полный список входов; минимум для каждого релевантного пути:

- Без handler — прежний результат/HTTP/callbacks. Allow → обычное исполнение.
- Deny → ноль HTTP, auth refresh, чтений cache и тела upload, записей файла/recording,
  Started/BeforeSend callbacks; локальный FAILED или типизированный throw/rejection.
- Handler падает с секретом в тексте → предыдущая ошибка доступна явно, в логе/экспорте
  секрета нет, повторов нет. Просроченный budget → timeout без отправки.
- Один клиент: retry/refresh/страницы сохраняют allow. Повторный send того же request
  проверяется заново; новый iterator тоже. Scope освобождается при завершении/exception/
  уничтожении iterator. Сохранённый generator после break остаётся приостановленным;
  его возобновление продолжает ту же область, чужой send её не наследует.
- Клиенты одного класса и URL с разными handlers: allow A не обходит deny B, в том числе
  через sendInContext; одинаковые traceId/role не объединяют их.
- Parent без действующей области, чужой или уже завершённый контекст не дают
  наследованного allow. Новый вызов проверяется заново. Детали передачи/копирования
  контекста уточнить при реализации; не строить защиту от намеренного обхода и Reflection.
- Пауза во время внешнего batch/pool блокирует только ещё не начатые элементы;
  композиция и существующие стратегии ошибок работают по согласованной матрице.
- Continuation проверяет каждый poll; отказ терминален. Mock/cache hit тоже проверяются.
- Одновременные/вложенные выполнения не переносят разрешение в другой вызов.
- Без logger и при фильтрации уровня reason/traceId сохраняются в результате/исключении;
  с logger — безопасное событие, без дублей на каждой попытке/page. Callback timeout
  отличается от HTTP timeout по stage; exception логгера не меняет причину запрета.
- Без handler/provider нет registry допусков и внешних чтений. С handler — один вызов
  на область; после batch/длинной выгрузки не удерживается история page contexts.
  Сравнить локальный mock workload до/после по времени/памяти, не вводить CI-порог на часы.

Сначала профильные execution/auth/pagination/result/continuation тесты, затем
`composer test`, `composer lint`, `composer analyse`, `composer check-docs`, `composer check-package`.
Проверять отсутствие эффектов счётчиками/реальными fixture streams и stores, а не
только кодом ошибки. Не обещать реальную параллельность нынешнего async-пути.

## Зависимости и совместимость

После рецензии предлагался порядок 023 → 024 → 022; после отложения активной очереди
нет. 022 не является предпосылкой.
024 для паузы не нужен. В1–В3 — реальные решения владельца, выполнение их зависимых
шагов не начинать по истечению времени без ответа. Остальные технические детали
решаются в рамках предлагаемого контракта.

Без opt-in сохраняется прежнее поведение и самостоятельность ядра. При opt-in
новые операции могут отказать локально; уже отправленный HTTP не отменяется.
Внешние пользовательские реализации ClientInterface/raw transport не получают
эту гарантию автоматически. Новых Composer-зависимостей нет.
