## F1. Классификация сетевых исключений

[TransportExceptionNormalizer](../../../src/Transport/TransportExceptionNormalizer.php)
сначала распознаёт PSR network exception, затем PSR request exception. Установленный
Guzzle в `vendor/guzzlehttp/guzzle/src/Handler/CurlFactory.php` относит 52/28
к ConnectException, а 55/56 — к RequestException. Поэтому наблюдаем:

| errno | Результат SDK | Что означает ошибка транспорта |
| --- | --- | --- |
| 55 | `invalid_request` | Ошибка отправки сетевых данных |
| 56 | `invalid_request` | Ошибка получения сетевых данных |
| 52 | `connection_failed` | Не получен ожидаемый ответ |
| 28 | `timeout` | Истёк таймаут операции |

Назначение кодов подтверждено [libcurl](https://curl.se/libcurl/c/libcurl-errors.html).
[PSR-18](https://www.php-fig.org/psr/psr-18/) различает непригодный запрос и сетевой сбой,
но не предоставляет доказательство доставки или выполнения операции сервером.

**Исправление:** распознавать подтверждённые cURL-коды до общей ветки PSR request
exception. Сохранять `previous`, опциональность Guzzle, классификацию действительно
некорректных запросов и идемпотентность повторной нормализации. Не анализировать
сообщения исключений и не превращать любое Guzzle RequestException в сетевую ошибку.

**Значимое последствие:** `ConnectionException` входит в обычный список повторяемых
исключений. После исправления GET/PUT/DELETE с разрешённым retry смогут повторяться
после 55/56. POST без разрешения safety повторяться не должен. POST с уже заданным
`safe: true` тоже может начать повторяться — это нужно назвать в upgrade notes.

## F1a. «Не отправлено» и «исход неизвестен»

Для 28/52/55/56 универсального вывода «не отправлено» нет. Данные могли дойти до
сервера, а ответ потеряться. Последняя попытка также не описывает весь вызов:
сначала мог оборваться ответ, а следующий retry завершиться до соединения.
Redirects и собственные повторы HTTP-клиента дополнительно ограничивают выводы
из последнего errno. Даже 6/7 без сведений обо всей отправке не следует превращать
в гарантию для всей операции.

Рекомендуется консервативная диагностика: `not_sent` только при доказанном отсутствии
отправки, иначе `unknown`. Это информация об отправке текущего запроса, не обещание
об отсутствии побочных эффектов всей бизнес-операции, auth или дочерних запросов.
В результате выполнения нельзя потерять неопределённость ранней попытки.
Диагностика сама по себе не разрешает автоматический повтор POST.

Цена выше простой переклассификации: потребуется протащить компактное состояние
через transport exception, retry и построение ошибки, включая deadline wrapping.
Телеметрия байтов, журнал доставок, дедупликация, проверка результата у провайдера
и exactly-once в предлагаемую работу не входят. Решение — В1.

## F2/F2a. Формат ответа

[ResponseHydrator](../../../src/Pipeline/Hydration/ResponseHydrator.php) в последней
ветке вызывает `json() ?? []`. Поэтому XML/HTML превращаются в успешное `data=[]`;
при этом JSON под `application/xml` неожиданно разбирается как JSON.
Скрипт воспроизводит оба поведения.

Утверждение «сырой ответ получить нельзя» слишком широкое. При result-first:

```php
$result = $client->send($request)->raw();
$body = $result->response?->body;
```

Тело присутствует и при `response_decoding_error`. Но `ResultHandle::raw()`
возвращает ExecutionResult, **не отключает** декодирование. С `throwOnErrors`
исключение может прервать получение результата. Есть также
[ResponseHandlerInterface](../../../src/Contracts/Interfaces/Response/ResponseHandlerInterface.php)
и extension registry: обработчик получает response/context и может использовать
тип запроса. Это существующая точка расширения, но для одной raw-операции требует
заметно больше пользовательского кода, чем атрибут/опция.

Отсутствующий Content-Type — отдельный случай. Валидный JSON успешно разбирается;
ошибка возникает для невалидного JSON. Считать непустое тело без Content-Type JSON
было принято в [плане 004](../../completed/pln-004-json-error-contracts.md).
Автоматически превращать этот случай в raw без согласования нельзя.

Рекомендация В2: без DTO неизвестный явно указанный формат возвращать строкой;
добавить точечный raw-режим для неверного/отсутствующего Content-Type, сохранить
строгий JSON по умолчанию. DTO/пагинации нельзя молча подставлять `[]` при чужом
формате. Существующие extension handlers сохраняют владение форматом в Auto.

Дополнительные границы проверены по коду:

- [CacheManager](../../../src/Pipeline/Cache/CacheManager.php) хранит status/headers/body,
  а не DTO. Отдельный cache namespace для raw не требуется: тот же ответ можно
  интерпретировать заново. Согласованное объединение custom key сохраняется.
- [RequestFlowRunner](../../../src/Pipeline/Flow/RequestFlowRunner.php) запускает
  BeforeHydrate только для массивов. Нельзя расширять `array`-сигнатуры hooks
  ради raw: строки должны следовать существующему пути скалярных результатов.
- Download имеет отдельный потоковый контракт. Raw не должен материализовать
  файловый stream в строку или включать кеш файлов.

## F3. Внешний дедлайн для нескольких вызовов

[Pipeline](../../../src/Pipeline/Pipeline.php) создаёт бюджет из собственного лимита
и переданного parent; [ExecutionBudget](../../../src/Timing/ExecutionBudget.php)
берёт более ранний deadline. [AbstractClient::send()](../../../src/Core/AbstractClient.php)
не передаёт parent, а `sendInContext()` передаёт. Внутренние retry пользуются
одним context/budget. Это соответствует
[действующему руководству](../../../docs/guides/client-config/timeouts-delay.md).

Воспроизведение с виртуальным временем:

- Два `send()`: транспорт получает 1000 и 1000 ms; оба могут завершиться успешно,
  хотя суммарно потрачено 1200 ms.
- Один `send()` с синтетическим `shouldRetry()` по бизнес-коду: 1000 и 400 ms;
  после превышения общего срока результат `timeout`.

Первоначальная проверка не подтвердила сбой наследования внутри SDK. После уточнения
пользователя 2026-09-13 установлена другая потребность: приложение объединяет
несколько независимых вызовов одним внешним сроком, например «создать → загрузить →
подтвердить». `attachment.not.ready` — лишь один пример. Для проектирования этого
общего механизма конкретный файл провайдера **больше не требуется**.

Проверка [RequestOptions](../../../src/Request/RequestOptions.php) и
[TimeoutResolver](../../../src/Pipeline/Preparation/TimeoutResolver.php) подтверждает:
`withTimeout(int $seconds)` задаёт целые секунды для HTTP-попытки, а не сокращает
ExecutionBudget. Поэтому им нельзя ограничить совокупное время нескольких send,
включая ожидания rate-limit/backoff/Retry-After и auth refresh. Передавать внешний
deadline через опции сейчас нельзя. Это недостающий общий контракт, не дефект
арифметики существующего ExecutionBudget.

**Согласованное решение (В5):** опциональный неизменяемый `ExecutionDeadline`, который
приложение создаёт один раз через `ExecutionDeadline::afterMs()` и передаёт через
`withDeadline()` нескольким вызовам. `withoutDeadline()` снимает только внешний
срок конкретного исполнения, сохраняя клиентский и родительский пределы.
SDK берёт минимум external deadline, собственного totalTimeoutMs и parent budget.
Оркестрация и бизнес-коды остаются у приложения; соблюдение срока внутри SDK —
в существующем ExecutionBudget. Отдельная система управления операциями не нужна.
Относительный остаток в ms не предлагается как второй API: его легко случайно
выдать заново, и он требует ручного пересчёта времени между вызовами.

Дополнительная [проверка существующих примитивов](artifacts/deadline-composition.php)
([результат](artifacts/deadline-composition.txt)) подтверждает, что композиция уже
даёт остатки 1000/600/200 ms для трёх последовательных интервалов по 400 ms, а
ожидание, равное остатку, отклоняется до sleep. Это тест ExecutionBudget и
TransportOptions с виртуальными часами, **не приёмка ещё отсутствующего runtime API**.

```bash
php .workflow/audit/aud-005-transport-response-retry/artifacts/deadline-composition.php
```

Границы и дополнительная работа:

- Срок фиксируется при создании объекта, а не при каждом send. Часы монотонные,
  общий срок нельзя пересчитывать через wall clock или продлевать дочерним вызовом.
- Сейчас Pipeline снимает startedMs до извлечения options. При реализации нужно
  согласовать источник часов до вычисления итогового срока и не сравнивать числа
  разных clock domains. ClockInterface расширять не требуется.
- Внешний срок должен работать и без RetryConfig, и после `withoutRetry()`:
  запрет повторов не означает снятие дедлайна.
- Просроченный срок отклоняется на старте, до HTTP, auth/cache I/O и пользовательских
  execution hooks, через прежний timeout/reason/stage. Внешний deadline не является
  частью cache identity и не хранится в состоянии клиента.
- Критерий «не более 1000 ms» проверяется на транспорте, соблюдающем timeout.
  SDK не может принудительно прервать произвольный блокирующий hook, callback,
  PSR store или код приложения. Время такого кода расходует срок; проверка после
  возврата обнаруживает превышение, но не устраняет уже случившееся превышение.
  Файловые операции сохраняют свои проверки между порциями данных.

Прежний совет использовать встроенный retry остаётся подходящим для повтора одной
операции, но недостаточен для уточнённого сценария нескольких разных вызовов.
Рекомендация и объём плана изменены на основании новых требований, см. В5.

## F4. Условная безопасность повтора

[RetryDecisionMaker::isSafe()](../../../src/Pipeline/Transport/RetryDecisionMaker.php)
видит запрос и HTTP-метод. Он не получает response/exception текущей попытки.
`shouldRetry()` отвечает на другой вопрос: требуется ли попытка, а не безопасна ли.
`safe: true` разрешает не только 429, но и настроенные сетевые/auth-повторы.

Вместе с тем существующий ClientConfig уже позволяет POST только после 429:
`retryOn: [429]`, `retryExceptions: []`, `safeMethods: [HttpMethod::POST]`,
`authRetryOn401: false`. Скрипт показывает 2 вызова для 429 и по 1 для 503/52.
Цена обхода: сетевые повторы отключаются глобально, в том числе для GET.
Retry-атрибут не умеет переопределять `retryExceptions` на запросе.

Рекомендация В4: один необязательный контракт на запросе для оценки safety по
response/exception; не расширять обязательный RequestInterface. Это позволяет
реализовать и «POST только 429», и проверку бизнес-кода в SDK провайдера без таблиц
провайдерских ошибок в ядре. Существующие `safe: true/false`, лимиты попыток,
восстановление тела и deadline сохраняют свои роли. При отсутствии контракта
поведение прежнее, новых обязательных настроек нет.

## F5. Retry-After

[ErrorPolicy](../../../src/Pipeline/Error/ErrorPolicy.php) использует `(int) $header`.
В [RetryAfterDelay](../../../src/Retry/RetryAfterDelay.php) уже есть отдельный
строгий разбор секунд/HTTP-date и контроль переполнения. Поэтому:

| Заголовок | RateLimitException::retryAfter, секунды | Ожидание retry, ms |
| --- | --- | --- |
| HTTP-date через 120 секунд | 0 | 120000 |
| `120` | 120 | 120000 |
| `garbage` | 0 | 0 |
| `-1` | -1 | 0 |

Заголовок допускает дату или неотрицательное число секунд:
[RFC 9110, 10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3).
Ошибка подтверждена в публичном исключении, а не в ожидании встроенного retry.

Рекомендуется переиспользовать текущий parser, предоставив единый nullable-результат
в секундах. Invalid/missing/overflow → `null`; корректный ноль или прошедшая дата → 0.
Retry задержка по-прежнему в ms и при неизвестном значении равна 0. Передавать
одни часы, не менять ClockInterface и не добавлять библиотеку дат. Существующий
внешний RetryHandler сохраняет свою ответственность за backoff.

## Ответы

### В3 — уточнение потребности, 2026-09-13

Источник: пользователь передал пояснение разработчика «Общий дедлайн для нескольких
независимых вызовов». Нужен внешний срок, передаваемый в несколько send: минимум
с клиентским лимитом, покрытие существующего budget, монотонные часы, прежняя ошибка
timeout и отсутствие HTTP после истечения. Без опции поведение сохраняется.

Влияние: запрос файла провайдера снят; F3 переквалифицирован в подтверждённую
нехватку runtime API. D4 и этап C плана переписаны под общий механизм. Форма
ExecutionDeadline/withDeadline на момент этого уточнения оставались рекомендацией
В5; последующее согласование записано ниже. В1, В2 и В4 остаются открытыми.

### В5 — внешний дедлайн и синтаксис, 2026-09-13

Источник: пользователь после обсуждения внешнего срока и соответствия стилю
ApiSutra ответил «ок, фиксируй».

Принято: `ExecutionDeadline::afterMs(1000)` создаёт один неизменяемый срок;
`withDeadline(ExecutionDeadline $deadline)` применяет его через существующую
цепочку runtime-опций, `withoutDeadline()` снимает внешний срок. Отдельный API
передачи остатка миллисекунд не добавляется. Клиентский и родительский пределы
сохраняются; без опции поведение прежнее. Создание объекта фиксирует начало отсчёта,
повторное применение не перезапускает срок. Обязательной конфигурации и новых
зависимостей нет.

Влияние: D4 плана согласован, примеры приведены к fluent-цепочке запроса, публичный
сброс через `withDeadline(null)` заменён на `withoutDeadline()`. Nullable поле
остаётся внутренним представлением отсутствующей опции. Шаги реализации и B5
обновлены. Вопросы В1, В2 и В4 этим ответом не закрываются; реализация не начата.
