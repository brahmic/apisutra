По поручению пользователя проверен каждый пункт

без собственного общего mapper, модификации reflection cache и настройки глобального
состояния потребителем SDK. Контекст задачи — обычные `final readonly` DTO,
одинаковые правила при `Returns` и standalone-преобразовании.

## AS-1. Строгие scalar-типы

### Доступный способ

[DtoHydrationProfileInterface::casts()](../../../src/Contracts/Interfaces/Serialization/DtoHydrationProfileInterface.php)
принимает casts по имени типа. [BuiltinHydrationCaster](../../../src/Serialization/BuiltinHydrationCaster.php)
использует такой cast до встроенного преобразования. Профиль, привязанный к базе DTO,
наследуется классами этой иерархии и действует при `from()` и `Returns`.

Рабочий пример: [StrictProfile](artifacts/Stubs/StrictProfile.php),
[StrictScalarCast](artifacts/Stubs/StrictScalarCast.php),
[StrictBase](artifacts/Stubs/StrictBase.php). Проверены все строки scalar-таблицы
фидбека, PHP_INT_MIN/MAX, переполнение, вложенный DtoInterface-объект без Nested, элементы-DTO списка,
явный IntegerCast, изоляция default-hydrator, sync/promise pipeline и отсутствие retry
при ошибке гидратации. Идентификаторы результатов: `AS1-default-*`, `AS1-profile-*`,
`AS1-child`, `AS1-items`, `AS1-pipeline-*`.

### Ограничения

- Профиль разрешается для конкретного DTO-класса и его родителей. Независимый
  plain-класс внутри строгого родителя использует собственные defaults:
  `AS1-unbound-child` принимает `"7"` как `7`. Это не область действия всего графа.
- `#[Cast]` имеет приоритет над профильным cast. Затем
  [HydrationValueValidator](../../../src/Serialization/HydrationValueValidator.php)
  сохраняет разрешённые reflection scalar conversions. `AS1-after-cast` возвращает
  из IdentityCast строку `"7"`, которая всё равно становится int. Возвращённый array
  отвергается: проверка совместимости есть, строгой scalar-проверки результата нет.
- Передача cast через `ClientConfig.casts` или конструктор Hydrator не заменяет
  DTO-профиль (`AS1-client-casts`, `AS1-registry`).
- Строгий cast отвергает переполненную числовую строку как неверный входной тип;
  это отказ до преобразования, но reason отличается от штатного `integer_out_of_range`.

**F1 / P2 — функциональный пробел AS-1.** Коллега прав о текущих defaults и отсутствии
общей опциональной строгой политики с требуемой областью действия. Для управляемой
SDK DTO-иерархии уже есть короткое решение. Для полного требования нужны изолированные
правила графа и строгая проверка после явного cast, с сохранением старых defaults.

### Scalar-элементы списков

**F9 / P2 — недостающая декларация типа scalar-элементов AS-1.** PHPDoc `list<int>`
не является runtime-правилом Hydrator. `array $ids` принимает `["1", "x", null]`
и у plain DTO, и у DTO со строгим профилем (`C09–C10`). Первоначальный аудит проверял
только списки объектов и слишком широко описывал покрытие элементов.

`Nested(itemCast: ReviewIntegerItemCast::class)` проверяет каждый элемент, включая
null, и сохраняет индекс (`C11–C13`). ItemCast создаётся без аргументов; передача
StrictScalarCast, требующего тип в конструкторе, даёт ArgumentCountError (`C14`).
Это ограничение конкретной точки подключения. Один параметризованный
[ReviewScalarListCast](artifacts/Stubs/ReviewScalarListCast.php) через
`Cast(..., 'int')` тоже решает задачу и не требует класса для каждого типа (`C34–C35`).
Нужны внешние правила типа элемента; автоматическое чтение PHPDoc не объявляется
существующим обещанием и не требуется как способ реализации.

## AS-2. Дополнительные поля

[Hydrator](../../../src/Serialization/Hydrator.php) обходит объявленные свойства,
выбирает значение по From/Map/Nested и передаёт разрешённые значения конструктору.
Набор использованных source-путей не накапливается. `resolveValueWithFallbacks()`
возвращает состояние и значение, но не выбранный путь; отсутствует декларация
свойства для остатков.

`AS2-extras` подтверждает пустой `extras` при наличии unknown-полей, включая null,
false, ноль, пустые строку/список и вложенные данные. `AS2-collision` показывает,
что ключ `extras` источника трактуется как обычное поле. `AS2-raw-response`
подтверждает сохранение исходного ответа: данные доступны для диагностики,
но автоматически не становятся частью DTO.

`computed()` получает весь источник только у ResponseDtoInterface. DefaultValue provider
тоже видит источник, однако не знает набор реально потреблённых mappings. BeforeHydrate
работает с данными ответа до штатной гидратации. Во всех этих вариантах общий сбор
остатков с dot-path/fallback потребует собственного анализа правил и обхода.
AfterHydrate не даёт штатного механизма доинициализировать приёмник уже созданного
readonly DTO. Наличие общего response handler также не реализует сбор остатков.

**F2 / P1 — функциональный пробел AS-2.** В заданных ограничениях штатного решения нет.
Нужно отслеживать потреблённые пути при обычном разрешении полей и декларативно
заполнять приёмник при создании DTO. Это новая возможность; отбрасывание непроецируемых
ключей без такой декларации не объявляется дефектом существующего поведения.

## AS-3. Внешние правила для чистых DTO

### Что уже работает

Публичный `Hydrator::hydrate(array|object, class-string)` не требует PipelineContext.
Корневому классу не обязательны наследование, интерфейс или атрибуты ApiSutra.
Проверены входной объект, native-типы, один вызов конструктора и отказ до конструктора
при неподходящей форме (`AS3-plain-object`, `AS3-constructor*`).

При доступных атрибутах Native plain-классы могут быть элементами `Nested(type: ...)`
и известными discriminator-вариантами. Повреждённый известный вариант даёт ошибку,
неизвестный сохраняется raw (`AS3-plain-list`, `AS3-discriminator`, `AS3-known-invalid`).
Для отдельного вложенного plain-свойства одного native-типа недостаточно:
автоматическая рекурсия в BuiltinHydrationCaster требует DtoInterface. Готовый
экземпляр принимается (`AS3-plain-nested`, `AS3-plain-instance`).

### Документированный одиночный Nested

**F8 / P1 — дефект одиночного Nested на массиве из JSON.** Пример из
[руководства DTO](../../../docs/guides/dto.md#вложенные-dto) с
`Nested(type: AddressDto::class)` и свойством `AddressDto $address` не исправляет
описанную выше проблему plain-child. На `['address' => ['city' => 'Sample']]`
получается `unexpected_response_shape` с путём `address[0]`; через Returns —
`data.address[0]` (`C01/C03`). Причина: hydrateNested трактует любой массив как
коллекцию независимо от одиночного типа свойства.

Уточнение границы: вложенный PHP-объект принимается (`C02`). Ошибка касается обычного
JSON-пути с assoc-массивами, а не всех входных представлений. В варианте Nested.from
и одного вложенного массива wrapCollection вызывает конструктор DTO с массивом
элементов: standalone выбрасывает TypeError (`C04`); ResponseHydrator оборачивает
его в HydrationException, но без reason/path, сохраняя HTTP 200 (`C05`).

Для plain-child работает короткий [ReviewChildCast](artifacts/Stubs/ReviewChildCast.php)
через property Cast, включая путь `child.count` (`C07–C08`). Это обход, требующий
атрибута на родителе, а не исправление Nested. Дефект и его регрессии выделены в
[pln-029](../../completed/pln-029-hydration-defects/pln-029-readme.md); pln-028 должен
переиспользовать исправленный механизм, а не считать одиночный Nested уже рабочим.

### Где заканчиваются расширения

[DtoHydrationProfileResolver](../../../src/Serialization/DtoHydrationProfileResolver.php)
читает привязанные к классу атрибуты. Он final, как и Hydrator; необязательный аргумент
resolver у Hydrator имеет конкретный тип. В клиенте Hydrator создаётся внутри
[AbstractClient](../../../src/Core/AbstractClient.php), готовый внешний набор правил
для него не принимается. Mapping metadata строится из reflection и атрибутов DTO.

Клиентский response handler регистрируется по MIME через extension. Ненулевой результат
`handle()` полностью обходит Returns::unwrap и штатную гидратацию (`C31`); null
возвращает управление штатному пути (`C32`). Это замена обработки ответа, а не
внедрение правил в Returns. Handler может вызвать внешний преобразователь, но преобразователь
с правилами AS-1–AS-4 придётся написать или взять из другой библиотеки. Он не становится
штатным декларативным mapper ApiSutra. BeforeHydrate с ручным переименованием решает
частный случай, а рекурсивный mapping графа повторяет запрещённую условием работу.
Запись во внутренний metadata cache не является поддерживаемым публичным решением.

**F3 / P1 — функциональный пробел AS-3.** Нужен внешний изолированный набор правил,
который использует существующий hydrator и доступен как клиенту, так и standalone-входу.
Повторно реализовывать constructor-first, Nested/discriminator и error pipeline не нужно.

### Диагностический путь

[HydrationException](../../../src/Exceptions/Serialization/HydrationException.php)
имеет один `path`. Hydrator добавляет имя DTO-свойства и порядковый индекс,
ResponseHydrator — unwrap. Выбранный From/fallback не сохраняется в этом пути.

`AS3-source-path`: вход `legacy.batch_id`, ошибка `batchId`.
`AS3-unwrap-path`: фактический путь `data.records[1].legacy.batch_id`,
диагностика `data.items[1].batchId`, отдельного sourcePath нет.
HTTP-ответ, `hydration_error`, reason и безопасный context сохраняются.
Это соответствует текущему [описанию ошибок](../../../docs/guides/errors.md),
но не выполняет дополнительное требование коллеги.

**F4 / P2 — недостающая source-диагностика AS-3.6.** Следует сохранить совместимость
нынешнего `path` и добавить происхождение значения для штатных mappings, индексов
и unwrap. Произвольные преобразования пользовательского hook могут уничтожать
происхождение; SDK не должен восстанавливать его догадкой.

## AS-4. Присутствие и форма контейнера

### Missing и explicit null

Коллега верно описывает обычное `?int $count = null`: missing использует default,
explicit null принимается и не вызывает property Cast (`AS4-missing-default`,
`AS4-null-cast`). Обязательный **параметр конструктора** `?int $count` требует
присутствия ключа и принимает null (`AS4-required-nullable`, `AS4-required-null`, `C22`).
Nullable-свойство вне конструктора без default получает null при отсутствии ключа,
в том числе у класса с другими constructor parameters (`C20–C21`).

Есть частичное решение без общего mapper:
[NullProviderDto](artifacts/Stubs/NullProviderDto.php) использует
`DefaultValue(provider: ..., when: [ValueState::Null])`, а
[RejectStateDefault](artifacts/Stubs/RejectStateDefault.php) бросает HydrationException.
Missing и значение 7 проходят, explicit null отвергается. Provider вызывается после
этапа нормализации, но **по умолчанию Keep сохраняет исходное состояние** (`C17`).
Оно меняется только при подходящей non-Keep политике или EmptyStringAsNull (`C18/C33`);
при наличии property Cast нормализация пропускается (`C19`). Ограничение касается
гарантии исходного состояния при любой конфигурации, а не обычного default-пути.

**F5 / P2 — дефект пути ошибки DefaultValue provider.** Вызов provider расположен
вне catch, который дописывает имя поля к HydrationException. Поэтому его исключение
не получает имя этого поля автоматически:
`AS4-provider-null` имеет пустой path, pipeline с unwrap показывает только `data`.
Точечный provider может сам вписать путь, но это не решение для повторно используемых
внешних правил. Во вложенном DTO получается `guardedChild` вместо
`guardedChild.count`, через Returns — `data.guardedChild` (`C15–C16`): путь указывает
неполное место ошибки. Аналогичный дефект есть при Missing (`AS4-typed-guard`).
Исправление контекста HydrationException выделено в pln-029 независимо от новых
внешних правил и sourcePath. Отсутствие field metadata у provider — отдельное
ограничение, не причина оставлять его исключения без корректного DTO path.

### Списки и обязательные коллекции

`Nested` принимает associative/sparse arrays и собирает элементы заново с индексами
0..n (`AS4-nested-*`). Готового opt-in list-shape в Nested нет.

Однако [StrictListCast](artifacts/Stubs/StrictListCast.php) выполняет `array_is_list()`
и делегирует создание элементов публичному `hydrateCollection()`. Он работает
без собственного рекурсивного DTO-mapper и без Laravel. Пример декларации —
[StrictListDto](artifacts/Stubs/StrictListDto.php), проверки `AS4-cast-*`.
Так можно решить простой список, если DTO допускает атрибут.

Если на одном поле
установить Cast и Nested, Hydrator выберет ветку Nested и пропустит property Cast
(`AS4-cast-nested-combination`). Однако это ограничение конкретной комбинации,
а не всех штатных расширений.

Повторная проверка 2026-09-14 выявила способ, не учтённый первоначально:
[ListShapeProvider](artifacts/Stubs/ListShapeProvider.php) с
`DefaultValue(..., when: [ValueState::Present])` проверяет вход и возвращает его
без изменения **до Nested**. [GuardedVariantListDto](artifacts/Stubs/GuardedVariantListDto.php)
совмещает его с discriminator и itemCast. Список принимается, associative/sparse
отвергаются; известные варианты штатно гидратируются, повреждённые дают ошибку.
Проверки `R01–R08`, `R14` — в [результатах](artifacts/extensions-results.json).

Статус способа: **воспроизведённая комбинация публичных расширений**. Руководство
описывает provider как вычисление значения, а в `tests/` на проверенном HEAD нет
сценария ValueState::Present. До регрессионного теста и явного описания его нельзя
выдавать за документированный рекомендованный способ валидации. DefaultValue не
повторяемый: null и shape объединяются в одном provider с `when: [Null, Present]`.
[ReviewListProvider](artifacts/Stubs/ReviewListProvider.php) подтверждает эту
композицию и её ограничения (`C23–C28`).

[MatrixDto](artifacts/Stubs/MatrixDto.php) сочетает тот же provider для внешнего списка
и [RowCast](artifacts/Stubs/RowCast.php) для строк. Внутри RowCast используется
StrictListCast с публичным hydrateCollection. Проверены оба уровня формы и путь
ошибки элемента `rows[0][0].count` (`R09–R13`); отдельный DTO для каждого ряда не нужен.

**F6 / P2 — неполный контракт shape для внешних правил.** Проверка формы совместима
с Nested через provider; прежняя формулировка о несоставляемости снята.
Но этот способ требует атрибутов DTO, а ошибка внешней формы теряет имя поля по F5:
пустой path standalone и только `data` после unwrap. Нужны компактные внешние правила
и штатная диагностика. Повторно разрабатывать базовый обход вложенных списков не нужно.

Missing обязательного array уже даёт `required_field_missing`. Для non-nullable
AbstractTypedCollection штатный autodefault создаёт пустую коллекцию даже у обязательного
constructor parameter (`AS4-list-missing`, `AS4-typed-missing`). Такое поведение
[документировано](../../../docs/guides/attributes/data-transfer.md) и должно сохраниться
по умолчанию. DefaultValue provider с `when: Missing` позволяет точечно отказать,
но имеет дефект пути F5. Новая декларация присутствия должна явно управлять
этим случаем, не меняя старый autodefault.

## Дополнительное наблюдение о документации и тестах

**F7 / P2 — вводящее в заблуждение описание registry-casts.**
[Гайд casts](../../../docs/guides/casts.md) связывает регистрацию в ClientConfig
с гидрацией DTO. На проверенной версии Hydrator получает отдельный registry только
из DTO-профиля; переданный конструктору registry не участвует в applyCasts.
Это воспроизведено `AS1-registry` и `AS1-client-casts`.

Проблема шире настройки клиента: `CastRegistry::global()` в Hydrator::default()
и `ExtensionRegistry::registerCast()` также не влияют на гидратацию plain DTO
(`C29–C30`). Поле Hydrator::$casts не читается; профильный registry остаётся
другим источником. Обещание registry-гидратации в гайде и комментариях API расходится
с реализацией. Проверки источников casts и исправление документации вынесены в pln-029;
новое неявное влияние global/client registries не включается без анализа совместимости.

Тест «применяет каст из реестра по типу» в
[HydratorTest](../../../tests/Unit/Serialization/HydratorTest.php) проходит, но
[CastStringDto](../../../tests/Stubs/Dto/CastStringDto.php) уже имеет
DtoHydrationProfile с тем же UppercaseCast. Тест не доказывает участие переданного
registry. Следует развести проверки источников casts и уточнить документацию;
восстанавливать глобальное влияние клиентских casts на DTO без отдельного решения нельзя.
