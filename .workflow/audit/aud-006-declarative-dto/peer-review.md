# Проверка замечаний к aud-006

- Дата создания: 2026-09-14
- Дата обновления: 2026-09-14

## Вывод и методика

Рецензия пользователя выявила реальный пропуск аудита: документированный одиночный
Nested сломан на ассоциативном массиве из JSON. Это **F8 / P1**, дефект существующего
сценария, а не пожелание о новых внешних правилах. **F5 / P2** переклассифицирован
в дефект пути ошибки provider. **F9 / P2** фиксирует непокрытые scalar-элементы списков
в AS-1; поддержка runtime-типов из PHPDoc ранее не обещалась.

Фактура предыдущих проверок воспроизводится. Большинство уточнений коллеги верны;
ниже отделены подтверждённые дефекты, новые возможности и слишком широкие формулировки.
Ядро, зависимости, публичные руководства и основной набор тестов этим аудитом не менялись.

Скриптов verify.php/verify2.php/verify3.php коллеги в переданном комплекте нет.
Созданы независимые [peer-review-probe.php](artifacts/peer-review-probe.php) и
именованные фикстуры в artifacts/Stubs. **35 наблюдений, 0 расхождений**:
[peer-review-results.json](artifacts/peer-review-results.json).
Ожидания заданы вручную, включая наблюдаемые дефекты; они не вычисляются из результата.
Успешный probe означает воспроизведение, а не выполнение AS-1–AS-4.

Проверены standalone и настоящий HttpTransport с локальным PSR-18 клиентом;
JSON действительно кодируется и декодируется в pipeline. Сеть отсутствует,
данные синтетические, Illuminate заблокирован автозагрузчиком. HEAD
`1bbd7da61eebbdf75d50a41bca62a17e4ea2447f`, PHP 8.4.15;
дерево src `ed2cbf16afada7631e362e640bf422cb7d3cb4d0` совпадает с релизом.

## Проверка замечаний по поведению

| Замечание | Независимая проверка | Вердикт и граница |
| --- | --- | --- |
| Одиночный Nested не работает | C01/C03: массив `address.city` даёт unexpected_response_shape на address[0]/data.address[0]. C04: один вложенный массив приводит к TypeError в wrapCollection. | F8 подтверждён для массива из JSON. Пример руководства сломан; атрибут Nested не является решением plain-child в этом пути. |
| Одиночный Nested не работает вообще | C02 передаёт дочерний PHP-объект и успешно получает DTO. | Абсолютная формулировка шире доказательства. Ветка object работает; обычный pipeline создаёт assoc-массив и попадает в дефект. |
| Голый TypeError выходит наружу | C04 standalone — TypeError. C05 через Returns — HydrationException с previous TypeError, HTTP 200, но без reason/path. | Прямой и HTTP-входы различаются. Pipeline оборачивает исключение; структурированная диагностика всё равно потеряна. |
| Plain-child можно получить только своим преобразованием | C06 native-type отвергает массив; C07/C08 property Cast вызывает публичный Hydrator и сохраняет child.count. AS1-child проверял DtoInterface-child без Nested. | Короткий cast работает, общего рекурсивного mapper не нужно. Он требует атрибута родителя и не решает внешний чистый граф AS-3. «Не решается атрибутами вообще» неточно: Cast тоже атрибут. |
| Scalar-списки не проверяются | C09/C10: `list<int>` в PHPDoc и строгий профиль не отвергают `["1", "x", null]`. C11–C13: itemCast проверяет элементы и даёт strictIds[1]. | F9 подтверждён. Исходные AS1-items проверяли DTO-элементы. Нужна явная декларация типа элемента; нельзя выдавать PHPDoc за нынешний runtime-контракт. |
| Для каждого scalar-типа нужен отдельный класс | C14: нынешний itemCast создаёт класс без аргументов; StrictScalarCast с обязательным типом даёт ArgumentCountError. C34/C35: параметризованный property Cast проверяет список с индексами. | Утверждение верно для нынешней формы Nested.itemCast, но не для всех casts. Есть один универсальный list cast с аргументом типа; основной чистый граф всё ещё требует AS-3. |
| F5 — дефект, путь может вводить в заблуждение | C15/C16: guardedChild/data.guardedChild вместо guardedChild.count/data.guardedChild.count. Вызов provider вне catch поля. | Подтверждено. Исправляется независимо от sourcePath и внешних metadata. Нельзя называть корректным путь только до родителя. |
| Present-provider ещё не закреплён контрактом | В tests/ на этом HEAD нет ValueState::Present. Руководство описывает provider значения; явного рецепта валидации нет. R01–R14 воспроизводятся. | Это работающая комбинация публичных расширений, но пока не документированный рекомендованный рецепт. Основной regression test и описание включены в pln-029. |
| DefaultValue не повторяемый | C28 проверяет флаги атрибута. C23–C27 объединяют Null/Present и shape в одном provider. | Подтверждено. Оба ограничения выражаются одним provider; два атрибута для разных состояний не поддержаны. |
| Provider по умолчанию видит исходное состояние | C17: Keep даёт Present для пустой строки; C18/C33: EmptyStringAsNull/non-Keep меняют его на Null; C19: Cast пропускает нормализацию. | Уточнение верно. Прежняя формулировка путала место этапа в алгоритме с обязательным изменением значения. |
| Required nullable касается конструктора | C20/C21: missing nullable-свойство вне конструктора становится null. C22: constructor parameter без default требует присутствия. | Подтверждено; вывод и матрица ограничены соответствующим способом объявления. |
| AS-1 «частично прав» смешивает контексты | Профиль привязан к DTO/базе атрибутом; отдельный plain-граф не получает внешних правил. | Вердикт изменён на «прав в заявленном контексте». Атрибутные обходы описаны отдельно и не считаются выполнением исходных условий. |
| Response handler заменяет Returns | C31: handler по application/json возвращает готовый массив при отсутствующем unwrap; C32: null от handler возвращает штатную ошибку unwrap. | Подтверждено. Это замена обработки ответа, не внедрение mappings в штатную гидратацию. |
| F7 шире ClientConfig | C29/C30: global registry и extension registerCast не меняют гидратацию plain DTO. Hydrator::$casts не читается; профиль имеет отдельный registry. | Подтверждено. План отдельно проверяет все источники, включая сериализацию; вводить новое глобальное влияние автоматически нельзя. |

## Гигиена материалов

- Строка issue/ и отсутствие iss в таблице подтверждены и исправлены в
  [.workflow/README.md](../../README.md): входящие замечания, закрытая ячейка,
  префикс iss.
- Главный файл переименован в
  [iss-002-readme.md](../../issue/iss-002-apisutra-reuse/iss-002-readme.md), ID совпадает
  с папкой. Входящие Markdown-ссылки и backlink upstream-requirements исправлены.
- Пути отсутствующего SDK в исходном аудите теперь явно подписаны и представлены
  текстом. Это касается и composer.lock: после импорта такая ссылка могла открывать
  lock самого ApiSutra, создавая неверное впечатление о проверенном исходном SDK.
- Имена внешнего проекта действительно присутствуют в полученном материале.
  Просмотренный commit 506cf77 удалял привязку публичных примеров/тестов/инструкций
  к конкретному приложению; он не задаёт запрета сохранять атрибуцию входящего
  свидетельства. Имена автора сохранены в импортированном тексте и его неизменённых
  PHP-фикстурах, новые воспроизведения и планы используют нейтральные типы.
  Исходный отчёт не считается руководством по архитектуре ядра.
- Правки двух исходных Markdown-файлов отражены в
  [editorial-changes.json](artifacts/editorial-changes.json): прежний/новый путь,
  SHA до/после и характер изменения. Старые manifest не переписаны. Поэтому текущая
  проверка даёт 66 совпадений, 2 учтённые редакторские правки и 1 удалённый источник;
  неучтённых несовпадений нет. Содержательные утверждения и PHP-фикстуры не изменялись.

ветки Nested и casts переиспользуются. Дефекты F8/F5 не закрепляются как legacy-инварианты.

Оба плана имеют статус новый. Эта проверка уточняет основания и объём работ;
исправления production-кода не объявляются выполненными.
