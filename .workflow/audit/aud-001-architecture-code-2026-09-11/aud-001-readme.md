# Аудит архитектуры, кода и документации ApiSutra

- Дата создания: 2026-09-11
- Дата обновления: 2026-09-11

## Проблематика

Объект: рабочая копия `~/www/packages/brahmic/apisutra`.

Главные проблемы находятся на границах выполнения: идентичность кешируемого
запроса, транспортные гарантии, изоляция состояния и интерпретация ответа.
Часть публичных возможностей описана увереннее, чем реализована. Перед выпуском
самостоятельного пакета стоит закрыть подтверждённые дефекты ниже и зафиксировать
границы поддерживаемого API. Синхронное выполнение под Promise API — принятое
ограничение; F04 относится к его описанию, а не к обязательной реализации async.

Рекомендую сохранить один Composer-пакет. Для обнаруженных проблем достаточно
уточнить контракты и ответственность модулей внутри него; отдельные репозитории
для каждого механизма сейчас добавят сопровождение без устранения причин ошибок.

## Подтверждённые дефекты и несоответствия

### F01. Ключ кеша теряет существенные части запроса

[CacheManager::buildCacheKey](../../../src/Pipeline/Cache/CacheManager.php#L276)
использует method, URL до `?`, query из `meta` и body. Заголовки и отдельный scope
авторизации отсутствуют. В
[нормализации query](../../../src/Pipeline/Cache/CacheManager.php#L304)
значения массивов сортируются независимо от их смысла.

Подтверждены три сценария:

- Два клиента с одним store, одним URL и токенами `synthetic-A` / `synthetic-B`:
  второй получает ответ с авторизацией первого; транспорт вызван один раз.
- `/account?id=1` и `/account?id=2`, когда query задан прямо в endpoint:
  второй запрос получает ответ первого, транспорт вызван один раз.
- `sort=[name,date]` и `sort=[date,name]`: порядок параметров меняется,
  но кеш возвращает первый ответ. Для API, где порядок задаёт приоритет сортировки,
  это разные запросы.

При общем store первое поведение создаёт риск выдачи данных другого пользователя.
Раздельный prefix вручную уменьшает риск, но текущий API этого не требует.
Query-аутентификация также меняет URL после сериализации без обновления `meta.query`.

**Исправление:** определить идентичность запроса после всех изменений URL/auth/hooks;
учитывать полный query, значимые заголовки и авторизационный scope. Упорядоченные
массивы сохранять. Явный ключ должен иметь документированную область действия.
Одинаковое правило требуется для чтения, записи и `clearCache()`.

**Регрессии:** два пользователя на общем store; literal query; query-auth;
порядок массивов; изменение запроса hook/enricher; адресное удаление записи.

### F02. Маскирование секретов неполно

[ExecutionResult::requestDebug](../../../src/Result/ExecutionResult.php#L199)
маскирует `query`, headers и части body, но возвращает исходный `prepared.url`.

Для `token=synthetic-secret` результат с маскированием по умолчанию содержит:

```text
query.token.value = "***"
url = "https://audit.invalid/account?token=synthetic-secret"
```

Дополнительные пути экспорта:
[RequestPreparationStep](../../../src/Pipeline/Flow/RequestPreparationStep.php)
пишет URL в logger;
[RecordingTransport](../../../src/Transport/RecordingTransport.php)
сохраняет URL, а
[FixtureRedactor](../../../src/Testing/FixtureRedactor.php)
обрабатывает headers/body, но не URL. Raw debug может быть намеренно сырым,
однако метод, обещающий маскирование, должен закрывать все копии секрета.

**Исправление:** единый sanitizer для диагностических снимков, logger и fixtures,
включая URL/query и соответствующие content-type варианты body. Raw-экспорт
должен оставаться явно отличимым от безопасного экспорта.

**Регрессии:** искать искусственный секрет во всём сериализованном снимке,
а не только проверять отдельное поле `query`.

### F03. Настройки таймаутов не действуют на HTTP-вызов

Поля есть в [ClientConfig](../../../src/Config/ClientConfig.php#L85), атрибуте
`Timeout` и runtime options. Поиск обращений показывает, что они не участвуют
в отправке [HttpTransport](../../../src/Transport/HttpTransport.php#L26).
`ClientConfig.timeout` используется ещё для TTL auth-блокировки.

Проверка Guzzle handler: заданы client timeout/connectTimeout и
`withTimeout(3, 4)`, но HTTP handler получает оба значения отсутствующими.
Это не доказывает отсутствие таймаута у любого внешнего HTTP-клиента;
действуют только его собственные настройки, а не обещанные настройки SDK.

[PSR-18](https://www.php-fig.org/psr/psr-18/#interfaces) не предоставляет
аргумент options в `sendRequest()`. Передачу таймаутов нужно проектировать
на границе конкретного адаптера, а не рассчитывать на универсальный PSR-вызов.

**Исправление:** определить transport options и адаптер, который их поддерживает;
проверять или явно объявлять неподдерживаемые возможности транспорта.
Общий deadline должен учитывать время HTTP, retry delay и rate-limit.
Сейчас `totalTimeoutMs` проверяется перед очередной попыткой и не прерывает
уже начатый вызов или ожидание.

**Регрессии:** реальный локальный медленный HTTP endpoint, приоритет
config/attribute/runtime override, connect timeout и общий deadline.

### F04. Документация не отражает принятое ограничение async API

**Уточнение после обсуждения аудита:** владелец подтвердил, что прохождение
async-вызова через синхронный транспорт принято в текущей архитектуре.
Само это поведение не классифицируется как дефект реализации; приоритет
замечания снижен до P2 и относится к согласованности документации.

Историческое обоснование сохранено в
[комментарии к AbstractClient::sendAsync](../../../src/Core/AbstractClient.php#L146):
пагинация зависит от meta предыдущих ответов и guard-проверок, а полноценный
async-пайплайн затрагивает retry, hooks, cache, hydration, error handling и тесты.
Там прямо отмечены размер рефакторинга, риск и изменения поведения.
[План перехода](../../backlog/pln-001-async-first.md) имеет статус «ОТЛОЖЕНО».
В [оценке вариантов](../../discussion/dsc-001-async-first-analysis.md) рассмотрен
масштабный async-first переход с изменением API, дополнительным runtime и более
сложными тестами. Это описанный тогда вариант развития, а не обязательный способ
реализовать async и не актуальная оценка трудозатрат.

Зависимость страниц объясняет последовательность запросов; сама по себе она
не исключает неблокирующего ожидания. Сохранённые материалы обосновывают отказ
от крупного рефакторинга на том этапе, а не техническую невозможность async.

Текущее поведение подтверждено кодом и локальным сценарием:

[Pipeline::executeAsync](../../../src/Pipeline/Pipeline.php#L278) вызывает
синхронный `execute()` до возврата Promise.
[HttpTransport::sendAsync](../../../src/Transport/HttpTransport.php#L36)
тоже сразу вызывает `send()`.
[ParallelBatchStrategy](../../../src/Execution/Batch/ParallelBatchStrategy.php)
и [PoolExecutor](../../../src/Execution/PoolExecutor.php) используют этот путь клиента.

В проверке сразу после `client->sendAsync()`, до ожидания результата:
`transport.syncCalls=1`, `transport.asyncCalls=0`. Наличие ещё не обработанного
Promise continuation не означает, что HTTP выполняется асинхронно.
Даже внедрение настоящего async-транспорта само по себе не меняет pipeline.

Оставшееся несоответствие: комментарий к `AbstractClient::sendAsync` рекомендует
batch/pool и независимые запросы для настоящего async;
[глоссарий](../../../docs/glossary/requests.md#асинхронность-sdk-sendasync) обещает
неблокирующее выполнение, а [руководство pool](../../../docs/guides/client-config/pool.md)
— снижение времени ожидания за счёт параллельности. Для текущего пути через
`AbstractClient` эти обещания не выполняются.

**Исправление документации:** явно закрепить текущий контракт — синхронное
выполнение с результатом через Promise/ResultHandle, без гарантии неблокирующего
HTTP и параллельности batch/pool. Сохранить обоснование и статус отложенного
решения в доступном архитектурном документе. Настоящий async планировать отдельно
при появлении соответствующей потребности; это не условие выпуска пакета.

[Provider Async Await](../../../docs/guides/provider-async-await.md) — отдельный механизм:
провайдер выполняет задачу у себя и возвращает token для polling. Для такого
протокола синхронная отправка HTTP-запросов допустима и не является проблемой F04.

**Проверки текущего контракта:** Promise/ResultHandle возвращает ожидаемый результат
и сохраняет семантику ошибок. Если будет принят неблокирующий режим, тогда нужны
отдельные проверки момента возврата, async-метода транспорта и реальной
конкурентности. Они не являются требованиями к нынешней реализации.

### F05. AuthRefreshLock освобождает не тот backend

[acquire()](../../../src/Pipeline/Auth/AuthRefreshLock.php#L20) при store без `add()`
использует локальный массив. Но
[release()](../../../src/Pipeline/Auth/AuthRefreshLock.php#L32) при любом ненулевом
store обращается только к нему и выходит, не очищая локальную блокировку.

Проверка `acquire → release → acquire`:
без store повторное получение успешно; с обычным `ArrayCache`, реализующим
PSR-16 без `add()`, повторное получение невозможно до истечения TTL.
Повторный refresh может ждать окончания своей уже завершённой блокировки.

**Исправление:** выбирать backend симметрично при захвате и освобождении.
Для межпроцессной синхронизации определить явный lock-контракт с атомарным
захватом и освобождением владельцем; один `method_exists('add')` его не задаёт.

**Регрессии:** без store, PSR-16 без `add`, store с lock-возможностями,
истечение TTL и смена владельца.

### F06. Ключи внутренних хранилищ несовместимы с PSR-16

[RateLimitApplier](../../../src/Pipeline/Transport/RateLimitApplier.php#L83)
создаёт `rate:<hash>`, а
[AuthHandler](../../../src/Pipeline/Auth/AuthHandler.php#L251) —
`auth_refresh_lock:...`, иногда с PHP namespace в строке.
[PSR-16](https://www.php-fig.org/psr/psr-16/#12-definitions) запрещает `:` и `\`
в ключах. Обычные тестовые stores эти ограничения не проверяют.

В проверке store с проверкой допустимости ключа отвергает `rate:...`;
pipeline завершается ошибкой до вызова транспорта.

Отдельное ограничение: [RateLimiter](../../../src/RateLimiting/RateLimiter.php#L71)
делает `get → count++ → set`. Это не атомарный межпроцессный лимитер.
Сам PSR-16 не обещает атомарного increment или lock; параллельный нагрузочный
прогон в этом аудите не выполнялся.

**Исправление:** нормализовать все внутренние ключи к допустимому формату
и длине; добавить строгий PSR-16 store в contract tests. Для распределённых
гарантий нужен отдельный атомарный backend либо явно ограниченный контракт.

### F07. Настройка контейнера клиента не применяется к валидации

[PipelineValidator](../../../src/Pipeline/Flow/PipelineValidator.php#L26) вызывает
статический `Validator::check($request)` без передачи контекста клиента.
[Validator::resolveFactory](../../../src/VO/Validation/Validator.php#L98)
смотрит на статическую factory или глобальный `ContainerProviderRegistry`,
игнорируя `ClientConfig::containerProvider`.

Подтверждено на запросе с `#[Validate('required')]` и пустым значением:

- фабрика доступна через контейнер конкретного клиента — `success`, HTTP выполнен;
- тот же контейнер зарегистрирован глобально — `failed`, HTTP не выполняется.

Пропуск валидации при полном отсутствии фабрики описан как опциональная возможность.
Здесь фабрика настроена, но не используется. Кроме того, `Validator::useFactory()`
не имеет симметричного публичного сброса и создаёт состояние на весь процесс.

**Исправление:** передавать validator/factory через контекст клиента или
конструктор pipeline. Явно различать «нет правил», «правила проверены» и
«проверка недоступна»; решение о пропуске должно быть осознанной политикой.

**Регрессии:** два клиента с разными factory в одном процессе, client-scoped
container, повторное использование worker и режим без Illuminate.

### F08. Стандартный retry не повторяет сетевую ошибку Guzzle

[RetryConfig](../../../src/Config/RetryConfig.php#L24) по умолчанию повторяет
SDK `ConnectionException`. `HttpTransport` пропускает исключение HTTP-клиента
без преобразования, а
[RetrySender](../../../src/Pipeline/Transport/RetrySender.php#L136) сопоставляет
его с настроенными классами.

Guzzle handler бросает `ConnectException`; при `attempts=3` фактически сделана
одна попытка. Итоговый код при этом `connection_failed` — классификация результата
сама по себе не исправляет решение о retry.

**Исправление:** преобразовывать сетевые исключения адаптера в единый SDK-контракт
с сохранением причины либо повторять по
[PSR-18 NetworkExceptionInterface](https://www.php-fig.org/psr/psr-18/#error-handling).
Ошибки формирования запроса должны оставаться отдельным случаем.

### F09. Safe scalar hydration допускает потерю числовых данных

[SafeScalarHydrationCaster](../../../src/Serialization/SafeScalarHydrationCaster.php#L33)
проверяет синтаксис числовой строки, но не диапазон `int` и не конечность `float`.

Подтверждено:

```text
DTO int: "92233720368547758070" → 9223372036854775807
float:   "1e1000" → INF, canHydrate() = true
```

Первый результат получен через публичный `DTO::from()`, второй — через caster.
Потеря данных проходит без сигнала ошибки.

**Исправление:** проверять диапазон и точность допустимого преобразования,
отклонять не представимые значения с ошибкой гидрации. Большие идентификаторы,
если они предусмотрены API, описывать строковым контрактом. Добавить проверки
границ, переполнения и `INF`/`NaN`.

### F10. Ошибка JSON-декодирования превращается в успешный результат

[ProviderResponse::json](../../../src/VO/Http/ProviderResponse.php#L47) не различает
JSON `null` и ошибку декодирования.
[RequestFlowRunner](../../../src/Pipeline/Flow/RequestFlowRunner.php#L174)
подменяет `null` пустым массивом.

HTTP 200 с телом `{broken-json` и объявленным `#[Returns]` для DTO с nullable
полем по умолчанию даёт `success`, DTO `{name: null}` и отсутствие ошибок.

**Исправление:** для JSON/DTO-контракта сохранять результат декодирования и ошибку
отдельно; malformed JSON должен приводить к ошибке ответа/гидрации.
Бинарные ответы, текст, JSON `null`, пустое тело и HTTP 204 требуют отдельных
явных правил, а не общего `?? []`.

### F11. Ошибка гидрации представляется ошибкой подключения

[ExecutionResultBuilder::buildExceptionResult](../../../src/Pipeline/Flow/ExecutionResultBuilder.php#L195)
начинает с `ConnectionFailed`, меняя код только для ограниченного набора
исключений. Коды `HydrationError` и `SerializationError` уже есть в enum,
но на этом пути не используются.

HTTP 200 с `{"id":"not-an-integer"}` для DTO с `int $id` возвращает
`connection_failed` с сообщением TypeError конструктора DTO.
Это искажает диагностику и может провоцировать бесполезные повторы на стороне
приложения, которое ориентируется на машинный код ошибки.

**Исправление:** классифицировать ошибки по стадии и причине; сохранять HTTP
контекст и исходное исключение. Контрактные тесты должны различать транспорт,
подготовку запроса, decoding, hydration, конфигурацию и расширения.

### F12. Попадание в кеш продлевает срок жизни ответа

После cache hit выполнение доходит до
[finalizeSuccessResult](../../../src/Pipeline/Flow/RequestFlowRunner.php#L199)
и снова вызывает `storeCache()` с полным TTL.

При TTL 10 секунд и запросах в моменты 0, 6 и 12 секунд транспорт вызван один раз.
Регулярное чтение способно сохранять старый ответ значительно дольше заданного
возраста данных. Скользящая TTL-политика не выделена в настройках.

**Исправление:** записывать кеш после свежего ответа; если sliding TTL нужен,
сделать его отдельной политикой. Проверять свежесть относительно времени получения
ответа, а не только наличия ключа.

### F13. Quickstart пропускает необходимую сборку Laravel-клиента

[Quickstart](../../../docs/guides/quickstart.md#5-выполнение) создаёт `$config`, но не
передаёт его `DemoClient` и не регистрирует binding перед `app(DemoClient::class)`.
У наследуемого конструктора есть обязательный `ClientConfig`, которому нужен
скалярный `baseUrl`.

Минимальный контейнер с зарегистрированным `SdkServiceProvider` не может собрать
показанный тип клиента: `Unresolvable dependency ... string $baseUrl`.
Полная Laravel application в этой проверке не поднималась.

Также в `composer.json` нет `extra.laravel.providers`, а руководство не показывает
необходимую ручную регистрацию provider. Возможность
[Laravel package discovery](https://laravel.com/framework/docs/12.x/packages#package-discovery)
нужно либо настроить, либо заменить явной инструкцией подключения.

**Исправление:** два коротких исполняемых примера — без Laravel с явно собранным
transport и с Laravel с показанными binding/provider. Проверять примеры как
consumer smoke, включая установку из дистрибутива.

### F14. Граница дистрибутива не задана

Фактический запуск `composer archive --format=zip` создал 6992 записи,
25 233 737 байт несжатого содержимого. Среди них:

| Каталог | Записей |
| --- | ---: |
| `vendor/` | 5807 |
| `.temp/` | 142 |
| `.idea/` | 7 |
| `.phpunit.cache/` | 1 |

Это проверка локального Composer archive. Состав будущего GitHub/VCS dist может
отличаться; в Git уже отслеживаются некоторые скопированные файлы `vendor/composer`.
Одного `.gitignore` для всех способов упаковки недостаточно.

**Исправление:** настроить `archive.exclude` для Composer и правила экспорта
для выбранного VCS-процесса, убрать генерируемые файлы из индекса Git при подготовке
релиза, проверить архив и установку из него. Composer описывает исключения
в [схеме archive](https://getcomposer.org/doc/04-schema.md#archive).
Какие tests/docs поставлять пользователю — отдельное решение; зависимости,
кэш и IDE-состояние в пакет попадать не должны.

### F15. SleeperInterface не управляет всеми ожиданиями

**Основание:** сверка кода и документации; отдельный сценарий с записывающим
sleeper в этом аудите не запускался.

[Руководство](../../../docs/guides/retries-rate-limit.md#sleeperinterface)
утверждает, что delay и retry используют подменяемый `SleeperInterface`.
Но [DelayApplier](../../../src/Pipeline/Transport/DelayApplier.php#L27)
и [RetryHandler](../../../src/Retry/RetryHandler.php#L36) вызывают `usleep`
напрямую, а [RateLimiter](../../../src/RateLimiting/RateLimiter.php#L96)
использует `sleep`. В
[RetrySender](../../../src/Pipeline/Transport/RetrySender.php#L103)
внедрённый sleeper применяется к `Retry-After`, что не покрывает остальные
ожидания. Подмена sleeper у клиента поэтому не даёт единой точки управления
задержками и виртуальным временем тестов.

**Рекомендация:** согласовать область действия контракта ожиданий, провести
соответствующие delay/backoff/rate-limit через одну зависимость либо явно
описать ограниченную область подмены. Это полезно и для синхронного исполнения;
реализации настоящего async здесь не требуется.

**Проверка при исправлении:** записывающий sleeper получает ожидаемые задержки
для каждого заявленного механизма, тесты не ждут реальное время. Проверить
совместную работу с deadline из F03 и не считать один подменённый sleeper
доказательством неблокирующего pipeline.

### F16. У duration расходятся документированные и фактические единицы

**Основание:** сверка исходников; измерительный HTTP-сценарий отдельно не запускался.

[ProviderResponse](../../../src/VO/Http/ProviderResponse.php#L30)
документирует `duration` в секундах. Однако
[HttpTransport](../../../src/Transport/HttpTransport.php#L71)
умножает разницу `microtime(true)` на 1000 и передаёт миллисекунды.
Пользовательский transport, следующий PHPDoc, будет передавать значение
в другой шкале. Это создаёт неоднозначность при сравнении длительностей
и экспорте метрик.

**Рекомендация:** выбрать и описать одну единицу для transport-контракта,
проверить mock/recording/result adapters и потребителей метрик. Если закрепляются
нынешние миллисекунды, исправить документацию; изменение публичного имени или
шкалы значения требует учёта совместимости. Указать единицы в примерах и
проверять их контрактным тестом адаптера.

## Рекомендации к отдельной проверке

### R01. Проверить Retry-After после последней разрешённой попытки

**Статус:** непроверенный сценарием кандидат. Не включён в число подтверждённых
дефектов; это рекомендация для следующего прохода по retry.

В [RetryDecisionMaker](../../../src/Pipeline/Transport/RetryDecisionMaker.php)
решение повторить ответ может быть положительным без проверки остатка попыток.
[RetrySender](../../../src/Pipeline/Transport/RetrySender.php#L103) после этого
обрабатывает `Retry-After`, увеличивает счётчик и возвращается к условию цикла.
Есть основание проверить, не происходит ли ненужное ожидание после последнего
HTTP 429, когда следующего запроса уже не будет. Также нужно проверить,
сохраняются ли статус и контекст последнего ответа при исчерпании попыток.

**Сценарий:** `attempts=1`, `baseDelay=0`, HTTP 429 с `Retry-After: 5`,
транспорт-счётчик и записывающий `SleeperInterface`, который не ждёт.
Зафиксировать число отправок, вызовы sleeper и итоговый результат. Повторить
с несколькими попытками, а также с 429 без заголовка и ответом 503 как контролем.
Когда следующая попытка невозможна, ожидание ради неё не должно выполняться.
Если сценарий подтвердит проблему, оформить отдельную находку и регрессию;
связанные вопросы deadline и подмены ожиданий уже описаны в F03 и F15.

## Архитектура и границы

### Что уже поддерживает самостоятельность пакета

- Базовый runtime работает без Laravel и без dev-зависимостей; это проверено
  установкой и выполнением запроса в отдельной копии.
- Есть заменяемый transport и отдельные стадии подготовки, auth, retry, hydration
  и сборки результата. Исправления можно делать на этих границах.
- DTO hydration, DX-сериализация и wire-политика разведены по отдельным объектам.
  Это полезная граница для SDK с нестандартными API.
- `RequestSpec`, `RequestOptions` и `RequestExecution` отделяют метаданные
  от параметров конкретного выполнения.
- Для provider metadata уже различаются статические каталоги, inventory
  операций и runtime meta. Эти механизмы стоит сохранить раздельными.

### Целевая карта ответственности внутри одного пакета

| Область | Ответственность | Что уточнить |
| --- | --- | --- |
| Request / DTO | Контракт данных и операции | Данные DTO и пользовательские overrides не должны зависеть от глобального контейнера |
| Pipeline / Execution | Выполнение, стадии и результат | Единый deadline, отдельные sync/async возможности, классификация ошибок по стадиям |
| Transport | HTTP, transport options, сетевые ошибки | Нормализация возможностей адаптера и исключений |
| Cache / Auth / Rate limit | Изоляция, свежесть, координация | Scope ключей, TTL, атомарные операции там, где нужны межпроцессные гарантии |
| Laravel | Сборка и адаптация к приложению | Явные зависимости и регистрация; client-scoped контейнер |
| Catalog / OperationInventory | Описание SDK | Статические данные, introspection и экспорт документов имеют разные обязанности |
| Testing / Docs | Инструменты разработчика | Публичные mock helpers отделить от внутренних fixtures, заметок и генерируемых файлов |

### Публичные контракты и расположение файлов

Интерфейсы распределены между `Contracts/Interfaces`, `Result`, `Response` и
`VO/Errors`. При этом `Contracts/Interfaces/Response` и `Factory` содержат
типы Symfony/Illuminate. Название `Contracts` не гарантирует независимость от
фреймворка. В `VO/Validation` расположен сервис со статическим состоянием,
а не только объект значения.

Предлагаю документировать поддерживаемую публичную поверхность: базовые классы,
контракты расширений, DTO/attributes, transport, ResultHandle и result factories.
Внутренние helpers пометить `@internal`. Выбрать один принцип размещения
интерфейсов — рядом с модулем либо в общей области контрактов — и применять его
при следующих изменениях, с учётом совместимости namespace.

Не требуется массовое переименование всех 418 файлов ради единообразия.
Приоритетные перемещения — фреймворк-специфичные контракты к адаптеру и
stateful validation из области `VO` к исполняемым сервисам.

### Состояние и сборка сервисов

[AbstractClient](../../../src/Core/AbstractClient.php) одновременно собирает
pipeline, регистры, сериализацию, response factories, continuation и inventory.
Размер класса сам по себе не дефект, но жёсткая сборка затрудняет внедрение
validator, clock, cache identity и transport capabilities, которые нужны для
исправлений F01–F08.

Выделять фабрику сборки стоит вокруг этих реальных точек замены. Универсальный
контейнер или дополнительный framework внутри SDK не нужен.

`Validator::$factory`, `ContainerProviderRegistry` и static metadata cache имеют
разные жизненные циклы. Метаданные класса можно разделять между клиентами;
factory валидации и настройки приложения должны иметь scope клиента/операции.
Сброс состояния для тестов и long-running worker должен быть явным.

### DTO и контекст выполнения

[ResponseDtoInterface::computed](../../../src/Contracts/Interfaces/DataTransfer/ResponseDtoInterface.php)
получает весь `PipelineContext`. Это связывает DTO с pipeline и даёт преобразованию
данных доступ к config/auth/request state. Для текущей совместимости это допустимая
точка расширения, но для следующего развития лучше определить узкий контекст
гидрации либо чистое преобразование данных. Такое изменение требует отдельного
решения о публичном контракте, а не механического удаления параметра.

### Introspection, экспорт и рабочие заметки

`OperationInventory/SdkCallPathMethodAnalyzer` читает исходники PHP и анализирует
методы; рядом находится Markdown exporter каталога DTO. Это инструменты
описания SDK, которым не обязательно участвовать в выполнении HTTP.
Стоит явно обозначить tooling-слой и отделить его I/O от статических каталогов.

На момент аудита исторические заметки об async находились в исходниках.
**Выполнено 2026-09-11:** [план](../../backlog/pln-001-async-first.md) перенесён
в `backlog`, [обсуждение](../../discussion/dsc-001-async-first-analysis.md) —
в `discussion`; добавлены статус и пояснение исторического контекста.
Сам перенос не задаёт состав дистрибутива: правила экспорта из F14 всё ещё нужны.

## Документация: содержание и навигация

Структура `guides / client-config / attributes / technical / glossary` пригодна
для дальнейшей работы. Основная проблема — полнота и согласованность обещаний.

1. **Исполняемый вход в пакет.** README и quickstart должны показывать создание
   клиента целиком, включая зависимости транспорта и binding конфигурации.
2. **Матрица возможностей.** Для sync, async, pool, timeout, validation,
   Laravel и shared cache указать: что работает, какой адаптер нужен,
   какие гарантии отсутствуют. Это устраняет необходимость искать ограничения
   в комментариях и старых обсуждениях.
3. **Результаты и ошибки.** Одной схемой связать `ProviderResponse`,
   `ExecutionResult`, `ResolvedResult`, `ResultHandle` и `ClientResponse`.
   Отдельно описать поведение malformed JSON и ошибки гидрации.
4. **Кеш и секреты.** Описать авторизационный scope, семантику query-массивов,
   свежесть ответа и границы raw/sanitized diagnostics. Документация должна
   сопровождать исправления, а не закреплять текущие опасные значения по умолчанию.
5. **Релизные заметки.** Исправить название `CHANEGLOG.md` и устаревшую ссылку
   на `ClientConfig.dateTime.parse`; текущий config использует `requestDateTime`
   и DTO profiles. Записывать изменения публичного контракта понятными примерами.
6. **Повторы.** В методологии оставить решения и порядок работы, в чеклисте —
   короткие критерии, в API-справочниках — точные параметры. Не переписывать
   defaults и precedence одновременно в нескольких больших документах.

## Что добавить в проверки

Текущий набор хорошо проверяет сценарии внутри SDK, но пропускает ошибки между
его слоями. При исправлении находок нужны проверки контрактов:

| Граница | Проверки |
| --- | --- |
| SDK → HTTP adapter | Transport options, PSR-18 network errors, streaming/deadline; Promise-семантика текущего режима, реальная конкурентность при отдельной реализации async |
| Cache → store | Строгий PSR-16, авторизационный scope, ordered query, TTL, lock backend |
| Pipeline → DTO | Невалидный JSON, переполнение, nullable defaults, код ошибки по стадии |
| Client → container | Разные клиенты и factory в одном процессе, работа без Illuminate |
| Docs → consumer | Исполнение quickstart и установка из подготовленного архива |

Минимальная CI-проверка: тесты на минимальной поддерживаемой версии PHP,
обычный dependency install и отдельный smoke с `--no-dev`, Composer validation,
проверка дистрибутива. Дополнительно полезен статический анализ прежде всего
для contracts, config, request options и результатов; единый большой baseline
без разбора ошибок не заменит эти проверки.

Прохождение одного перемешанного прогона не доказывает отсутствие общего
состояния. Но воспроизводимого падения штатных тестов от порядка в этом аудите
не обнаружено, и утверждать такое падение оснований нет.
