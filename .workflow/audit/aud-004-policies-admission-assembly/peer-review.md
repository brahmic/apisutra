# Проверка замечаний коллеги — 2026-09-13

Статус на 2026-09-13: реализация отложена до востребования пользователем.
[Итоговая позиция](../../discussion/dsc-004-client-policies-and-assembly.md#итоговая-позиция-и-отложенная-реализация--2026-09-13)
имеет приоритет над вариантами ниже. Сборщик, политики и допуск сохраняются; пример
нескольких интеграций не является буквальным ТЗ. Конкретные механизмы и цену динамики
уточнять при возобновлении, не добавляя инфраструктуру приложения или защиту от
намеренного обхода SDK пользовательским кодом.

Поручение владельца: проверить все замечания, не считать их установленными фактами,
оценить стоимость и лишние механизмы. Это рецензия и уточнение рекомендаций;
слова коллеги не означают ответы владельца на В1–В4 и не запускают реализацию.

## Что перепроверено

N1–N5 подтверждаются текущими исходниками: TimeoutResolver, RetryConfigResolver,
RequestFlowRunner, AbstractClient/RequestResolver/Paginator, конструкторы потребителей
ClientConfig. Уточнение N2: runtime управляет также enabled/withoutRetry, а не только
attempts; для обычного RequestInterface без AbstractRequest resolver возвращает базовый
retry раньше обработки этих overrides. Это существующая граница, не повод расширять
публичный контракт в рамках текущего проектирования.

[Проверочный скрипт](artifacts/review-probe.php) подтвердил 49 constructor parameters,
публичность PipelineContext constructor/sendInContext и совпадение всех 22 хешей
исходников/тестов прежнего baseline. Результат — [review-probe.json](artifacts/review-probe.json).
164 теста / 859 assertions — подтверждённый результат запуска 2026-09-12, не новый запуск.
Повторять неизменённые тесты ради этой текстовой рецензии не потребовалось.

## Четыре продуктовых решения

| Замечание | Оценка после проверки | Уточнение рекомендации |
| --- | --- | --- |
| В1: запрет cache hit | Поддерживаю, но технический аргумент коллеги излишне категоричен | CacheManager использует auth identity, однако AuthHandler.resolveForCache специально выбирает auth без authenticate/refresh. В текущем RequestFlowRunner полноценная auth всё равно стоит до cache lookup. Cache-only путь теоретически возможен, но требует отдельного контракта; для паузы он не нужен |
| В2: fail-closed у обоих источников | Поддерживаю раздельное описание | Неуправляемые клиенты без policy provider продолжают работать. Все шесть откажут только если все шесть подключены к упавшему источнику. Пустая policy снимает динамические overrides/caps — это не универсально безопасный fallback |
| В3: продолжение начатой операции | Поддерживаю явное продуктовое объяснение | Пауза не останавливает уже запущенные 500 страниц. Для коротких порций — отдельные pages/range вызовы, где протокол это позволяет; maxPages — аварийный guard, а не успешное разбиение выгрузки |
| В4: порядок внутри политик | Поддерживаю timeout/budget → ordinary retry → диагностика | Число строк TimeoutResolver не равно полной стоимости: есть budget, вложенность и ошибки до HTTP. Диагностика действительно шире, включая RecordingTransport. Отложить её можно только явно, не обещая работающий redaction/debug до завершения всей цепочки |

Fallback должен быть явным решением приложения. Для необязательной диагностики оно
может поймать конкретную ошибку хранилища и вернуть пустую policy. Если в policy есть
обязательные потолки или маскировка, предпочтительнее явный безопасный снимок с этими
ограничениями либо прежний локальный отказ. SDK не добавляет failureMode, собственный
cache политики или автоматический last-known-good. Старый снимок тоже может устареть;
его допустимость и срок определяет приложение.

Fail-closed и продолжение начатой операции — рекомендуемые продуктовые контракты,
а не единственно технически возможные варианты. Проверять паузу между страницами
можно без отмены уже отправленного HTTP, но это изменит обещание о продолжении
начатой выгрузки и потребует отдельного согласования.

## Шесть дополнений к планам

| Предложение | Решение и стоимость |
| --- | --- |
| 1. Самодельный parent | Добавить обязательные проверки самодельного, чужого, скопированного и завершённого контекста. Конструктор scope сам по себе не даёт допуска: исполнитель проверяет происхождение parent, владельца и действующий срок. PHP namespace/@internal не создаёт пакетной видимости, а публичная фабрика при private constructor не решает подделку. Нужна локальная проверка выданных контекстов; без криптографии, глобального registry и защиты от произвольного Reflection-кода |
| 2. with/fromLaravel | Добавить отдельные тесты каждого handler: with() без overrides, смена другого поля, явная замена и null; fromLaravel сохраняет именно переданный объект. Никакого рефакторинга всех 49 полей ради двух новых |
| 3. Обязательный лог отказа | Уточнить: SDK формирует безопасное диагностическое событие, но запись во внешний sink подчиняется наличию logger и logLevel. Сейчас AuditLogger именно так работает. Не заводить файл/stderr/logger автоматически и не обходить уровень пользователя. Reason/traceId доступны в результате/исключении независимо от logger; ошибка logger не подменяет основной отказ |
| 4. Время provider | Добавить монотонную duration и machine stage=policy_resolution/admission_check к существующей диагностике, включая сбой/timeout. budget.check сам по себе не измеряет длительность. Не вводить новую систему tracing, дополнительные логи каждой страницы или enum cases PipelineStage только ради таймера |
| 5. 500 элементов = 500 чтений | Точно: 500 вызовов provider, но число I/O зависит от приложения. Показать job/request-scoped snapshot в приложении. Снимок исходных настроек кешируется по подключению и версии, итоговая политика учитывает сценарий; не переносить такое кеширование автоматически на допуск |
| 6. Архитектурная проверка | Снимок явно доступен через execution scope/PipelineContext. Для полноты — инвентаризация чтений, точечный список допустимых static fallback и поведенческие тесты разных revisions. Не вводить хрупкий тест на точный текст/строки всех файлов или новую AST-зависимость: поиск не доказывает отсутствие чтений через alias/helper |

Строковые причины стоит именовать единым **ExecutionControlReason: string** из трёх
значений. Это небольшой полезный enum, без отдельного registry или изменения ErrorCode.
В RequestError.context.reason остаётся строка; типизированный доступ — через enum value
или tryFrom для известной строки. Не заменять весь context либо тип поля enum-объектом;
не обещать, что произвольные другие причины SDK принадлежат этому enum.
Новый ErrorCode case мог бы нарушить исчерпывающий пользовательский match при получении
этого нового case, но не ломает все старые запросы автоматически.

## Дополнительная находка: срок жизни генератора

Воспроизведено в PHP 8.5.4: `break` из foreach при сохранённой ссылке на generator
не выполняет его finally немедленно. Finally срабатывает при завершении/уничтожении.
Поэтому прежний критерий «scope очищается после early break» слишком сильный.

Исправление проекта: scope приостановленного iterator принадлежит только этому iterator;
при его возобновлении продолжается та же операция, новый send/новый обход её не наследует.
Завершение, исключение и уничтожение освобождают scope; немедленную очистку при сохранённой
ссылке после break не обещаем. Не добавлять отдельный публичный close/cancellation API.
Проверять также сохранённый generator, чужой send между yield и next, уничтожение и
отсутствие удержания всех прежних page contexts в долгой выгрузке.

## Накладные расходы и порядок

- Без обоих opt-in механизмов — старый путь, без вызовов источников, I/O, построения
  дерева политик и registry допусков. Проверки null допустимы; «ноль наносекунд» не обещаем.
- С допуском — один callback на согласованную область и локальная проверка происхождения
  при наследовании. Учёт живых contexts можно сделать приватным WeakMap на владельца,
  если он требуется выбранному устройству scope; не удерживать историю batch/pages.
- С политикой — один provider на область; страницы/retry повторно источник не читают.
  I/O и его кеширование контролирует приложение. Никаких reflection/scanning в hot path.
- Enum причин и несколько измерений монотонного времени не требуют Composer-зависимостей.
  Абсолютный runtime-overhead пока не измерен: механизмы ещё не реализованы.
- В приёмке сравнить mock workloads без controls/с пустыми controls, число вызовов,
  время и память; записать результат без выдуманного процента допустимой просадки и CI-флейков.

Рекомендуемый порядок пересмотрен: **023 → 024 → 022**. Поддержанная владельцем
декомпозиция сохраняет ценность для сопровождения; она не нужна для поставки паузы.
Аргумент о меньших конфликтах был недостаточным: пересечения есть (добавление зависимостей
тоже затрагивает конструктор Pipeline), но не создают обязательной зависимости от 022.
Тезис «пауза нужна прямо сейчас» — предположение коллеги, не новый установленный приоритет
владельца. Предлагаемый порядок основан на независимой поставке функции и зависимостях.

Внутри 024 — три последовательных проверяемых этапа. Не создавать три новых плана,
не проводить параллельный рефакторинг одних центральных файлов без отдельной необходимости.
Поздняя перепроверка допуска между страницами остаётся будущей сменой поведения:
границу можно сохранить в устройстве scope, но режим/флаг/вызов handler заранее не добавлять.

Zero-config подтверждён пока на уровне проекта: новые поля ещё не реализованы,
поэтому нельзя выдавать null defaults из планов за проверенный runtime-контракт.
В будущей реализации это подтверждают тесты старого пути, копирования config и
замеры. Отсутствие новых Composer-зависимостей в текущей документальной правке
проверено; дальнейшим планам такие зависимости также не нужны.
