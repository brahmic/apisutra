# Модель настроек и проверка сценариев

Статус на 2026-09-13: реализация отложена до востребования пользователем.
[Итоговая позиция](../../discussion/dsc-004-client-policies-and-assembly.md#итоговая-позиция-и-отложенная-реализация--2026-09-13)
имеет приоритет над вариантами ниже. Сборщик, политики и допуск сохраняются; пример
нескольких интеграций не является буквальным ТЗ. Конкретные механизмы и цену динамики
уточнять при возобновлении, не добавляя инфраструктуру приложения или защиту от
намеренного обхода SDK пользовательским кодом.

Приложение может управлять шестью клиентами из одного источника настроек.
ApiSutra не требуется знать, что приложение называет провайдером, подключением
или сценарием. Приложение связывает источник политики с экземпляром клиента;
credentials и адрес остаются его постоянной конфигурацией подключения.
Все новые имена типов в этом документе — проектируемый API.

## Инвентаризация текущего ClientConfig

Все 49 параметров конструктора перечислены ниже; машинный список получен reflection
в [baseline](artifacts/baseline.json). Группировка описывает ответственность, не требует
немедленно переносить поля или менять named arguments.

| Текущие параметры | Владелец и срок жизни | Оперативное управление |
| --- | --- | --- |
| baseUrl, auth, authScopes, authPolicy, credentialsConfig, originPolicy | Приложение выбирает подключение, провайдер задаёт протокол; срок жизни клиента/его auth-механизма | Смена адреса/credentials — отдельный lifecycle подключения. Не включать в динамический снимок |
| timeout, connectTimeout, delay | Defaults исполнения; сейчас 30 s, 10 s, 0 ms | Первая поставка: timeout/connectTimeout. Произвольный delay пока статичен |
| retry | RetryConfig: попытки, задержки, backoff/jitter, коды, исключения, budget, safeMethods | Первая поставка: attempts, числовые задержки, jitter, budget. retryOn/retryExceptions/safeMethods/backoff остаются программным контрактом |
| authRetryOn401, authRetryAttempts | Механизм восстановления auth, отдельный счётчик | Пока статичен; ordinary attempts не выдавать за лимит всех HTTP-вызовов |
| logLevel, debug, redaction | Диагностические значения на выполнение | Первая поставка: logLevel/debug, дополнительная маскировка и уменьшение maxBodyBytes |
| logger | Объект инфраструктуры, срок жизни клиента | Не сериализовать в админку, не пересоздавать при смене logLevel |
| cache, cacheConfig | Store, identity/key, TTL и правила допустимости — смешанная существующая группа | Пока статичны. Позднее отдельно обсуждать запрет кеша/потолок TTL; никаких файлов в кеше |
| rateLimit | Конфигурация частоты/ожидания, store/key; квота живёт в limiter/store | Пока статичен. Новая диагностика не меняет ключ, окно или счётчик |
| pool | Планирование и stopOnError | Пока статичен; изменение concurrency не делает HTTP неблокирующим |
| paginationConfig, paginationRule | Протокол страниц плюс maxPages и стратегия получения результата | Пока статичны. Кандидат на будущее — maxPages; cursor/имена полей и rule остаются кодом провайдера/сценария |
| queryArrayFormat, serializeNulls, namingStrategy, dtoSerializationProfile, wireBodySerializationPolicy, requestPartsEnumOutput, requestPartsStrictEnums, requestDateTime, textBooleanFormat | Wire-формат провайдера; срок жизни клиента | Не административные defaults |
| casts, extensions, requestEnrichers | Исполняемые стратегии и регистрация при сборке | Не заменять во время операции |
| throwOnErrors, resolvedResultFactory, errorMapper, errorContextFactory, responseFactory | Программный контракт результата и доставки ошибок | Не переключать оперативно: вызывающий код на него рассчитывает |
| environment, containerProvider | Режим сборки/интеграция с окружением | Статичны. environment влияет, в частности, на metadata cache |
| idempotencyHeader | Провайдерский контракт безопасности/заголовков | Не менять общей административной политикой |
| archive | Работа с архивами/файлами | Вне первой поставки, самостоятельные требования |
| continuationTokenExtractor, resultMetaExtractor, providerCatalogRegistry, defaultContinuationMode, defaultPollRequest, continuationModeApplicator | Протокол continuation/метаданные SDK | Статичны; каждый новый poll — отдельное исполнение |

Новые кандидаты: `executionAdmission` и `executionPolicyProvider` — необязательные
объекты, подключаемые кодом приложения, по умолчанию `null`. Это не таблицы БД,
не строки имён сервисов и не обязательный интерфейс для самого приложения.

Пример будущего подключения источника, **не текущий API**:

```php
$config = new ClientConfig(
    baseUrl: 'https://provider.example',
    executionPolicyProvider: new CallbackExecutionPolicyProvider(
        function (ExecutionDescriptor $execution) use ($settings, $connectionId): ExecutionPolicy {
            $snapshot = $settings->snapshot($connectionId);

            return new ExecutionPolicy(
                defaults: new ExecutionDefaults(
                    timeoutSeconds: $snapshot->timeoutFor($execution->requestClass),
                    debug: $snapshot->debug,
                ),
                limits: new ExecutionLimits(maxRetryAttempts: 3),
            );
        },
    ),
);
```

Методы `$settings`/`$snapshot` иллюстрируют интерфейс самого приложения. snapshot обязан
возвращать согласованную версию значений, например одной операцией хранилища или из
собственного immutable снимка. Для простого приложения достаточно статического конфига:
подключать provider ради одного timeout не требуется.

## Конкретный объём первой поставки политик

Предлагаются `ExecutionPolicyProviderInterface::resolve(ExecutionDescriptor): ExecutionPolicy`,
необязательный адаптер callable и immutable результат из двух частей:

- `ExecutionDefaults`: timeoutSeconds, connectTimeoutSeconds, retryAttempts,
  retryBaseDelayMs, retryMaxDelayMs, retryJitter, totalTimeoutMs, logLevel, debug.
- `ExecutionLimits`: maxTimeoutSeconds, maxConnectTimeoutSeconds, maxTotalTimeoutMs,
  maxRetryAttempts, maxDiagnosticBodyBytes, дополнительные redaction headers/fields/paths.

Поля `null` означают «нет override/ограничения»; пустой объект ничего не меняет.
Для маскирующих списков default — `[]`, применение — объединение с правилами SDK
и провайдера. Это типизированный allowlist, не `ClientConfig::with(...любой массив)`.
В первой версии нет операции «стереть установленный бюджет через null» или снять
обязательную маскировку. RetryAttempts = 1 означает одну обычную попытку; это не
запрет отдельного auth recovery. Ноль допустим для default timeout/connectTimeout,
как и сейчас; положительный потолок ограничивает даже такой «без таймаута» default.
Лимиты должны быть положительными; значения defaults проверяются как текущие поля.
Проверять также итоговые сочетания после применения defaults/атрибутов/options,
например maxDelay >= baseDelay; несовместимое сочетание — явная ошибка конфигурации
до HTTP, а не молчаливое исправление одного из значений.

Default retries не включаются лишь от изменения задержек/jitter. Явный retryAttempts
может включить обычные повторы так же, как существующий runtime withRetry; запрет
конкретной операции и проверки безопасности остаются в силе. При отсутствии RetryConfig
использовать его текущие стандартные значения только при явном включении попыток.

Безопасность повтора, retryOn/retryExceptions и auth policy этот слой не расширяет.
`maxRetryAttempts` ограничивает обычный цикл, включая первую попытку, а не число
всех вызовов auth/зависимостей. В UI приложения показывать «обычных попыток максимум».
Универсальный лимит всех HTTP-отправок потребовал бы отдельного контракта и сюда не входит.

## Приоритет и источник значения

1. Приложение само разрешает свои scopes: общее → провайдер → подключение → сценарий.
   Эти названия — пример приложения; в SDK нет обязательных providerId/tenantId,
   таблиц, глобального registry и собственного языка наследования.
2. Возвращённые defaults заменяют соответствующие defaults базового ClientConfig.
3. Действуют существующие атрибуты и runtime-опции с их текущей семантикой. У Timeout
   поля наследуются независимо; Retry-атрибут уже задаёт собственные значения полей,
   а runtime withRetry меняет attempts. Это поведение сохраняется.
4. После разрешения операции применяются жёсткие ограничения: min для положительных
   потолков, объединение маскирующих полей. withoutRetry остаётся выключением ordinary
   retries; лимит не включает их обратно. Budget действует независимо от retries.
5. Проверки replay/safe, origin, file transfer, валидации и фактической поддержки
   transport остаются обязательными. Политика их не обходит.

Если приложение использует несколько обязательных потолков, оно должно вернуть их
пересечение. Пример: общий hard cap 20 s не может быть снят сценарием отчёта 60 s.
Чтобы разрешить отчёт, 20 s следует хранить как default, а не как универсальный запрет.
SDK получает уже одну итоговую политику и не проверяет устройство административной БД.

Явный totalTimeoutMs из текущего RetryConfig и maxTotalTimeoutMs политики образуют
минимум с родительским budget. Default totalTimeoutMs заменяет лишь default клиента
по явному opt-in. Нового общего бюджета на весь paginator, batch или await не появляется:
сроки жизни текущих budgets сохраняются. Снимок политики и таймер — разные сущности.

`ExecutionPolicy` может содержать необязательную безопасную revision для диагностики.
Приложение показывает происхождение значений в своей UI; SDK фиксирует применённые
значения/ревизию без credentials. Revision не является частью cache identity.

## Жизненный цикл

Новый логический вызов: минимальное описание операции → допуск → один immutable
снимок политики → выполнение. Если допуска нет, сразу получение снимка. Если нет
обоих обработчиков, остаётся прежний путь. Запись в БД сама по себе клиент не меняет:
актуальные значения обязан возвращать подключённый приложением provider.

Одинаковый снимок передаётся retry, страницам одного запуска paginator и связанным
вызовам того же экземпляра клиента. Разные запросы получают собственные effective
настройки из этого снимка плюс своих атрибутов/options. Другой клиент получает своё
решение и снимок. Область закрывается в finally при завершении, exception, Promise rejection
и уничтожении generator; break с сохранённой ссылкой оставляет generator приостановленным.
Его scope не наследуется другим send; никакого static/currentPolicy на клиенте или в глобальном registry.

Каждый новый элемент внешнего batch/pool и каждый poll получает новое решение.
Заново запущенный iterator — новая область. Lazy paginator начинает область при первом
чтении, а не при создании объекта. Пользовательские callbacks, отправляющие несвязанный
send, не получают скрытое право наследования: без явно переданного внутреннего контекста
это новый вызов. Подробнее — [матрица допуска](admission-contract.md).

Время чтения политики учитывается от начала выполнения. Сначала ограничение известным
статическим/родительским budget, после получения снимка — проверка нового deadline
с тем же начальным временем. Блокирующий callback нельзя принудительно прервать:
timeouts его БД/HTTP задаёт приложение. При просрочке — существующий timeout;
при иной ошибке provider — локальный execution_error с reason=policy_resolution_failed,
без HTTP, молчаливого fallback к старым settings и retry со стороны SDK (предложение В2).

Уточнение [рецензии 2026-09-13](peer-review.md): клиенты без policy provider не зависят
от административного store. Приложение вправе само обработать ошибку источника и вернуть
policy, но пустая policy снимает и динамические caps/redaction. Она подходит лишь там,
где такой результат допустим; для обязательных ограничений вернуть явно безопасный
снимок либо оставить отказ. SDK не вводит failureMode и автоматический fallback.

Получение policy измеряется монотонными часами, stage=policy_resolution/durationMs
сохраняются в диагностике, особенно при timeout/ошибке; причина именуется через
ExecutionControlReason, сохраняя строковый context.reason. Отдельная tracing-система,
новые enum cases PipelineStage и дополнительный лог каждого retry/page не нужны.

500 новых элементов внешнего batch означают 500 вызовов provider, но не обязательно
500 чтений БД. Приложение может загрузить immutable снимок настроек подключений один раз
в начале HTTP-запроса/job и передать provider, разрешающий политику из него в памяти.
Ключи должны различать подключения/версии; итоговое разрешение учитывает request/scenario.
Снимок освобождается с request/job, не хранится в singleton worker на следующие задания.
Цена — изменения настроек не видны внутри этого job. Когда нужна свежесть, источник
перечитывается. Мемоизация политик не распространяется автоматически на проверку паузы.

## Где применять, чтобы не потерять часть настроек

| Потребитель | Изменение в 024 |
| --- | --- |
| Pipeline / PipelineContextFactory | Согласованный снимок, старт времени до проверок; explicit execution scope |
| TimeoutResolver / TransportOptions | Resolve defaults/attributes/options, затем caps; 0 не обходит потолок |
| RetryConfigResolver / RetrySender | Читать defaults выполнения, сохранить старые overrides/safe; caps после разрешения, budget независимо |
| AuditLogger | logLevel/redaction на конкретное выполнение; не хранить последнее значение в общем logger |
| ExecutionResultBuilder / DebugInfo / безопасные экспорты | debug и маскировка из того же снимка, включая ошибки и окончательный результат |
| RecordingTransport / FixtureRedactor | Передать дополнительные маскирующие правила текущего выполнения, сохранив статические; лимит диагностического тела не обрезает полные fixtures |
| CacheManager и другие внутренние вызовы AuditLogger | Передать диагностическую политику при логировании, не менять store/identity/TTL |
| RequestResolver / Paginator / вложенные исполнители | Передавать область, не получать новую политику на каждый retry/page |

ResponseHydrator, Serializer и другие потребители статичных программных контрактов
сохраняют исходный ClientConfig. Не следует подменять весь config только в PipelineContext:
это создаст расхождение с объектами, захватившими прежний config в конструкторе.
Logger, limiter, stores, реестры и transport остаются теми же объектами.

Для проверки полноты сохранить инвентаризацию обращений к управляемым полям и точечные
обоснования оставшихся static fallback; повторить поиск после каждого этапа. В частности,
включать logLevel/connectTimeout/redaction, не только debug/timeout/retry. Использовать
существующие инструменты, не новую AST-зависимость или тест на номера строк исходников.
Поиск не видит все aliases/helpers, поэтому дополняется реальными сценариями разных revisions.

У RecordingTransport redactor также захвачен при создании. Для динамической маскировки
передавать правила через данные конкретного исполнения PreparedRequest/TransportOptions,
сохраняя их при копировании/effective options; не менять общий redactor между вызовами.
Публичные raw-данные остаются доступны явно. Запись fixture сохраняет свой полный формат
и атомарность; диагностический maxBodyBytes к полным fixture-файлам не применяется.

## Проверка четырёх продуктовых сценариев

Это пошаговая проверка предложенной модели, не заявление о существующем API.
Нынешние правила overrides и безопасности подтверждены baseline-тестами.

| Сценарий / вход | Разрешение и ожидаемый результат | Что проверять в реализации |
| --- | --- | --- |
| Шесть SDK: каталог, платежи, доставка, CRM, аналитика, документы; общий timeout default 10 s | Без специальных настроек все используют 10 s; auth/DTO/baseUrl у каждого свои. Платёжный POST сам по себе не становится повторяемым | Шесть клиентов, один источник значений, независимые protocol/identity и без обязательных идентификаторов SDK |
| Интерактивный запрос 10 s, отчёт с атрибутом Timeout 60 s, runtime 75 s | Обычный default даёт 10/60/75. Если дополнительно maxTimeout=90, отчёт остаётся 75; при maxTimeout=20 будет 20. Сценарный default 60 не перекрывает явный атрибут 30 | Различие default/cap, 0, runtime/атрибут и общий budget; UI объясняет источник ограничения |
| Config attempts=2, атрибут=5, runtime=7, maxRetryAttempts=3 | После старого resolver получается 7, затем максимум 3 обычных попытки. withoutRetry → одна; небезопасный POST → без автоматического повтора; auth recovery учитывается отдельно | Общий потолок нельзя обходить runtime; safety, auth и withoutRetry не меняют смысл |
| У клиента уже израсходованы 2 из 3 запросов окна; админ включает debug | Текущее выполнение заканчивает старую версию. Следующее получает debug=true, остаются тот же limiter/key и расход 2 из 3; третья отправка расходует последнюю квоту | Один живой клиент; counters/logger/registries identity до и после; четвёртая отправка ограничена прежним окном |

Дополнительная проверка: одновременно A использует revision 10, B — revision 11;
завершение B не меняет маскировку результата A. Более подробные логи не раскрывают
стандартные или провайдерские секреты и не читают заново исходные потоковые тела.

## Совместимость и отложенный объём

Старые constructor arguments и config.with сохраняются; новые поля добавляются
в конец и по умолчанию выключены. Не переносить существующие настройки в обязательный
`policies: ...`. Без handler/provider выполняется прежний контракт.
При opt-in ожидаемо меняется поведение только явно управляемых значений/ограничений.

Кандидаты cache TTL, rateLimit, pool, maxPages, delay и изменения auth retry оценены,
но не входят в 024. Для их динамики нужны отдельные ответы: судьба уже кешированных
данных, изменение активного окна, предел batch/iterator и стоимость refresh.
Они остаются предложениями в этой модели, а не скрытыми этапами принятого плана.
