# Предлагаемый контракт допуска

Статус на 2026-09-13: реализация отложена до востребования пользователем.
[Итоговая позиция](../../discussion/dsc-004-client-policies-and-assembly.md#итоговая-позиция-и-отложенная-реализация--2026-09-13)
имеет приоритет над вариантами ниже. Сборщик, политики и допуск сохраняются; пример
нескольких интеграций не является буквальным ТЗ. Конкретные механизмы и цену динамики
уточнять при возобновлении, не добавляя инфраструктуру приложения или защиту от
намеренного обхода SDK пользовательским кодом.

Продуктовая цель: приложение приостанавливает новые операции выбранного подключения,
не вмешиваясь в auth/DTO другого SDK. Источник состояния и административная UI остаются
в приложении. Проверка необязательна; без неё все операции разрешены как прежде.
Вопросы В1–В3 из [аудита](aud-004-readme.md#вопросы) ещё открыты.

## Выбор формы

Рекомендуется один `ExecutionAdmissionInterface` с методом
`decide(ExecutionDescriptor $execution): AdmissionDecision` и готовый
`CallbackExecutionAdmission` для короткого `callable(ExecutionDescriptor): bool`.
`true` адаптируется в allow, `false` — deny; неправильный тип ответа считается ошибкой
обработчика. `AdmissionDecision` имеет только allow/deny, без произвольного текста,
credentials и программного «повторить через N секунд». Отдельная бизнес-причина паузы
может храниться в приложении. Не вводить registry, цепочки и приоритеты нескольких handlers.

Почему так: интерфейс удобен для DI и тестирования сложной проверки; адаптер оставляет
простой путь без собственного класса. Регистрация через существующие hooks короче,
но их порядок не гарантирует ранний запрет. Интерфейс без адаптера создавал бы лишнюю
работу для одной булевой настройки; один голый callback слабее выражает основной контракт.

Предлагаемые новые типы находятся в группе Execution/Admission; общая структура
`ExecutionDescriptor` содержит requestClass, clientClass (nullable для standalone
Pipeline), traceId и role. Только неизменяемые описательные данные, без request/config,
URL, query, тела и токенов. Role — диагностика, а не основание наследовать допуск.
При необходимости различать подключения handler связывается с ними при сборке клиента.
Ни обязательного connectionId, ни знания приложения о внутреннем object id не требуется.

Проектируемое подключение, **пока не существующий API**:

```php
$config = new ClientConfig(
    baseUrl: 'https://provider.example',
    executionAdmission: new CallbackExecutionAdmission(
        fn (ExecutionDescriptor $execution): bool => !$settings->isPaused($connectionId),
    ),
);
```

`$settings` и `$connectionId` принадлежат приложению; для другого подключения оно
передаёт свой handler. Без `executionAdmission` пользователь вообще ничего не добавляет.
В Laravel объекты/closures создаются при binding клиента, не сохраняются в массив
конфигурации для `config:cache`. Дополнительных Composer-зависимостей нет.

## Граница и порядок

1. Зафиксировать начало времени, распаковать RequestExecution, определить фактически
   исполняющий клиент и минимальное описание операции. Не вычислять подписи/тело.
2. Проверить известный budget и наличие действующей внутренней области того же клиента.
3. Для новой области вызвать handler один раз. Проверить истечение budget после возврата.
4. При allow открыть область и продолжить обычный pipeline: Started/валидация,
   composite/depends-on, сериализация и файлы, cache preparation, auth, cache lookup, HTTP.
5. При deny или ошибке сформировать локальный результат, не запускать перечисленные
   стадии и пользовательские hooks. Формируется безопасное диагностическое событие отказа;
   запись в logger зависит от его наличия и logLevel. Новый обязательный sink не появляется.

Передача решения выполняется через отдельный внутренний execution scope с identity
владельца и признаком действующего срока жизни. Одного parent/role/traceId недостаточно.
Identity берётся от фактически исполняющего клиента, не только от request.getClient(),
класса клиента, URL или объекта handler. У standalone Pipeline собственный владелец.
Смена transport не меняет владельца; одинаковые классы двух клиентов не объединяют допуск.

Дополнение после [проверки 2026-09-13](peer-review.md): исполнитель проверяет, что parent
выдан им для действующей области. Самодельный/чужой parent, clone, скопированная ссылка
на scope в незарегистрированном контексте и завершённый parent не дают допуска.
Одного private constructor недостаточно, если scope можно выпустить публичной фабрикой.
Не строить пакетную систему безопасности: локальная проверка происхождения/владельца/
срока жизни, без криптографии или глобального реестра. Когда controls выключены,
учёт выданных контекстов не нужен. Учёт не должен удерживать историю всех страниц.

Область передаётся SDK явно, не через глобальный singleton, mutable currentScope или
автоматическое наследование произвольного вложенного send. Она живёт до завершения
логической операции; повторный send того же RequestInterface не использует старое allow.
Проверка действует на вызовы через штатный executor SDK, а не на произвольный PHP-код:
пользовательские конструкторы/фабрики запросов и сам handler могут иметь свои эффекты.

## Матрица входов и продолжений

| Путь | Предлагаемая граница | Где обеспечить |
| --- | --- | --- |
| client.send, send(mode: Async), sendAsync; request.send; RequestExecution.send | Новая область на каждый запуск; отказ в том же result/Promise-контракте | AbstractClient, RequestResolver, Pipeline |
| Прямой Pipeline.execute/executeAsync | Новая область, если нет действующей внутренней области этого владельца | Защитная проверка в Pipeline до start, включая skipComposite/skipValidation |
| Retry и повтор после успешного auth recovery | Продолжение уже допущенной операции, без повторного handler | RetrySender, AuthHandler; не проверять перед каждой HTTP-попыткой |
| Auth refresh, composite, depends-on того же клиента | Наследуют allow; основной depends-on запрос не проверяется повторно | AuthHandler, CompositeFlow, BatchContext, sendInContext |
| Вызов через другой фактически исполняющий клиент | Собственная проверка и политика; если отказал B, разрешение A не позволяет его обойти | sendInContext и Pipeline; существующая доставка ошибки зависимости сохраняется |
| Автопагинация одного send, paginator.all/pages/range / iterator | Одна область с начала исполнения до конца обхода; дальнейшие страницы продолжаются после паузы | RequestResolver/Paginator, включая путь без executor closure |
| Lazy iterator создан, но ещё не начат; повторный обход | Проверка при начале каждого обхода, а не в конструкторе | Paginator; finally при завершении/уничтожении, а не немедленно при break с сохранённым generator |
| Внешний batch/pool | Каждый элемент — новый запуск. После паузы ещё не начатые элементы отказывают; прежние FailAll/Partial/stopOnError определяют судьбу остальных | BatchContext, Sequential/ParallelBatchStrategy, PoolExecutor |
| Batch как внутренняя часть composite/depends-on | Наследует действующую область того же клиента | Явный parent scope, не одно значение role |
| await/continuation | Каждый новый poll — новая операция; пауза не прерывает отправленный poll | ContinuationService; локальный отказ терминален для SDK poll loop |
| Cache hit, mock, запись/воспроизведение | Проверка как для обычной операции; при deny нет cache lookup/recording/подмены успехом | До RequestFlowRunner и transport |
| clearCache, чтение каталога операций/DTO, построение RequestExecution | Не являются исполнением интеграционной операции и не проверяются | Публичные сервисные методы остаются доступны |
| Прямое использование raw transport/чужая реализация ClientInterface | За пределами гарантии AbstractClient/Pipeline | Документировать; не менять PSR/transport-интерфейсы ради глобальной блокировки |

Пауза между страницами не останавливает начатую выгрузку; это осознанное предложение
В3. Для остановки длинной выгрузки потребуется отдельная отмена, которой в этом плане нет.
Один запуск paginator не означает новый единый budget на все страницы.

Это следует описать явным абзацем публичного гайда: **выгрузка на 500 страниц,
начатая до паузы, продолжится**. Для более коротких операций приложение может запускать
отдельные порции pages/range, где протокол позволяет корректное продолжение. maxPages
возвращает guard-ошибку при достижении предела; это не успешный механизм порционирования.
Для cursor API продолжение требует сохранения поддерживаемого протоколом cursor.
Повторная проверка между страницами меняла бы обещанную семантику; не добавлять её или
флаг отмены заранее. Сохранить границы в коде достаточно для будущего отдельного решения.

Если приложение сохраняет generator после break, он приостановлен и может быть продолжен
в той же области. Эта область не становится текущей для других вызовов. Finally освобождает
её при завершении/исключении/уничтожении; немедленного закрытия после break не обещаем.

## Отказы, исключения и диагностика

| Ситуация | Рекомендуемый результат |
| --- | --- |
| Handler вернул deny | FAILED, code=`execution_error`, context.reason=`execution_denied`, исключение ExecutionDeniedException, response=null |
| Handler бросил исключение / callback вернул неправильный тип | FAILED, code=`execution_error`, reason=`admission_check_failed`, исключение AdmissionCheckException с previous, response=null |
| Истёк известный budget во время проверки | Существующий timeout/deadline-контракт, без отправки HTTP |
| throwOnErrors=true | Типизированное исключение; async — rejection; ResultHandle не подменяет отказ успехом |
| Ошибка зависимого B | Существующая композиция сохраняет конкретный отказ B; не подставлять response родителя A как ответ запрещённой операции |

Причины машинные и стабильные, сообщения общие и безопасные.
Причины именуются ExecutionControlReason: string, а в context.reason остаются строками.
Enum не заменяет ErrorCode или все остальные reason SDK. Проверка допуска измеряется
монотонными часами: stage=admission_check и durationMs сохраняются в диагностике,
включая ошибку/timeout. Без logger причина и traceId остаются доступны в результате
или исключении; ошибка logger не должна заменять основной отказ.

Сырые сообщения
исключений хранилища не попадают автоматически в лог/debug; previous остаётся для
явной диагностики. Выбран существующий ErrorCode, чтобы не добавлять enum case,
способный сломать исчерпывающий пользовательский match. HTTP 403/503 не выдумывается.

Ни ordinary retry, ни auth retry, ни пользовательский retryOn не повторяют отказ SDK.
Continuation также не продолжает polling после паузы, даже если пользовательский
token extractor пытается вернуть очередной token для локальной ошибки;
обычные стратегии коллекций по-прежнему могут продолжить другие элементы.
SDK не кеширует allow до следующего вызова и не организует очередь отвергнутых операций.

## Оценка объёма

Подключение для пользователя короткое. Основная стоимость реализации — единая область
выполнения, её передача через пагинацию/зависимости и терминальные ошибки. Эта работа
не требует нового сборщика или системы динамических политик, но последние смогут
использовать тот же механизм срока жизни. Контракт требует матричных тестов;
сроки в часах по одному callback не оцениваются.
