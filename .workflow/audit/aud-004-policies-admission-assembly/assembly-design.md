# Внутренняя сборка клиента

Статус на 2026-09-13: реализация отложена до востребования пользователем.
[Итоговая позиция](../../discussion/dsc-004-client-policies-and-assembly.md#итоговая-позиция-и-отложенная-реализация--2026-09-13)
имеет приоритет над вариантами ниже. Сборщик, политики и допуск сохраняются; пример
нескольких интеграций не является буквальным ТЗ. Конкретные механизмы и цену динамики
уточнять при возобновлении, не добавляя инфраструктуру приложения или защиту от
намеренного обхода SDK пользовательским кодом.

Цель — отделить знания о создании и соединении зависимостей от исполнения запросов.
Это поддержанная внутренняя декомпозиция. Публичный конструктор, способы создания SDK,
состояние и поведение сохраняются. Реализация допуска/политик для этого не требуется.

## Выбранный минимальный дизайн

Рекомендуется один внутренний `Core\Assembly\ClientAssemblyFactory`, без публичной
регистрации в контейнере, интерфейса фабрики и обязательного параметра конструктора.
Он создаётся автоматически и не читает БД/глобальную административную политику.

Объект `ClientComponents`/`ClientDependencies` **не вводится в первой поставке**:
при текущем объёме это был бы широкий мешок всех полей клиента. У фабрики есть
именованные типизированные методы существующих стадий: создание metadata cache,
регистрация casts/extensions, подключение auth cache, сборка Pipeline и фабрик результата.
Простое присваивание `new HookRegistry()` само по себе не нуждается в отдельной абстракции.
Параметры createPipeline соответствуют нужным зависимостям Pipeline; типизированные
аргументы предпочтительнее массива сервисов или передачи полного клиента ради getters.
Владелец client передаётся отдельно для уже существующих provider callbacks/auth identity.

AbstractClient сохраняет короткую последовательность присваивания своих полей;
специфические правила создания уходят в фабрику. Private buildPipeline/rebuildPipeline
могут остаться делегирующими точками, поскольку ими пользуется TestingClientTrait.
Фабрика не запускает запросы и не становится service locator во время send.

Публичные config.with, fromLaravel и DI провайдеров не меняются. Точные имена внутренних
методов можно уточнить при реализации без дополнительного продуктового решения.

## Порядок, который нужно сохранить

Основание — [конструктор AbstractClient](../../../src/Core/AbstractClient.php), а не
старый PHP-эскиз из закрытой дискуссии.

1. Присвоить config/transport/clock через прежние constructor parameters.
2. Выбрать logger и sleeper; создать metadata cache по environment.
3. Присвоить hooks, attributes и casts; зарегистрировать casts из config.
4. Присвоить extensions (переданный либо созданный с теми же реестрами), затем
   зарегистрировать extensions. Пользовательская регистрация выполняется ровно один раз.
5. Передать cache в CacheAware auth, если он настроен.
6. Применить существующий global mock transport.
7. Создать Hydrator/Serializer с теми же casts/metadata cache, затем один RateLimiter.
8. Собрать Pipeline с действующим transport и новым RetryHandler этого transport.
9. Присвоить resolvedResultFactory, затем clientResponseFactory; сохранить вызов
   withErrorMapper для поддерживающей его пользовательской фабрики.
10. Создать RequestResolver с executor closure на этого клиента.

Не объединять стадии в один `return new Bundle(...)`, если из-за этого пользовательский
callback выполнится до присваивания поля клиента, которое раньше было доступно.
Например, extension registry должен быть присвоен до registerExtensions. Аналогично
response factory настраивается после Pipeline. Даже совпадающий конечный граф объектов
не оправдывает изменения порядка этих эффектов.

## Владение и повторная сборка

| Объект / состояние | Владелец / lifetime | При смене transport |
| --- | --- | --- |
| ClientConfig, logger, clock, sleeper | Клиент; переданные объекты сохраняются | Те же ссылки |
| MetadataCache, casts, hooks, attributes, extensions | Клиент; переданные registry не заменяются | Те же ссылки, без повторной регистрации |
| Serializer, Hydrator | Клиент | Те же ссылки |
| RateLimiter и локальные счётчики | Клиент | Та же ссылка и израсходованная квота |
| Внешние cache/rate/auth stores, auth object | Приложение передаёт, SDK использует | Без повторного configureAuthCache и смены namespace |
| Transport | Клиент, заменяется штатным testing API | Новый текущий transport |
| Pipeline, RetryHandler и внутренние transport handlers | Конкретная сборка pipeline | Создаются для нового transport; сохраняется traceId по текущему контракту testing API |
| Result/Response factories, RequestResolver | Клиент | Не пересоздаются, closures обращаются к актуальному pipeline |
| ContinuationService, operation inventory, DTO catalog | Ленивое состояние клиента | Не очищается автоматически |
| Будущие admission/policy handlers | Стабильные зависимости клиента | Те же handlers; решения/снимки принадлежат выполнению, не сборщику |

## Код до и после: граница ответственности

Сейчас private buildPipeline непосредственно вызывает большой конструктор Pipeline,
а AbstractClient содержит правила metadata cache, регистрации и фабрик результатов.
После refactor buildPipeline делегирует `ClientAssemblyFactory::createPipeline(...)`;
конструктор сохраняет явный порядок стадий выше. Внешний код остаётся прежним:

```php
$client = new ProviderClient($config, $transport);
$result = $client->send($request);
```

Пользователю не нужно создавать фабрику или получать объекты из ClientComponents.
Разница для сопровождения: изменение схемы соединения Pipeline/зависимостей идёт
в фабрику; изменение send/async/result остаётся в клиенте. Это разделение причин
изменения, а не переход на новую систему DI и не обещание полностью развязать классы.

## Проверка прочности

Тестовый trace должен зафиксировать порядок кастов/extensions/auth cache/response
factory и global mock; extension/response callbacks проверяют доступность нужных
частей клиента. Отдельно сравнить identity реестров и limiter при fake/record/playback,
реальную сохранность квоты, выбор нового transport и auth owner.

Шесть экземпляров с разными config/transport используют одну реализацию фабрики,
но получают независимые собственные реестры/limiter. Только явно переданный объект
может быть общим. Нельзя случайно сделать фабрику глобальным хранилищем зависимостей.
Снимок политики при новом send не вызывает createPipeline или конструктор клиента.
