## Предмет и основание

Проверка по поручению пользователя после коммита `ec8d80c`.
Основание — [AS-11](../../issue/001/technical-specification.md#14-as-11--rate-limiting)
и [F06 исходного аудита](../aud-001-architecture-code-2026-09-11/aud-001-readme.md#f06-ключи-внутренних-хранилищ-несовместимы-с-psr-16).
На этапе исходной проверки изменения ядра не выполнялись. Наблюдения и первоначальные рекомендации сохранены;
текущие согласованные решения приведены в разделе «Ответы и итоговый объём». Архив history не использовался.

Затронуты RateLimiter, RateLimitApplier, RateLimitConfig/атрибут/runtime overrides,
порядок RetrySender и общий ExecutionBudget. Проверка ограничена одним правилом
лимита на попытку; полноценный набор иерархических квот и async-first не исследовались.

В гонке запускаются два настоящих PHP-процесса. Барьер фиксирует допустимое

детерминированное доказательство потери обновления, не нагрузочный тест Redis/Laravel.
Стенд рассчитан на одну операцию на процесс и окно 60 s; TTL и прочие cache-методы
не моделируют полноценный backend. Барьер ограничен 3 s, orchestrator — 6 s;
временный каталог удаляется после завершения.

Затронутые тесты: **43 passed, 133 assertions**, 0.14 s. Тесты закрепляют и прежние
контракты (per-instance memory, формат ключа), поэтому не опровергают находки.
Полный suite не запускался: производственный код не менялся.

## Первоначальные рекомендации и статус согласования

### В1. Область квоты без обязательных ключей

- Статус: отвечен. Расширение отложено по ответу О1 ниже.
- Ниже сохранена первоначальная рекомендация, не текущий scope.
- Рекомендация: без store сделать общее состояние внутри одного PHP-процесса
  для одинакового SDK-клиента, baseUrl и объявления лимита. Создание ещё одного
  клиента само по себе не должно добавлять разрешения. Без настроенного rateLimit
  или атрибута лимитер по-прежнему выключен: ядро не угадывает квоту внешнего API.
- Автоматическая область по умолчанию — SDK/baseUrl. Не включать URL каждого
  запроса, query/body или credentials автоматически: это может размножить общий
  лимит сервиса/IP. Для квот на credentials/ресурс SDK-провайдер сможет объявить
  стабильную identity явно; пользователь обычного клиента не обязан задавать prefix.
- Custom key — логическая группа внутри области SDK/baseUrl, без случайных коллизий
  между разными API. Объединение разных адресов, если потребуется по контракту API,
  должно быть явным расширением, а не побочным эффектом короткой строки `orders`.
- Пример: приложение создаёт клиент на каждый вызов. При 10 запросах в минуту
  три клиента к одному API должны делить 10, а не получать 30.
- Для плана: определить каноническое описание правила и поведение разных limit/period
  для одной явной группы; не складывать молча разные окна. Заложить очистку истёкшего
  локального состояния и изоляцию тестов/долгоживущих процессов.
- Последствия: изменение per-instance контракта и namespace custom key; старые ключи
  не переиспользуются. Межпроцессной гарантии без общего backend не появляется.

### В2. Гарантия общего лимита через атомарный backend

- Статус: отвечен. Расширение отложено; обычный store сохраняется по ответу О1.
- Ниже сохранена первоначальная рекомендация, не текущий scope.
- Рекомендация: локальный режим работает автоматически. Для общего хранилища
  нужен контракт атомарного acquire; предусмотреть Laravel-совместимый адаптер
  и автоматический выбор при доступной поддерживаемой возможности.
- PSR-16 get/set сам по себе не объявлять строгим limiter. Если пользователь явно
  настроил shared store, но атомарный механизм недоступен, завершать понятной ошибкой
  конфигурации до HTTP. Не заменять незаметно общий лимит локальным и не продолжать
  с приблизительным счётчиком.
- Конкретный backend не включать в обязательные зависимости ядра. Наличие Laravel
  или PSR-16 не гарантирует возможность блокировок; доступность адаптера должна
  проверяться по фактической capability. Детали адаптера проверить при подготовке плана.
- Пример: два worker одновременно хотят отправить по запросу при одном оставшемся
  разрешении. Получить разрешение должен только один; второй ждёт или получает отказ.
- Последствия: прежний обычный PSR-16 store может потребовать совместимого адаптера.
  Это реальное ограничение zero-config: распределённую атомарность нельзя получить
  из интерфейса, который её не предоставляет.

### В3. Ожидание и немедленный отказ

- Статус: отвечен. Принято по О3 с обычным перечитыванием вместо атомарного acquire.
- Атомарность отложена, текущий Wait/Throw сохраняется.
- Рекомендация: сохранить Wait по умолчанию и существующий Throw для немедленного
  отказа. После пробуждения повторно атомарно проверять квоту; занятое место означает
  новое ожидание/отказ, без перезаписи чужого счётчика.
- Общий бюджет остаётся обязательной границей, если он задан. Если ожидание
  не помещается в остаток, возвращать timeout без sleep и HTTP, как сейчас.
- При немедленном отказе отдавать rate_limited с reason локального ограничения
  и retryAfter в error context. Если HTTP не было, response должен быть null,
  без искусственного ответа 429. Если уже была предыдущая HTTP-попытка, сохранять
  только действительно полученный ответ, отдельно обозначив локальную причину остановки.
- Локальный отказ/сбой лимитера не должен запускать обычный HTTP retry; сохранение
  разрешённой попытки и последнего ответа проверить в матрице реализации.
- Пример: в обычном скрипте SDK дождётся места. Worker очереди с Throw получит срок
  следующей попытки и сможет перенести job, не удерживая процесс в ожидании.
- Последствия: ожидание остаётся блокирующим в текущем sync/promise API; synthetic
  response исчезнет. Новый флаг для обычного пользователя не нужен.

### В4. Отказ хранилища — остановка отправки

- Статус: отвечен. Принято по О2 ниже.
- Рекомендация: если хранилище/атомарный backend не подтвердил учёт разрешения,
  возвращать диагностируемую ошибку до HTTP. Не выдавать разрешение и не переключаться
  на память автоматически. Не повторять неопределённую запись вслепую: разрешение
  могло быть учтено до потери подтверждения.
- Отличать исчерпанную квоту от поломки инфраструктуры. В плане закрепить безопасную
  причину вроде `rate_limit_backend_error`, сохранив техническое previous для ручного
  разбора; не включать содержимое ключей/credentials в автоматическое сообщение.
- Пример: Redis недоступен. SDK останавливается, чтобы несколько worker не отправили
  неограниченный поток запросов к внешнему API.
- Последствия: отказ store::set(false), который сейчас игнорируется, станет ошибкой.

## Ответы и итоговый объём

Ответы получены 2026-09-12 от владельца пакета после повторного обсуждения продуктовых
последствий. Источник: «1. Согласен, всё что сверху — в беклог с отложкой до
востребования; 2. Хорошо; 3. ОК» в ответ на три итоговых вопроса.

### О1 — существующий store и границы SDK (В1, В2)

Сохранить существующий необязательный RateLimitConfig::store для совместимости,
явно описав отсутствие строгой атомарной гарантии между процессами. Не требовать
нового адаптера от нынешних потребителей PSR-16. Без store оставить отдельный
счётчик экземпляра клиента; автоматически разные клиенты не объединять.

Дополнительная координация, новые области identity/ключей, атомарные адаптеры и
связанные расширения перенесены в [backlog до востребования](../../backlog/pln-015-shared-rate-limit-coordination.md).
Очередь заданий и worker — ответственность приложения.

### О2 — ошибка записи/чтения store (В4)

Отказ хранилища, включая set(false), останавливает отправку с диагностируемой
ошибкой. Не переключаться скрыто на память и не продолжать без учёта разрешения.
Это изменение прежнего поведения; недоступность backend может приостановить интеграцию.

### О3 — локальный отказ без вымышленного HTTP (В3)

Сохранить Wait/Throw и deadline. После ожидания перечитать состояние и проверить
свободное место; межпроцессная атомарность этим не обещается. Локальное исчерпание
квоты даёт rate_limited и время следующей попытки в контексте результата. Если
HTTP-вызова не было, не создавать искусственный ProviderResponse(429).

### Техническая поставка и совместимость

- Сохранить отключённый по умолчанию limiter и текущие defaults RateLimitConfig:
  100/60, Wait, store=null, key=null. Новых обязательных зависимостей и полей нет.
- Логическую группировку по baseUrl/custom key сохранить; исправить только кодирование
  ключей для PSR-16. Новые физические ключи не читают прежний счётчик: при обновлении
  возможен однократный сброс квоты, а смешанные версии могут считать отдельно.
  Старые записи не удалять массово — оставить штатный TTL.
- Положительные limit/period валидировать. Нулевые/отрицательные значения, которые
  раньше принимались, станут ошибкой конфигурации; для отключения есть withoutRateLimit.
- При исправленном перечитывании Wait может ждать дольше, если место занял другой
  участник; общий бюджет остаётся прежним ограничением.
- Отказ store больше не выглядит разрешением; result-first и режимы исключений
  сохраняются. Список причин и тип ошибки backend уточнить в плане реализации.
- Отсутствующий реальный HTTP означает response=null в локальном отказе. Клиентам,
  читающим response->status без проверки, потребуется миграция на SDK code/retryAfter.
- В текущем коде RateLimitException наследует RequestException с обязательным
  ProviderResponse. Точный способ устранения synthetic response требует проверки
  цепочки исключений в плане; целевой контракт — сохранить узнаваемый rate_limited,
  catch RateLimitException и retryAfter, не выдавая nullable-изменение за полностью
  совместимое. Нельзя менять общую иерархию исключений без проверки потребителей.

Решения согласованы и перенесены в
[план реализации](../../completed/pln-016-rate-limit-correctness.md). Дополнительная
проверка иерархии исключений и интеграции с retry записана в плане.
