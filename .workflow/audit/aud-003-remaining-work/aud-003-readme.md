- Дата создания: 2026-09-12
- Дата обновления: 2026-09-12

## Основание и границы

Поручение пользователя: проанализировать четыре оставшихся направления и создать
четыре плана. Проверен HEAD `c10ec96`; src, tests, Composer и CI не изменялись.
Основание требований — [issue 001](../../issue/001/technical-specification.md) и
[исходный аудит](../aud-001-architecture-code-2026-09-11/aud-001-readme.md).
Документы issue не являются автоматически согласованной новой функциональностью.
Принятые ранее ограничения и zero-config сохраняют приоритет.

Проверка включает auth retry, Laravel DI, остаточные контракты пагинации/runtime/
диагностики, тесты и состав выпуска. Не включает настоящий async, атомарные лимиты,
управление очередями, live API и полноценную сертификацию Laravel-приложения/Octane.
Файлы history не использовались для архитектурных выводов; в проверке архивов
учтены только имена файлов, попадающих в дистрибутив.

## Находки

| ID | Приоритет / основание | Наблюдение и значение |
| --- | --- | --- |
| A1 | P1, воспроизведено | Без auth и с неизменяемым Bearer ответ 401 приводит к двум основным HTTP-вызовам при authRetryAttempts=1; refresh не существует. |
| A2 | P1, воспроизведено | После исходного 401 refresh получает 503, но результат содержит созданный SDK ответ 401 с body `Unauthorized`; исходный заголовок и тело теряются. |
| A3 | P1, воспроизведено | `client->send(new Request())` доходит до 401, но refresh падает с «Клиент не установлен для запроса». При явном setClient тот же успешный refresh даёт три HTTP-вызова и 200. |
| A4 | Контроль, пройдено | Привязанный request с нормальным refresh работает: основной 401 → refresh 200 → основной 200. TokenAuthenticator уже имеет версию токена и повторное чтение кеша после ожидания lock; это нужно сохранить. |
| L1 | P1, воспроизведено | Laravel resolving callback заменяет явно заданное query=`explicit` на входящее `incoming`; без входящего Request значение становится null. |
| L2 | P1, воспроизведено | SdkServiceProvider заменяет уже зарегистрированные RequestFactoryInterface и ClientRegistry. Default TransportInterface, напротив, защищён bound-проверкой — это не тот же дефект. |
| L3 | P2, сверка | Нет extra.laravel.providers; актуальный guide не показывает полноценный способ регистрации provider. Тесты используют Container, не полноценный Laravel/config:cache/worker. |
| P1 | P1, воспроизведено | Ошибка страницы HTTP 403 в агрегате превращается в server_error без error.response; исходный результат доступен лишь среди nested. |
| P2 | P1, воспроизведено | Cursor A → B → A не распознаётся как цикл; повторяется до maxPages. При явно отключённом maxPages код не содержит защиты от такого цикла. Бесконечный запуск не выполнялся. |
| P3 | P1, воспроизведено | Partial после ошибки cursor-страницы отправляет тот же cursor снова, увеличивая page, до maxPages. Продолжить cursor-обход без нового cursor нельзя достоверно. |
| P4 | Контроль / сверка | Cursor `"0"` сохраняется: второй HTTP содержит cursor=0. Соседний повтор cursor и maxPages уже покрыты тестами. Iterator при guard молча завершает обход — по коду; семантика требует решения. |
| E1 | P1, воспроизведено | Один HTTP 403 в parallel batch: throwOnErrors=false даёт forbidden/403, true — connection_failed/null. Общая ExecutionErrorFactory теряет HTTP-смысл исключения. |
| O1 | Наблюдение, не доказанный дефект отправки | withoutRateLimit оставляет объект override, но disabled=true выключает лимитер. withCache(10) → withoutCache → withCache() сохраняет TTL=10. Null/режимы нельзя массово переопределять без контракта. |
| D1 | P2, воспроизведено | Невозможность записать fixture даёт warnings, но при невыбрасывающем обработчике Recorder возвращает HTTP 200 без fixture. |
| D2 | P2, воспроизведено | Бинарное тело с невалидным UTF-8 превращается в файл fixture длиной 0; HTTP остаётся успешным. json_encode/file_put_contents не проверены. |
| D3 | P2, сверка | Recorder не ограничивает строковые тела; имена файлов выбираются file_exists → write и конкурентно не резервируются. Потоковые тела уже пропускаются. Гонка записи отдельно не воспроизведена. |
| D4 | P3, сверка | ProviderResponse документирует duration в секундах, HttpTransport вычисляет миллисекунды. Менять численные значения не требуется: сначала унифицировать описание и экспорт. |
| R1 | P1 для выпуска, воспроизведено | Composer archive текущей рабочей копии: 7201 файл, 33 399 296 байт, включая 5794 файла vendor и 202 workflow. Git archive HEAD: 1396 файлов, 7 229 440 байт, включая 192 workflow. Не утверждается, что опубликованный dist уже содержит эти данные. |
| R2 | P2, воспроизведено | 34 отчёта deprecation относятся к Reflection::setAccessible в src/tests пакета. По показанным сообщениям это не проблема зависимостей. |
| R3 | P2, сверка | CI уже содержит PHP 8.4/8.5 и composer test. Нет отдельных обязательных проверок no-dev, Laravel harness, lowest dependencies, архивов, стиля и статического анализа. Composer validate уже проходит. |

Подтверждённые дефекты не означают, что всё направление нужно переписать. В частности,
AS-13 требует закрепления существующих расширений; DTO/Nested/enum/URI и большинство
reset-сценариев уже имеют тесты и завершённые планы.

## Вопросы

Адресат всех вопросов — владелец пакета. В1/В3/В4/В5 отвечены (О1 ниже),
В2 отвечен после продуктового объяснения (О2 ниже). Все решения согласованы;
открытых продуктовых вопросов по четырём планам нет.

| ID | Что согласовать | Рекомендуемое решение | Где зависит реализация |
| --- | --- | --- | --- |
| В1 — отвечен, О1 | Условие auth retry и доставка ошибки refresh | Автоматический auth retry только после доступного успешного refresh/подтверждённого обновления TokenAuthenticator; без него сохранить 401. После неудачного refresh сохранить основной настоящий 401 и отдельную диагностику зависимости, до первого основного HTTP — фактическую ошибку refresh. Явный обычный retryOn=[401] остаётся обычной политикой. | pln-017 |
| В2 — отвечен, О2 | Автоподключение Laravel и заполнение request из HTTP | Безопасный provider подключается discovery; обычный DI не копирует входящие данные. Для копирования используется существующая явная RequestFactory. Ручная регистрация продолжает работать. | pln-018 |
| В3 — отвечен, О1 | Ошибки и завершение cursor-обхода | Сохранять исходные ошибки страниц, прекращать cursor-обход при потере возможности продолжения даже с Partial; цикл ловить по всем посещённым cursor. Iterator сообщает guard отдельным FAILED-результатом, без исключения по умолчанию. | pln-019 |
| В4 — отвечен, О1 | Доставка ошибки recorder | Явная recording_failed с фактическим HTTP-ответом; SDK не повторяет HTTP. Корректные replay fixtures не обрезать и не ограничивать новым порогом размера. Неподдерживаемое тело/сбой записи не должны создавать пустую fixture. | pln-019 |
| В5 — отвечен, О1 | Ограничение тел safe debug/log | Default 64 KiB на тело, выше — маркер пропуска и размер. Лимит можно увеличить без отключения маскирования. Исходный ответ и replay fixture не ограничиваются этим правилом. | pln-019 |

границах. Статус каждого — «новый»: согласование не означает выполнения кода
или прохождения будущих критериев приёмки.


## Перепроверка четырёх планов — 2026-09-12

По просьбе пользователя проверены планы 017–020, их зависимости, совместимость и
продуктовые последствия. [Результат перепроверки](artifacts/plan-review.json):
контрольные суммы 12 исходников совпадают; повторены 16 auth/DI/pagination/runtime/batch
и 2 recorder сценария, результаты совпали с baseline. Полный suite не запускался
повторно: код и постоянные тесты не менялись. Предыдущий результат 1413/34 сохранён
с его фактической командой и датой; это не новый прогон.

В плане 019 обнаружено лишнее продуктовое ограничение: предложенный отказ записи
любой fixture больше 1 MiB не обоснован дефектом. Рекомендация пересмотрена до
согласования: сохранить запись корректных больших fixtures, отдельно ограничить
safe debug/log и дать увеличить этот лимит без снятия маскирования. В4 теперь
относится к доставке ошибки recorder, В5 — к diagnostic body limit. Предыдущая
рекомендация 1 MiB не была принята пользователем и не реализовывалась.

По 017 уточнены сохранение обоих ответов и совместимость auth-интерфейса; по 018 —
граница явной фабрики и безопасного автоподключения; по 020 — отсутствие нового
продуктового решения, production-зависимостей или автоматического выпуска.
Планы проверены для согласования; полноценные Laravel/CI/release проверки остаются
их будущими критериями реализации. На момент перепроверки статус всех планов — новый, В1–В5 были открыты;
последующее согласование записано ниже.


## Ответы

### О1 — приняты В1, В3, В4 и В5

- Дата: 2026-09-12.
- Источник: ответ владельца пакета «2. продуктовое объяснение нужно, по остальным ок»
  на пять пунктов итоговой проверки планов.
- Приняты рекомендации по auth recovery, остановке cursor-пагинации, доставке ошибки
  recorder и ограничению safe debug/log с возможностью увеличить лимит без снятия
  маскирования. Нового ограничения размера корректной replay fixture нет.
- Планы 017 и 019 обновлены: продуктовые решения согласованы, реализация ещё не начата.
- На момент О1 В2 не согласован: требовалось объяснить последствия изменения Laravel
  auto-fill. Последующий ответ зафиксирован в О2.

### О2 — принят В2; согласование завершено

- Дата: 2026-09-12.
- Источник: ответ владельца пакета «принято, фиксируй всё» после продуктового
  объяснения изменения Laravel auto-fill.
- Принята рекомендация В2: package discovery автоматически подключает безопасный
  provider; обычный DI сохраняет значения SDK-запроса и не копирует параметры
  входящего HTTP-запроса. Пользовательские bindings сохраняют приоритет.
- Если контроллер намеренно переносит входящие данные в SDK-запрос, он явно вызывает
  существующую RequestFactory. Контроллерам, полагавшимся на прежнее автоматическое
  заполнение, потребуется миграция; это последствие принято и должно быть описано
  в документации с примером.
- Zero-config сохранён: для обычного подключения не нужны новый флаг, атрибут,
  опубликованный конфиг или дополнительные runtime-зависимости ядра. Ручная
  регистрация provider остаётся допустимой.
- План 018 обновлён. Решения В1–В5 приняты, планы 017–020 готовы к реализации;
  открытых продуктовых вопросов нет. Реализация ещё не начата, порядок —
  017 → 018 → 019 → 020. Подготовка выпуска не означает разрешения на публикацию.
