# Разделение хранилища и параметров кеша клиента

- Дата создания: 2026-09-15
- Дата обновления: 2026-09-15
- Статус: новый

## Основание и результат

**AS-6 / F02, P2** из [issue](../../issue/iss-003-apisutra-contracts/iss-003-readme.md).
[AS-6](../../issue/iss-003-apisutra-contracts/upstream-requirements.md#as-6-корректное-копирование-и-переопределение-конфигурации-кеша)
требует корректного копирования, применения явных настроек и однозначного отключения
без очистки backend. Автор не предписывает синтаксис; владелец допускает миграцию.

Подтверждённые [upstream-probe](../../issue/iss-003-apisutra-contracts/artifacts/upstream-probe.php)
наблюдения старого API:

| Наблюдение | Исходное поведение |
| --- | --- |
| U13–U14: cache=store плюс cacheConfig без store | with()/with(timeout:7) теряют хранилище, два GET дают два HTTP |
| U06: замена cacheConfig после цельного блока в cache | Новые настройки игнорируются, TTL остаётся 60 вместо 10 |
| U07: with(cache:null) после цельного блока | cache=null, но кеш продолжает работать через cacheConfig.store |
| U08–U09 | Оба null отключают подключение; новый цельный блок через cache применяется |

Принятый результат: **один cacheStore и независимый CacheConfig без store**.
Два источника одного подключения исчезают из API; with меняет поля независимо.
Исправление включает миграцию вызовов, HTTP/auth-потребителей, примеров и тестов.
Промежуточную нормализацию старой пары сначала реализовывать не требуется.

## Архитектура и затронутые места

| Компонент | Изменение |
| --- | --- |
| [ClientConfig](../../../src/Config/ClientConfig.php) | Заменить аргумент/поле cache на cacheStore: ?CacheInterface; копировать независимо от cacheConfig |
| [CacheConfig](../../../src/Config/CacheConfig.php) | Удалить store; сохранить параметры и их defaults/типы |
| [CacheManager](../../../src/Pipeline/Cache/CacheManager.php) | Читать store из клиента; разрешать отдельно только параметры, включая Cache-атрибут и runtime overrides; убрать перенос store внутрь CacheConfig |
| [CacheExecutionState](../../../src/Pipeline/Cache/CacheExecutionState.php), [CacheIdentityResolver](../../../src/Pipeline/Cache/CacheIdentityResolver.php) | Сохранить ссылку на store в состоянии выполнения и прежнюю identity по параметрам; публичный конфиг не смешивать с execution state |
| [AuthBindingResolver](../../../src/Pipeline/Auth/AuthBindingResolver.php), [AuthHandler](../../../src/Pipeline/Auth/AuthHandler.php) | Один источник cacheStore; прежние identity/locks и правила общей/локальной области |
| [AbstractClient](../../../src/Core/AbstractClient.php) | Перенести начальное подключение store к auth; удалить fallback старой пары |
| [TestClientFactory](../../../tests/Support/TestClientFactory.php) и standalone helpers | Перейти на новый API; различать отсутствующий override и явный null, не маскировать отключение запасным store |

CacheManager меняет не только prepareExecution: проверить clearScope, clearCache,
resolveCacheConfig/State, hasStore, check/storeCache и проверки повторной identity.
Конкретные private helpers можно упростить; нового публичного resolver-а нет.
CacheExecutionState по-прежнему может содержать store: это выбранная зависимость
вызова, а не способ объявить ещё одно хранилище.

Не переименовывать самостоятельные cache/store в metadata, сериализаторах,
AttributeRegistry, RateLimitConfig и пользовательских расширениях. Параметры
identity/locks не переносить в новый auth-блок; разные store HTTP/auth не добавлять.
Старые записи backend, алгоритмы ключей и scope generations сохраняются.
Масштаб переноса тестовых вызовов зафиксирован построчно в migration-inventory.json
сохранённого прогона; он включает тесты разных модулей и standalone/helpers,
а не только тесты кеша. Это список кандидатов для адресной миграции, не автозамена.

## Зависимости и завершение

План независим от [032 — полей конструктора](../pln-032-constructor-owned-fields/pln-032-readme.md).
Общая работа в документации/changelog и синтаксисе тестовых клиентов согласуется
при сборке изменений. Если 033 идёт первым, AS-5 probe адаптируется к новым аргументам
без изменения проверок DTO; это перенос вызовов, не зависимость механизма гидратации.

Завершение включает новый API, исправленные исходные сценарии, всю матрицу,
публичную миграцию, исполняемые примеры и документацию. Отдельного плана на перенос
или недостающие тесты нет. Готовность к реализации не означает доступность нового API.
