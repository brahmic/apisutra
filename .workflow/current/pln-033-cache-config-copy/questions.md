# Решения по AS-6

Действующий выбор — **K03: раздельные cacheStore и cacheConfig с миграцией**,
принятый 2026-09-15. K01/K02 ниже сохраняют происхождение прежнего решения; их
таблица совместимости заменена новым [контрактом](contracts.md), не действует параллельно.

## K01. Что означает отключение

- **Статус:** отвечен; прежняя API-форма заменена K03.
- **Адресат решения:** владелец ApiSutra; требования уточнил автор issue через пользователя.
- **Сохраняется:** изменение конфигурации не очищает backend и не перенастраивает
  старый клиент; store и настройки можно менять независимо; отключение HTTP отдельно.

Вопрос был поставлен как выбор полного сброса через with(cache:null). Владелец
ответил: «Надо обсудить и понять замысл того, кто написал ишью».

### Что требует автор issue

[AS-6.4](../../issue/iss-003-apisutra-contracts/upstream-requirements.md#as-6-корректное-копирование-и-переопределение-конфигурации-кеша)
допускает сохранить прежнюю null-семантику, если документирован полный способ
отключения. AS-6.6 требует различать HTTP-кеш и общий auth store.

### Ответ автора issue

- **Статус внешнего уточнения:** отвечен.
- **Дата и источник:** 2026-09-15, комментарий автора, переданный пользователем в чате.

Автор подтвердил:

1. Отключение — прекращение использования кеша новым клиентом, без удаления записей
   общего backend и изменения уже созданного клиента.
2. with(cache:null) вправе убирать только один источник store; сохранение подключения
   через cacheConfig.store само по себе не объявляется дефектом.
3. Старый with(cache:null, cacheConfig:null) допустим как полный способ удаления
   подключения, записи backend и исходный клиент сохраняются.
4. Обязательные дефекты — потеря store при with()/смене timeout и игнорирование
   нового cacheConfig. Синтаксис отключения выбирает разработчик ApiSutra.

Нового внешнего ответа не требуется. Разрешение миграции владельцем не меняет
этих требований, а уточняет API, которым они решаются.

### Предшествующие ответы владельца

Сначала был выбран N2 — сохранить смысл одиночного cache:null и документировать
оба null. Источник: «Хорошо, оставшиеся вопросы какие?» от 2026-09-15. Это согласие
не распространялось на ещё не выбранные строки cacheConfig.

Затем владелец отдельно ответил:

- «С согласен с рекомендуемым решением» — новый cacheConfig без store сохраняет
  хранилище, но целиком заменяет параметры; cacheConfig:null сохраняет store и
  сбрасывает параметры, включая возможное возвращение HTTP Enabled после Disabled.
- «Да, отклонять эти сочетания (рекомендую)» — разные цельные CacheConfig в двух
  аргументах отклоняются даже с одинаковыми данными; один и тот же экземпляр разрешён;
  with(cache: $block, cacheConfig: null) тоже отклоняется.

Это была принятая таблица исправления **старого** API. После K03 сохранить N2
буквально нельзя: аргумент cache и второй store удаляются. Независимая замена/сброс
параметров сохраняются в новом API; конфликтные формы заменены отсутствием второго
входа и явным отказом использовать удалённые имена.

## K02. Конфликт явно переданных хранилищ

- **Статус:** отвечен; способ устранения конфликта заменён K03.
- **Адресат:** владелец ApiSutra.
- **Ответ:** «ConfigurationException при конфликте (рекомендую)».
- **Дата и источник:** 2026-09-15, сообщение пользователя в чате.

Первоначально принято отклонять разные store через cache и cacheConfig; не считать
унаследованный старый store вторым явным указанием. K03 устраняет возможность
объявить два store в поддерживаемом API. Старые имена/неверные типы отклоняются
на границе PHP-сигнатур; специальный ConfigurationException для прежней пары не
вводится. Намерение «не выбирать один из конфликтующих store молча» сохраняется.

## K03. Разделение API и миграция

- **Статус:** принято 2026-09-15.
- **Адресат:** владелец ApiSutra.
- **Закрывает:** архитектуру, новый контракт, миграцию, ADR-004, матрицу C01–C26
  и готовность 033 к этапу реализации.
- **Источник:** текущий чат; сначала предложение владельца архитектурно развести
  сущности, затем ответ на конкретный вариант cacheStore + CacheConfig без store.

Ответ владельца: «миграцию конечно допускаем, если данное решение с архитектурной
точки зрения более чистое и гибкое».

Выбрано разделение: одно поле/аргумент cacheStore для PSR-16 store, один блок
cacheConfig только для параметров. Старое cache и CacheConfig.store удаляются без
совместимых алиасов; возвращать несколько источников в переходный API не требуется.
Это обосновано независимыми операциями настройки и устранением самой причины
приоритетов/коллизий. Кеш HTTP и auth сохраняют общий источник, identity/locks —
прежнее назначение. Новый публичный API и миграция выполняются в том же плане 033.

[ADR-004](../../adr/adr-004-cache-store-separation.md) принят; конкретное поведение —
в contracts, перенос — в migration. [Архитектурный разбор](architecture-review.md)
содержит предшествующие альтернативы и пометку их пересмотра, не второй контракт.
Открытых вопросов для начала реализации нет; номер выпуска определяется при релизе.
