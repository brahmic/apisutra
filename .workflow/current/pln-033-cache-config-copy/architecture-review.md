# Разделение источника хранилища и параметров кеша

Разбор для [плана 033](pln-033-readme.md), 2026-09-15. **Обсуждение завершено:**
владелец допустил миграцию и выбран раздельный API по
[K03](questions.md#k03-разделение-api-и-миграция) и
[ADR-004](../../adr/adr-004-cache-store-separation.md). Действующее поведение задаёт
[контракт](contracts.md); ниже сохранены рассмотренные варианты и причины пересмотра.
Исходный код в рамках этого разбора не менялся.

## Откуда возникает неоднозначность

У [ClientConfig](../../../src/Config/ClientConfig.php) cache принимает
CacheInterface или целый CacheConfig. Отдельный cacheConfig тоже содержит store.
Таким образом, есть и два имени для блока, и два источника одного подключения.

Потребители дополнительно разрешают эту пару:
[CacheManager](../../../src/Pipeline/Cache/CacheManager.php) предпочитает store
из блока, [AuthBindingResolver](../../../src/Pipeline/Auth/AuthBindingResolver.php)
и [AuthHandler](../../../src/Pipeline/Auth/AuthHandler.php) — прямой cache.
[AbstractClient](../../../src/Core/AbstractClient.php) тоже читает эту пару при сборке.
Это фактура по коду, а не новый воспроизведённый дефект сверх issue.

Различие касается одного общего подключения HTTP/auth. Раздельные хранилища для
этих подсистем не требуются AS-6; их добавление потребовало бы самостоятельного
контракта identity, блокировок и отключения. Само переименование cache в cacheStore
также не устранит коллизию, пока CacheConfig сохраняет второй store.

## Прежний вариант без смены API — заменён

Этот вариант ранее был принят для сохранения совместимости; после K03 не реализуется.

У ClientConfig — единственное место разрешения входной пары и её overrides.
Конструктор и with используют общую нормализацию; with предварительно различает
переданные и унаследованные значения. Потребители не изобретают новые приоритеты.

Инвариант результата: если оба источника store ненулевые, это один и тот же объект.
Поэтому нынешние чтения HTTP/auth дают одинаковый store при любом порядке fallback.
Нового публичного resolver/getter и самостоятельных правил копирования в pipeline
для этого не требуется. Если helper выделен из ClientConfig, он внутренний.

Нельзя просто записать эффективный store в оба публичных поля: это нарушит принятый
N2 для split-формы. Чистая копия сохраняет исходные поля/ссылки; изменённая пара имеет
явно выбранное представление копии. Прежняя таблица представления заменена K03.
Тем самым старые формы остаются входным синтаксисом с одним владельцем семантики,
а не независимыми решениями разных подсистем.

Этот вариант закрывает подтверждённые дефекты с принятой совместимостью. Он
устраняет расхождение исполнения, но не удаляет дублирование публичных аргументов:
запрет противоречивых деклараций остаётся частью контракта.

## Выбранное упрощение публичной модели

При разрешённой миграции предпочтительно разделить источник и настройки:

| Часть | Ответственность |
| --- | --- |
| Аргумент cacheStore | Только PSR-16 хранилище, общее по умолчанию для HTTP/auth |
| Один блок параметров без store | TTL, prefix, mode, identity и locks с их нынешними областями действия |

Имена и сигнатуры теперь приняты в контракте. Store не дублируется внутри блока, аргумент store не
принимает целый блок. Его null однозначно убирает подключение; null блока сбрасывает
параметры при сохранении store. Это согласуется с намерением уже принятого K01,
но меняет публичные сигнатуры и не может считаться тихой реализацией нынешней таблицы.

Альтернатива — оставить только цельный CacheConfig со store. Тогда исчезает второй
источник, но замена только параметров должна выражаться копированием этого блока,
а не неявным наследованием store от удалённого аргумента. Нужен отдельный удобный
контракт частичных изменений. Для заявленного намерения разделение store/параметров
прямее отражает два разных действия.

Миграция включает новые сигнатуры и поля, удаление прежнего cache/CacheConfig.store,
обновление потребителей HTTP/auth, тестовых фабрик и всех публичных примеров.
Совместимых алиасов нет: пока старые формы принимались бы, нормализация и конфликты
оставались бы на границе. Теперь порядок переноса зафиксирован в [migration](migration.md).

**Пересмотр рекомендации:** после разрешения миграции выполнить разделение в 033,
не реализовывать сначала промежуточный helper старой пары. Дополнительный план не нужен.
Сам этот файл остаётся записью обсуждения; принятое архитектурное решение — ADR-004.
