# Остаточные контракты результатов, пагинации и диагностики

- Дата создания: 2026-09-12
- Дата обновления: 2026-09-12
- Статус: новый

## Основание и границы

[Аудит P1–P4, O1, D1–D4, E1](../audit/aud-003-remaining-work/aud-003-readme.md),
остатки AS-02/AS-09/AS-10/AS-13 и F16. Цель — устранить подтверждённые расхождения
существующих контрактов и закрепить их общей приёмкой. Новый paginator, DTO-engine,
универсальный reset API и дополнительная транспортная архитектура не требуются.

Это один план из трёх последовательных частей: доставка ошибок и пагинация;
проверка runtime/DTO; безопасная диагностика и recorder. Каждая часть получает
свои regression-тесты до общей приёмки.

## Подтверждённые проблемы

- Агрегат paginator превращает HTTP 403 страницы в server_error без error.response;
  исходный результат остаётся только в nested.
- Cursor A → B → A повторяется до maxPages; Partial при ошибке повторяет старый
  cursor, увеличивая page. Guard iterator завершает обход без сообщения об ошибке.
- Parallel batch при throwOnErrors=false сохраняет forbidden/403, при true превращает
  тот же ответ в connection_failed/null. Новые rate-limit ветки этот общий пробел не закрыли.
- Recorder не проверяет mkdir/json_encode/file_put_contents: невалидный UTF-8 даёт
  пустую fixture; неудачная запись может остаться лишь PHP warning. Выбор имени через
  file_exists не резервирует файл при конкурентной записи — вывод по исходникам.
- Строковые диагностические тела не ограничены. Duration в VO описан в секундах,
  а HttpTransport передаёт миллисекунды.

Уже работает: cursor `"0"`, соседний повтор cursor, maxPages, большинство DTO/Nested/enum
контрактов, scoped auth reset, очистка PreparedRequest и signed URL. Их проверка
не является разрешением переписать принятую семантику.

## Согласованные решения

В3–В5 приняты пользователем 2026-09-12 — О1 в
[ответах аудита](../audit/aud-003-remaining-work/aud-003-readme.md#ответы).

### Пагинация

Рекомендуется сохранять исходный SDK-код/ответ страницы и добавлять номер страницы/метаданные остановки. Непрозрачный cursor не экспортировать
в автоматическую диагностику.
FailAll прекращает обход; ранее собранные данные остаются в PARTIAL по текущему
контракту агрегата. Partial может продолжать page/offset-обход, где следующий запрос
известен, но прекращает cursor-обход после ошибки: следующего cursor нет.

Любой повтор посещённого cursor означает остановку до повторной отправки этой
страницы. `maxPages=1000` остаётся стандартным пределом, null — явным отключением
количественного предела, но не защиты от цикла. Cursor сравнивается как непрозрачная
строка, без потери `"0"`. Отсутствие следующего cursor при hasMore=false — обычное
завершение, а hasMore=true без продолжения — диагностируемая остановка.

Guard выдаёт `execution_error`, reason=`pagination_stalled` или
`pagination_max_pages_reached`, без вымышленного HTTP server_error. Iterator после
уже выданных успешных страниц возвращает один FAILED ExecutionResult с причиной
остановки, затем завершается; по умолчанию не бросает исключение. Явные pages(N)/range
сохраняют семантику ограничения выборки и не становятся ошибкой maxPages сами по себе.

Пример: первые 20 объектов получены, следующая cursor-страница вернула 403 — результат
PARTIAL с этими объектами, forbidden и настоящим 403; повторять прежний cursor нельзя.

### Диагностика и recorder

Рекомендуется встроенный предел **64 KiB на тело в safe debug/log представлении**.
При превышении пропускать тело целиком с причиной и исходным размером; не обрезать
JSON посередине и не раскрывать часть credentials. Предусмотреть необязательное
переопределение лимита для safe export: просмотр большого тела не должен требовать
отключения маскирования. Raw-доступ по существующему явному opt-in сохраняется. RedactionPolicy остаётся необязательной и отвечает за маскирование;
ограничение safe export не должно случайно обрезать replay fixtures через общий redactor.

Recorder уже включается приложением явно. Его ошибка означает, что запись не выполнена:
возвращать отдельную диагностируемую ошибку исполнения с reason=recording_failed и
сохранённым фактическим ProviderResponse. HTTP уже состоялся, поэтому retryExceptions
не должен повторно отправлять операцию из-за ошибки fixture. В exception.previous
сохранить техническую причину, в автоматическом сообщении не раскрывать пути/тела.

Жёсткий предел размера replay fixture в ближайшей поставке не вводить. Предложенные
ранее 1 MiB были необоснованным новым ограничением: большой корректный JSON должен
продолжать записываться без дополнительной настройки. Recorder включается явно и может
создавать большие файлы; ограничение их размера — отдельная возможность до востребования.
Не обрезать replay fixtures лимитом safe debug/log.

Невалидный UTF-8/неподдерживаемое бинарное тело, которое нельзя сохранить в текущем
формате fixture, должно давать явную ошибку записи вместо пустого файла. Новый бинарный
формат/Base64 не вводить автоматически. Потоки, как сейчас, не читать ради записи:
сохранять bodyOmitted/size.

Пример: API успешно выполнил POST, но каталог fixtures недоступен — приложение видит
ошибку записи и реальный HTTP 200; SDK не отправляет POST ещё раз. Это изменение
доставки ошибки recorder согласовано в О1 аудита.

## Часть 1. Ошибки и пагинация

1. Перенести E1/P1–P3 в постоянные pipeline/Execution/Pagination тесты.
2. Исправить ExecutionErrorFactory для известных SDK/HTTP исключений: фактический
   RequestException.response и его HTTP-код сохраняются; отсутствие ответа не даёт
   connection_failed без признаков сетевой ошибки. Согласовать с ExecutionResultBuilder,
   включая timeout, JSON/hydration/configuration/hook и новые auth/recording ошибки.
   Не менять отличие «throw или result» между существующими стратегиями; исправить
   смысл упакованного результата. Проверить raw/resolved/dataOrFail.
3. В Paginator сохранять исходные ошибки страницы с page context, фактическими
   response/traceId и nested-структурой. Не сворачивать все причины в server_error.
4. Добавить локальное множество посещённых cursor на один обход, общее правило
   прогресса для iterator и all/pages/range, корректную остановку Partial cursor.
   Состояние разных запусков и клиентов не смешивается; новый обход начинается заново.
5. Проверить пустую страницу, отсутствующую meta, противоречивые hasMore/cursor,
   cycle A→B→A, соседний повтор, cursor `"0"`, maxPages, ограниченные pages/range,
   page/offset Partial, ошибку на первой/последующей странице, исходный 403/429/timeout.
   Верхняя граница тестового обхода обязательна, тест не должен зависать.
6. Проверить страницы после withPage(N), offset + limit, custom meta resolver и
   DTO items container. Если найдётся новое расхождение, сначала сформулировать
   конкретный контракт; не менять семантику пустых pages(0)/range без основания.

## Часть 2. Runtime и существующие расширения

Составить таблицу nullable полей RequestOptions/PaginationOptions/PreparedRequest:
какой публичный метод задаёт/сбрасывает значение, что означает null, какое поведение
видно в отправленном HTTP. Дополнить только непокрытые комбинации.

- Auth scope A→B→default, without/force auth, timeout/connect reset, url/download/body
  reset уже реализованы — перепроверить взаимодействия, не дублировать все unit-тесты.
- Сохранённый override при withoutRateLimit сам по себе не дефект, если disabled
  работает. При внутренней очистке объекта подтвердить неизменность поведения.
- withCache(null) сейчас сохраняет ранее заданный TTL. Рекомендация: документировать
  и сохранить это значение «не задавать новый TTL»; не менять на default скрыто.
- Для idempotencyKey, traceId, baseUrl, role, credentialsScope и paginationRule
  отсутствие отдельного reset не считать автоматически дефектом. Использовать новую
  execution-копию/пустые опции; новый публичный reset добавлять только при доказанном
  недоступном сценарии, после отдельного согласования семантики.
- Закрепить сквозной provider-neutral сценарий AS-13: path/query/body/header, пять
  HTTP-методов, readonly DTO/mapping/Nested/discriminator, false/0/null/missing,
  custom pagination resolver и подменяемые зависимости. Переиспользовать текущие
  тесты и фикстуры; исправлять код только при подтверждённом расхождении.

## Часть 3. Safe export и recorder

1. Добавить постоянные тесты D1/D2 и ограничений safe export согласно ответам на В4/В5.
2. Ограничивать safe body до дорогого декодирования/экспорта, где известна длина
   исходной строки; сохранять метаданные пропуска. Не читать и не перематывать потоки.
3. В recorder строго проверять кодирование и все результаты файловых операций.
   Резервировать уникальный путь безопасно для конкурентов, писать во временный файл
   и публиковать только полностью записанную fixture. Убирать только собственные
   незавершённые файлы, не перезаписывать чужую fixture.
4. Ввести RecordingException с реальным response, классифицировать её до обычного
   HTTP retry и в batch/pool. Не маскировать ошибку записи как connection_failed.
5. Проверить JSON/text/binary/stream/большое тело, ошибку каталога и записи, два
   recorder-процесса, crash/частичную запись насколько воспроизводимо без внешнего API.
   Старые корректные JSON fixtures должны оставаться читаемыми.
6. Унифицировать документацию duration как миллисекунды; проверить арифметику
   транспорт → audit/result/export. Не умножать уже сохранённые значения повторно.

## Зависимости, совместимость и завершение

Предпочтительно выполнять после [auth recovery](../completed/pln-017-auth-recovery-contract.md)
и [Laravel](../completed/pln-018-laravel-integration.md), чтобы общая матрица учитывала их ошибки.
Новых runtime-пакетов нет. Лимит safe export действует по умолчанию и допускает необязательную настройку;
лимит fixture, префиксы и обязательная RedactionPolicy не вводятся. Большие исходные HTTP-ответы сами по себе не запрещаются —
ограничения относятся к диагностическим копиям и явно включённой записи.

Breaking changes: исходные коды ошибок вместо server_error/connection_failed,
ранняя остановка cursor Partial, новый guard-result iterator, явные recording failures
и ограничение safe diagnostic bodies. Размер корректной replay fixture не ограничивается. Все изменения требуют migration-примеров.

Проверки: Pagination, Execution, Result, Request, Diagnostics, Transport/recording,
Serialization, затем полный composer test и standalone без Illuminate. Обновить
pagination/errors/testing/diagnostics guides, публичные примеры и CHANEGLOG.md.
Итоговая матрица должна ссылаться на существующие и новые тесты, различать исправления,
пройденные проверки и сознательно сохранённые ограничения. В3–В5 отвечены (О1 аудита);
реализация этого плана ещё не начата.


## Проверка плана — 2026-09-12

Целевые воспроизведения повторены, исходники совпадают с контрольными суммами аудита.
План уточнён: убран предлагаемый жёсткий порог fixture 1 MiB, добавлено сохранение
маскирования при увеличении safe-export лимита; В4 и В5 разделяют независимые решения.
При recording_failed основной HTTP уже мог успешно изменить данные: сохранить
response и явно указать это в документации результата. SDK не повторяет отправку,
но приложение также не должно автоматически повторять такую операцию как сетевой сбой.

В iterator финальный guard-result не является ещё одной HTTP-попыткой; не дублировать
ошибочный результат страницы и не выдавать его items повторно. Проверить dataOrFail
и имеющуюся политику исключений, не вводить дополнительные throw по умолчанию.
Матрица runtime должна проверять фактическое наследование опций: одна новая
execution-копия не гарантирует сброс настроек, оставшихся на исходном request.
После проверки В3–В5 согласованы пользователем (О1 аудита); изменения src/tests
не выполнялись.
