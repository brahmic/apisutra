## Основание и цель

Основание — [требования AS-1–AS-4](../../issue/iss-002-apisutra-reuse/upstream-requirements.md) и
[аудит aud-006](../../audit/aud-006-declarative-dto/aud-006-readme.md), подготовленный
по поручению пользователя от 2026-09-14. Аудит подтвердил пробелы F1–F6 и расхождение
документации/проверки registry-casts F7. Пользователь поручил подготовить план при
обнаружении недостатков. Реализация этим документом не считается начатой.

После изучения [оригинала A01–A08](../../issue/iss-002-apisutra-reuse/iss-002-readme.md)
и его артефактов [повторная проверка](../../audit/aud-006-declarative-dto/recheck.md)
сузила F6. Проверка shape уже сочетается с Nested через DefaultValue provider;
itemCast поддерживает локальную raw-фабрику и строки двумерного списка.
Эти возможности переиспользуются. A06–A08 не требуют нового API ядра,
а P20 относится к адаптеру внешнего SDK и в объём исправлений ApiSutra не входит.

[Рецензия аудита](../../audit/aud-006-declarative-dto/peer-review.md) выявила F8:
одиночный Nested на массиве из JSON не работает. F8, дефект пути provider F5,
документация/проверки registry F7 и закрепление Present-provider F6 вынесены в
[самостоятельный pln-029](../../completed/pln-029-hydration-defects/pln-029-readme.md).
План 029 завершён: [приёмка и регрессии](../../completed/pln-029-hydration-defects/acceptance.md)
задают основу для интеграции вложенных объектов в этом плане. Новые правила должны
сохранять этот контракт; источники client/global/extension casts не активированы. F9 добавляет типы scalar-элементов
списка: первоначальные проверки AS-1 покрывали только scalar-поля и DTO-элементы.

Цель: SDK один раз связывает правила с графом обычных `final readonly` DTO и получает
одинаковое преобразование через Returns и standalone-вход. Правила должны выражать
mapping, вложенные объекты/списки/известные discriminator-варианты, дополнительные
поля, строгую scalar-политику, присутствие и форму контейнера. Ошибки сохраняют
путь исходных данных и текущую диагностику результата.

Переиспользовать существующие Hydrator, From/Map, работающие списковые ветки Nested,
исправленный в pln-029 одиночный Nested, профильные и явные casts,
constructor-first, HydrationException и pipeline. Подтверждённые простые решения
через профиль и касты сохранить и документировать.

## Приоритеты и объём

| Направление | Основание | Результат |
| --- | --- | --- |
| Внешние изолированные правила и единое исполнение | F3 / AS-3 | Подключение правил без изменения DTO, без global registry и собственного рекурсивного mapper. |
| Происхождение разрешённого значения | F2, F4 / AS-2, AS-3.6 | Выбранный source-путь и потреблённые данные используются для extras и диагностики. |
| Присутствие и shape | F5, F6 / AS-4 | Внешние декларации проверок с точным путём до потери состояния/ключей; управляемый autodefault коллекций. Существующий provider перед Nested сохраняется. |
| Строгие scalar-типы | F1, F9 / AS-1 | Политика графа, явный тип scalar-элемента списка и native-проверка результата cast. PHPDoc не считается неявным runtime-правилом. |
| Приёмник дополнительных данных | F2 / AS-2 | Сбор остатка после штатного разрешения mappings, включая dot-path и fallback. |
| Документация новых правил | Частичные решения AS-1/4 и результаты pln-029 | Примеры внешнего набора и точные границы; исправление F7 принадлежит pln-029. |

P1 в аудите означает блокировку совокупного сценария чистых DTO; P2 — ограничения
частичных способов и диагностики. Текущие scalar conversions, игнорирование
непроецируемых ключей и typed-collection autodefault сами по себе не являются дефектами.

В объём входят профильные изменения `src/Serialization`, DTO-атрибутов/конфигурации/
контрактов, интеграция с клиентом и ResponseHydrator, диагностикой, тестами и документацией.
Также учесть CompositeFlow, ContinuationService и ResultHandle: подключение набора
входит в сквозное исполнение. Исправление готовности и доставки ошибок await —
объём 030; его публичный контракт здесь переиспользуется.
Точные новые имена выбрать при проектировании; названия классов не являются целью.
Новые runtime-зависимости, Laravel как обязательная среда, отдельный общий pipeline,
генератор DTO, бизнес-схемы провайдеров и отложенные планы 001/022–024 не входят в работу.

## Инварианты совместимости

- Без новых правил сохраняется поведение базовой версии после принятых 029, 031 и 030;
  дефекты F8/F5 не превращаются в инварианты совместимости. Строгие scalar
  и list-shape включаются явно; defaults не меняются глобально.
  Исключение для исправления await в 028 не вводится: переход старого поведения
  целиком принадлежит 030 и принимается до подключения правил к await.
- Plain DTO не обязаны наследовать классы/интерфейсы ApiSutra, иметь её атрибуты
  или зависеть от Laravel. Конструктор вызывается один раз, после проверки аргументов.
- Один набор правил используется pipeline и standalone-входом. Вызвавший код не
  создаёт PipelineContext; источник правил задаётся при сборке SDK.
  Повторная гидратация внутри legacy-cast через default не наследует внешний набор;
  для переноса новых правил нужен выбранный контракт области выполнения из В04.
- Разные клиенты/преобразователи могут использовать разные правила для одного
  DTO-класса. Уже созданный объект преобразователя и глобальный `DTO::from()`
  не меняются из-за создания другого набора правил.
- Существующие профильные/атрибутные правила продолжают работать. Не возвращать
  неявное влияние ClientConfig.casts или глобального CastRegistry на все DTO.
- Ошибки данных дают HydrationException с reason и путями; ошибки объявления правил
  дают ConfigurationException. В запросе сохраняются HTTP-ответ, result-first,
  throwOnErrors и отсутствие повторного HTTP из-за ошибки гидратации.
- Не выводить значения полей, credentials и raw payload в диагностические сообщения.
  Неизвестный discriminator может остаться raw, повреждённый известный вариант — ошибка.
- Сбор extras относится к чтению: receiver не сериализуется в запросах клиента с набором
  ни под своим именем, ни развёрнутым в корень; в DX остаётся обычным свойством.

Предложения по всем открытым вопросам перенесены в

| Подключение, конфликты деклараций и наследование | В01–В03 |
| Жизненный цикл обработчиков, strict и элементы списков | В04–В06 |

ожидания — в `acceptance.md`; в дискуссии сохраняются альтернативы и основания
выбора. Объём и критерии этого плана остаются действующими.

### 4. Политики типов, присутствия и формы

- [ ] Добавить opt-in scalar strictness с наследованием по набору правил и явными
  исключениями поля. Явный cast может преобразовать значение, но его результат
  проверяется без произвольного последующего scalar conversion в strict mode.
  Единственное допустимое числовое расширение выбирается в В05; проверить его
  для обычного float, union, scalar-элемента и результата cast.
- [ ] Применить strictness к объявленным scalar-элементам списков. Сохранить
  рабочие itemCast и параметризованный property Cast; учесть, что текущий itemCast

- [ ] Разделить optional missing/default и запрет исходного explicit null.

- [ ] Добавить opt-in list-shape до переиндексации. Составить проверку с одиночным

## Приёмка и проверки

Приёмку разделить на порции внутри одного плана. Это не автоматическое разрешение
выпускать промежуточный публичный API до проверки всех обязательств AS-1–AS-4.

| Порция | Условие начала основного кода порции | Что проверить |
| --- | --- | --- |
| A: правила, strict и форма | Приняты В01–В09 и В16–В17, записаны соответствующие contracts/acceptance и ADR; интеграция общего metadata cache ждёт 031, await-интеграция — завершения 030 | Подключение набора, конфликты/defaults, scope, все входы, изоляция и legacy; заложить внутренний учёт происхождения |
| B: дополнительные поля | Приняты В10–В11 и доступны необходимые части A; исходящий контракт В12 принят (раздел 10 contracts.md) | Receiver, readonly, aliases, каждый уровень и рекурсивные проекции each/discriminator, выбранный outgoing-контракт |
| C: sourcePath и безопасный лог | Приняты В13–В15 и доступны необходимые части A/B | Точный/ожидаемый/граничный путь, преобразования, полная доставка ошибки и отдельный безопасный контекст логирования |

Готовность фиксируется по порциям в contracts.md и acceptance.md; решения по
публичным границам имеют ADR-002. На 2026-09-14 порции A, B и C готовы к реализации.

Раздел 3 выше включает внутренние предпосылки A/B и публичную диагностику C.
Полный sourcePath нельзя направлять в автоматический лог на промежуточном этапе.

На каждый пункт [матрицы аудита](../../audit/aud-006-declarative-dto/criteria.md)
должна быть новая проверка требования либо ссылка на уже достаточный тест.
Сохранённые probes aud-006 описывают старое состояние; не превращать их успешный
выход в доказательство новой приёмки и не переписывать исходные результаты.

Обязательная комбинированная приёмка: два независимых набора правил для одного
графа чистых readonly DTO, mapping с fallback, одиночный объект, список и discriminator,
строгие scalar-поля и scalar-списки, optional-but-not-null, required collection
и receiver на двух уровнях. Для одиночного Nested используются регрессии pln-029.
Одинаковый набор входов проходит standalone и Returns. Сравниваются не только DTO,
но также reason, DTO/source paths, число вызовов конструктора и отсутствие HTTP retry.

Порядок проверок: затронутые Serialization/DataTransfer/Result/Core/Pipeline тесты,
затем `composer test`, `composer lint`, `composer analyse`, `composer check-docs`.
После изменения автозагрузки — `composer dump-autoload --optimize --strict-psr`.
Проверить standalone-установку без dev-зависимостей через существующую проверку
дистрибутива; зафиксировать ref, поскольку обычный `composer check-package`
использует Git HEAD, а для некоммиченных изменений предусмотрен `--staged`.
Тестовые данные искусственные, HTTP заменён fake. Наличие Illuminate в dev-зависимостях
не должно маскировать обязательную зависимость нового standalone API.

Результаты сохранить в `acceptance.md` и `artifacts/` этого плана: версия/commit,
команды, результаты, матрица совместимости и примеры. Исполнение и размер графа
проверить на конечном вложенном fixture; не вводить отдельные произвольные performance
пороги, если изменение не даёт признаков повторных обходов или утечки кеша.

## Критерии завершения

- [ ] AS-1–AS-4 и общая приёмка исходных требований выполнены единым поддерживаемым способом.
- [ ] Обычные readonly DTO остаются независимыми от ApiSutra и Laravel.
- [ ] Источник правил изолирован, совпадает в Returns/standalone и не меняет defaults
  других пользователей; старые attribute/profile-сценарии прошли проверки.
- [ ] Правила применяются в composite/continuation/cached awaitAs и повторной
  гидратации обработчиков через выбранный scope; legacy-границы явно описаны.
- [ ] Ошибка готового continuation-результата не превращается в pending или
  configuration-ошибку без previous: контракт завершённого 030 сохранён при интеграции.
- [ ] Дополнительные поля сохраняются по правилам потребления source-путей и коллизий.
- [ ] Strict mode проверяет входные scalar-поля, объявленные scalar-элементы списков
  и итог явного cast; legacy conversions
  и autodefault коллекций доступны с прежним поведением.
- [ ] Missing/null/list/object различаются в пределах доступного входного представления;
  ошибки сохраняют reason и пути без утечек payload.
- [ ] Подтверждены constructor once, отсутствие скрытого I/O и одинаковая доставка
  ошибки через result-first/throwOnErrors с сохранённым HTTP-ответом.
- [ ] Результаты pln-029 учтены, сквозной пример воспроизводится, необходимые проверки пройдены
  на принимаемом состоянии, evidence сохранено.
- [ ] После выполнения критериев статус и каталог синхронно изменены на `завершён`
  и `completed/`.

## Вывод о принятом объёме

Полный сценарий коллеги требует расширения декларативного контракта гидратации.
План добавляет недостающие правила и происхождение данных вокруг существующего
исполнителя. Частичные решения через profiles/casts/DefaultValue сохраняются,
