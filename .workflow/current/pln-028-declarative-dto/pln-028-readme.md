# Декларативные правила для графа DTO и диагностика преобразования

- Дата создания: 2026-09-14
- Дата обновления: 2026-09-14
- Статус: новый

## Основание и цель

Основание — [требования AS-1–AS-4](../../issue/iss-002-apisutra-reuse/upstream-requirements.md) и
[аудит aud-006](../../audit/aud-006-declarative-dto/aud-006-readme.md), подготовленный
по поручению пользователя от 2026-09-14. Аудит подтвердил пробелы F1–F6 и расхождение
документации/проверки registry-casts F7. Пользователь поручил подготовить план при
обнаружении недостатков. Реализация этим документом не считается начатой.

После изучения [оригинала A01–A08](../../issue/iss-002-apisutra-reuse/iss-002-readme.md)
и его артефактов [повторная проверка](../../audit/aud-006-declarative-dto/recheck.md)
сузила F6. Проверка shape уже сочетается с Nested через DefaultValue provider;
itemCast поддерживает локальную raw-фабрику и строки двумерного списка.
Эти возможности переиспользуются. A06–A08 не требуют нового API ядра,
а P20 относится к адаптеру внешнего SDK и в объём исправлений ApiSutra не входит.

[Рецензия аудита](../../audit/aud-006-declarative-dto/peer-review.md) выявила F8:
одиночный Nested на массиве из JSON не работает. F8, дефект пути provider F5,
документация/проверки registry F7 и закрепление Present-provider F6 вынесены в
[самостоятельный pln-029](../pln-029-hydration-defects/pln-029-readme.md).
Он не зависит от новых внешних правил; его исправленный контракт нужен перед
интеграцией вложенных объектов в этом плане. F9 добавляет типы scalar-элементов
списка: первоначальные проверки AS-1 покрывали только scalar-поля и DTO-элементы.

Цель: SDK один раз связывает правила с графом обычных `final readonly` DTO и получает
одинаковое преобразование через Returns и standalone-вход. Правила должны выражать
mapping, вложенные объекты/списки/известные discriminator-варианты, дополнительные
поля, строгую scalar-политику, присутствие и форму контейнера. Ошибки сохраняют
путь исходных данных и текущую диагностику результата.

Переиспользовать существующие Hydrator, From/Map, работающие списковые ветки Nested,
исправленный в pln-029 одиночный Nested, профильные и явные casts,
constructor-first, HydrationException и pipeline. Подтверждённые простые решения
через профиль и касты сохранить и документировать.

## Приоритеты и объём

| Направление | Основание | Результат |
| --- | --- | --- |
| Внешние изолированные правила и единое исполнение | F3 / AS-3 | Подключение правил без изменения DTO, без global registry и собственного рекурсивного mapper. |
| Происхождение разрешённого значения | F2, F4 / AS-2, AS-3.6 | Выбранный source-путь и потреблённые данные используются для extras и диагностики. |
| Присутствие и shape | F5, F6 / AS-4 | Внешние декларации проверок с точным путём до потери состояния/ключей; управляемый autodefault коллекций. Существующий provider перед Nested сохраняется. |
| Строгие scalar-типы | F1, F9 / AS-1 | Политика графа, явный тип scalar-элемента списка и native-проверка результата cast. PHPDoc не считается неявным runtime-правилом. |
| Приёмник дополнительных данных | F2 / AS-2 | Сбор остатка после штатного разрешения mappings, включая dot-path и fallback. |
| Документация новых правил | Частичные решения AS-1/4 и результаты pln-029 | Примеры внешнего набора и точные границы; исправление F7 принадлежит pln-029. |

P1 в аудите означает блокировку совокупного сценария чистых DTO; P2 — ограничения
частичных способов и диагностики. Текущие scalar conversions, игнорирование
непроецируемых ключей и typed-collection autodefault сами по себе не являются дефектами.

В объём входят профильные изменения `src/Serialization`, DTO-атрибутов/конфигурации/
контрактов, интеграция с клиентом и ResponseHydrator, диагностикой, тестами и документацией.
Точные новые имена выбрать при проектировании; названия классов не являются целью.
Новые runtime-зависимости, Laravel как обязательная среда, отдельный общий pipeline,
генератор DTO, бизнес-схемы провайдеров и отложенные планы 001/022–024 не входят в работу.

## Инварианты совместимости

- Без новых правил сохраняется поддержанное поведение после исправлений pln-029;
  дефекты F8/F5 не превращаются в инварианты совместимости. Строгие scalar
  и list-shape включаются явно; defaults не меняются глобально.
- Plain DTO не обязаны наследовать классы/интерфейсы ApiSutra, иметь её атрибуты
  или зависеть от Laravel. Конструктор вызывается один раз, после проверки аргументов.
- Один набор правил используется pipeline и standalone-входом. Вызвавший код не
  создаёт PipelineContext; источник правил задаётся при сборке SDK.
- Разные клиенты/преобразователи могут использовать разные правила для одного
  DTO-класса. Уже созданный объект преобразователя и глобальный `DTO::from()`
  не меняются из-за создания другого набора правил.
- Существующие профильные/атрибутные правила продолжают работать. Не возвращать
  неявное влияние ClientConfig.casts или глобального CastRegistry на все DTO.
- Ошибки данных дают HydrationException с reason и путями; ошибки объявления правил
  дают ConfigurationException. В запросе сохраняются HTTP-ответ, result-first,
  throwOnErrors и отсутствие повторного HTTP из-за ошибки гидратации.
- Не выводить значения полей, credentials и raw payload в диагностические сообщения.
  Неизвестный discriminator может остаться raw, повреждённый известный вариант — ошибка.
- Сбор extras относится к чтению; содержимое приёмника автоматически не добавляется
  в корень исходящего HTTP payload. DX/wire сериализация сохраняет собственные правила.

## Проект решения

### Внешний набор правил

Добавить компактный публичный контракт описания правил по целевому class-string
и изолированный объект набора правил. Внешняя декларация должна уметь выразить
переименование/путь с fallback, одиночный вложенный DTO, список, discriminator,
приёмник extras и политики присутствия/shape/scalar. Правила из атрибутов и внешнего
описания приводятся к общей внутренней модели, которую исполняет существующий Hydrator.

Предлагаемый приоритет: явное внешнее правило поля → атрибут поля → применимые
правила класса/профиля → defaults набора → defaults ядра. Это проект, подлежащий
проверке на этапе 1: уточнить приоритет внешних правил класса, class-level overrides
и профильных casts. Несовместимые декларации должны отклоняться с понятной причиной,
а не зависеть от порядка сканирования. Отсутствующее значение настройки отличается
от явно заданного null/false.

Отделить кеш reflection, общий для классов, от разрешённых правил конкретного набора.
Результаты внешнего разрешения нельзя кешировать только по имени DTO-класса.
Набор правил после сборки имеет стабильную конфигурацию; новое правило создаёт
новый набор или явно ограничивается стадией построения.

### Происхождение данных и порядок обработки

Текущее разрешение значения расширить данными о выбранном пути и исходном состоянии.
Приоритеты выполнения для нового opt-in пути зафиксировать до реализации:

1. Выбрать primary/fallback, сохранить source path и missing/null/present.
2. Проверить явно заданные правила присутствия, null и исходной формы контейнера.
3. Применить разрешённые нормализацию пустой строки и defaults.
4. Применить явные casts и правила вложенности в документированном порядке.
5. Проверить итоговый native-тип согласно выбранной scalar-политике.
6. Собрать остаток источника, подготовить constructor arguments и создать DTO.

Обработка старых деклараций должна сохранять прежний порядок. Внешняя форма
«одиночный объект» задаётся явно и не выводится из того, что PHP array похож на объект.
Нельзя восстанавливать различие JSON `{}`/`[]`, уже потерянное вызывающим decoder.
Каждый объявленный вложенный контейнер проверяется на своём уровне.

### Приёмник дополнительных полей

Один назначенный receiver на конкретный DTO; имя свойства произвольное. До запуска
проверить тип, доступность и возможность инициализации с учётом readonly/конструктора.
У каждого вложенного DTO свой набор потреблённых путей и свой receiver.

Предлагаемый контракт остатка:

- исключать только фактически использованный source-путь; неиспользованные aliases
  сохранять, primary выигрывает при наличии, включая explicit null;
- при потреблении листа `profile.id` сохранять соседние данные `profile.future`;
- при передаче целого subtree вложенному DTO он считается потреблённым у родителя,
  а остатки внутри subtree принадлежат приёмнику вложенного DTO;
- сохранять false, ноль, null, пустые строки/списки и остальные значения без фильтрации;
- исходный ключ с именем receiver не подменяет собираемый остаток: хранить его
  обычным ключом внутри receiver. Не выполнять скрытое flatten/merge при сериализации;
- несколько полей, использующих один source-путь, могут читать его, но в остатке
  он учитывается как потреблённый один раз. Правила пересечения parent/leaf путей
  определить и проверить до реализации.

### Ошибки и source path

Сохранить существующий `HydrationException::path` и добавить отдельное происхождение
значения; рабочее имя — `sourcePath`. Для штатных mappings учитывать выбранный alias,
вложенность, индексы, Nested.each/discriminator и Returns::unwrap. При missing
зафиксировать ожидаемый primary path и доступные aliases без исходных значений.

Оборачивать ошибки state/default providers и casts на уровне поля: generic provider
не должен сам знать имя свойства. Корректный DTO path provider берётся из pln-029;
здесь добавляется source path новых правил. Уже заполненные вложенные пути дополняются без
дублирования префиксов. Для произвольного computed/hook, меняющего структуру данных,
явно определить границу происхождения; недоступный исходный путь не выдумывать.
Автоматические логи должны использовать безопасные объявленные пути и индексы,
не раскрывая произвольные ключи дополнительных данных и значения discriminator.

## Этапы реализации

### 1. Зафиксировать контракты и приёмку

- [ ] Перепроверить исходную версию и результаты aud-006; сохранить baseline нового цикла.
- [ ] Создать `contracts.md` и `acceptance.md` внутри этого плана: каждый критерий
  AS-1–AS-4 связан с ожидаемым поведением, совместимостью и проверкой.
- [ ] Уточнить приоритеты внешних правил/атрибутов/profiles, shape object/list,
  missing vs normalized null, пересечения consumed paths и правила receiver.
- [ ] Для strict mode закрепить точное совпадение scalar-типов; union выбирает
  подходящую ветвь без преобразования, mixed не сужается автоматически. Отдельно
  проверить float, literal bool и результат явного cast, сохраняя legacy-режим.
- [ ] Явно объявить тип scalar-элемента списка, включая вложенные списки: int/bool/string,
  native/строковые/неверные/null-элементы, пустой список, override cast и точный индекс
  ошибки. Разделить тип контейнера и элемента; PHPDoc parser не вводить автоматически.
- [ ] Выбрать минимальный публичный способ подключения набора к клиенту и standalone;
  показать один пример, в котором конечный пользователь SDK не настраивает гидратор.

### 2. Общая модель и изолированное разрешение правил

- [ ] Ввести только необходимые контракты и данные правил. Адаптировать существующие
  атрибуты и профили к общей модели без второго механизма исполнения.
- [ ] Валидировать class-string, mappings, типы receiver, вложенные формы, discriminator
  maps и конфликты деклараций до выполнения преобразования.
- [ ] Разделить reflection metadata и кеш resolved rules; проверить два набора для
  одного класса, смену порядка вызовов, вложенный граф и повторное использование клиента.
- [ ] Сохранить прежние атрибутные сценарии и работу без внешнего набора.

### 3. Source-aware разрешение и диагностика

- [ ] Сохранять выбранный primary/fallback и состояние до нормализации; вести локальные
  consumed paths для каждого DTO, не складывая payload в глобальный контекст.
- [ ] Добавить source path рядом с текущим DTO path, включая unwrap и вложенные индексы.
- [ ] Переиспользовать исправленный в pln-029 DTO path provider; добавить source path
  для ошибок providers, casts и новых правил, не дублируя контексты.
- [ ] Проверить доступность HTTP-ответа, reason, previous, безопасные логи и отсутствие retry.

### 4. Политики типов, присутствия и формы

- [ ] Добавить opt-in scalar strictness с наследованием по набору правил и явными
  исключениями поля. Явный cast может преобразовать значение, но его результат
  проверяется без последующего неявного scalar conversion в strict mode.
- [ ] Применить strictness к объявленным scalar-элементам списков. Сохранить
  рабочие itemCast и параметризованный property Cast; учесть, что текущий itemCast
  создаётся без аргументов и сам по себе не представляет внешние правила элемента.
- [ ] Разделить optional missing/default и запрет исходного explicit null.
  Проверять состояние до преобразований, способных потерять различие.
- [ ] Добавить opt-in list-shape до переиндексации. Составить проверку с одиночным
  объектом, Nested, itemCast, each и discriminator, не заставляя писать общий mapper.
- [ ] Дать явно требовать присутствие typed collection; существующий autodefault
  без нового правила сохранить. Проверить вложенные списки на каждом объявленном уровне.

### 5. Сбор дополнительных полей

- [ ] Реализовать receiver на основе consumed paths из этапа 3, без повторного
  reflection-обхода с дублированием mapping-логики.
- [ ] Проверить shallow/deep mappings, primary/fallback/null, aliases, falsy-значения,
  несколько уровней DTO, discriminator и коллизии имени receiver.
- [ ] Включить receiver в единственную инициализацию DTO; не дописывать readonly
  свойства после их создания и не вводить сетевые/прочие скрытые I/O.
- [ ] Проверить отсутствие неявного переноса extras в исходящий payload;
  обычное явно настроенное представление свойства receiver описать отдельно.

### 6. Интеграция с SDK и standalone

- [ ] Подключить общий преобразователь/набор правил при сборке клиента и в существующий
  ResponseHydrator; standalone API принимает данные и тип без PipelineContext.
- [ ] Подтвердить эквивалентность результатов и ошибок для одного набора правил:
  direct hydrate, Returns, sync/promise, unwrap и повторные вызовы.
- [ ] Проверить независимость клиентов, standalone-наборов и глобального default,
  отсутствие дублирования конструкторов и скрытых побочных действий.
- [ ] Сохранить известные invalid discriminator как ошибки, неизвестные — по выбранной
  политике; не заменять существующую логику raw/ошибок собственным общим pipeline.

### 7. Документация новых правил

- [ ] Описать готовые способы AS-1/AS-4 из аудита и их ограничения, включая provider
  перед Nested, raw-фабрику в itemCast и двумерный список без DTO ряда; затем новый
  декларативный путь для plain-графа с одним сквозным примером.
- [ ] Сослаться на уточнённые в pln-029 источники casts и статус Present-provider.
  Не копировать задачи F7 и не выдавать комбинацию Present за ранее документированный рецепт.
- [ ] Обновить DTO/casts/attributes/config/errors и миграцию без копирования полных
  контрактов. Согласовать целевые пути с [pln-027](../pln-027-documentation-restructure/pln-027-readme.md)
  по фактическому состоянию; выполнение этого плана не зависит от переработки всей документации.

## Приёмка и проверки

На каждый пункт [матрицы аудита](../../audit/aud-006-declarative-dto/criteria.md)
должна быть новая проверка требования либо ссылка на уже достаточный тест.
Сохранённые probes aud-006 описывают старое состояние; не превращать их успешный
выход в доказательство новой приёмки и не переписывать исходные результаты.

Обязательная комбинированная приёмка: два независимых набора правил для одного
графа чистых readonly DTO, mapping с fallback, одиночный объект, список и discriminator,
строгие scalar-поля и scalar-списки, optional-but-not-null, required collection
и receiver на двух уровнях. Для одиночного Nested используются регрессии pln-029.
Одинаковый набор входов проходит standalone и Returns. Сравниваются не только DTO,
но также reason, DTO/source paths, число вызовов конструктора и отсутствие HTTP retry.

Порядок проверок: затронутые Serialization/DataTransfer/Result/Core/Pipeline тесты,
затем `composer test`, `composer lint`, `composer analyse`, `composer check-docs`.
После изменения автозагрузки — `composer dump-autoload --optimize --strict-psr`.
Проверить standalone-установку без dev-зависимостей через существующую проверку
дистрибутива; зафиксировать ref, поскольку обычный `composer check-package`
использует Git HEAD, а для некоммиченных изменений предусмотрен `--staged`.
Тестовые данные искусственные, HTTP заменён fake. Наличие Illuminate в dev-зависимостях
не должно маскировать обязательную зависимость нового standalone API.

Результаты сохранить в `acceptance.md` и `artifacts/` этого плана: версия/commit,
команды, результаты, матрица совместимости и примеры. Исполнение и размер графа
проверить на конечном вложенном fixture; не вводить отдельные произвольные performance
пороги, если изменение не даёт признаков повторных обходов или утечки кеша.

## Критерии завершения

- [ ] AS-1–AS-4 и общая приёмка исходных требований выполнены единым поддерживаемым способом.
- [ ] Обычные readonly DTO остаются независимыми от ApiSutra и Laravel.
- [ ] Источник правил изолирован, совпадает в Returns/standalone и не меняет defaults
  других пользователей; старые attribute/profile-сценарии прошли проверки.
- [ ] Дополнительные поля сохраняются по правилам потребления source-путей и коллизий.
- [ ] Strict mode проверяет входные scalar-поля, объявленные scalar-элементы списков
  и итог явного cast; legacy conversions
  и autodefault коллекций доступны с прежним поведением.
- [ ] Missing/null/list/object различаются в пределах доступного входного представления;
