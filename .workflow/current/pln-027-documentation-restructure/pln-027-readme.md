## Цель и текущая база

По запросу владельца от 2026-09-14 документация должна вести разработчика и ИИ-агента
от анализа внешнего API до проверенного SDK: конфигурация, клиент, операции, DTO,
ошибки и тесты. У каждого поддерживаемого контракта должно быть одно полное описание.
Уточнение от 2026-09-15: заранее выбрать папки, файлы, группировку и границы объёма.

База планирования — commit `cddd036a0955e3379a244355fe23d3e888b1ba4a`.
028, 029, 030 и 031 завершены; их API не проектируется повторно. Последующая
[проверка документации](../../completed/pln-028-declarative-dto/documentation-followup.md)
обновила 25 публичных документов, включая рекомендацию `_extra`, миграцию и глоссарий.
Успех её проверок не означает, что весь прежний комплект уже актуален.

Состав базы: 90 публичных Markdown-файлов, 14 329 строк; 14 файлов длиннее 300 строк,
6 — длиннее 400. Методология SDK занимает 700 строк, auth — 499, DTO — 452,
сериализация — 451, внешние правила — 351. Данные и SHA-256 — в
[baseline.json](artifacts/baseline.json); команды — в [приёмке](acceptance.md).

## Объём и границы

Входят README, `docs/`, исполняемые примеры, инструкции `AGENTS.md` / `.agents/`,
проверки документации и их подключение к существующим CI/проверкам поставки.
Разделы `start`, `guides`, `reference`, `technical`, `glossary`, `migration`, `example`
имеют разные задачи, описанные в [структуре](structure.md).

`src/`, публичный PHP API и продуктовые решения 028–031 сохраняются. Подтверждённые
дефекты ядра оформляются отдельно; случайный результат нельзя объявлять контрактом.
Отложенные async-first, client assembly и execution policies не возобновляются.
Сайт документации, переводы, реальные SDK провайдеров, плагин/skill и живые внешние
API не входят; учебный образец описан отдельно в маршрутах.

Старые аудиты, приёмка и манифесты остаются фактами своих commit. Их не переписывать
ради новой раскладки. `.workflow/history/` исключён из обычной инвентаризации.
Для примеров использовать нейтральный учебный API, fake и искусственные данные.

## Остаточные проблемы и приоритет

Ниже подтверждено чтением текущих файлов; это не новые прогоны runtime-сценариев.

| Приоритет | Что проверить и исправить |
| --- | --- |
| Сначала | [Quickstart](../../../docs/guides/quickstart.md) создаёт `$config`, но получает клиент через `app()` без его передачи или binding. Сделать полностью исполняемую явную сборку и отдельный Laravel-вариант. |
| Сначала | [Глоссарий](../../../docs/glossary/requests.md) обещает non-blocking/fire-and-forget; [executeAsync()](../../../src/Pipeline/Pipeline.php) вызывает `execute()` синхронно. Развести promise API, конкурентность транспорта и provider await без изменения кода. |
| Затем | [AttributeScanner](../../../docs/glossary/attributes.md) не соответствует классу в `src/`; проверить остальные имена и публичность символов. |
| Затем | [Обзор](../../../docs/technical/architecture.md) исключает валидацию без контейнера, хотя [Validator::useFactory()](../../../src/VO/Validation/Validator.php) позволяет передать фабрику. |
| Затем | Правила `.agents/providers.md` и навигация ещё тяготеют к атрибутным профилям. Согласовать их с выбором внешних правил, не делая профиль обязательным для plain DTO. |
| Далее | Полные правила и примеры повторяются в методологии, guides, client-config, attributes и glossary. Разделить декларации, поведение, рецепты и определения по карте. |
| Сопровождение | `composer check-docs` пока проверяет существование файлов; проверка якорей из последней приёмки не стала штатной. Сигнатуры, выполнение примеров и полнота покрытия — отдельные проверки. |

## Порядок реализации

### 1. Проверить покрытие и исправить первые примеры

- [ ] Сохранить commit начала реализации; сверить его с baseline планирования.
- [ ] В `inventory.md` перечислить поддерживаемые возможности по `src/` и тестам:
  символ, контракт, тест, все места описания, владелец, расхождение, статус. Файловая
  [карта](content-map.md) не заменяет эту проверку покрытия API.
- [ ] Проверить сначала проблемы из таблицы выше; устаревшее описание исправлять,
  предполагаемый дефект воспроизводить и отделять от документированной границы.
- [ ] Исправить quickstart в текущем адресе и выполнить опубликованный код;
  отдельным сценарием проверить Laravel binding. Не ждать завершения всех переносов.

### 2. Создать каркас и правила сопровождения

- [ ] Создать индексы и первые непустые целевые страницы из [дерева](structure.md).
  Не создавать пустые заготовки всех будущих файлов.
- [ ] До переноса заполнить для выбранной порции `moves.md`: старый раздел/якорь,
  новый раздел/якорь, входящие ссылки, совместимость, проверка, статус.
- [ ] Синхронно изменить `.agents/documentation.md`, `AGENTS.md`, `.agents/providers.md`
  и индексы: новые владельцы справочников — в `reference/`; прежние пути до переноса
  ещё действуют. Публичные инструкции не должны зависеть от `.agents/`.
- [ ] Подключить проверку новых и сохранённых адресов с якорями; далее каждый перенос
  заканчивается проходящей проверкой, а не временно сломанной навигацией.

### 3. Перенести полные контракты тематическими порциями

| Порция | Состав | Условие завершения |
| --- | --- | --- |
| A | Клиент, конфигурация, транспорт, запрос и результат | Воспроизводится первая операция; явная сборка и зависимости точны |
| B | DTO, формы, внешние правила, profiles, casts, DX и wire | Сохранены контракты 028/029/031, `_extra`, strict, scope, sourcePath и ограничения сериализации |
| C | Auth, retry, квоты, cache, deadline, пагинация, batch/pool, continuation, файлы | Сохранены контракты 030 и остальных реализованных механизмов; нет обещаний будущего async-first |
| D | Hooks/extensions, Laravel/Redis/validation, testing, catalogs/inventory/версии | Указаны зависимости и границы; рецепты не подменяют справочник |

- [ ] В каждой порции перенести поведение в тематический reference, параметры
  атрибутов — в attributes; ClientConfig оставить каталогом ссылок на владельцев.
- [ ] Убрать повторные полные спецификации из guides/glossary/technical; сохранить
  полезные примеры и объяснения причин, связав их с владельцем контракта.
- [ ] Переносить существующие исправления, а не пересказывать их по старым аудитам.
  Учесть лимиты размера и адреса совместимости из [структуры](structure.md).

### 4. Написать маршруты и связать учебный SDK

- [ ] Реализовать [маршруты](entry-points.md): создание SDK, инструкция агенту,
  добавление операции, DTO, использование SDK, диагностика и работа над ядром.
- [ ] Разделить старую методологию на анализ, проектирование, первую операцию,
  покрытие и выпуск. Общий порядок существует только в `start/create-sdk.md`.
- [ ] Добавить небольшой учебный SDK в `docs/example/sdk/`; guide ссылается на
  его исходники, проверка исполняет именно их. Классы и binding не подразумеваются.
- [ ] Сохранить атрибутный путь и показать plain DTO с внешним набором как отдельный
  выбор. `Hydrator::default()` не объявлять наследующим правила клиента.

### 5. Завершить навигацию, проверки и поставку

- [ ] Завершить карту всех разделов/якорей, страницы перехода и входящие ссылки.
  Не менять доказательные артефакты прежних планов; сохранить нужные им старые адреса.
- [ ] Подключить проверки деклараций, примеров и состава docs в существующие команды.
  Не вводить эвристику «любое слово в backticks — PHP API».
- [ ] Проверить маршруты из установленного пакета без `.workflow`, `.agents` и tests.
- [ ] Выполнить [приёмку](acceptance.md) на принимаемом commit/tree, сохранить отчёт;
  только затем перенести план в `completed/` со статусом `завершён`.

## Критерий результата

Разработчик или агент находит нужный контракт из маршрута, создаёт минимальный SDK
и проверяет его без чтения всего комплекта и исследования внутренних классов.
Все публичные темы учтены, каждый контракт имеет одного владельца, страницы
укладываются в заданные границы, примеры выполняются, старые ссылки продолжают вести
к актуальному описанию. Проверки ссылок сами по себе этого результата не доказывают.
