- Дата создания: 2026-09-14
- Дата обновления: 2026-09-14
- Статус: новый

## Основание и цель

Основание — запрос пользователя от 2026-09-14: проверить полноту и актуальность
документации, улучшить структуру, устранить дублирование правил и предусмотреть
точки входа, включая маршрут ИИ-агента, которому поручено создать SDK внешнего API.
После обсуждения пользователь поручил оформить план работ в `.workflow`.
Создание плана не означает начала его реализации.

Цель — дать разработчику и агенту последовательный путь от изучения API и выбора
возможностей ApiSutra до работающего клиента, деклараций запросов и DTO, обработки
ошибок и проверки SDK. Каждый публичный контракт должен иметь одно полное описание,
согласованное с реализацией и контрактными тестами.

Основной критерий: по публичной точке входа можно создать небольшой корректный SDK,
находя необходимые правила без самостоятельного исследования внутренних механизмов
ядра и без чтения всей документации подряд.

## Объём и границы

В работу входят:

- `README.md`, публичные материалы `docs/`, примеры и навигация;
- согласование `AGENTS.md` и `.agents/` с новой структурой и областями применения;
- проверки документации в `tests/Support/` и CI в объёме ссылок, публичных деклараций,
  воспроизводимости примеров и состава дистрибутива;
- карта покрытия документацией, карта переносов и результаты приёмки внутри этого плана.

Поведение `src/` и публичные PHP-контракты сохраняются. Обнаруженные ошибки ядра
фиксируются отдельно; документация не должна закреплять случайное поведение как
обещанный контракт. План не возобновляет отложенные async-first, client assembly,
execution admission и execution policies. Новые провайдеры, сайт документации,
переводы и отдельный плагин/skill для агента в этот объём не входят.

Использовать нейтральный учебный API с искусственными данными. Для примеров и обычных
проверок не требуются credentials, реальные внешние запросы и платные операции.
Исторический архив `.workflow/history/` исключён из инвентаризации и массовых переносов.

воспроизводимые основания в материалах плана.

| Наблюдение | Основание и направление исправления |
| --- | --- |

| В глоссарии остались отсутствующие компоненты | [AttributeScanner](../../../docs/glossary/attributes.md) описан как внутренний компонент, но одноимённого класса в текущем [модуле атрибутов](../../../src/Attributes) нет. Проверить остальные публичные и внутренние имена. |
| Зависимость валидации от контейнера описана неточно | [Обзор архитектуры](../../../docs/technical/architecture.md) исключает DTO-валидацию без контейнера, хотя [Validator](../../../src/VO/Validation/Validator.php) предоставляет `useFactory()`, а [руководство](../../../docs/guides/validation.md) описывает этот путь. |
| Правила сериализации и разработки провайдера повторяются | [Методология](../../../docs/guides/provider-methodology.md), [DTO](../../../docs/guides/dto.md), [сериализация](../../../docs/guides/serialization.md), [настройки](../../../docs/guides/client-config/serialization.md) и [чеклист](../../../docs/guides/provider-checklist.md) содержат пересекающиеся правила и рекомендации. Назначить владельца каждого контракта. |
| Успешная проверка ссылок не подтверждает точность документации | [check-docs.py](../../../tests/Support/check-docs.py) проверяет существование файлов, отбрасывает якоря и не проверяет PHP API или выполнение примеров. Расширить проверки по отдельным проверяемым требованиям. |

## Подход к единому источнику истины

Для каждой темы назначить основной документ или раздел. В нём хранить полный
контракт: входы, результаты, defaults, приоритеты, зависимости, ограничения,
ошибки и значимые исключения. В маршрутах, обзорах и примерах оставлять достаточное
краткое пояснение и ссылку на этот раздел. Повторять полные таблицы и правила нельзя.

Код показывает фактическое поведение, контрактные тесты подтверждают сценарии,
публичная документация описывает поддерживаемое использование. Расхождение между
ними требует проверки причины; механическое переписывание текста под любой результат
исполнения не считается исправлением. Генерация деклараций из PHP допустима,
но не заменяет объяснения поведения и взаимодействия механизмов.

Во всех маршрутах различать обязательный контракт, рекомендуемый исходный подход
и решение по условиям API. Приоритеты настроек описывать отдельно для каждого
механизма; не распространять одну общую формулу на auth, DTO, retry и совместные квоты.

## Целевая организация

Рабочая схема для этапа 2; точные имена тематических файлов определить по карте
содержимого. Перенос выполнять после назначения владельцев контрактов.

| Раздел | Назначение и границы |
| --- | --- |
| `docs/README.md` | Главная навигация: задачи читателя, возможности и ограничения пакета, ссылки на маршруты и справочник. |
| `docs/start/` | Точки входа по задачам, порядок чтения, условия выбора дополнительных тем и ожидаемый результат. |
| `docs/guides/` | Практические действия и сквозные сценарии с воспроизводимыми примерами. |
| `docs/reference/` | Полные контракты возможностей, публичных интерфейсов, атрибутов и конфигурации; сюда выделяется справочная часть текущих guides. |
| `docs/technical/` | Устройство ядра, жизненный цикл и причины архитектурных решений; ссылки на публичные контракты. |
| `docs/glossary/` | Короткие определения и ссылки; без самостоятельных перечней параметров и копий спецификаций. |
| `docs/example/` | Доступные потребителю примеры и инструкции запуска; исполняемые образцы связываются с guides. |
| Руководство миграции | Изменения между версиями и действия потребителя; текущие правила живут в профильном справочнике. |

Текущие [правила документации](../../../.agents/documentation.md) закрепляют прежние
пути справочников. На этапе 2 синхронно обновить их вместе со структурой, индексами
и ссылками. `.agents/` остаётся инструкциями сопровождения репозитория, а публичные
правила создания SDK размещаются в `docs/` и доступны из установленных пакетов.
По [composer.json](../../../composer.json) `.agents/`, `AGENTS.md` и `.workflow/`
не входят в дистрибутив.

## Этапы работ

### 1. Инвентаризация и проверка покрытия

- [ ] Зафиксировать commit, версию PHP и используемые команды проверки.
- [ ] Перечислить публичные возможности по `src/`, документации и контрактным тестам;
  отделить внутренние детали, устаревшие упоминания и отложенные предложения.
- [ ] Создать `inventory.md` в каталоге плана: возможность/контракт, декларация,
  подтверждающие тесты, все места описания, владелец, пробел или расхождение,
  приоритет и состояние исправления. Отсутствующий тест отмечать явно.
- [ ] Проверить группы: создание клиентов, конфигурация и DI; ресурсы/discovery/версии;
  запросы и атрибуты; DTO/casts/collections; результаты и ошибки; auth/cache/retry/
  rate-limit/deadlines; hooks/extensions; pagination/batch/pool/continuation;
  транспорт/URL/files/archive; каталоги/inventory; testing и Laravel.
- [ ] Для ошибок поведения указать воспроизведение либо точное основание по коду.
  Приоритет сначала у неработающих первых примеров и ложных гарантий, затем у
  пробелов, противоречий и дублей, после — у редакционных улучшений.

Результат: учтены все публичные возможности и все документы в области плана;
каждое расхождение имеет способ проверки и целевое место исправления.

### 2. Владельцы контрактов и карта содержания

- [ ] Создать `content-map.md`: текущий раздел → сохранить/перенести/объединить/
  сократить → целевой путь и якорь → основной контракт → входящие ссылки.
- [ ] Назначить одно полное описание каждой темы; убрать конкуренцию между guides,
  client-config, attributes, technical и glossary.
- [ ] Определить шаблон справочника: назначение, декларация, defaults, приоритеты,
  зависимости, результаты/ошибки, ограничения и минимальный пример.
- [ ] Определить шаблон маршрута: задача, исходные сведения, шаги, условные ветви,
  ссылки на точные разделы и проверяемый результат.
- [ ] Зафиксировать окончательную раскладку и обновить связанные правила `.agents/`.

Результат: переносы имеют обоснование по содержанию; ни один актуальный контракт
не теряется при объединении файлов.

### 3. Актуальные справочники

- [ ] Исправить подтверждённые расхождения, удалить устаревшие имена и восполнить
  пробелы по `inventory.md`; спорные дефекты ядра оформить отдельно.
- [ ] Разделить гидрацию DTO, DX `toArray()`, сериализацию DTO в HTTP-тело и
  сериализацию query/path/header/остальных частей запроса.
- [ ] Для DTO описать mapping, профили и наследование, missing/null/default,
  пустые строки, безопасные casts, enum, даты, большие целые, вложенные варианты,
  коллекции, computed и диагностику. Декларативные описания полей опирать на контракт API.
- [ ] Для конфигурации показать реальные defaults, точечные overrides и правила
  взаимодействия. Отдельно проверить безопасность retry, replay тела, auth recovery,
  общий дедлайн, совместные квоты и изоляцию credentials/cache.
- [ ] Развести штатное синхронное исполнение, promise API и ожидание готовности
  данных у провайдера. Отдельно описать зависимости Laravel, validation и транспорта.
- [ ] Сократить остальные описания до контекста и ссылок; терминологию и названия
  разделов согласовать между документами.

Результат: полные правила имеют одного владельца и подтверждены текущим API.

### 4. Точки входа и маршрут ИИ-агента

- [ ] Создать индекс маршрутов: создать SDK; добавить операцию; описать DTO;
  подключить SDK к приложению; диагностировать ошибку; изменить ядро.
- [ ] Для создания SDK предоставить публичную инструкцию агенту, доступную из
  главного индекса. Обязательные правила должны находиться в поставляемом `docs/`.
- [ ] В начале маршрута дать компактную карту возможностей и ограничений ApiSutra.
  Разделить обязательное чтение и темы, выбираемые по признакам API.
- [ ] Задать последовательность: анализ источников внешнего API → карта решений
  и неизвестных условий → границы клиентов/ресурсов/типов → конфигурация и auth →
  одна операция с DTO и обработкой ошибок → тесты → расширение покрытия → документация SDK.
- [ ] Для каждого этапа указать вход, действия, выходной артефакт и критерий готовности.
  Неизвестные свойства API фиксировать явно; примеры, коды и ограничения не придумывать.
- [ ] Включить выбор простой или мультисервисной структуры, размещение общих типов,
  профили DTO, декларации полей, границы business data/result meta/catalogs и тестовый минимум.
- [ ] Вынести pagination, files, continuation, refresh, versioning, Redis и Laravel
  в условные ветви. Наличие возможности не означает необходимость её подключения.
- [ ] Переработать provider-analysis, provider-methodology и provider-checklist:
  анализ собирает факты, маршрут задаёт порядок, чеклист проверяет результат;
  подробные контракты остаются в справочниках.

Результат: агент может определить следующий шаг и его приоритет, а человек может
пройти тот же маршрут. Для добавления одной операции не требуется весь маршрут нового SDK.

### 5. Сквозные воспроизводимые примеры

- [ ] Исправить quickstart: показать создание транспорта, передачу `ClientConfig`,
  привязку клиента к запросу и чтение результата. Разделить явную сборку и Laravel binding.
- [ ] Подготовить небольшой учебный SDK: клиент, ресурс, запросы, входной/выходной DTO,
  enum или вложенная структура, успешный ответ и обработка ошибки.
- [ ] Примеры использовать как сопровождаемые образцы; основные исполняемые фрагменты
  проверять из их источника, чтобы тест не проверял независимую копию примера.
- [ ] Указать зависимости и точные команды запуска. Проверки используют fake или
  локальный стенд; standalone-сценарий не зависит от приложения Laravel.

Результат: потребитель получает рабочий путь от конфигурации до DTO и ошибки;
в примерах отсутствуют необъявленные binding, переменные и классы.

### 6. Навигация, переносы и совместимость ссылок

- [ ] Обновить README, все затронутые индексы, глоссарий, примеры, правила и входящие
  ссылки в актуальных рабочих материалах; архив не переписывать.
- [ ] Проверить файловые пути и якоря по `content-map.md`. Для изменённых публичных
  адресов определить совместимость: сохранить путь или оставить короткую страницу
  перехода со ссылкой и нужными якорями, без копии старой спецификации.
- [ ] Исключить страницы без входящих ссылок и цепочки общих индексов там, где маршрут
  должен вести прямо к нужному контракту. Проверить названия страниц по их содержанию.
- [ ] Проверить поставку новых точек входа и связанных примеров; публичные инструкции
  не должны ссылаться на исключённые из дистрибутива файлы.

Результат: новые и сохранённые точки входа ведут к актуальному содержимому,
документация пригодна для чтения из установленного пакета.

### 7. Автоматические проверки и сопровождение

- [ ] Расширить `composer check-docs`: относительные пути, локальные якоря и ссылки
  между разделами с учётом используемого Markdown, кириллицы и повторяющихся заголовков.
- [ ] Добавить проверяемое соответствие справочников публичным декларациям:
  имена классов/методов, параметры конфигурации и атрибутов, defaults.
  Выбрать ограниченный способ проверки по результатам инвентаризации; произвольные
  слова и псевдокод не трактовать автоматически как PHP API.
- [ ] Проверять поведение и приоритеты контрактными сценариями и редакционной сверкой;
  совпадения сигнатур недостаточно для подтверждения описания.
- [ ] Включить запуск основных примеров и проверку наличия маршрутов в дистрибутиве

- [ ] При изменении проверяющих скриптов покрыть существенные ошибки: неверный якорь,
  отсутствующий символ/параметр, неисполняемый пример и ссылка на непоставляемый файл.
- [ ] Закрепить в правилах сопровождения: изменение контракта обновляет основной
  справочник, соответствующий пример/тест и затронутые маршруты.

Результат: автоматические проверки обнаруживают основные причины повторного
рассогласования; область автоматизации и ручной проверки явно описана.

### 8. Приёмка по задачам читателя

- [ ] Отдельно пройти маршруты добавления операции и DTO, настройки Laravel и

- [ ] Сверить `inventory.md` и `content-map.md`: все возможности учтены, исправления

## Зависимости и проверка

Порядок: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8. При работе над отдельной темой её исправление,
перенос и обновление ссылок выполнять согласованно; не оставлять промежуточные копии
контракта как постоянное состояние. Требования к будущим проверкам определять уже
на этапах 1–2, чтобы структура справочника и образцов позволяла их проверять.

При реализации руководств провайдера применять [правила провайдеров](../../../.agents/providers.md),
при изменении проверок — [правила тестирования](../../../.agents/testing.md).
Новый цикл начинается со сверки актуальных зависимостей; прежние результаты тестов
и доступность локальных инструментов не переносятся на новую версию автоматически.

- Для текстов: `git diff --check`, `composer check-docs`, проверка затронутых API
  и маршрутов. PHP-тесты не запускать только ради изменения прозы.
- Для исполняемых примеров и тестовой инфраструктуры: профильные команды и сценарии;
  полный `composer test` — при влиянии на общий стенд. Для затронутого PHP-кода
  выполнить применимые `composer lint` и `composer analyse`.
- Для состава поставки: `composer check-package` либо
  `python3 tests/Support/check-package.py --staged --report <путь-к-отчёту>`.
  По текущей реализации обычная команда проверяет Git `HEAD`; приёмка должна
  подтверждать именно изменения плана, а не только прежний commit. Зафиксировать ref.
- Зафиксировать отдельный запуск Laravel-примера с его зависимостями;
  не считать standalone-пример подтверждением Laravel binding.

## Критерии завершения

- [ ] Публичные возможности и документы учтены в матрице покрытия; пробелы и
  подтверждённые ошибки в области плана закрыты, ограничения описаны явно.
- [ ] У каждого контракта одно полное описание; остальные документы ссылаются на него.
- [ ] Точки входа доступны из README/главного индекса и поставляются с пакетом.
- [ ] Маршрут агента охватывает конфигурацию, создание клиента, запросы, декларации DTO,
  обработку ошибок и проверки; обязательные и условные шаги различимы.
- [ ] Основные примеры воспроизводятся, зависимости standalone и Laravel указаны точно.
- [ ] Переносы сохраняют значимые адреса, актуальные ссылки и якоря работоспособны.
- [ ] Проверки и CI контролируют описанные классы ошибок документации и проходят
  на принимаемом состоянии файлов.
- [ ] Результаты приёмки сохранены; статус и каталог плана переведены в `завершён`
  и `completed/` только после выполнения критериев.

## Вывод о принятом объёме

План объединяет проверку точности, распределение владельцев контрактов, устранение
дублей, создание маршрутов и воспроизводимых примеров, проверку навигации и поставки.
Назначение каждого переноса определяется задачей читателя и содержимым документа.
Изменения поведения SDK и реализация отложенных механизмов остаются отдельными задачами.
