2. Проверить ссылки публичной документации на исключаемые пути: ссылка на репозиторий
   допустима для исходников теста, но runtime не должен читать исключённый файл.
   Публичные changelog/docs не должны зависеть от workflow.
3. Создать git и Composer архивы в отдельном временном каталоге; проверить списки,
   размеры и отсутствие внутренних материалов. Не считать наличие .gitignore
   достаточным исключением из архивов.
4. Распаковать архив в чистый каталог и выполнить composer install --no-dev,
   autoload и representative standalone smoke. Проверить именно дистрибутив,
   а не только source checkout, в котором есть скрытые dev-файлы.
5. Добавить повторяемый packaging-check в CI. Source checkout сохраняет тесты и
   рабочие материалы; исключения касаются дистрибутива, не удаления из репозитория.

Поле [archive.exclude](https://getcomposer.org/doc/04-schema.md#archive) проверено
по документации Composer. Локальный Composer archive и git/GitHub dist — разные пути;
проверять оба, не утверждать по одному архиву состав уже опубликованных версий.

## 3. Deprecation, стиль и статический анализ

- Удалить ненужные setAccessible из src/tests, сохранив смысл проверки доступа
  и использования Reflection. Не заглушать E_DEPRECATED глобально. Отдельно
  перепроверить reflection helpers, не попавшие в 34 отчёта текущего прогона.
- Зафиксировать PSR-12 checker и composer script; сначала отчёт, затем механические
  правки отдельным обозримым этапом. Не смешивать форматирование всего проекта
  с функциональными исправлениями. Исключить vendor/workflow/сгенерированные файлы.
- Добавить PHPStan для src с целью level 5 как начальной проверяемой границы;
  новые/изменённые API не должны добавлять ошибки. При наличии большого legacy-объёма
  сначала разобрать отчёт. Допустимый baseline должен быть конкретным, проверенным
  и связанным с отложенными исправлениями; broad ignore и скрытое исключение проблемных
  модулей не считаются прохождением анализа.
- Уровень 5 — предлагаемая стартовая настройка качества, не утверждение о достигнутом
  уровне. При невозможности разумно закрыть её в этой поставке зафиксировать фактический
  отчёт и согласовать объём, а не снижать gate незаметно.
- Проверить PHPDoc generic DTO/collections/Promise в публичных точках, имена импортов,
  strict_types и типы возвращаемых результатов. Не менять API только ради удобства
  анализатора, если изменение затрагивает продуктовое поведение.

Установка PHPStan как [dev-инструмента](https://phpstan.org/user-guide/getting-started)
не добавляет зависимость пользователям ядра. Совместимые версии инструментов под
PHP 8.4/8.5 выбрать и закрепить lock при реализации; сейчас composer.json не меняется.

## 4. Матрица проверок

| Контур | Приёмка |
| --- | --- |
| PHP 8.4 и 8.5 | Существующий полный suite; предупреждения пакета исправлены; проверка в произвольном порядке по фиксированному seed при риске глобального состояния |
| Production-only | Чистая установка --no-dev, явный PSR транспорт, standalone auth/retry/rate-limit/timeout/URI/JSON/body/files/validation smoke по существующим сценариям |
| Laravel 12 | Полное приложение из 018: auto/manual registration, HTTP/Artisan/job, config:cache, пользовательские bindings, последовательные контексты |
| Composer metadata/autoload | validate --strict; dump-autoload --optimize --strict-psr; соответствие runtime-пакетов реальному использованию |
| Зависимости | Lock-набор и минимально допустимый совместимый набор в изолированной копии; update --prefer-lowest --prefer-stable не изменяет основной lock. Для верхнего набора — актуальный совместимый resolution в CI |
| Качество | Зафиксированные lint/static-analysis commands, без маскировки новых ошибок |
| Дистрибутив | Нет vendor/workflow/tests/tool caches; установка распакованного архива и smoke проходят |
| Документация | Локальные ссылки, действующие символы API, запускаемые ключевые примеры и согласованная таблица совместимости |

Наличие строки PHP 8.4 в YAML не доказывает успешный удалённый прогон; зафиксировать
фактические результаты CI на конкретном commit. Если какой-то контур недоступен,
указать его как непроверенный, а не завершать релизную приёмку по локальному PHP 8.5.
Реальный внешний API и БД для перечисленных unit/smoke сценариев не нужны.

сверки использования, не запрещать существующее расширение массово.

changes. Создание плана и реализация quality-checks не являются поручением публиковать
пакет: tag/push/release выполнять по отдельному поручению на готовый проверенный результат.

Готовность: первые три плана завершены или их исключения явно приняты, таблица issue
сведена, все согласованные gates прошли на итоговом commit, состав архива и migration
проверены. Отложенные расширения не выдаются за реализованные. Реализация ещё не начата.
