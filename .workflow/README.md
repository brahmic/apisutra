# Рабочие материалы ApiSutra

`.workflow/` содержит внутренние материалы сопровождения. Публичный контракт описан
в [документации](../docs/README.md); перенос или статус рабочего документа его не меняет.
Предложения из аудитов и обсуждений сами по себе не являются решениями или поручениями.

Архив `.workflow/history/` не используйте в обычном рабочем процессе; обращайтесь
к нему только при целевом разборе прошлого по [правилам архива](#исторический-архив).

## Каталоги и статусы

Пути в таблице — относительно `.workflow/`. Создавайте каталоги по мере необходимости.

| Каталог | Назначение и статус плана |
| --- | --- |
| `current/` | План: `новый` — сформулирован, не начат; `в работе` — выполняется согласованный объём |
| `backlog/` | Отложенные планы (`отложен`, с причиной) и предварительные предложения |
| `completed/` | Планы: `завершён` — критерии выполнены, проверки записаны |
| `audit/` | Аудиты, наблюдения и рекомендации к проверкам |
| `adr/` | Архитектурные решения и последствия |
| `discussion/` | Варианты и рассуждения без обязательства реализации |
| `history/` | Архив для особых расследований, исключённый из обычной работы |

Статус и каталог плана меняйте вместе; при возобновлении возвращайте его в `current/`.
Закрытый без реализации план оставляйте в `backlog/` с причиной: `завершён` не означает отмену.
Из обсуждения создавайте новый план или ADR со встречными ссылками, сохраняя исходное обсуждение.

## Именование и приложения

- Формат: `xxx-001-korotkoe-imya.md` — префикс из трёх строчных латинских букв (см. таблицу ниже), номер
  минимум из трёх цифр и имя латиницей в kebab-case; дата в имени необязательна.
- Нумерация независима по префиксам и общая для каталогов workflow. Берите следующий номер
  после наибольшего среди файлов и папок документов; разные документы не могут делить ID.
  Сохраняйте ID при переносах и смене статуса; удалённые номера повторно не используйте.
- Аудит с несколькими файлами обязательно имеет собственную папку. Для документа из нескольких
  файлов схема: `aud-001-topic/aud-001-readme.md`; папка носит имя документа без `.md`, основной
  файл — `<тип>-<номер>-readme.md` с тем же ID, без нового номера; `readme` — строчными.
  Одиночный `aud-001-topic.md` при добавлении приложений переводите в эту структуру.
- Приложения храните только внутри папки документа, при необходимости в `artifacts/`.
  Дайте ссылки и инструкции запуска; доказательства не должны существовать только в `/tmp`.
  Переносите весь комплект вместе. Имена скриптов и фикстур — по назначению, без обязательного ID.
  Обычный `README.md` предназначен для служебных индексов; им и другим приложениям префикс не нужен.

## Шапка и содержание

Сразу после H1 основного документа, включая `<тип>-<номер>-readme.md`, обязательна шапка:

```text
- Дата создания: YYYY-MM-DD
- Дата обновления: YYYY-MM-DD
```

Для плана добавьте `- Статус: ...` с одним значением из таблицы каталогов. При правке меняйте
дату обновления, при изменении состояния — статус. У исторического импорта допустимо
`Дата создания: неизвестна (исторический материал)`; дату переноса укажите отдельно, не вместо создания.
Служебные индексы и приложения шапки не требуют; для `history/` действуют исключения ниже.

| Тип / префикс | Содержание |
| --- | --- |
| Аудит / `aud` | Проблематика, границы, методика, факты, находки, рекомендации, выводы. Различайте воспроизведённые дефекты, наблюдения по коду, принятые ограничения и непроверенные предположения. У находки: ID, приоритет, основание и способ проверки/исправления. |
| План / `pln` | Проблематика, подход, шаги, зависимости, критерии завершения, выводы о принятом объёме; ссылка на исходный аудит или решение. |
| ADR / `adr` | Контекст, статус, решение, последствия; полезные для понимания альтернативы. При пересмотре — ссылка на заменяющий ADR. |
| Обсуждение / `dsc` | Свободное изложение вопроса и вариантов без требования готового решения. |

Заголовки свободные; пустые блоки и «вопросов нет» не нужны. Ссылки ставьте рядом с фактами,
отдельные «Референсы» — по необходимости.

## Вопросы и ответы в аудите

- Если вывод зависит от внешнего ответа, перед «Выводами» добавьте «Вопросы»: стабильный ID
  (`В1`, `В2`, …), формулировка, статус `открыт`/`отвечен`, адресат и что зависит от ответа.
- После ответа сохраните вопрос, отметьте `отвечен` и свяжите с записью в «Ответах» после
  «Выводов»: ID вопроса, ответ, дата, источник и влияние на находки, выводы или план.
  Изменившиеся выводы и дату документа обновляйте явно.
- Уточнение готовой находки можно записать по её ID без создания вопроса задним числом.
  Блоки нужны только при наличии записей. Непроверенный технический сценарий — рекомендация
  к проверке, а не автоматически вопрос, требующий решения пользователя.

## Исторический архив

`history/` (в том числе бывшая `.temp/`) может содержать ошибки, устаревшие сведения,
отменённые решения и нереализованные планы. **Это дополнительный контекст, не источник истины.**

- Исключайте архив из начального чтения, обычных поисков, текущих планов и проверок документации.
  Читайте только относящиеся к делу материалы при расследовании конкретной проблемы, требующей
  выяснить причины прошлых решений или поведения, либо по прямому запросу на изучение истории.
- Старые инструкции, приоритеты и «обязательно» не задают текущих правил и не возобновляют работы;
  действуют актуальные инструкции репозитория и задачи.
- Утверждения перепроверяйте по текущему коду, тестам, актуальной документации и действующим решениям.
  Неподтверждённое помечайте как историческое предположение со ссылкой на источник. Полезные
  подтверждённые выводы фиксируйте в текущем аудите, плане или ADR с основанием проверки;
  ссылка на архив объясняет происхождение идеи, но не заменяет подтверждение.
- Сохраняйте исторические тексты и контекст. Правила именования, шапок и структуры активных
  документов не требуют переоформлять архив или массово обновлять его старые ссылки и описания.

## Ссылки и актуальность

Markdown-ссылки отсчитываются от файла, текстовые пути — от корня репозитория, если не указано иное.
При переносах обновляйте входящие и исходящие ссылки и индексы. Сохраняйте исторические факты
и результаты проверок; поздние исправления отмечайте отдельно с датой и текущим статусом.
Старый результат теста не считается проверкой новой версии кода.
