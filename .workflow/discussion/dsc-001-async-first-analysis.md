## Сохранённое обсуждение

Если breaking changes допустимы, **самый чистый и честный путь — сделать async‑first архитектуру** и перестроить контракты. Тогда “реальный async” будет правдой и для пагинации (пусть и последовательной для cursor‑based). Что это значит на практике:

## Предлагаемое решение (breaking)
1) **Async‑first контракты**
- `TransportInterface` → async‑вариант (`sendAsync(): PromiseInterface<ProviderResponse>`), синхронный `send()` либо убрать, либо оставить как thin wrapper `wait()`.
- `Pipeline::executeAsync()` становится основной, `execute()` просто `->wait()`.

2) **Полный async‑пайплайн**
- Все стадии (`hooks`, `retry`, `rateLimit`, `cache`, `hydrate`) работают в цепочке промисов.
- `SleeperInterface` превращается в non‑blocking (таймер/loop), иначе async будет «липовой».

3) **Async‑пагинация**
- Новый `AsyncPaginator` с `allAsync()/pagesAsync()/rangeAsync()` и/или `eachAsync()` (стриминг страниц).
- **Cursor‑based** — строго последовательная цепочка промисов (но без блокировки потока).
- **Offset‑based** — можно параллелить страницы через pool.

4) **API‑поведение**
- `send()` может вернуть `PromiseInterface` (async‑first), а `sendSync()` — блокирующий wrapper.
- `throwOnErrors`: при `false` **resolve с ExecutionResult**, reject — только при runtime‑сбоях или если `throwOnErrors=true`.

### Итог
Это **самый правильный** путь, если действительно хотим “реальный async” и готовы ломать API.  
Да, это крупный рефактор, но зато вычищает двусмысленность навсегда.

Если хочешь, могу расписать конкретный план миграции и начать с изменения контрактов (`TransportInterface`, `Pipeline`, `AbstractClient`).

## Ниже оценка по **breaking‑рефактору на async‑first** и влияние на DX.


### 1) Объём работ (оценка)
**Вариант “настоящий async” (без блокирующих sleep): ~4–6 недель одного инженера.**  
Критические блоки:

- **Контракты и базовые API** (Client/Transport/Pipeline, сигнатуры, обратные обёртки `sendSync()/wait()`): 3–5 дней.  
- **Async‑пайплайн** (Pipeline/Flow/HookRunner/ResultBuilder → цепочки промисов): 1–2 недели.  
- **Retry/RateLimit/Delay** (неблокирующие таймеры, интеграция с event loop): 1–1.5 недели.  
- **Async‑пагинация**  
  - cursor‑based: последовательная цепочка промисов  
  - offset‑based: параллельная через pool  
  4–6 дней.  
- **Тесты + документация**: 1–2 недели.

**Если оставить блокирующие sleep** (т.е. “async API, но внутри всё равно блокируем”), объём можно ужать до **~2–3 недель**, но это не решает исходную проблему «реального async».

### 2) Как изменится DX (для разработчика)

**Плюсы:**
- `sendAsync()` реально неблокирующий — ожидания совпадают с поведением.  
- Единый “promise‑поток”: удобно композировать параллельные запросы, batch/pool, await‑паттерны.  
- При чёткой политике (resolve `ExecutionResult`, reject только runtime) — предсказуемая модель ошибок.

**Минусы:**
- Появляется **обязательная работа с Promise/await**. Для sync‑кода — придётся явно вызывать `wait()` или пользоваться `sendSync()`.  
- Нужен **event loop / async‑runtime** (ReactPHP и т.п.) — дополнительная инфраструктура и знания.  
- Тесты усложняются: нужно тестировать промисы, цепочки, таймеры.  
- Поведение hooks/cache/retry становится асинхронным → это **новая модель мышления**.

**Итог по DX:**  
- Для тех, кто уже в async‑контексте — DX **сильно лучше** и честнее.  
- Для большинства “обычного PHP” — DX **сложнее**, потому что появляется необходимость явно управлять промисами.

Если хочешь, могу накидать конкретный пошаговый план миграции (с изменениями в контрактах и минимальной стратегией тестов).

### 1) Что такое event loop / async‑runtime (ReactPHP, Amp) — простыми словами  
**Event loop** — это «диспетчер» внутри одного процесса, который:
- запускает неблокирующие операции (сеть, таймеры, файлы),
- ждёт их готовности,
- вызывает коллбеки/продолжает промисы, когда данные доступны.

Без такого цикла `Promise` — это просто объект‑обёртка. Если внутри стоят `sleep/usleep` или синхронный HTTP, то процесс всё равно **блокируется**, и «async» становится номинальным.

**Async‑runtime** — это библиотека, которая даёт:
- сам event loop,
- неблокирующие таймеры (`await delay()` вместо `sleep`),
- неблокирующие сокеты/HTTP‑клиент,
- соглашения для промисов/корутин.

Примеры:
- **ReactPHP**: event loop + HTTP client + timers + DNS.
- **Amp**: корутины/await, таймеры, сетевые клиенты.

**Почему это важно для нас:**  
Сейчас в пайплайне есть синхронные места: транспорт, retry, rate limit, `sleep` — без loop это всё блокирует процесс. Поэтому «реальный async» требует именно event loop и неблокирующих реализаций.

### 2) Практическая ценность «настоящего async» для разработчика

**Главная выгода** — **снижение общего времени** и **рост пропускной способности** для IO‑нагруженных сценариев.

#### Реальные кейсы / бизнес‑сценарии
- **Агрегация данных из нескольких внешних API**  
  Можно параллельно запросить 5–10 сервисов и ждать всех сразу. Время ≈ max(latency), а не сумма.
- **Mass‑операции для мульти‑тенантов**  
  Обработка десятков/сотен запросов в одном воркере без блокировки.
- **Фан‑аут вебхуков**  
  Отправка в десятки систем одновременно, без “конвейера” из sync‑запросов.
- **Пакетные загрузки/обновления**  
  Например, параллельные запросы на мета‑инфо/статусы/списки.
- **Rate‑limit/backoff без простоя**  
  Вместо `sleep` можно ждать таймер и в это время обслуживать другие запросы.
- **Снижение затрат**  
  Один воркер может обслуживать больше запросов, меньше процессов → ниже инфраструктурная стоимость.

#### Где эффект минимален
- В **короткоживущих HTTP‑запросах** (типичный PHP‑FPM) — меньше пользы.
- Для **CPU‑bound** задач — async не ускоряет.

#### Особый случай — пагинация
- **Cursor‑based** всё равно остаётся последовательной (но неблокирующей), так что выгода — в том, что процесс не простаивает и может выполнять другие задачи в ожидании сети.
- **Offset‑based** можно реально распараллелить страницы.
