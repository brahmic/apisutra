- Дата обновления: 2026-09-13

## Основание и статус

Владелец попросил сохранить перечисленные направления из
[первоначального аудита](../audit/aud-001-architecture-code-2026-09-11/aud-001-readme.md#архитектура-и-границы)
и продуктово объяснить первый пункт. Это список для последующего обсуждения;
приоритеты, конкретные контракты и реализация пока не согласованы. Четыре пункта
не являются четырьмя готовыми планами и не возобновляют отложенный async/rate-limit.

По первому направлению владелец поддержал внутреннюю декомпозицию ради ясности
и сопровождения, без обязательного ожидания новой функции. Зафиксированы сохранение
публичного API и zero-config; конкретный дизайн, роль и имя объекта зависимостей
ещё уточняются. [Итог обсуждения](dsc-003-client-assembly-factory.md#фиксация-позиции-по-итогам-обсуждения).
Это не поручение приступить к реализации; остальные три направления остаются предложениями.

## Список в согласованном для обсуждения порядке

1. **Выделение фабрики сборки клиента.** Отделить создание и соединение внутренних
   компонентов от обязанностей клиента по выполнению запросов. Существующий
   AbstractClient сам создаёт Hydrator, Serializer, RateLimiter и Pipeline.
   Конкретный контракт фабрики и способы подмены определить только после проверки
   реальных сценариев расширения. Существующие параметры транспорта, logger,
   clock/sleeper и прочие точки настройки не выдавать за новые возможности.
2. **Сужение контекста DTO.** Рассмотреть передачу в computed() только необходимых
   данных вместо всего PipelineContext. Учесть существующие пользовательские
   реализации и необходимость совместимой миграции.
3. **Упорядочивание интерфейсов.** Выбрать последовательный принцип расположения
   контрактов и отделить фреймворк-специфичные зависимости от общих механизмов.
   Массовые переносы namespace без практической пользы не являются целью.
4. **Отделение tooling.** Обозначить границу анализа исходников, построения каталогов
   и экспорта документации относительно выполнения HTTP. Отдельный Composer-пакет
   не является обязательным решением.

## Продуктовый смысл первого пункта

Актуальный взгляд, договорённости и открытые вопросы —
[политики приложения, допуск и сборка клиента](dsc-004-client-policies-and-assembly.md).
Продуктовые сценарии и прежние PHP-эскизы сохранены в
[закрытом обсуждении фабрики](dsc-003-client-assembly-factory.md).

Обычный пользователь создаёт клиент и отправляет запросы прежним способом.
Предложение относится прежде всего к сопровождению: добавление или замена внутреннего
компонента требует меньше вмешательств в клиент, отвечающий также за выполнение,
пагинацию и результаты. Отдельная сборка позволяет проверять согласованность
зависимостей сама по себе. Возможность нестандартной сборки для SDK-провайдера
нужно обосновать конкретным сценарием; это пока потенциальная польза, не готовый API.

Сквозное требование владельца — **zero-config**: стандартная сборка автоматическая,
без обязанности создавать фабрику, регистрировать каждый компонент или подключать
Laravel. Рефакторинг сам по себе не обещает ускорения HTTP и новых возможностей API.
До реализации подтвердить, что отдельная фабрика уменьшает сложность и сохраняет
существующее поведение, а не только перемещает код между файлами.


## Дополнение: централизованная политика приложения

Владелец предложил сценарий шести SDK-провайдеров с управлением некоторыми
настройками из общей админки. [Разбор в дискуссии сборки](dsc-003-client-assembly-factory.md#сценарий-приложения-с-шестью-провайдерами)
разделяет контракт провайдера, политику приложения и инфраструктуру; фиксирует
кандидатов настроек, defaults/обязательные ограничения и жизненный цикл изменений.
Первоначально рассмотрен смысл операционной паузы. Затем владелец поддержал её
полезность и необязательную проверку допуска в SDK. Callback, интерфейс и регистрация
обработчика ещё сравниваются. Актуальная позиция перенесена в
[новую дискуссию](dsc-004-client-policies-and-assembly.md); конкретный публичный API
и реализация всех кандидатов настроек не утверждены.
