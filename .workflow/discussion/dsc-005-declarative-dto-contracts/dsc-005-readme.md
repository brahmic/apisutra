## R1. Подключение и разрешение правил

### В01. Как SDK подключает правила и получает standalone-вход

**Рекомендую:** неизменяемый набор `HydrationRules` с defaults и словарём
`class-string → DtoRules`; внутри описания DTO — правила свойств и один receiver.
Описание значения различает scalar, конкретный DTO, список с описанием элемента
и discriminator. Не вводить строковый язык, разбирающий PHPDoc.

Подключение — необязательный `ClientConfig(hydrationRules: $rules)`.
SDK создаёт его при своей обычной сборке; пользователь SDK вызывает существующий
конструктор/фабрику клиента. Внутри используется текущий Hydrator с дополнительным
необязательным аргументом в конце конструктора.
Для standalone предложить `Hydrator::forRules($rules)->hydrate($payload, Dto::class)`:
это новый экземпляр того же Hydrator, без PipelineContext, HTTP и изменения singleton.

Набор можно собрать из типизированных описаний один раз. Метод изменения создаёт
новый набор; сохранённый в клиенте набор не дополняется регистрациями во время запросов.
Внешний публичный контракт не должен требовать доступа к reflection cache.

**Альтернатива:** инъекция произвольного HydratorInterface в клиент. Она даёт полную
замену алгоритма, но сама по себе не решает AS-1/AS-2/AS-4 и расширяет контракт сильнее
задачи. Для 028 достаточно подключения данных правил к существующему исполнителю.

**Проверка:** один набор и два синтетических envelope дают одинаковые DTO/ошибки
через standalone и Returns; пользователь SDK не регистрирует правила перед вызовом.
`Hydrator::default()` и ранее созданный другой клиент сохраняют своё поведение.

### В02. Как совместить внешние правила и старые декларации

**Рекомендую:** после второго разбора для первой версии отвергать пересечение
явного внешнего правила поля с атрибутами его входной гидратации через
ConfigurationException. В03–В17 используют это обновлённое предложение; В02
остаётся открытым до фиксации контракта. Семь уровней больше не являются
предпочтительным направлением.

| Сочетание | Предлагаемое поведение первой версии |
| --- | --- |
| Plain DTO и внешнее описание поля | Применить внешнее описание |
| Явное внешнее поле и входной атрибут того же свойства | ConfigurationException, даже если mapping и cast описывают разные части обработки |
| Атрибут другого поля, у которого нет внешнего описания | Сохранить штатное атрибутное поведение этого поля |
| Внешнее описание DTO-класса и применимый DtoHydrate/атрибутный профиль класса | ConfigurationException вместо нового межисточникового слияния; учитывать унаследованный профиль |
| Только старые атрибуты/профиль | Прежнее разрешение 029, включая Nested над Cast |
| Атрибут только исходящей сериализации или сторонней библиотеки | Сам по себе не конфликтует; Map участвует во входной гидратации и не считается исключительно исходящим |

Перечень атрибутов поля для этой проверки фиксирован по текущей входной metadata:
**From, Map, Nested, Cast, DateTimeFrom, EmptyStringAsNull, DefaultValue**.
Map участвует в обеих сторонах преобразования. **To и DateTimeTo** относятся
к исходящей сериализации и сами по себе пересечения входных правил не создают.
**DtoHydrate и атрибутный профиль DTO** проверяются отдельно на уровне класса,
включая применимое наследование. У AbstractDto и AbstractResponseDto классовых
атрибутов нет: одно наследование от них не создаёт конфликт. Список и отдельная
матрица нижних defaults против профильных casts должны войти в contracts.md;
перечень атрибутов эту матрицу не заменяет.

Defaults набора остаются нижним источником для не объявленных иначе настроек.
Явное правило поля выбирается из одного источника; класс использует либо внешние
class defaults, либо целиком прежнее разрешение class-level/profile. Defaults
не заменяют явно выбранные правила. До закрытия В02 нужна конечная таблица
поддерживаемых параметров, в том числе профильных casts против defaults набора:
простого запрета двух явных правил поля для этого недостаточно.

Во внешних описаниях сохраняются различие Unspecified/false/пустого массива/default
null и атомарные группы mapping/преобразования. Явный None может отключать
унаследованное внешнее преобразование; отменять им атрибутный Cast при запрещённом
пересечении нельзя. ClientConfig.casts, global и extension registry сохраняют
свои [области применения](../../../docs/guides/casts.md#регистрация-кастов).

Причина пересмотра — стоимость обязательств совместимости: позднее можно разрешить
ранее запрещённое сочетание, сохранив поведение уже допустимых конфигураций.
Это не абсолютная гарантия совместимости любого клиента, который мог специально
полагаться на отклонение конфигурации. Подмена уже опубликованного приоритета
меняет результат ранее успешных вызовов и потому существенно труднее.

**Альтернатива:** первоначальное семиуровневое слияние: внешнее поле → атрибут поля
→ внешние class defaults → DtoHydrate → профиль → defaults набора → ядро.
Оно позволяет заменить mapping и сохранить атрибутный cast, но требует закрепить
результат каждого пересечения. Полная замена атрибутного описания внешним — ещё
одна альтернатива. Ни одно из этих поведений не было выпущено или принято.

**Проверка:** plain-граф; конфликт на одном поле; атрибут на другом поле;
class defaults/унаследованный профиль; нижние defaults; исходящие и посторонние
атрибуты; Unspecified/false/пустые fallbacks/default null; прежние DTO без набора.
Ошибки декларации должны возникать до преобразования данных, независимо от их
значений. Старый пример смешанного mapping/cast в UC-02 обновлён под этот выбор.

### В03. Как defaults распространяются по графу и наследованию PHP

**Рекомендую:** defaults набора действуют на каждый DTO, в который вошёл этот
Hydrator, включая дочерние DTO без собственного внешнего descriptor.
Правила конкретного класса ищутся по точному class-string; не добавлять неявный
поиск внешних правил по родителям/интерфейсам. При необходимости SDK явно повторно
использует одно описание для нескольких классов. Привязка существующих атрибутных
профилей по иерархии PHP сохраняется.

Override класса относится к его полям. Override поля относится к самому значению
и его явно объявленным scalar-элементам, включая вложенные списки. При входе в
дочерний DTO его policy разрешается заново из его класса и того же набора.
Отключение strictness у родителя не отключает её незаметно у всех потомков.
Контекстных схем одного класса в зависимости от пути до него в первой версии нет.

Для plain-дочернего объекта внешний descriptor должен задать DTO-вложенность,
если она не поддержана имеющейся декларацией. Подключение одних defaults не означает
автоматического превращения любого native-класса, например VO с фабрикой, в DTO.

**Альтернатива:** наследование любых настроек вниз по пути графа или внешним
PHP-родителям. Это удобнее для отдельных деревьев, но делает схему класса зависимой
от точки входа и усложняет приоритеты и ключ кеша.

**Проверка:** один дочерний класс в двух ветках, класс с атрибутным профилем и без него,
явный legacy-override родителя, отдельный override scalar-списка, два независимых набора.

## R2. Типы и экземпляры обработчиков

### В04. Как создавать cast/provider и передавать им область гидратации

**Рекомендую:** новый внешний API хранит описания `class-string + constructor args`,
а не готовые mutable-объекты. Аргументы первой версии — scalar/null, enum cases и
массивы этих значений; произвольные объекты и closures в кеше правил не сохраняются.
Это покрывает в том числе параметризованный `StrictScalarCast('int')`.

Внешний descriptor создаёт обработчик для одного применения к значению; для
элементов списка это отдельные применения. Он не делит mutable-экземпляр между
клиентами, корневыми вызовами и соседними элементами. Состояние операции передаётся
через область текущего вызова, а не хранится в наборе правил.

Для обработчиков, повторно запускающих гидратацию, рекомендую отдельный
опциональный контракт с явно передаваемым `HydrationScope` — рабочее имя.
Он предоставляет hydrate/hydrateCollection того же исполнителя и набора,
nullable PipelineContext и принадлежность текущему корневому вызову. Для cast
и provider вводятся opt-in методы с аргументом scope; существующие сигнатуры
CastInterface/DefaultValueProviderInterface не изменяются. Точные имена и форма
этих методов входят в contracts.md. Scope передаётся на вызов, не сохраняется
в декларации или глобальном singleton; вложенный вызов учитывает общий предел
глубины и правила изоляции. Произвольное преобразование всё равно создаёт границу
точности source path по В14.

Выбор opt-in метода определяется контрактом самого обработчика, независимо от
регистрации: внешний descriptor, property Cast, Nested(itemCast:), DefaultValue
provider и cast профиля. Это относится и к старому атрибутному DTO, если его
обработчик явно реализовал новый opt-in контракт. Без внешнего набора scope
представляет обычный набор текущего Hydrator; менять global default не требуется.
Обработчик без нового контракта получает прежний вызов с PipelineContext/null.
Scope передаётся аргументом каждого вызова, не сохраняется в переиспользуемом
атрибутном itemCast. Сериализация не переключается на метод гидратации со scope.

В частности, RowCast подключён через Nested(itemCast:). Его новый метод должен
передать scope и внутреннему помощнику либо вызвать scope.hydrateCollection
напрямую: если помощник продолжит обращаться к default, набор снова потеряется.

Одной ссылки на набор в PipelineContext недостаточно: standalone передаёт null.
RowCast и cast одиночного DTO могут перейти на scope, сохранив свои локальные
преобразования и общий исполнитель. Старый вызов Hydrator::default() внутри
обработчика остаётся явной границей: он не наследует набор клиента. Совместимость
старого рецепта не означает автоматического распространения новых правил через
такой вызов. Raw-фабрика, лишь создающая готовый RawVariant, scope не требует.

Жизненный цикл **старых** деклараций не менять ради нового кеша: профиль разрешается
прежним способом, property Cast создаётся по прежним правилам, атрибутный
Nested.itemCast сохраняет создание одного экземпляра на свой проход списка.
Новая граница аргументов не ограничивает ранее разрешённые атрибуты и профили.

**Альтернатива:** один обработчик на descriptor в пределах корневого вызова.
Он также изолирует разные клиенты и корневые вызовы и сокращает число создаваемых
объектов, но разделяет состояние между элементами/полями одной операции. Это
полноценный вариант выбора, а не нарушение изоляции клиентов. Стоимость варианта
«на применение» растёт с числом применений; измеренной проблемы производительности
пока нет. Глобальное переиспользование, factory/DI и отказ от scope с документированной
границей default остаются другими вариантами с отдельными последствиями.

**Проверка:** stateful test cast, последовательные и вложенные вызовы, два клиента;
описание правил не меняется. Кеширование metadata не вызывает прежние handlers реже
или иначе. Проверить повторную гидратацию из RowCast/одиночного cast/provider
в standalone и HTTP с двумя наборами, а также legacy-вызов default как границу.
Для каждой формы регистрации проверить opt-in и обычный обработчик, включая
атрибутный RowCast, профиль и DefaultValue; внешнее описание поля не обязательно.
При сравнении жизненных циклов считать создания и проверить состояние соседей;
произвольного порога времени пока не вводить.

### В05. Что означает strict для scalar, union и результата cast

**Рекомендую:** проверять тип перед вызовом reflection. Для float допустить
единственное числовое расширение int → float в явно заданном безопасном
диапазоне. Строки и bool автоматически не преобразовывать, в том числе после cast.
Legacy-режим сохраняет действующий валидатор.

| Цель в strict | Принять | Отклонить без явного cast |
| --- | --- | --- |
| int | PHP int в поддерживаемом диапазоне | Числовую строку, float, bool |
| float | PHP float; int от -2^53 до 2^53 включительно с точным преобразованием в float | int вне этого диапазона, числовую строку, bool |
| bool | true и false | 0/1 и строки |
| literal true / false | Только соответствующий literal | Другой bool и остальные типы |
| string | PHP string, включая пустую | Числа, bool, Stringable |
| int\|string | int либо string с сохранением выбранного входного типа | float, bool |
| mixed | Исходный тип/значение | Нет автоматического сужения |

Nullable проверяется отдельно. Исходная рекомендация отклоняла любой int для float;
после рецензии она оставлена альтернативой: JSON.stringify(10.0) даёт `10`, а PHP
декодирует этот токен в int. AS-1 не требует отвергать такое число. Основания и
воспроизведение — в [PR-03](peer-review.md#pr-03-float-и-json).
Диапазон включительно ±2^53 — консервативная граница этой рекомендации; некоторые
большие чётные int также представимы точно, но автоматическое расширение для них
здесь не разрешается. Это не определение JavaScript safe integer, у которого
граница ±(2^53−1). NaN/INF в standalone остаются float:
проверка доменного диапазона или возможности JSON-сериализации — отдельная задача.
В union сначала ищется точное соответствие: int остаётся int при int|float.
Только при отсутствии точной ветви рассматривается описанное расширение в float;
выбор не зависит от порядка в ReflectionUnionType. Для DTO union нужна явная цель или discriminator.
DateTime/enum не являются scalar-политикой: их существующие преобразования сохраняются.

Сохранить `integer_out_of_range` для значения, которое существующая проверка
распознаёт как переполнение целевого int; обычная неверная scalar-форма даёт
`invalid_field_type`. Явный cast может превратить строку в int, но его строковый
результат для int повторно приводить нельзя. Допуск int → float применяется
одинаково к исходному значению и результату cast. Для promoted-параметра проверяется
тип параметра, для прямого заполнения — тип свойства, как в constructor-first 029.

**Альтернатива:** исходное требование только PHP float; либо точная проверка
представимости каждого int, включая числа за ±2^53. Неограниченные reflection
conversions не следуют из разрешения безопасного числового расширения.

**Проверка:** min/max/overflow, JSON `1` и `1.0`, false, пустая строка, union в разных
порядках, Stringable, корректный и некорректный результат cast, constructor defaults.
Отдельно ±(2^53−1), ±2^53, ±(2^53+1), ±(2^53+2), PHP_INT_MIN/MAX;
на границах не использовать сравнение, само неявно превращающее int во float.

### В06. Как объявлять scalar-элементы и вложенные списки

**Рекомендую:** отдельно описывать контейнер и рекурсивное правило элемента:
например, `list(int)`, `list(nullable(int))`, `list(list(string))`, `list(dto(ItemDto))`.
Здесь это условная запись структуры descriptor, не PHPDoc parser и не строковый API.
Scalar union элемента задаётся перечислением разрешённых scalar-типов.

Bare array по-прежнему не означает list и не проверяет тип элементов.
Явная list-декларация требует последовательных ключей, включая пустой список;
тип элемента и nullable проверяются независимо. Strictness приходит из В03,
элемент может иметь явный cast с аргументами. Политика legacy для элемента разрешает
старые scalar conversions, но не отключает отдельно объявленную list-форму.

**Альтернатива:** читать `list<T>` из PHPDoc или использовать только itemCast.
Первое добавляет новый язык и зависимость контракта от комментария; второе не задаёт
форму каждого уровня и при атрибутной настройке не принимает constructor args.

**Проверка:** все scalar-типы из В05, null-элемент, пустой список, неверный элемент
второй строки двумерного списка; ошибка указывает оба индекса. Матрица явного cast
та же, что у одиночного scalar-поля.

## R3. Состояние и порядок преобразования

### В07. Как разделять присутствие, null и форму контейнера

**Рекомендую:** независимые входные правила `required`, `forbidExplicitNull`
и `inputShape`. Их проверять после выбора primary/fallback и до нормализации/defaults.
Required требует именно присутствия во входе; default не исправляет его отсутствие.
Отсутствие нового required сохраняет текущие constructor/default/collection правила.

| Декларация | Вход | Результат |
| --- | --- | --- |
| Optional `?int = null`, explicit null запрещён | Missing | Constructor default null |
| То же | Null | Ошибка исходного null до DefaultValue и Cast |
| То же, NullIfEmpty включён | Пустая строка | Запрет исходного null не срабатывает; дальнейшая nullable-проверка допускает полученный null |
| Required typed collection с default | Missing | `required_field_missing`, без автоподстановки коллекции |
| Явный list | Ассоциативный/разреженный массив | Ошибка формы до переиндексации |

Object принимает PHP-объект либо ассоциативный массив; непустой list отклоняется.
Пустой PHP-массив допускается и у object, и у list: потерянное различие JSON `{}`/`[]`
не восстанавливается. При assoc=true теряется и часть непустых различий:
`{"0":"a","1":"b"}` и `["a","b"]` декодируются одинаково. Числовое имя
"1" становится PHP int-ключом 1, а "01" остаётся строкой. InputShape проверяет
доступную PHP-форму, а не доказывает исходный вид JSON-контейнера; восстановление
этой информации потребовало бы отдельного контракта декодера и не обещается здесь.
Missing/null не проверяются как контейнер: сначала действуют
правила состояния, затем nullable/default и проверка полученного значения.
Traversable не объявлять эквивалентом входного PHP list автоматически.

Для нового list-описания рекомендую строгую форму по умолчанию. При необходимости
совместимого ассоциативного входа выбирать отдельную явную нормализацию ключей;
она сохраняет соответствие исходных ключей индексам результата для В13.
Нативный тип или объявленная вложенность всё равно проверяет форму значения,
которое реально поступает на соответствующий шаг после defaults/преобразований.

**Альтернатива:** проверять только итоговое значение после casts/defaults.
Тогда запрет исходного null и требование присутствия снова невыразимы.

**Проверка:** полный продукт missing/null/пустая строка/list/object и политик
Keep/NullIfEmpty/EmptyStringAsNull/Cast; вложенные контейнеры проверяются каждый
на своём объявленном уровне.

### В08. В каком порядке выполнять Cast и вложенность

**Рекомендую:** внешний descriptor содержит одно преобразование всего поля:
либо field Cast, либо структурное описание DTO/list/discriminator. Их одновременное
указание считать ConfigurationException. Внешний field Cast возвращает готовое
значение, которое проходит проверку объявленного результата, без второй гидратации DTO.
Описание **результата** cast может включать DTO-тип или `list(int)`:
оно проверяет instance/type/элементы и не конструирует DTO повторно. Это отдельно
от структурного преобразования входного массива в DTO. Поэтому параметризованный
cast всего scalar-списка не теряет поэлементную проверку результата в strict mode.

У структурного списка разрешены `each` и `itemCast`: выбор элемента через each →
itemCast → проверка/гидратация элемента → обёртка коллекции. Готовый DTO, возвращённый
itemCast, принимается по совместимому типу; массив/объект данных проходит обычную
гидратацию один раз. Scalar-результат проверяется по правилу элемента. Явная
`inputShape` элемента проверяет вход соответствующего шага, а описание целевого DTO
проверяет данные, дошедшие до гидратации; эти две проверки не смешиваются.

Общий порядок поля: поиск и сохранение происхождения → входные правила →
нормализация → применимый DefaultValue → missing fallback → выбранное преобразование
→ итоговая проверка типа → подготовка аргумента конструктора.
Если после default получен новый контейнер, его целевая форма также проверяется.
Field Cast сохраняет пропуск empty-string normalization, как в 029; itemCast
не является field Cast и эту нормализацию всего поля не отключает.

**Альтернатива:** добавить для singleton отдельный явный этап preCast перед DTO.
Это выразительнее, но добавляет публичную композицию и ещё одну границу происхождения.
Для первой версии рекомендую отказаться от неявного «Cast, затем Nested»;
потребность в singleton preCast можно оценить отдельно при обсуждении этого вопроса.

**Совместимость:** атрибутный Nested + Cast без внешнего override сохраняет старое
игнорирование field Cast. Новый внешний конфликт не переносится задним числом
на работающие атрибутные DTO. Сохраняется и legacy-работа each/itemCast.

**Проверка:** все комбинации деклараций, provider перед Nested, готовый DTO от cast,
каждый счётчик конструктора, ошибка каждого шага и границы source path из В14.

### В09. Что делать с discriminator и неизвестными вариантами

**Рекомендую:** переиспользовать текущие режимы Value/Key и политики KeepRaw/Skip/Error.
По умолчанию неизвестный вариант сохраняется raw; известный выбирается до гидратации,
а ошибка его полей остаётся ошибкой. Не переопределять известный повреждённый объект
как unknown ради успешного результата. Scalar strictness полей не меняет незаметно
существующий алгоритм поиска discriminator.

Новый descriptor проверяет совместимость всех объявленных классов с результатом.
KeepRaw допустим, когда контейнер/тип элемента может хранить raw; для коллекции,
которая требует только конкретные DTO, выбрать Skip/Error либо явное преобразование
SDK. Предсказуемую несовместимость деклараций отклонять при их валидации.
Специальная raw-фабрика SDK остаётся небольшим внешним преобразованием; универсальный
реестр неизвестных вариантов в ядре не требуется.

**Альтернатива:** обязательный Error или общий UnknownDto. Первое ухудшает
расширяемость API, второе навязывает публичный тип чужому SDK.

**Проверка:** known-valid/known-invalid/unknown/missing discriminator, оба режима,
все три политики, исходный индекс после Skip. Для Key учитывать ключ обёртки в
source path, если соответствие известно.

## R4. Дополнительные поля

### В10. Как считать остаток при aliases и пересекающихся путях

**Рекомендую:** читать все поля из неизменяемого локального источника DTO; после
разрешения правил вычесть объединение реально потреблённых путей. Вести дерево
сегментов, чтобы не смешивать строковые префиксы и отношения parent/leaf.
Локальный источник — данные, дошедшие до этого DTO после BeforeHydrate/computed;
восстановление уже удалённых пользовательским callback полей не обещается.

| Случай | Предлагаемый остаток |
| --- | --- |
| Есть primary и fallback | Удалён primary; невыбранный fallback сохранён |
| Primary равен null | Удалён primary; fallback не выбирается |
| Все aliases missing, использован default/provider | Несуществующий путь не удаляет ничего |
| Потреблён `profile.id`, рядом есть `profile.future` | Сохранён `profile.future` |
| Потреблён единственный лист `profile.id` | Ставшая пустой ветка profile удалена |
| В источнике изначально есть непотреблённый `future: []` | Пустая ветка сохранена |
| Два поля читают один путь | Оба получают значение; путь удаляется один раз |
| Одно поле читает profile целиком, другое profile.id | Оба чтения допустимы; для остатка целый parent поглощает leaf независимо от порядка |
| Subtree целиком передан дочернему DTO | У родителя потреблён этот subtree; остатки внутри принадлежат ребёнку |
| each передаёт ребёнку только часть элемента | Потреблена переданная часть; соседи проекции остаются в receiver владельца списка |

False, ноль, null, пустые строки и исходные пустые контейнеры сохраняются без
фильтрации. Provider/cast может читать произвольные данные из source, но ядро не
угадывает такие чтения: потребление определяется декларативным mapping, а не
результатом анализа пользовательского кода. Необъявленные прочитанные ключи
по-прежнему попадают в extras.

После рецензии уточняется граница проекций each/discriminator. Объявление списка
не означает потребления всех его обёрток. Для
`rows = [{value: {id: 7, future: 1}, meta: {revision: 2}}]`, each=value и приёмников
у родителя/ребёнка рекомендую `child.extra = {future: 1}` и
`parent.extra = {rows: [{sourceKey: 0, remainder: {meta: {revision: 2}}}]}`.
После второго разбора рекомендую для **созданного остатка проекции списка**
всегда плотный PHP-список записей sourceKey/remainder. В sourceKey сохраняется
ключ и его PHP-тип **после входного декодирования, до нормализации списка**;
remainder содержит только остаток данного элемента.
Записи идут в порядке исходного обхода; элементы без остатка не добавляются.
Если остатков нет вовсе, созданная ветка rows удаляется. Это не правило для
нетронутых неизвестных массивов: они сохраняют исходную структуру и значения.
При нормализации исходного словаря sourceKey хранит исходный строковый/числовой
ключ, а не индекс итогового DTO. Остатки обёртки не смешиваются с extra ребёнка.

SourceKey не хранит утраченный тип ключа JSON: имя "1" после assoc-декодирования
уже имеет PHP-тип int, в отличие от "01". Поэтому sourceKey=1 сам по себе не
отличает ключ словаря от индекса списка. Это та же граница доступной информации,
что и потеря различия `{}`/`[]` в В07. Текст JSON Pointer не меняется: сегмент 1
обозначает соответствующий ключ/индекс; утверждать исходный вид контейнера нельзя.

Рекурсивная форма строится по декларациям проекции, а не по догадке о виде массива:

- остаток обычного объекта — карта непотреблённых полей; значение поля может
  содержать остаток следующего уровня;
- созданный остаток проецируемого списка — `list<{sourceKey: int|string, remainder: R}>`,
  где R — остаток элемента по этим же правилам; R может быть картой **или ещё одним
  списком записей**, если элемент сам является проецируемым списком;
- нетронутое значение сохраняется целиком, включая собственные массивы и поля
  sourceKey/remainder. Эти имена служебные только в созданных записях проекции;
- отсутствие остатка — отдельное внутреннее состояние, не raw null/false/[]:
  пустые созданные ветки удаляются, исходные непотреблённые пустые значения остаются.

Например, внешний список groups содержит внутренние списки, а у внутренних
элементов each=value. Источник
`groups = [[{value: {id: 7}}, {value: {id: 8}, meta: "b"}]]`
даёт у владельца обоих списков
`extra.groups = [{sourceKey: 0, remainder: [{sourceKey: 1, remainder: {meta: "b"}}]}]`.
Цепочка записей сохраняет происхождение groups/0/1/meta. Если между списками
объявлен DTO, его локальный остаток принадлежит его receiver; сквозное
выталкивание extras ребёнка родителю не добавляется.

Обычный массив с сохранёнными ключами не имеет стабильной JSON-формы: ключи 0..n−1
дают список, а единственный ключ 1 — объект. Новое представление всегда даёт список
записей и работает с обычной сериализацией массива. Оно требует явно читать
sourceKey/remainder вместо доступа extra.rows по исходному индексу; это цена
стабильной формы. Проверка формата — [followup-probe](artifacts/followup-probe.json),
не доказательство реализации самого сборщика extras.
Если у владельца списка нет receiver, автоматическое сохранение обёртки не обещается;
SDK может явно моделировать DTO обёртки с собственным receiver.

Чтение discriminator — выбор маршрута, само по себе не потребление значения:

| Режим | Куда попадают данные |
| --- | --- |
| Value, поле type не сопоставлено свойству варианта | type остаётся в локальном receiver варианта вместе с прочими немоделируемыми полями |
| Value, type сопоставлен свойству | Потребляется этим mapping, повторно в extra не попадает |
| Key, выбран known из `{known: payload, meta: value}` | payload передаётся варианту; meta сохраняется в receiver владельца списка по исходному пути |
| Key, имя known | Это сегмент пути обёртки, не отдельное значение; искусственное поле type в extra не добавляется. Для доступа к самому тегу SDK моделирует обёртку явно |
| KeepRaw | Сохраняется весь элемент, дошедший до discriminator; соседи предшествующего each сохраняются у владельца списка |
| Skip | Явное удаление исходного элемента целиком, включая обёртку; это выбранная потеря, не гарантия сохранения данных |

Эти правила требуют ledger потребления для проекций, а не только DTO-полей.
Известные повреждённые варианты по-прежнему завершаются ошибкой. Данные,
утраченные до этой границы произвольным callback, восстановить нельзя.

**Альтернатива:** удалять весь top-level ключ при любом dot-path или запрещать
любое пересечение. Первый вариант теряет данные, второй запрещает полезное
повторное представление одного значения без необходимости. Для проекций можно
требовать явный DTO обёртки; это проще для ядра, но сужает обещание автоматического
сохранения при each. Такой вариант должен явно отразиться в AS-2 и юзкейсах.
Другие варианты формы — объект с числовыми именами свойств либо список с пустыми
позициями. Они сохраняют более прямой доступ по исходному индексу, но вводят
объектный контейнер или заполнители. Не применять JSON_FORCE_OBJECT ко всему
payload: это изменит и нетронутые списки дополнительных данных.

**Проверка:** каждая строка таблицы, перестановка порядка полей, два уровня receiver,
discriminator и возврат исходного массива без изменения после гидратации.
Обязательны each + meta, Value/Key с receiver и без него, двойные проекции,
Skip/KeepRaw и сохранение исходных ключей в sourceKey. Для сериализации обязательны
плотные остатки 0/1, единственный остаток 1, отсутствие всех остатков, строковый
ключ нормализованного словаря и нетронутый неизвестный список. Отдельно проверить
ключи "1"/"01" после JSON-декодирования и рекурсивный пример двух списков:
на обоих уровнях плотный набор остатков, единственный непервый остаток и отсутствие
остатка. Формат рекурсивного примера воспроизводит
[clarification-probe](artifacts/clarification-probe.json), не сборщик extras.

### В11. Какие receiver поддерживать и как заполнить readonly

**Рекомендую:** один public receiver типа array или ?array, фактически всегда
получающий массив. Поддержать параметр конструктора с совпадающим именем и
совместимым типом, включая promotion с default `[]`; собранный массив передаётся
вместе с остальными аргументами. Для DTO без конструктора допустимо существующее
однократное заполнение public-свойства.

Для первой версии отклонять receiver, который конструктор заполняет самостоятельно
без соответствующего параметра, а также static/virtual/non-public receiver.
Это ограничение позволяет не искать свободное место для записи после конструктора.
Обычные свойства DTO продолжают использовать свой существующий fallback 029.
Не проверять правила пробным созданием DTO.

Receiver не является обычным входным полем: сочетание с входным mapping,
DefaultValue-атрибутом, Cast или Nested на нём считать конфликтом. Constructor default
не конфликтует. Исходный ключ с именем receiver сохраняется внутри собранного массива:
`{"id":7,"extra":{"future":1}}` → `extra = {"extra":{"future":1}}`, если id потреблён.
Пользовательский конструктор остаётся ответственным за свою явную бизнес-логику.

**Альтернатива:** принимать любой ArrayAccess/DTO receiver и дописывать после создания.
Это требует дополнительных преобразований, усложняет readonly и скрывает конфликт
с логикой конструктора. Для AS-2 достаточно массива.

**Проверка:** promotion, required/optional параметр, класс без конструктора,
конфликтующие атрибуты/тип/доступность, коллизия имени, constructor once.

### В12. Как receiver влияет на исходящую сериализацию

Внешний вопрос [В12-Q1](questions.md) снят 2026-09-14: исходящее представление receiver
выбирает владелец пакета.

**Решение 2026-09-14:** receiver не участвует в запросах клиента, чей набор его объявляет,
а в DX остаётся обычным свойством. Выбрана альтернатива ниже с явной передачей набора
сериализатору клиента: исключение определяется классом и набором клиента, а не
происхождением объекта. Рекомендация «сериализовать под своим именем» отклонена:
она отправляет API незнакомый ключ. Начав с исключения, явное включение можно
добавить позже без ломки. Контракт — раздел 10
[contracts.md](../../current/pln-028-declarative-dto/contracts.md).

**Рекомендую:** гидратационные правила не меняют сериализацию. Extras автоматически
не разворачиваются в корень исходящего payload. Само свойство receiver может
сериализоваться обычным образом под своим именем, как и любое другое свойство DTO.
Обещание «не flatten» не означает автоматического исключения свойства из запроса.
Если ответ нельзя отправлять обратно, SDK использует отдельную модель запроса
либо свои явные правила исходящего представления.

Трактовка AS-2.5 остаётся предметом выбора: формулировка «не означает автоматическое
добавление этих ключей» допускает чтение как запрет flatten, но может подразумевать
полное исключение мешка из запросов. Исходные материалы не закрепляют последнее
однозначно. Рекомендация здесь — первый вариант; сценарий «ответ целиком отправили
обратно, лишних ключей нигде нет» ею не покрывается. Если требуется второй вариант,
до принятия В12 нужно задать явный outgoing-контракт, работающий и для вручную
созданного DTO, а не скрытую метку происхождения объекта.

**Альтернатива:** скрыто исключать любой зарегистрированный receiver из wire body.
Тогда один объект сериализуется по-разному в зависимости от того, какой Hydrator
раньше его создал, либо serializer тоже получает внешние hydration rules.

**Проверка:** DX и wire до/после гидратации; extras не появляются в корне и не
теряются при явно выбранном представлении самого свойства.

## R5. Происхождение и доставка ошибки

### В13. Как представлять source path и missing

**Рекомендую:** сохранить текущий DTO `path`. Внутри хранить source path как
последовательность сегментов; наружу отдавать отдельную строку `sourcePath`
в формате JSON Pointer: `/data/rows/1/value/record_id`. В сегменте `~` кодируется
как `~0`, `/` как `~1`; корень — пустая строка. Это позволяет представить ключи
с точками и скобками без смешения с синтаксисом DTO path.
Формат входных From/Map/Nested путей от этого не меняется.

Дополнить путь признаком `sourcePathKind`:

| kind | Значение sourcePath |
| --- | --- |
| resolved | Точное известное расположение ошибочного значения |
| expected | Ожидаемый primary при missing; это не утверждение, что ключ существует |
| boundary | Ближайший известный вход пользовательского преобразования, без точного соответствия внутренних полей |
| unavailable | null; расположение не установлено |

При missing отдельно доступны объявленные кандидаты primary/fallback без данных.
При fallback-null путь указывает именно найденный alias. При каждом элементе списка
сохраняется исходный ключ до нормализации/Skip; DTO path продолжает использовать
прежний порядковый индекс. Поля source-диагностики добавляются совместимо: новые
необязательные аргументы исключения, сохранение при его оборачивании и в previous.

Для обычного `unwrap=data`, `items from rows`, `each=value`, `id from record_id`
ошибка второго элемента имеет DTO path `data.items[1].id` и sourcePath
`/data/rows/1/value/record_id`. Ни один префикс не добавляется дважды.

**Альтернатива:** использовать один path или неизменно печатать `a.b[1]` для обоих.
Первое ломает существующую диагностику, второе без экранирования неоднозначно
для произвольных ключей источника.

**Проверка:** aliases, null/missing, пустой корень, точки/скобки/слеши в исходном ключе,
числовые индексы, each, Key discriminator, Skip и unwrap. Новые поля заполнены только
при подключённом внешнем наборе; legacy-ошибки сохраняют прежний контекст.

### В14. Что обещать после computed, hooks, providers и произвольных casts

**Рекомендую:** точное происхождение только для операций, которыми управляет ядро:
выбор aliases, each, discriminator, unwrap и нормализация индексов.
Произвольный пользовательский callback является границей происхождения.

Ошибка самого field cast/provider относится к известному входу поля. Если callback
перестроил данные и последующая ошибка относится к внутреннему полю, указывается
ближайший известный sourcePath с kind=boundary; DTO path остаётся полным.
Например, после JsonCast содержимое строки не объявляется дочерним объектом исходного
HTTP JSON: источник — поле со строкой. У default, синтезированного при missing,
есть ожидаемый входной путь, но нет найденного исходного значения.

Пользовательский computed, BeforeHydrate и объектный `toArray()` также создают
границу; штатные identity-ветки ядра её не создают. Даже возврат равного массива
не считается доказательством соответствия путей. Present-provider, проверяющий
список, продолжает работать, но не получает автоматически обещание точных путей
внутри произвольно возвращённой структуры. Для этого подходят встроенные входные
правила 028, которые не выполняют непрозрачного преобразования.

**Альтернатива:** требовать от каждого callback таблицу соответствий или сравнивать
массивы до/после. Первое меняет все расширения, второе не устанавливает происхождение
дубликатов/вычисленных значений. Протокол явного предоставления соответствий можно
обсудить позднее; AS-1–AS-4 не требуют прослеживания произвольного PHP-кода.

**Проверка:** переименование/создание/удаление в hook, provider для missing и Present,
cast JSON-строки, ошибка с собственным суффиксом. Ни один boundary/unavailable путь
не выдаётся за resolved.

### В15. Как дать точный путь в результате и не перенести ключи ответа в лог

**Рекомендую:** `HydrationException::context()` и контекст машинного результата
содержат полную source-диагностику для вызывающего кода. Добавить отдельное
`logContext()` для автоматического логирования. Message сохраняет безопасный
DTO path; точные произвольные source-ключи в текст сообщения не вставляются.

В logContext оставлять только объявленные сегменты mapping/discriminator и
позиционные индексы настоящих списков. Остальные сегменты заменять маркером `*`.
Числовой ключ ассоциативного массива не считать безопасным индексом списка:
он также может быть идентификатором из данных. Kind точности сохраняется;
отрисованный для лога путь явно считается безопасным представлением, а не полным.
Один array_is_list после assoc-декодирования не доказывает исходный вид JSON:
при недостатке сведений о происхождении числовой сегмент также маскируется.

Обновить все автоматические потребители контекста ошибки. Сейчас
[ExecutionResultBuilder](../../../src/Pipeline/Flow/ExecutionResultBuilder.php)
использует один context и для результата, и для лога;
[RedactionPolicy](../../../src/Diagnostics/RedactionPolicy.php) не маскирует
динамические сегменты внутри обычной строки. Повторное prefix/оборачивание должно
сохранять исходные сведения о сегментах, а не пытаться восстановить их из сообщения.

**Альтернатива:** маскировать sourcePath везде. Она лишает вызывающий код точной
диагностики. Добавить raw sourcePath в существующий общий context без изменения
логирования также нельзя: это создаст новый канал вывода ключей ответа.

**Проверка:** искусственный секрет в строковом и числовом ключе; точный путь доступен
в результате, отсутствует в message/автоматическом логе, включая ошибки после
unwrap и предыдущие исключения. При `debug=false` правило не ослабляется.

## R6. Исполнение, конфигурация и кеши

### В16. Какие входы должны использовать один набор

**Рекомендую:** один экземпляр Hydrator клиента с его набором используется и для
Returns, и для hydrateCollection в пагинации, итогового DTO CompositeFlow,
финального результата continuation и повторного awaitAs для кешированного значения.
Клиент передаёт эту зависимость при сборке соответствующих сервисов/ResultHandle;
публичный доступ к reflection cache или изменение ClientInterface ради getter
гидратора не требуется. Сам перенос двух default()-вызовов на переданный гидратор
и совместимость конструкторов относятся к 030: рекомендуются последний
необязательный аргумент и fallback для прежних вызовов/чужого ClientInterface.
В 028 достаточно настроить набор у уже подключённого исполнителя; повторное
изменение конструкторов этих сервисов не входит в его объём.
Standalone forRules создаёт такой же исполнитель с теми же декларациями.
Не переносить выбор правил в MIME handler или отдельные hooks операций.

Исправление определения готовности и потери ошибок await вынесено в
[pln-030](../../current/pln-030-continuation-errors/pln-030-readme.md).
В нём выбираются Pending/Ready, переходный legacy-режим и доступ к последнему
ответу и передача исполнителя. Изоляция значений metadata исправляется отдельно
в 031 и предшествует этой передаче. В16 не определяет эти правила заново: здесь подключается текущий набор
к уже исправленным точкам преобразования и проверяется сохранение контракта 030.

Интеграция правил в await зависит от завершения 030. Нельзя направлять strict-ошибки
в старую эвристику «любое исключение означает pending». Если принятый 030 оставит
ограниченный legacy-режим, В16 должен явно определить допустимость его сочетания
с внешними правилами: миграция SDK на точный режим либо configuration-ошибка,
а не молчаливое игнорирование набора/ошибки. Остальные внутренние решения 028
могут обсуждаться до завершения 030.

Await возвращает значение либо бросает исключение согласно 030; raw() сохраняет
result-first. При повторной гидратации уже созданного DTO точный путь в исходном
HTTP JSON может быть недоступен: применяются В13–В14. Дополнительный sourcePath
не должен разрушать принятую в 030 связь ошибки с исходным ответом.

ClientConfig::with() сохраняет набор при обычном копировании, заменяет его только
при явном override; явный null отключает его у нового клиента. Уже созданный клиент
не перенастраивается. Если набор собирается в Laravel-интеграции, сборка выполняется
в provider/factory; сериализуемый framework config не обязан содержать живые объекты.

HTTP cache хранит исходный ответ: при cache hit он гидратируется правилами текущего
клиента. Новые правила не требуют нового ключа HTTP cache или хранения DTO в кеше.
Ненулевой результат response handler, raw-response и download сохраняют прежние
отдельные ветки; подключение набора не заставляет их проходить через Returns.

**Альтернатива:** каждый путь сам создаёт mapper/выбирает registry либо кешируются
готовые DTO. Это создаёт расхождения standalone/HTTP и зависимость кеша от набора.

**Проверка:** direct/Returns/sync/promise, unwrap, обе ветки пагинации, cache hit,
CompositeFlow (включая границу пользовательской агрегации), continuation
Sync/Auto/Async, awaitByToken/awaitByTokenAs, cached await/awaitAs и смена целевого
типа, ClientConfig::with(), response handler/raw/download. В await отдельно:
pending → ready, invalid ready с token и без него, лимит попыток, отсутствие
лишних запросов, сохранение исходной ошибки/ответа и границы source path.
Для обычного результата сохраняются HTTP-ответ,
result-first/throwOnErrors и отсутствие HTTP retry из-за гидратационной ошибки.
Constructor once относится к каждому вызову гидратации узла; пользовательский
withItems/AfterHydrate может создавать другие объекты по своему прежнему контракту.

### В17. Где хранить metadata и как разрешать рекурсивный граф

Исправление общего дефекта удержания значений из defaults/атрибутов предусмотрено
отдельным планом 031; интеграция metadata в 028 опирается на его завершённую реализацию.
В17 выбирает новый кеш внешних descriptors, не повторяет исправление старого.

**Рекомендую:** общий reflection cache хранит только факты класса; кеш скомпилированных
внешних descriptors принадлежит экземпляру Hydrator с одним закреплённым набором.
Сам публичный набор содержит только неизменяемые декларации. При правилах В03 одна схема
класса в одном наборе не зависит от пути, поэтому class-string допустим как локальный
ключ. Глобального кеша только по имени класса для всех наборов быть не должно.
Обработчики из В04, текущий payload, consumed paths и source stack в этот кеш не входят.
Результат пользовательского вызова profile/provider не превращается в статический
кешированный факт: их прежний жизненный цикл сохраняется согласно В04.

Сборка проверяет явно зарегистрированные descriptors и их ссылки без пробного
вызова DTO-конструкторов. Рекурсивные ссылки разрешаются через состояния
«разрешается/готово» и уже посещённые классы; `Node → Node` не является ошибкой
конфигурации. Исполнение идёт по конечным данным. Для нового внешнего пути предлагаю
лимит вложенности 512, по аналогии с защитным пределом
[DtoSerializer](../../../src/Serialization/DtoSerializer.php), с HydrationException
`hydration_depth_exceeded` и текущим путём. Считать активные DTO/list-узлы, корень —
первый уровень, соседние ветки не суммировать. Это предел рекурсии, а не норматив
скорости или размера обычного списка. Дополнительно
повтор одного PHP-объекта среди активных предков даёт `cyclic_hydration_input`.
Общий объект в двух независимых ветках не является циклом. Legacy-ограничения
глобально не изменяются этим решением.

**Альтернатива:** запретить рекурсивные DTO или рекурсивно раскрывать всё описание
при каждом вызове. Первый вариант исключает обычные деревья, второй не завершается
для рекурсивной схемы и создаёт повторную работу.

**Проверка:** два набора и перестановка их вызовов с включённым metadata cache,
конечное дерево рекурсивного DTO, цикл PHP-объектов, общая ссылка без цикла и граница
глубины. Для стоимости обхода достаточно контроля повторной компиляции и удержания
payload; произвольные временные пороги не вводятся.

## Сквозной пример для будущей приёмки

Использовать plain readonly-граф: `EnvelopeDto`, одиночный `OwnerDto`, список
`RecordDto`, массив scalar `ids` и вложенный список `matrix`. У envelope и owner
есть array receiver, у envelope — optional count с default null и required items.
DTO не содержат атрибутов и интерфейсов ApiSutra.

Один descriptor набора задаёт strict defaults; id берётся из `record_id` с fallback
`legacy_id`; owner — из `profile`; records — из `rows` через each/discriminator;
ids — list(int), matrix — list(list(string)); count запрещает входной null.
Для второго набора изменить mapping и разрешить только явное приведение ids.

Входы обеих конфигураций проверяют совпадение результатов standalone/Returns,
неиспользованные aliases в extras, неизвестный discriminator, nested/receiver
ошибки, strict cast-result, одинаковое число конструкторов, полный sourcePath
и безопасный лог. К этому примеру добавляются таблицы граничных случаев В01–В17;
одного успешного payload недостаточно для принятия контракта.

## Что переносить в план после обсуждения

В первую очередь выбрать В01–В04, В08, В11 и В13–В15: они определяют публичные
границы и структуру модели. В16 требует согласовать подключение
набора с контрактом отдельного 030. Затем закрепить таблицами остальные правила и
сквозную приёмку. В `contracts.md` должны попасть выбранные варианты, а не все
альтернативы этой дискуссии. У отклонённых предложений здесь сохраняется причина.

План 028 описывает декларативные правила; дефект await исправляется отдельным 030.

с сохранением поведения базовой версии после 030 для пользователей, которые
их не подключили. Исключения для исправления await в объёме 028 больше не нужны.

Приёмку рекомендую разделить внутри 028 на три порции: правила/strict/форма и все
входы исполнения (await после 030) → extras с проекциями → sourcePath с безопасным автоматическим

публикуется в общий лог до готовности безопасного контекста. Это порядок проверки,
а не три автоматически готовых к выпуску независимых пакета изменений.
После выбора публичных границ оформить ADR со ссылкой на contracts.md; .workflow
предусматривает этот формат, но не требует отдельного ADR для каждого вопроса.
