## CR-01: входы клиента и время жизни

В [ClientConfig](../../../src/Config/ClientConfig.php) environment по умолчанию
Production. [AbstractClient](../../../src/Core/AbstractClient.php) отключает
metadata cache только для Local/Testing и передаёт один кеш гидратору и сериализатору.

В probe один клиент без environment override сначала выполняет Returns. Изменение
state первого DTO до 73 видно во втором ответе, в элементах следующей страницы и
в финальном DTO CompositeFlow. У элементов одной страницы state тоже общий.
При Local/Testing эти же вызовы дают независимые объекты. DTO::from() для того же
класса также независим, поскольку [AbstractDto](../../../src/DataTransfer/AbstractDto.php)
использует Hydrator::default() без metadata cache. Следовательно, проблема уже
существует на обычных клиентских входах и зависит от конфигурации кеша.

[ClientRegistry](../../../src/Resolver/ClientRegistry.php) сохраняет экземпляры
клиентов и результаты их разрешения. Probe удаляет ссылку на первый DTO, затем
повторно получает клиента из реестра: изменение до 91 остаётся в следующем DTO.
Отдельно созданный клиент получает собственный объект с исходным значением.

По коду [SdkServiceProvider](../../../src/Laravel/SdkServiceProvider.php) регистрирует
реестр через singletonIf. При сохранении контейнера/клиента между операциями worker
это позволяет состоянию перейти между заданиями или пользователями. Реальный
Laravel worker в probe не запускался: доказаны удержание в одном процессе и
условия риска, а не утечка в конкретном приложении. Singleton относится к контейнеру;
он не означает общий объект между всеми процессами или независимо созданными клиентами.
Без изменяемых объектов в соответствующих defaults/атрибутах такого переноса нет.

## CR-01: args атрибутов и исходящая сериализация

Подтверждено предложение коллеги: #[Cast] удерживается в metadata вместе с args.
Каждый раз создаётся новый cast, но он получает старый вложенный объект-счётчик.
Новые вызовы дают [1, 2] при включённом кеше против [1, 1] при выключенном:

- Hydrator — при входной гидратации;
- DtoSerializer — при прямой исходящей сериализации DTO;
- RequestPartsCollector через публичный Serializer — при сборке query;
- вложенный DtoSerializer через Serializer — для wire body DTO.

Дополнительно те же последовательности воспроизведены на реальном TestClient
с окружением по умолчанию: проверены гидратированный ответ и записанные транспортом
query/body. Поэтому исходящая часть теперь подтверждена исполнением, не только кодом.

Установлены ещё две формы той же причины: массив constructor default содержит
созданный через new объект; DefaultValue.value содержит такой объект внутри массива.
Для DefaultValue прямой объект типом value не разрешён, но массив объектов допустим.
Обе формы разделяют вложенные объекты при cache on и независимы при cache off.
Исправления только верхнеуровневого object default или только создания cast
недостаточно. Поверхностное копирование массивов также не изолирует вложенные объекты.

Причина локализована в [Hydrator](../../../src/Serialization/Hydrator.php),
[DtoSerializer](../../../src/Serialization/DtoSerializer.php) и
[RequestPartsCollector](../../../src/Serialization/RequestPartsCollector.php):
производные кеши хранят результаты newInstance()/getDefaultValue(), а не только
reflection-описания. AttributeRegistry/warmup уже сохраняют ReflectionAttribute;
само существование кеша не является дефектом. Полный объём и границы описаны
один раз в 031; намеренно общие profile/registry-объекты этим планом не клонируются.

## Готовность и порядок

Порядок исправлений: **031 → подключение гидратора в 030 → await-интеграция 028**.
031 должен исправить уже действующие Returns/пагинацию/composite/serialization
самостоятельно, не ждать работ над await. Контракты 030 и решения 028 можно выбирать
одновременно с уточнением поведения 031. Общие изменения metadata в 028 опираются
на завершённый 031. План 027 остаётся отложенным.

Граница CR-01 теперь описана шире и вынесена из 030; условие о полноте его scope
закрыто на уровне планирования. Это не завершение этапа 1: у 030 ещё не выбраны
определитель готовности, переходный режим, доставка последнего ответа и публичные
сигнатуры; у 028 В01–В17 открыты. У 031 отдельно нужно закрепить границу вычисления
defaults/атрибутов и их побочные вызовы в contracts.md/acceptance.md. В12-Q1 остаётся
подготовленным, но не отправленным вопросом и не блокирует эти внутренние решения.
