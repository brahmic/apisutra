# Продуктовые юзкейсы внешних правил DTO

Приложение к [дискуссии dsc-005](dsc-005-readme.md), подготовлено 2026-09-14.
Сценарии описывают ожидаемое поведение рекомендуемых вариантов В01–В17.
**2026-09-14 владелец пакета принял их; по В12 выбрано исключение receiver из запросов**;
действующий контракт —
[contracts.md 028](../../completed/pln-028-declarative-dto/contracts.md). Описанные
возможности ещё не реализованы; при расхождении с юзкейсом действует контракт.

Источник технических правил и альтернатив — основная дискуссия. Здесь показаны
задачи, действия и наблюдаемые результаты. Таблицы настройки описывают намерение
автора SDK, а не готовый синтаксис PHP API. Условия отдельных сценариев независимы,
если явно не сказано, что используется пример UC-01.

Уточнения после [перепроверки рецензии](peer-review.md): безопасное int → float,
область повторной гидратации обработчиков, остатки each/discriminator и await.
Это обновлённые рекомендации; статус принятия решений не изменён.

После [второго разбора](followup-review.md) исправление await относится к
[030](../../completed/pln-030-continuation-errors/pln-030-readme.md), В02 рекомендует
конфликт деклараций, остатки проекций списка имеют явные sourceKey/remainder,
а уточнение исходящих extras вынесено в [В12-Q1](questions.md).

## Участники и ожидаемая польза

| Участник | Что хочет получить |
| --- | --- |
| Автор SDK | Один раз описать соответствие внешнего ответа своим публичным моделям и поддерживать его при изменениях API |
| Разработчик приложения | Вызвать метод SDK и получить предсказуемые объекты либо понятную ошибку, без ручной настройки преобразования ответа |
| Автор общей библиотеки моделей | Использовать одни DTO в SDK, обработчике событий и локальном импорте, сохраняя независимость моделей от ApiSutra |
| Сопровождающий интеграцию | Найти неверное значение во внешнем ответе и понять, где исправлять данные или правила |

## UC-01. Получить готовый граф моделей через обычный вызов SDK

**Задача.** Разработчик приложения получает отчёт: владельца, записи и их
идентификаторы. Ему нужны типизированные объекты, включая вложенные, при обычном
вызове операции SDK.

Автор моделей определяет три обычных readonly-класса. Ни один не содержит
атрибутов, интерфейсов или базовых классов ApiSutra:

| Модель | Данные |
| --- | --- |
| ReportDto | id: int, owner: OwnerDto, items: array, ids: array, count: ?int = null, extra: array = [] |
| OwnerDto | id: int, nickname: string, extra: array = [] |
| RecordDto | id: int, title: string |

Автор SDK один раз подключает набор правил при сборке клиента и указывает
ReportDto в описании результата операции. Для этого примера набор задаёт:

| Что настраивает SDK | Правило |
| --- | --- |
| Граф моделей | Строгие scalar-типы по умолчанию |
| ReportDto.id | record_id, при отсутствии — legacy_id |
| ReportDto.owner | profile → одиночный OwnerDto |
| ReportDto.items | Обязательный rows → список RecordDto; данные каждого элемента находятся в value |
| ReportDto.ids | Список int с проверкой каждого элемента |
| ReportDto.count | Отсутствие допустимо, явный null запрещён |
| ReportDto.extra и OwnerDto.extra | Приёмники дополнительных полей своего уровня |
| OwnerDto.id и RecordDto.id | user_id и record_id соответственно |
| HTTP-ответ | Извлечение содержимого data через Returns::unwrap |

Внешний сервис отвечает:

```json
{
  "data": {
    "record_id": 7,
    "legacy_id": 6,
    "profile": {"user_id": 9, "nickname": "Ada", "timezone": "UTC"},
    "rows": [{"value": {"record_id": 11, "title": "First"}}],
    "ids": [1, 2],
    "future": false
  }
}
```

**Ожидаемый результат.** В успешном результате операции находится ReportDto:

```text
id = 7
owner = OwnerDto(id: 9, nickname: "Ada", extra: {timezone: "UTC"})
items = [RecordDto(id: 11, title: "First")]
ids = [1, 2]
count = null
extra = {legacy_id: 6, future: false}
```

Пользователь SDK не регистрирует правила перед запросом. Конструктор каждого
гидратируемого узла вызывается один раз с подготовленными данными, включая extra.
Все модели остаются пригодными для использования вне ApiSutra.

**Граница.** Одной общей настройки strict недостаточно для превращения любого
plain-класса во вложенный DTO: связь profile → OwnerDto и тип элементов rows
задаются явно. Пакет не угадывает эти связи по PHPDoc.

Основание: В01, В03, В06, В07, В10, В11, В16.

## UC-02. Пережить переименование поля без изменения публичных моделей

**Задача.** Сервис переходит с legacy_id на record_id, а приложения уже используют
свойство id. Автор SDK меняет внешний mapping и сохраняет публичную модель.

Для id выбираются primary record_id и fallback legacy_id:

| Ответ сервиса | Наблюдаемый результат |
| --- | --- |
| Только record_id = 7 | id = 7 |
| Только legacy_id = 6 | id = 6 |
| Оба поля | id = 7; неиспользованный legacy_id остаётся в extra при наличии приёмника |
| record_id = null, legacy_id = 6 | Выбран record_id; для обязательного int возникает ошибка, fallback не скрывает неверное значение |
| Ни одного поля | Срабатывают правила отсутствия id; для обязательного id — ошибка |

**Ожидаемый результат.** Приложение продолжает обращаться к тому же свойству id.
Поддержка старого и нового ответа сосредоточена в адаптере SDK; модель и код
потребителя не повторяют логику выбора версии поля.

Если DTO уже использует атрибутный cast того же поля, попытка задать внешний mapping
даёт ConfigurationException по обновлённой рекомендации В02. Для перехода SDK
переносит входные правила поля в один источник либо оставляет атрибутный сценарий.
Атрибуты других полей без внешнего описания продолжают работать. Для plain DTO
из UC-01 это ограничение не мешает: их декларации целиком находятся снаружи.
Новый внешний mapping заменяет прежнюю группу primary/fallbacks целиком.

**Граница.** В одном наборе у класса одна схема. Если одна версия API использует
record_id, а другая — item_id с несовместимым значением, SDK создаёт отдельные
наборы для клиентов либо разные модели. Внешние правила базового PHP-класса
не распространяются на потомков автоматически; автор SDK связывает нужные классы
с описанием явно. Существующее наследование атрибутных профилей сохраняется.

Основание: В02, В03, В10.

## UC-03. Обнаружить изменение типов до передачи данных приложению

**Задача.** Приложение рассчитывает на числовые идентификаторы и настоящие boolean.
Если сервис вместо них присылает строки, сопровождающий хочет сразу увидеть
нарушение контракта.

Автор SDK включает строгую политику набора и объявляет типы элементов массивов.
Для каждого поля ниже действует соответствующее правило:

| Данные → модель | Ожидаемый результат без явного cast |
| --- | --- |
| id: 7 → int | Принять |
| id: "7" → int | Ошибка типа |
| active: "false" → bool | Ошибка типа |
| score: 1 → float | Принять как 1.0; числовое расширение допускается без потери значения |
| score: "1" или true → float | Ошибка типа |
| score: целый 9007199254740993 → float | Ошибка вне разрешённого диапазона; незаметное округление запрещено |
| code: "7" → int или string | Сохранить строку |
| ids: [1, 2] → список int | Принять |
| ids: [1, "2"] → список int | Ошибка у ids[1] |
| ids: [1, null] → список int | Ошибка у ids[1]; null допустим только при отдельно объявленном nullable-элементе |
| matrix: [["a"], ["b", 3]] → список списков string | Ошибка у matrix[1][1] |

**Ожидаемый результат.** При первой обнаруженной ошибке приложение получает
структурированную ошибку преобразования с расположением проблемного поля или
элемента. Неправильное значение не становится корректным только из-за неявной
конверсии PHP. Исключение для int → float ограничено диапазоном от -2^53 до 2^53
включительно; при union int|float исходный int сохраняется. Это сценарий отказа
при ошибке, а не обещание собрать все нарушения
за один проход.

**Граница.** Обычный array без описания элементов остаётся обычным массивом.
Комментарий list<int> сам по себе не включает проверку. Strict не задаёт бизнесовые
ограничения вроде положительного id или диапазона score. Исключение из общей
политики задаётся явно; отключение strict у родительского DTO не отключает её
автоматически у дочернего класса.

Основание: В03, В05, В06.

## UC-04. Различать отсутствие значения и явный null

**Задача.** В одном ответе count может отсутствовать, но присутствующий count
должен быть числом. При этом rows сервис обязан прислать даже для пустого отчёта.

Для примера UC-01 автор SDK задаёт запрет явного null у count и обязательность
rows независимо от defaults модели:

| Входное состояние | Ожидаемый результат |
| --- | --- |
| count отсутствует | count = null из default конструктора |
| count = 0 | Принять 0 |
| count = null | Ошибка; default и cast не обходят запрет исходного null |
| count = "7" | Ошибка strict-типа, если не объявлен явный cast |
| rows = [] | Успешный пустой список items |
| rows отсутствует | Ошибка required_field_missing, даже если у модели есть default [] |

**Ожидаемый результат.** Приложение различает «данных нет» и «источник нарушил
свой контракт», не разбирая исходный ответ вручную.

**Граница.** Запрет исходного null не равен запрету итогового null. Если SDK
отдельно включил преобразование пустой строки в null, count = "" может дать null
для nullable-поля. При стандартном Keep строка остаётся строкой и проходит
соответствующую проверку типа. Новые правила присутствия не включаются для всех
nullable-полей автоматически.

Основание: В07, В08.

## UC-05. Обнаружить неправильную форму объекта или списка

**Задача.** Сервис обещает одного владельца и упорядоченный список записей.
Изменение формы ответа должно стать видимой ошибкой интеграции.

| Настройка и вход | Ожидаемый результат |
| --- | --- |
| owner — одиночный объект; profile = {"user_id":9,"nickname":"Ada"} | Создать OwnerDto |
| owner — одиночный объект; profile = [{"user_id":9,"nickname":"Ada"}] | Отклонить непустой список вместо объекта |
| ids — список int; ids = {"first":1} | Отклонить словарь вместо списка |
| ids — список int; PHP-массив с ключами 0 и 2 | Отклонить разреженный список |
| matrix — список списков string; одна строка является словарём | Ошибка формы на уровне этой строки |

**Ожидаемый результат.** Ошибка указывает поле или вложенный контейнер, где форма
перестала соответствовать объявленной. Приложение может отличить пустую выборку
от неверной структуры ответа.

Если другой endpoint действительно возвращает словарь записей, автор SDK может
явно выбрать нормализацию ключей в список. Тогда приложение получает последовательные
индексы, а диагностика сохраняет связь с исходным ключом.

**Граница.** После декодирования JSON в ассоциативные PHP-массивы пустые {} и []
неразличимы. Пустой массив проходит проверку обеих форм, но создание OwnerDto
всё равно потребует его обязательных полей. Пустая форма не означает успешную
гидратацию любого объекта.

Основание: В06, В07, В13.

## UC-06. Разрешить нужное преобразование в конкретном месте

**Задача.** Один endpoint по контракту возвращает числовые идентификаторы строками.
Автор SDK хочет принять эту особенность, сохранив строгую проверку остальных полей.

Он назначает элементам ids явный SDK-cast, который переводит допустимую десятичную
строку в int. Для правил можно указать класс обработчика и параметры его конструктора:
например, один параметризованный валидатор scalar-типа применяется с аргументом int
или string, без отдельного подкласса для каждого типа. Сам валидатор не обязан
выполнять преобразование — это поведение выбранного обработчика.

**Ожидаемый результат.** Для преобразующего cast ["1", "2"] становится [1, 2].
Недопустимая строка даёт ошибку элемента. Если cast ошибочно возвращает строку
вместо int, строгая проверка результата обнаруживает это. Для cast всего списка
можно объявить проверку результата «список int», сохранив проверку элементов.

У списка объектов можно сначала извлечь value, затем выполнить itemCast,
затем создать DTO из полученных данных. Если обработчик уже вернул совместимый DTO,
пакет принимает объект без повторного вызова его конструктора.

Если обработчику самому нужна повторная гидратация, он использует предлагаемый
opt-in контракт с HydrationScope: тот передаёт вызов тому же исполнителю и набору.
Так RowCast может создавать строки DTO с правилами текущего SDK и при standalone,
где PipelineContext отсутствует. Данные после произвольного преобразования при этом
не получают автоматически точный путь в исходном ответе.

Opt-in метод вызывается также у обработчика из property Cast, Nested(itemCast:),
DefaultValue или профиля. Поэтому атрибутный RowCast может перейти на scope без
перевода самой регистрации во внешний descriptor. Вызовы его помощников тоже
должны использовать scope; оставшийся внутри помощника default не наследует набор.

**Граница.** Cast всего одиночного поля должен вернуть готовое значение. Одновременная
внешняя декларация «field Cast и затем гидратировать одиночный DTO» считается конфликтом.
Для такой предварительной обработки потребуются подготовка данных до гидратации
либо cast, возвращающий готовый DTO; отдельный singleton preCast в рекомендации
не включён. Произвольный объект с зависимостями или closure также нельзя положить
в новый набор вместо описания обработчика.
Старый обработчик с Hydrator::default() остаётся на стандартных правилах:
новые mapping/strict/extras через этот вызов автоматически не наследуются.
Для готового RawVariant без вложенной гидратации передача scope не требуется.

Основание: В04, В05, В06, В08.

## UC-07. Сохранить работоспособность при появлении нового варианта записи

**Задача.** Сервис возвращает неоднородную ленту и постепенно добавляет виды записей.
SDK знает text и image; новый poll ещё не описан моделью.

Автор SDK объявляет соответствие type → класс DTO и выбирает поведение неизвестных
вариантов с учётом публичного типа коллекции:

| Вход | Выбранная политика | Ожидаемый результат |
| --- | --- | --- |
| type = text, корректные поля | Любая | TextDto |
| type = text, неверный тип обязательного поля | Любая | Ошибка известного варианта |
| type = poll | KeepRaw, политика по умолчанию | Сохранить исходные данные элемента в коллекции, допускающей raw |
| type = poll | Skip | Исключить элемент |
| type = poll | Error | Вернуть ошибку неизвестного варианта |

**Ожидаемый результат.** SDK может заранее выбрать, отдавать ли новые данные
приложению, пропускать их или требовать обновления модели. Повреждённый известный
тип не превращается в «неизвестный», чтобы скрыть ошибку. При выборе по ключу
обёртки вместо поля type результат подчиняется тем же политикам.

**Граница.** KeepRaw несовместим с коллекцией, которая разрешает только DTO
определённых классов. Такое сочетание отклоняется как ошибка правил. Если SDK
обещает приложению собственный UnknownRecordDto, его создание остаётся явно
заданным преобразованием SDK; ядро не навязывает универсальную модель.

Основание: В09, В13.

## UC-08. Сохранить данные, которые ещё не вошли в модель

**Задача.** Автор SDK типизирует основные поля, но хочет дать приложению доступ
к новым и пока не моделируемым данным без выпуска новой версии на каждое поле.

Он назначает по одному массиву extra у отчёта и владельца. В UC-01 приложение
получает future и невыбранный legacy_id в ReportDto.extra, а timezone —
в OwnerDto.extra. Весь profile уже принадлежит дочерней модели и не дублируется
в дополнительных полях родителя.

Для списка с each=value обёртка требует отдельного учёта. Если rows[0] содержит
`value = {id: 7, future: 1}` и `meta = {revision: 2}`, рекомендуемый результат —
future у ребёнка и `extra.rows = [{sourceKey: 0, remainder: {meta: {revision: 2}}}]`
у родителя. Исходный индекс хранится в sourceKey, а созданный остаток списка
всегда является плотным списком записей. Если остаток есть только у второго
элемента, это `[{sourceKey: 1, remainder: {...}}]`, а не JSON-объект с ключом "1".
При отсутствии всех остатков созданная ветка rows отсутствует. Нетронутые
неизвестные массивы сохраняют свою прежнюю форму. Сбор только extra внутри value
не сохранил бы meta; нужны приёмники на соответствующих уровнях.

В списке списков остаток также рекурсивен. Если только второй элемент первой
группы содержит meta, приложение читает
`extra.groups = [{sourceKey: 0, remainder: [{sourceKey: 1, remainder: {meta: "b"}}]}]`.
Внешний remainder здесь — список записей внутреннего уровня. Полная форма и
принадлежность остатков при появлении промежуточного DTO заданы в В10.
SourceKey хранит доступный PHP-ключ до нормализации, после декодирования входа:
JSON-имя "1" уже превратилось в int 1, а "01" осталось строкой. Исходный JSON-тип
ключа по sourceKey восстановить нельзя; нетронутые данные не переоформляются.

Другие варианты того же приёма:

| Настройка или данные | Что остаётся доступным |
| --- | --- |
| Из profile прочитан только profile.id | Соседний profile.future остаётся в extra родителя |
| profile содержал только потреблённый id | Опустевшая из-за потребления ветка profile удаляется из остатка |
| Непотреблённые значения false, 0, null, "", [] | Все сохраняются |
| Источник содержит ключ extra | Его значение хранится внутри собранного extra под ключом extra |
| Два свойства читают один путь | Оба получают значение; в extra оно не дублируется |
| Одно свойство читает весь profile, другое profile.id | Оба чтения успешны; весь profile считается потреблённым независимо от порядка свойств |
| Discriminator Value прочитал type, но у модели нет соответствующего свойства | type остаётся в extra варианта |
| Discriminator Key выбрал known из {known: payload, meta: value} | meta остаётся у владельца списка; имя known не превращается в выдуманное поле type |

**Ожидаемый результат.** Приложение видит ещё не типизированные данные, а readonly DTO
получает полный extra через параметр конструктора. При отсутствии дополнительных
данных приёмник получает пустой массив.

**Граница.** Поддерживается один public array/?array-приёмник на DTO с подходящим
параметром конструктора либо public-свойство DTO без конструктора. Конструктор,
самостоятельно заполняющий приёмник без такого параметра, в рекомендованный вариант
не входит. Поля, которые пользовательский hook уже удалил из данных, не восстанавливаются.

Сбор extra относится к чтению ответа. По решению В12 от 2026-09-14 клиент,
чей набор объявляет приёмник, не отправляет extra в запросах: ни под своим именем,
ни развёрнутым в корень. Отчёт с `id = 7` и `extra = {future: false}` в теле запроса
даёт `{"id":7}`, а `toArray()` того же объекта сохраняет extra под своим именем.
Если приложению нужно отправить неописанные поля обратно, SDK использует
отдельную модель запроса.

Основание: В10, В11, В12.

## UC-09. Найти неверное поле именно во внешнем ответе

**Задача.** Приложение сообщает о сбое при получении отчёта. Сопровождающему нужно
понять и проблемное свойство модели, и расположение данных, присланных сервисом.

В UC-01 добавляется вторая запись. Её value.record_id содержит строку "bad":

| Сведения об ошибке | Ожидаемое значение |
| --- | --- |
| Причина | invalid_field_type |
| Путь модели | data.items[1].id |
| Путь в ответе | /data/rows/1/value/record_id |
| Точность пути | resolved — значение действительно найдено здесь |

Если сработал fallback, путь указывает выбранный alias. Если обязательное поле
не найдено ни по одному alias, доступен ожидаемый primary с признаком expected
и список объявленных кандидатов: диагностика не утверждает, что значение там было.
После пропуска неизвестного варианта или явной нормализации ключей путь источника
продолжает ссылаться на исходный элемент, даже если его индекс в DTO изменился.

**Ожидаемый результат.** Сопровождающий связывает ошибку модели с конкретным местом
полученного ответа. HTTP-ответ сохраняется в результате ошибки; включённый
throwOnErrors сохраняет предусмотренный способ доставки ошибки через исключение.
Повторный HTTP-запрос только из-за ошибки гидратации не выполняется.

**Граница.** Формат пути источника — JSON Pointer, а путь модели сохраняет прежний
формат. Они могут отличаться. Точный путь содержит расположение, а не копию
ошибочного значения или всего payload.

Основание: В13, В16.

## UC-10. Диагностировать обработанные данные и безопасно записать ошибку в лог

**Задача.** В SDK есть пользовательская подготовка данных, а часть ключей ответа
содержит идентификаторы. Сопровождающий хочет полезную диагностику без ложных
указаний на структуру ответа и без автоматического вывода этих ключей в журнал.

Если provider преобразовал JSON-строку в поле details в данные дочернего DTO,
последующая ошибка details.count сохраняет полный путь модели. Известный источник —
исходное поле details со строкой; путь не изображает count дочерним JSON-полем
исходного HTTP-ответа. Его точность обозначается boundary. Для computed и
пользовательских hooks действует такая же граница, а когда расположение неизвестно,
используется unavailable. Один лишь возврат неизменённого массива пользовательским
обработчиком не доказывает происхождение его внутренних значений.

Отдельный пример: rows является словарём с ключом account-secret, SDK явно
нормализует его в список и извлекает value. Ошибка record_id даёт:

| Получатель диагностики | Представление источника |
| --- | --- |
| Вызывающий код, контекст результата или исключения | /data/rows/account-secret/value/record_id |
| Автоматический лог | /data/rows/*/value/record_id — обозначенное безопасное представление |
| Текст сообщения | Безопасный путь модели, без account-secret |

**Ожидаемый результат.** Вызывающий код сохраняет точное расположение для разбора,
а автоматические журналы не получают динамический ключ. Числовые ключи словаря
также маскируются; обычные позиционные индексы списка могут остаться в логе.

**Граница.** Эти правила относятся к автоматическому логированию пакета.
Приложение, самостоятельно записывающее полный контекст результата, получает
именно полный контекст. Точную связь внутренних полей после произвольного PHP-кода
пакет не обещает; boundary не выдаётся за resolved.

Основание: В14, В15.

## UC-11. Использовать одинаковые модели в HTTP, событиях и локальном импорте

**Задача.** Один отчёт приходит через SDK, другой — из события, третий импортируется
из сохранённого файла. Автор приложения хочет одинаковые значения и правила ошибок.

SDK предоставляет тот же набор правил для standalone-гидратации. Обработчик
события или импорта передаёт содержимое отчёта обычным массивом/объектом и указывает
ReportDto. Ему не нужны HTTP-запрос, PipelineContext или контейнер Laravel.

**Ожидаемый результат.** Для одинакового содержимого и набора создаются одинаковые
DTO, extras и ошибки типов. Префикс источника зависит от точки входа: при Returns
он включает unwrap data, а standalone считает переданный объект своим корнем.
Извлечение отчёта из внешней обёртки события остаётся задачей вызывающего кода.

При HTTP-вызовах синхронный режим, promise, итоговая модель composite-запроса и
гидратация элементов пагинации применяют правила соответствующих моделей из того
же набора. Пользовательская агрегация composite создаёт границу точности исходного
пути. Ожидание отложенного результата отдельно описано в UC-14. Если ответ взят из HTTP-кеша,
он заново преобразуется с правилами текущего клиента; прежние DTO другого клиента
из кеша не возвращаются.

**Граница.** Ненулевой результат собственного MIME response handler завершает
свою ветку обработки и обходит Returns. Подключение набора не заставляет такие
результаты, raw-response или download проходить дополнительную гидратацию.

Основание: В01, В16.

## UC-12. Независимо обслуживать две версии API в одном процессе

**Задача.** Долгоживущий worker использует два клиента с одними PHP-моделями.
Первый принимает только числовой id, второй по контракту сервиса разрешает
числовую строку через явно заданный cast.

Автор SDK создаёт два неизменяемых набора и связывает каждый со своим клиентом:

1. Клиент A отклоняет id = "7" в строгом режиме.
2. Клиент B получает id = "7", выполняет объявленный cast и возвращает id = 7.
3. Повторный вызов A снова отклоняет строку, независимо от вызовов B и прогрева кеша.

**Ожидаемый результат.** Порядок запросов, общий класс DTO и включённый metadata cache
не меняют поведение клиента. Копия ClientConfig с другим timeout сохраняет набор;
явная замена набора или null действует при создании нового клиента. Уже созданный
клиент и глобальный standalone default сохраняют своё поведение.

Обработчики из новых внешних правил не переносят своё изменяемое состояние между
клиентами, запросами и соседними элементами: каждое применение получает свой экземпляр.
Автор SDK может параметризовать обработчик, но не рассчитывает на накопительный
счётчик внутри него как на состояние всей операции.

**Граница.** Клиенты без нового набора сохраняют прежние правила гидратации и жизненный
цикл атрибутных/profile-обработчиков. Исправления доставки ошибок await требуют
отдельного плана 030, описанного в UC-14. Подключение внешних правил не активирует
client/global/extension cast registry для гидратации. При Laravel-интеграции
набор собирается в provider/factory; гидратация не требует установки Laravel.

Основание: В01, В02, В03, В04, В16, В17.

## UC-13. Получить дерево категорий с повторяющимся типом узла

**Задача.** Сервис отдаёт каталог: у категории есть дочерние категории того же
типа. Автор SDK хочет описать CategoryDto один раз и получить конечное дерево.

Он объявляет children списком CategoryDto. Один класс может встречаться на разных
уровнях; рекурсивная ссылка в схеме сама по себе не считается ошибкой. В пределах
одного набора схема CategoryDto везде одна и та же.

**Ожидаемый результат.** Конечное дерево в допустимых пределах вложенности
преобразуется в DTO. Неверный id у потомка диагностируется с полным путём.
Повторное применение схемы не требует её бесконечного раскрытия или повторной
сборки для каждого узла.

**Граница.** Рекомендация предусматривает предел 512 активных DTO/list-уровней:
корень считается первым, каждый контейнер списка тоже учитывается. Это не лимит
512 записей и не обещание 512 поколений категорий. Превышение даёт
hydration_depth_exceeded. Цикл во входных PHP-объектах даёт cyclic_hydration_input;
один объект в независимых соседних ветках сам по себе циклом не является.
Сохранение общей идентичности DTO между такими ветками не обещается.

Основание: В03, В17.

## UC-14. Дождаться готового результата и увидеть ошибку финальных данных

**Задача.** SDK запускает длительную операцию и получает continuation token.
Приложение ждёт готовый отчёт и должно получить те же модели и проверки, что при
обычном ответе, включая повторное awaitAs для уже сохранённого результата.

SDK объявляет способ отличить pending от финала: например, появление поля data
или отдельный определитель готовности для плоского ответа. Контракт принят
и реализуется в [030](../../completed/pln-030-continuation-errors/contracts.md);
Сам гидратор клиента и совместимые конструкторы await-сервисов также относятся
к 030; перед его подключением общий дефект удержания значений metadata исправляет
[031](../../completed/pln-031-metadata-value-isolation/pln-031-readme.md).
028 затем настраивает набор у этого исполнителя. Наличие token само по себе не значит,
что отчёт ещё не готов.

| Ситуация | Ожидаемый результат |
| --- | --- |
| Pending с token, затем готовый корректный отчёт | Ожидание продолжается; финал гидратируется набором клиента |
| Финал объявлен готовым, в id неверный тип | Структурированная ошибка гидратации сразу, даже если ответ также содержит token |
| await уже вернул данные, затем awaitAs запрошен для DTO | Преобразование набором клиента без нового polling |
| Cached awaitAs обнаружил неверный тип | Сохраняется исходная диагностика; ошибка не маскируется как «результат ещё не готов» |

**Ожидаемый результат.** Приложение отличает ожидание операции от некорректных
финальных данных. Лимит polling расходуется на ожидание, а не на повторное
преобразование заведомо неверного готового ответа.

**Граница.** Это исправление ещё не реализовано: нынешний await может поглотить
ошибку, а cached awaitAs — потерять её структуру и previous. DTO с defaults может
также преждевременно завершить ожидание, в том числе при отсутствующем/null unwrap.
По [ADR-001](../../adr/adr-001-continuation-readiness.md) старая
эвристика удаляется без переходного режима: SDK объявляет `unwrap` или resolver
готовности. Await возвращает значение либо бросает `ContinuationAwaitException`
с причиной, числом попыток и последним результатом.
В16 отвечает за подключение правил; дополнительный sourcePath и его точность
после повторной гидратации определяются В13–В14 при уже исправленном исполнении.

Основание: В13, В14, В16.
