## PR-01. Входы await и доставка ошибок

[ContinuationService::tryResolveFinal](../../../src/Continuation/ContinuationService.php)
вызывает Hydrator::default() и перехватывает Throwable с результатом resolved=false.
[ResultHandle::mapCachedAwaitValue](../../../src/Result/ResultHandle.php) также
вызывает default, а при ошибке создаёт ContinuationConfigurationException без previous.
Набора 028 пока нет, поэтому его игнорирование — следствие устройства этих входов,
а не результат запуска несуществующей конфигурации.

Потеря ошибки уже воспроизводится на обычном DTO из tests/ с полем string value
и входом value=[]:

| Вход исполнения | Фактический результат |
| --- | --- |
| Прямая гидратация | HydrationException, invalid_field_type, path=value |
| Polling, в неверном ответе остаётся token | Две попытки, затем ContinuationConfigurationException о лимите; reason/path/previous утрачены |
| Polling без следующего token | Одна попытка, затем configuration-ошибка об отсутствии финала/token |
| Sync | Сразу configuration-ошибка сборки финала; polling не выполняется |
| await вернул массив, затем cached awaitAs | ConfigurationException с текстом исходной ошибки, но без её структурированных полей и previous; нового polling нет |

Следовательно, «ожидание до таймаута» — слишком широкая формулировка: в наблюдаемом
коде есть лимит попыток, а исход зависит от режима/token. Кроме того, catch относится
к попытке гидратации, не ко всем возможным исключениям сервиса.

[CompositeFlow](../../../src/Pipeline/Execution/CompositeFlow.php) уже получает
гидратор клиента через исполнителя. Его отсутствие в В16 — пробел проверки,
не третий вызов default. Пользовательская агрегация создаёт границу source path.

**Действие:** В16 и этапы 1/6 плана дополнены всеми входами. Рекомендовано определять
Pending/Ready отдельно от успешности гидратации и сохранять ошибку Ready/cached.
Просто удалить catch нельзя: старые pending без полей финального DTO тоже дают
ошибку гидратации. Для Auto/polling требуется выбрать способ определения готовности
и переход для старых деклараций. Ошибки Sync/cached — отдельные наблюдаемые изменения,
которые нужно описать при реализации. Появился продуктовый сценарий UC-14.

## PR-02. Повторная гидратация из обработчиков

[CastInterface](../../../src/Contracts/Interfaces/Casting/CastInterface.php) и
[DefaultValueProviderInterface](../../../src/Contracts/Interfaces/DataTransfer/DefaultValueProviderInterface.php)
не получают текущий Hydrator. [PipelineContext](../../../src/VO/Pipeline/PipelineContext.php)
содержит config, но не ссылку на исполнитель; standalone передаёт null. Новый probe
подтвердил оба случая для cast/provider. Декларация будущего набора в config сама
по себе проблему nullable standalone-контекста не решает.

Сохранённые [StrictListCast](../../audit/aud-006-declarative-dto/artifacts/Stubs/StrictListCast.php)
(через него RowCast) и
[ReviewChildCast](../../audit/aud-006-declarative-dto/artifacts/Stubs/ReviewChildCast.php)
действительно используют default. Готовый DTO после такой вложенной гидратации
может пройти проверку класса: повторная проверка его native-значений не восстановит
исходные строки, потерянные при приведении, mapping или несобранные extra.
Встроенная вложенность Hydrator при этом использует текущий экземпляр через $this;
проблема касается самостоятельных вызовов расширений.

Уточнение: [UnknownVariantCast](../../audit/aud-006-declarative-dto/artifacts/Stubs/UnknownVariantCast.php)
создаёт RawVariant напрямую и оставляет известный вариант штатному обработчику.
Приписывать этой конкретной фабрике вызов default неверно.

**Действие:** В04 предлагает opt-in область HydrationScope для повторных вызовов,
с неизменёнными обязательными сигнатурами старых интерфейсов. Legacy-вызов default
остаётся явной границей; UC-06 уточнён. Сохранение старого рецепта и наследование
новых правил теперь не смешиваются. Точные интерфейсы ещё предстоит выбрать.

## PR-03. Float и JSON

JSON определяет числовое значение с необязательной дробной частью, без отдельных
типов integer/float. ECMAScript сериализует конечный Number через строковое
представление. [RFC 8259, раздел 6](https://www.rfc-editor.org/rfc/rfc8259#section-6),
[ECMAScript SerializeJSONProperty](https://tc39.es/ecma262/multipage/structured-data.html#sec-serializejsonproperty).
Локально воспроизведено: JSON.stringify(10.0) → 10; PHP json_decode('10') → int,
json_decode('10.0') → float. Отклонение первого случая было бы следствием нашей
рекомендации, а не обязательным свойством JSON или AS-1.

Порог нужно формулировать точно. 2^53 представим без потери, 2^53+1 при int → float
уже округляется, а 2^53+2 снова представим точно. JavaScript safe integer и
интероперабельный диапазон из RFC ограничены ±(2^53−1). Поэтому «все большие int
неточны» также неверно.

**Действие:** В05 и UC-03 рекомендуют разрешить int → float в консервативном
диапазоне [-2^53, 2^53] включительно, отвергать строки/bool и int за границей.
Для union сначала выбирается точная ветвь; правило распространяется и на результат
cast. Исходный вариант «только PHP float» сохранён как альтернатива.
Это выбор будущего контракта, не исправление src в текущем цикле.

## PR-04. Остатки each и discriminator

[Hydrator](../../../src/Serialization/Hydrator.php) перед гидратацией ребёнка:

- each=value заменяет элемент выбранным value; соседний meta ребёнок не видит;
- Value-discriminator передаёт весь элемент, включая type;
- Key-discriminator передаёт значение выбранного ключа; сам ключ и соседи обёртки
  в локальном входе ребёнка отсутствуют.

Это подтверждено снимками child_inputs нового probe. Extras пока не реализованы:
нельзя выдавать будущую потерю meta за регрессию уже существующего receiver.
Однако прежнее предложение считать весь список потреблённым действительно оставляло
meta без места хранения и не покрывало требование сохранения данных AS-2.

**Действие:** В10 рекомендует сохранять соседей проекции в receiver владельца списка
по исходным путям; у ребёнка хранить его локальные остатки. Чтение Value-тега для
маршрутизации само по себе не потребляет поле. Для Key отдельно описаны соседи,
структурное имя варианта и отсутствие искусственного поля type. KeepRaw/Skip
также определены. Без receiver соответствующего уровня сохранение не обещается.
UC-08 и задачи приёмки дополнены. Альтернатива — обязательная модель обёртки —
остаётся вариантом с более узким автоматическим поведением.

## PR-05. Приоритеты и конфликт деклараций

[AS-3.5](../../issue/iss-002-apisutra-reuse/upstream-requirements.md) допускает
документированный приоритет либо явную ошибку конфигурации. Замечание коллеги верно
как предложение упростить первую версию. Данных, доказывающих ошибку семиуровневого
варианта или его неприемлемую стоимость, нет.

**Действие:** В02 дополнен альтернативой конфликта входных правил одного поля.
Она запрещает текущий рекомендуемый UC-02 с переопределением mapping и сохранением
атрибутного cast. Запрет только на поле не определяет конфликт class defaults и
профиля: эти границы всё равно предстоит выбрать. Рекомендация слияния пока сохранена;
ни один вариант не принят автоматически по факту рецензии.

## PR-06. Жизненный цикл и стоимость обработчиков

Один экземпляр на descriptor/корневой вызов действительно не делит состояние между
корнями и клиентами. Он делит его внутри корня между применениями; один экземпляр
на применение не делит и это состояние. Оба варианта допустимы при явном контракте.
Число созданий «элементы × поля» — возможная форма стоимости, не измерение её
значимости и не универсальная формула для всех деклараций.

**Действие:** В04 уточняет эту альтернативу и её последствия. Выбор сопровождать
проверкой stateful-обработчика и счётчика созданий; произвольного performance-порога
не вводить. Старый жизненный цикл не меняется из-за нового кеша.

## PR-07. Исходящая сериализация receiver

AS-2.5 говорит: «Сбор данных при чтении не означает автоматическое добавление этих
ключей в исходящие payload». Это не однозначная формулировка обязательного удаления
свойства extra из любого исходящего представления. В исходном фидбеке также
сохраняются отдельные инварианты Input и не обещается отправка всей модели ответа.
Подтверждения более сильного требования от коллеги в доступных материалах нет.

Новый probe проверяет объявленное public-свойство обычного DTO: serializer отдаёт
`{id: 7, extra: {future: false}}`. Это текущая сериализация свойства, не работа
несуществующего receiver. Она подтверждает практическую разницу между отсутствием
flatten и полным исключением данных из wire.

**Действие:** В12 и UC-08 явно отмечают неоднозначность. До принятия В12 нужно
выбрать трактовку, при строгом исключении — отдельный outgoing-контракт. Без такого
выбора нельзя обещать безопасную отправку всей модели ответа обратно. Самостоятельных
сообщений коллеге не отправлялось; этот отчёт не утверждает, что трактовка согласована.

## PR-08. Объём, порции приёмки и ADR

Разбиение проверки на A: правила/strict/форма и все входы, B: extras, C: sourcePath
и безопасный лог добавлено в план. Внутренний учёт происхождения нужен уже для A/B;
безопасное логирование нельзя откладывать после публикации полного sourcePath.
Порции не объявлены отдельными релизами или тремя новыми планами.

[Правила workflow](../../README.md) предусматривают ADR, но не устанавливают
обязанность создавать отдельный ADR на каждый публичный тип или предварительное
одобрение каждого вопроса. После выбора контракта ADR полезен для оснований
и последствий; детальные сигнатуры остаются в contracts.md.

Дополнительно перепроверены факты, с которыми коллега согласился: внутреннее
создание Hydrator в AbstractClient, явный null в ClientConfig::with(), хранение
status/headers/body в HTTP-кеше, два применения context() в ExecutionResultBuilder
и защитный предел 512 в DtoSerializer. Фактических расхождений здесь нет.
Предел serializer относится к активной ветке объектов, а будущий DTO/list-предел
из В17 является отдельной рекомендацией, не уже действующей общей гарантией.
