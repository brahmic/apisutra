## Отдельный дефект await

Дополнение использует ExtraDto — plain readonly-класс без родителя, интерфейсов
и атрибутов ApiSutra. При id=[] прямая гидратация даёт HydrationException с
invalid_field_type и path=id. Тот же вход через Sync теряет эти сведения и даёт
ContinuationConfigurationException. Первые probes отдельно воспроизвели polling
с token/без token и cached awaitAs. Внешних правил ни в одном случае не требуется.

В [ContinuationService](../../../src/Continuation/ContinuationService.php) дефект
совмещён с эвристикой готовности, а в
[ResultHandle](../../../src/Result/ResultHandle.php) есть независимая замена ошибки
без previous. Определитель Pending/Ready — предлагаемое средство исправления,
а не уже существующий API, который осталось подключить.

Поэтому [030](../../completed/pln-030-continuation-errors/pln-030-readme.md) получает
готовность, доставку ошибок, последний ответ и переход старого поведения.
[028](../../current/pln-028-declarative-dto/pln-028-readme.md) получает принятую базу
после 030 и подключает к ней свой набор. Инвариант 028 снова простой:
без подключения новых правил поведение базовой версии не меняется.

Порядок жёсткий именно у интеграции await: нельзя пускать strict-ошибки в catch,
который превращает их в pending. Само проектирование DTO-правил или их независимое
исполнение не зависит от готовности polling. В 030 оставлен выбор переходного
режима; один лишь перенос задачи не решает неоднозначность старых ответов.

## В02: конфликт как первый публичный контракт

У ранее допустимых конфигураций проще сохранить поведение, позднее разрешив новые
сочетания, чем менять уже выпущенные приоритеты успешного слияния. Это аргумент
в пользу конфликта в первой версии. Он не доказывает абсолютную совместимость
любого ослабления валидации: вызывающий код мог полагаться на сам факт отказа.

В02 теперь рекомендует отказ при явном внешнем правиле и входном атрибуте одного
поля; отдельно предложен отказ при внешнем описании класса с применимым
DtoHydrate/профилем. Атрибут другого поля и правила исходящей сериализации имеют
отдельные границы. Старый смешанный пример UC-02 исправлен: сохранить атрибутный
cast и внешне заменить mapping того же поля этим вариантом нельзя.

Нижние defaults и таблицу поддерживаемых параметров всё равно надо зафиксировать.
Поэтому формулировка «просто закрыть В02» пока опережает полный контракт этого
вопроса. В05 в пересмотренном варианте не получил новых возражений; он остаётся
рекомендованным кандидатом для записи в contracts.md.

## В04: способ регистрации не должен ограничивать scope

[MatrixDto](../../audit/aud-006-declarative-dto/artifacts/Stubs/MatrixDto.php)
содержит Nested(itemCast: RowCast::class).
[RowCast](../../audit/aud-006-declarative-dto/artifacts/Stubs/RowCast.php) вызывает
StrictListCast, который гидратирует коллекцию через default.
В существующем [Hydrator](../../../src/Serialization/Hydrator.php) itemCast создаётся
в списковой ветке, независимо от [BuiltinHydrationCaster](../../../src/Serialization/BuiltinHydrationCaster.php),
где вызываются property/profile casts. Provider имеет третью точку вызова.

Будущий диспетчер opt-in метода должен охватить все эти места. В04 теперь говорит
об этом прямо: наличие нового контракта обработчика определяет передачу scope;
регистрация атрибутом не мешает. Старый обработчик получает старую сигнатуру,
жизненный цикл регистрации сохраняется. Сам scope может представлять обычный
Hydrator без внешнего набора, если явно обновлённый обработчик вызван таким путём.

Новый метод только у RowCast не поможет, если внутри он по-прежнему вызывает
старый метод помощника с default. В приёмку добавлена передача scope по всей
цепочке помощников, с двумя наборами и при standalone/HTTP. Это проверка будущей
реализации, не утверждение, что scope уже существует в коде.

## В10: стабильная форма остатка

Коллега прав: [0 => metaA, 1 => metaB] кодируется списком, а [1 => metaB] — объектом.
Это воспроизведено без библиотечных преобразований. Уточнение: не любое отсутствие
элемента создаёт разреженность — удаление только хвоста может оставить ключи
0..n−1. Существенны фактические ключи оставшегося PHP-массива.

Рекомендация В10 теперь — плотный список записей с исходным ключом внутри:

```json
[
  {"sourceKey": 0, "remainder": {"meta": "a"}},
  {"sourceKey": 1, "remainder": {"meta": "b"}}
]
```

Когда остаток есть только у второго элемента:

```json
[
  {"sourceKey": 1, "remainder": {"meta": "b"}}
]
```

У списка всегда одна форма, а sourceKey сохраняет исходный int/string-ключ.
Исходные значения лежат в remainder; служебные имена не смешиваются с полями
самого остатка. За стабильность приходится платить новым способом доступа,
поэтому это явно названо рекомендацией и отражено в UC-08. Полностью пустая
созданная ветка удаляется; нетронутые неизвестные массивы не переводятся в этот
формат. Дополнительно проверены строковый ключ, false и обычная сериализация DTO.
Для будущей приёмки оставлены отсутствие всех остатков и нетронутый список.
