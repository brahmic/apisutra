## 1. Передача гидратора и совместимость конструкторов

[AbstractClient](../../../src/Core/AbstractClient.php) создаёт Hydrator с metadata
cache; оба await-входа вызывают default() без кеша. ClientInterface не предоставляет
гидратор. В самом AbstractClient пять мест создания ResultHandle и одно ленивое
создание ContinuationService. Поэтому границу разумно спроектировать один раз в 030.

Рекомендация 030 теперь конкретна: необязательный Hydrator последним параметром
обоих публичных конструкторов, явная передача из клиента, fallback для прежних
вызовов и стороннего ClientInterface. Имена и порядок старых параметров сохраняются,
getter в ClientInterface не добавляется. Это предложение подлежит фиксации
в contracts.md; совместимость прямых/именованных вызовов и всех фабричных веток
включена в матрицу. 028 настраивает правила у уже подключённого исполнителя.

### CR-01. Объектный default разделяется при включённом metadata cache

Приоритет **P1 после расширенной проверки**; прежняя оценка P2 занижала область.
Это существующий дефект клиента с окружением по умолчанию, не только условие
переноса гидратора в await. Неактивность registry не устраняет эту разницу поведения.

Plain readonly [DefaultFinalDto](artifacts/Fixtures/DefaultFinalDto.php) объявляет
`public stdClass $metadata = new stdClass()` в конструкторе. Два вызова default()
дают разные объекты. Два вызова Hydrator с включённым AttributeMetadataCache
дают один объект; после изменения первого DTO поле marker видно и у второго.
Это не проверка приватного метода: используются публичные hydrate и свойства DTO.

Причина в [Hydrator](../../../src/Serialization/Hydrator.php): getHydrationMetadata
сохраняет результат ReflectionParameter::getDefaultValue(), а buildConstructorArguments
повторно передаёт его конструкторам. Cache хранит живое значение вместо описания
default. AbstractClient включает этот кеш вне Environment::Local/Testing, поэтому
обычный тестовый клиент не выявляет различия, существующие в рабочем окружении.

Первоначальное исправление только constructor defaults в 030 недостаточно:
кешированные атрибуты удерживают объектные args/value по той же причине.
Полный объём и новая приёмка вынесены в 031, включая все три преобразователя.
Поверхностный clone не эквивалентен новому вычислению выражения и не является
предлагаемым решением. Жизненный цикл намеренно общих registry/profile обработчиков
не меняется автоматически; границы В04 остаются отдельным вопросом.

## 2. Ложная готовность с defaults и unwrap

Через публичный Auto/awaitFromStartResult передан промежуточный payload
`{operationToken: "synthetic-token", status: "pending"}` без полей финального DTO.
Проверены три случая: unwrap не объявлен; объявлен unwrap=data, но data отсутствует;
объявлен unwrap=data при data=null. Все возвращают DTO со значением value="default",
без HTTP-запросов. Обозначение pending здесь задаёт смысл синтетического протокола;
текущий пакет не знает этого критерия и не читает status автоматически.

[ContinuationService::applyUnwrap](../../../src/Continuation/ContinuationService.php)
возвращает весь payload через `unwrapped ?? data` и при missing, и при null.
Таким образом, прежнее заключение «по коду» теперь имеет прямое воспроизведение,
в том числе при объявленном unwrap. Приёмка 030 включает все три случая;
старый unwrap нельзя задним числом превратить в определитель готовности без
явного переходного контракта. Границы выбранного legacy-режима проверяются отдельно.

## 3. SourceKey после JSON-декодирования

Подтверждено: JSON-имя "1" при assoc=true становится PHP int-ключом, "01" остаётся
строкой. Более того, объект с ключами "0"/"1" и список могут дать одинаковый PHP
массив. Это не только потеря различия пустых `{}`/`[]`.

В07/В10 теперь обещают сохранить доступный PHP-ключ после декодирования и до
нормализации списка. SourceKey=1 не доказывает, был ли это ключ словаря или индекс.
Текст JSON Pointer не меняется. В15 уточнён: одного array_is_list после декодирования
недостаточно, чтобы признать динамический числовой ключ безопасным для лога;
при неизвестном происхождении применяется маскирование.

## 4. Двойные проекции

В10 теперь задаёт рекурсивную форму. Остаток объекта — карта полей; созданный
остаток проецируемого списка — плотный список записей sourceKey/remainder;
remainder элемента может сам быть таким списком. Нетронутые значения сохраняются
без переоформления. Отсутствие остатка не отождествляется с raw null/false/пустым
контейнером. При промежуточном DTO сохраняется принадлежность его receiver.

Для списка списков записан конкретный пример и сохранена проверка сериализации
двух уровней записей. Будущая приёмка дополнена плотными/неплотными остатками на
каждом уровне и отсутствием остатка. Продуктовый UC-08 согласован с этим описанием.

## 5. Атрибуты и условия перехода к коду

Текущая входная metadata перечисляет From, Map, Nested, Cast, DateTimeFrom,
EmptyStringAsNull, DefaultValue. To/DateTimeTo относятся к исходящему преобразованию;
Map участвует в обеих сторонах. В02 теперь перечисляет их явно, отделяя классовые
DtoHydrate/профили. Reflection подтверждает отсутствие классовых атрибутов
у AbstractDto и AbstractResponseDto. Нижние defaults против профильных casts
по-прежнему требуют конечной таблицы и решения, а не только запрета пересечения.

Условия готовности по порциям зафиксированы в
[плане 028](../../current/pln-028-declarative-dto/pln-028-readme.md#приёмка-и-проверки):
A — В01–В09/В16–В17, B — В10–В11 с отдельной зависимостью исходящего В12/AS-2.5,
C — В13–В15. В каждой порции нужны выбранные contracts/acceptance и публичный ADR;
await-интеграция A ждёт реализации 030, одного его контракта недостаточно.

030 не имеет внешних вопросов или зависимости от 028; после четвёртой проверки
его подключение исполнителя и завершение ждут реализации 031. Граница metadata
вынесена туда, а передача исполнителя осталась в 030. Контракты 030 можно выбирать
одновременно с внутренними решениями 028. [В12-Q1](questions.md) остаётся
подготовленным, не отправленным и без ответа: он не блокирует эти внутренние
решения, но не позволяет принять исходящее требование AS-2.5. Рецензия не содержит
ответа адресата на этот вопрос и не заменяет выбор владельца пакета.
