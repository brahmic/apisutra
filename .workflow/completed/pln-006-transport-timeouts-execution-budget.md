## Цель и основание

AS-01 и часть AS-03 из [issue/001](../issue/001/technical-specification.md), после
[безопасных повторов](../completed/pln-005-safe-retries-stream-replay.md).

Настройки SDK должны ограничивать фактический HTTP-вызов. Общий бюджет должен
учитывать время выполнения и не разрешать очередную отправку или ожидание за его
пределами. Сохранить zero-config: действующие значения по умолчанию, автоматическое
разрешение настроек и отсутствие обязательных объектов часов, бюджетов или адаптеров
для пользователя штатной интеграции.

## Объём и границы

Входит:

1. Разрешение timeout/connectTimeout и передача в transport типизированными опциями.
2. Реальное применение таймаутов хотя бы в одном штатном транспорте; явная проверка
   поддерживаемых возможностей, сохранение standalone-ядра.
3. Deadline одного выполнения на монотонных часах, включая начальную авторизацию,
   HTTP, request delay, rate-limit wait, backoff, Retry-After и ожидание refresh lock.
4. Наследование оставшегося бюджета дочерними запросами без его перезапуска.
5. Однозначный результат исчерпания бюджета, сохранение контекста и регрессии.

Не входят настоящий параллельный async, новый планировщик задач, процессное прерывание
произвольного PHP-кода, redesign rate-limit store/атомарности, новый протокол auth refresh,
потоковые download/sink и новые правила redirects. Await/polling с многими независимыми
выполнениями и batch как целое не получают нового общего таймаута в этом этапе.
Публичные настройки batch/await не расширять; их дочерние запросы соблюдают собственные
бюджеты и уже переданный родительский deadline, если он есть.

## Согласованный контракт

2026-09-12 пользователь принял рекомендации по D1–D3 и поручил оформить план
(«Отлично, делай план»). Согласованы ошибка конфигурации при неподдерживаемом таймауте,
окончательный timeout при исчерпании бюджета и сохранение дефолтов 30/10 секунд
с необязательным общим бюджетом. Технические детали ниже описывают способ реализации;
существенные отклонения от этих правил требуют отдельного согласования.

### D1. Транспорт не поддерживает таймаут

При необходимости HTTP и невозможности применить эффективный лимит
возвращать configuration_error до отправки, с указанием транспорта и неподдерживаемого
параметра. Это касается и ненулевых дефолтов: обещать лимит, который не выполняется,
нельзя. Не вводить переключатель молчаливого игнорирования.

Штатная интеграция должна автоматически выбирать реализацию, поддерживающую её дефолты.
Пользователь не обязан выбирать адаптер или отдельно включать поддержку таймаутов.
Для Guzzle обеспечить передачу per-request options через соответствующий адаптер,
без изменения глобального клиента и пользовательского набора middleware. Сохранить
http_errors=false и allow_redirects=false, чтобы 4xx/5xx и redirects не сменили семантику.
Не добавлять обязательную зависимость Guzzle HTTP Client в standalone-ядро.

PSR-18 сам по себе не имеет per-request timeout options. Для произвольного PSR-18
клиента нужен адаптер с явной поддержкой или явно выбранный режим без SDK-лимитов.
Если timeout=0, connectTimeout=0 и deadline отсутствует, обычный PSR-18 путь допустим;
его собственные ограничения остаются в ведении HTTP-клиента. Это миграционное изменение
для существующих пользовательских транспортов с ненулевыми дефолтами.

Сначала выбрать минимальное расширение текущей сборки HttpTransport; не требовать
переключателя адаптера от пользователя обычного поддерживаемого транспорта. Для
неизвестных handlers, включая Guzzle без поддержки connect timeout, не заявлять
возможность на основании одной лишь проверки instanceof. Конкретный механизм
проверки capability определить до реализации адаптера и покрыть контрактными тестами.

### D2. Бюджет исчерпан или требуемое ожидание в него не помещается

Завершать выполнение ошибкой timeout с диагностической причиной
execution_deadline_exceeded и стадией остановки. Не начинать ещё один HTTP-вызов,
auth refresh или полное ожидание. Если Retry-After/обязательная задержка не помещается
в остаток, завершаться сразу; не ждать сокращённый интервал и не отправлять раньше
разрешённого сервером срока.

Последний реальный HTTP-ответ, например 503, сохраняется для диагностики с исходными
status/headers/body; первичная причина остановки — бюджет. Не выдавать прошлый ответ
за результат несостоявшейся следующей попытки. Сохранить исходное исключение в цепочке,
если оно было. Перед первым HTTP ответ отсутствует; синтетический ответ не создавать.

Если транспорт вернул ответ после deadline, проверка на границе обнаруживает превышение:
ответ сохраняется, но результат не становится успехом и не записывается в кеш как успех.
Timeout отдельной попытки и исчерпание всего бюджета различать диагностически:
первый может допускать безопасный retry, второй всегда окончателен для этого выполнения.
throwOnErrors меняет доставку ошибки, не её смысл; sync, promise API и batch-составляющие
используют ту же классификацию.

### D3. Дефолты, единицы и область бюджета

Сохранить timeout=30 и connectTimeout=10 секунд; 0 означает отключение
соответствующего SDK-лимита, отрицательные значения запрещены на всех уровнях.
timeout ограничивает одну HTTP-попытку целиком; установление соединения входит
в этот интервал. Дефолты 30/10 не означают суммарное ожидание 40 секунд.
Для runtime и атрибута отсутствие/null означает наследование соответствующего поля.
Разрешать поля независимо: runtime → атрибут запроса → ClientConfig с его дефолтами.
Например, withTimeout(5) меняет HTTP timeout, но не обнуляет унаследованный connect timeout.

Внутри SDK использовать миллисекунды/монотонный deadline; существующие публичные
параметры в секундах не переименовывать и не менять их единицы. Остаток менее секунды
передавать транспорту с доступной точностью. Не округлять положительный остаток до
безлимитного 0; если остаток меньше минимального поддерживаемого кванта, завершить
бюджет вместо увеличения доступного времени. Проверять переполнение при конвертации.

Общий бюджет оставить опциональным: существующий RetryConfig.totalTimeoutMs=null
не вводит новый конечный лимит на всё выполнение. Не вычислять общий бюджет
автоматически из числа попыток и их таймаутов. Не добавлять обязательную настройку
и второй конкурирующий totalTimeout в ClientConfig в этой поставке. attempts=1 позволяет
задать общий бюджет без обычных повторов. withoutRetry отключает повторы, но не отменяет
уже заданный общий бюджет; resolve бюджета отделяется от resolve включения retry.

Бюджет начинается на входе в выполнение pipeline, до начальной авторизации и отправки,
и проверяется перед завершением успехом. Дочерний запрос наследует абсолютный deadline
родителя; собственный более короткий бюджет может его сократить, но не продлить.
Независимые вызовы одного клиента получают независимые сроки. timeout=0 не отменяет
общий deadline: HTTP-попытка всё равно ограничивается остатком.

Произвольный hook, валидатор, cache-store или пользовательский transport нельзя жёстко
прервать переносимым синхронным PHP-кодом. Проверять бюджет до/после таких границ;
превышение обнаруживается после возврата управления. Фактическое прерывание HTTP
обеспечивает поддерживающий его транспорт. Эту границу гарантии описать явно.

## Минимальный поток и компоненты

1. Resolver строит эффективные timeout/connectTimeout и отдельно исходный totalTimeoutMs.
   Immutable transport options в PreparedRequest сохраняются при with/auth/header-копиях.
   Метаданные не должны неявно менять параметры общего HTTP-клиента.
2. Контекст выполнения получает внутренний бюджет с абсолютным монотонным deadline.
   Часы и sleeper внедряются через существующую сборку; в обычном использовании
   создаются автоматически. Для тестов — управляемые clock/sleeper без реального сна.
3. Единая операция ожидания проверяет доступный бюджет до/после sleep. Убрать прямые
   sleep/usleep из DelayApplier и RateLimiter; учитывать backoff встроенного RetryHandler,
   Retry-After и ожидание auth lock. TTL общего store и HTTP-date используют календарное
   время; монотонные отметки не записываются в межпроцессное хранилище.
4. После всех предварительных ожиданий непосредственно перед HTTP пересчитать остаток.
   Лимит попытки = min(положительный timeout, остаток бюджета); 0 не участвует как лимит.
   Connect timeout также ограничен доступным временем попытки. Проверять capability
   с учётом полученной точности и не терять ограничения в custom retry-handler пути.
5. После HTTP и стадий pipeline повторно проверить бюджет. Обновлять последний
   HTTP-контекст честно, не выполнять retry после окончательного deadline failure.
   AuthHandler обязан пробрасывать исчерпание общего бюджета из refresh-запроса,
   а не считать его обычным неудачным refresh и продолжать цикл.

Сохранить существующие сигнатуры TransportInterface и RetryHandlerInterface по возможности.
При расширении возможностей предпочтителен дополнительный контракт с ясной проверкой;
не маскировать несовместимость собственных реализаций автоматически. Тестовые транспорты
явно моделируют принятие опций, не объявляются доказательством реального сетевого timeout.

## Реализация и проверка — 2026-09-12

Реализован согласованный контракт D1–D3. Публичные настройки сохраняют секунды,
`TransportOptions` передаёт миллисекунды и абсолютный `ExecutionBudget`. Проверка
capability вынесена в `TimeoutAwareTransportInterface` / `HttpClientOptionsInterface`;
неподдерживаемый активный лимит завершается до HTTP. Plain PSR-18 без SDK-лимитов
сохраняет прежний путь. `GuzzleHttpClient` владеет известным cURL handler; автоматическая
Laravel-сборка и `HttpTransport::createDefault()` используют его. Произвольный Guzzle
handler не подменяется: существующий middleware stack требует своего явного адаптера.
Guzzle HTTP Client и ext-curl не добавлены в обязательные зависимости ядра.

Deadline создаётся при входе в pipeline и независимо от включения retry. Встроенные
ожидания используют единый sleeper и бюджет; адаптер пересчитывает остаток после
ожиданий custom retry handler. HTTP-date Retry-After использует календарные часы,
сам бюджет — монотонные. Исчерпание не ретраится, поздний ответ не становится успехом,
исходное исключение и доступный HTTP-ответ сохраняются также при throwOnErrors.

Обнаруженный обход наследования через batch устранён: `ContextualClientInterface`
передаёт parent/role/traceId при вложенной отправке. Composite/depends-on используют
его автоматически; основной depends-on HTTP наследует бюджет после зависимостей.
Независимый batch не получает нового общего таймаута. Пагинация и результат остаются
в существующем resolver. Новый контракт не обещает параллельный I/O.

Пределы гарантии сохранены: произвольный PHP-код обнаруживает превышение на границах,
его начатые побочные эффекты не откатываются. Синхронный HTTP прерывает cURL. Await,
