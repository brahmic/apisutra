## Объём этапа

1. Отделить причину повтора от разрешения повторять операцию и возможности повторить тело.
2. Дать SDK провайдера и отдельному выполнению явный способ разрешить/запретить повтор.
   Сам по себе Idempotency-Key не подтверждает серверную дедупликацию.
3. Восстанавливать исходную позицию seekable-тела перед дополнительной отправкой;
   отказывать в повторе non-seekable тела без скрытого чтения в память.
4. Исправить число попыток, отключение retry и сохранение настроек при overrides.
5. Упорядочить backoff и Retry-After, использовать подменяемое ожидание.
6. Добавить регрессии, документацию о совместимости и запись changelog.

Общий deadline, передача per-attempt timeout до HTTP-клиента и ограничение всех ожиданий
оставлены следующему совместному этапу AS-01/AS-03. Здесь сохраняется totalTimeoutMs
при overrides, но это не объявляется полноценным соблюдением бюджета времени.

Также не входят: настоящий параллельный async, новая redirect/origin policy, потоковые
download/sink и binary upload без материализации, фабрики повторяемых потоков,
автоматическая буферизация, переработка multipart-полей, генерация нового протокола
серверной идемпотентности. Полные AS-03 и AS-08 этим планом не закрываются.

## Согласованный контракт

2026-09-12 пользователь согласовал базовые правила D1 и решения D2/D3 в переписке.
Для D1 дополнительно согласовал политику в конфиге клиента с приоритетом атрибута
и эквивалентность отсутствующего safe и явного null (ответ «Согласен»).
Требование пользователя: zero-config, без новых обязательных настроек.

### D1. Какие операции разрешено повторять

При включённом retry стандартная политика разрешает GET, PUT и DELETE;
POST и PATCH требуют явного подтверждения безопасности конкретной операции.
Для любого метода можно явно запретить повтор. Не добавлять новые HTTP-методы в enum.

Разрешение не включает retry самостоятельно и не отменяет лимит попыток. Обычная
RetryConfig без изменения политики, withRetry(attempts), Retry без признака безопасности, shouldRetry и
RetryableException задают настройку/причину повтора, но не подтверждают безопасность POST.
Наличие Idempotency-Key или существующего Idempotent также не считается подтверждением.
Провайдер объявляет разрешение только при гарантии идемпотентности операции либо
поддержке сервером дедупликации по ключу.

Согласованный API: опциональный `safeMethods` в RetryConfig на уровне
клиента, по умолчанию GET/PUT/DELETE; `safe: ?bool = null` в атрибуте Retry.
Два уровня: конфиг клиента → переопределение на запросе. Встроенный список —
значение по умолчанию самого конфига, а не отдельный уровень настройки.
`safe: true` разрешает операцию, `safe: false` запрещает, null наследует политику.
Отсутствующий аргумент safe эквивалентен явному null. При отсутствии всего атрибута
безопасность также определяется конфигом клиента.
Список клиента заменяет стандартный. Пустой список запрещает повторы операций
без разрешающего атрибута. Добавление POST/PATCH означает явное подтверждение
безопасности этих методов для данного SDK-клиента; исключения задаются на запросах.

Без настройки действует встроенная политика; `new RetryConfig()` не требует новых
аргументов. Отдельный объект политики и runtime withRetrySafety пока не нужны.
Старые сигнатуры вызова сохраняются. При слиянии с атрибутом не терять safeMethods.
Безопасность разрешать независимо от включения общих retry, в том числе для auth retry.
Атрибут не обходит отключение повторов, лимит попыток или невозможность восстановить тело.

### D2. Управляющие и авторизационные повторы

Согласовано пользователем 2026-09-12 («ок»): проверять безопасность операции и воспроизводимость тела перед каждой
дополнительной отправкой, в том числе после RetryableException и 401. Управляющее
исключение не обходит запрет операции или исчерпание попыток.

`attempts` — максимум основных HTTP-попыток с учётом первой. `withoutRetry()` и
`#[Retry(enabled: false)]` отключают общие повторы, включая управляющие. Runtime
может явно переопределить атрибут. Auth retry сохраняет отдельный существующий
лимит и настройку authRetryOn401; withoutRetry его самостоятельно не отключает,
но проверки безопасности операции и тела применяются и к нему.

Это означает изменение поведения POST после 401: для дополнительной отправки
потребуется явное разрешение безопасности. Исключения из проверок для auth retry
не вводятся. Обнаружение реальной возможности refresh, исключение
повтора с неизменяемым API key и общий временной бюджет auth — следующий этап.

### D3. Невозможность восстановить тело

Согласовано пользователем 2026-09-12 («согласен»): разрешить первую отправку non-seekable тела, запретить дополнительную
и сохранить исходный HTTP-ответ/исключение через действующий error mapping.
Добавить доступную в диагностике причину отказа в повторе, не записывая тело или
секреты. Отказ не должен подменять service_unavailable на connection_failed.
Управляющее исключение при невозможном повторе остаётся исключением; не превращать
его в молчаливый успех. Точный способ представить диагностическую причину выбрать
из существующих audit/result-механизмов до введения нового публичного типа.

### Восстановление тела

Снимок позиции делать для фактически подготовленного stream перед первой HTTP-отправкой,
после подготовки, beforeSend и auth. Начальная позиция может быть ненулевой; нужен
seek к сохранённой позиции, а не безусловный rewind в 0. Для строки повторно передаются
те же байты. Для multipart сохраняются состав, boundary и соответствующий Content-Type.

Проверять seekability и ошибки tell/seek; отказ восстановления останавливает повтор
до HTTP и до retry-ожидания. Не закрывать переданный пользователем поток. SDK не
гарантирует неизменность содержимого файла, изменяемого извне во время выполнения.
Замена stream пользовательским обработчиком не должна наследовать позицию старого
потока или обходить проверку воспроизводимости; проверить этот случай отдельно.

### Ожидание и настройки

Первая попытка выполняется без retry-backoff. Первый повтор использует baseDelay;
затем применяется выбранная стратегия и jitter в пределах maxDelay. Явный request
delay и rate limit сохраняют своё назначение.

Для разрешённых повторов 429 и 503 учитывать Retry-After: неотрицательные целые
секунды или HTTP-date. Дату в прошлом трактовать как нулевое ожидание; отрицательные,
дробные и некорректные значения игнорировать. Защититься от переполнения числа секунд.
Ожидание равно max(backoff, Retry-After), а не сумме; maxDelay ограничивает backoff,
но не разрешает отправить запрос раньше серверного срока. После финальной попытки,
при запрете операции или тела ожидания нет. Нулевое ожидание не вызывает sleeper.

Убрать прямой usleep из встроенного RetryHandler, переиспользовать SleeperInterface;
для HTTP-date предусмотреть подменяемый источник текущего времени. Не обещать
неблокирующее выполнение от одной лишь инъекции sleeper. Сохранить работу собственного
RetryHandlerInterface; явно разделить обязанности встроенного и пользовательского
handler, не добавлять двойное ожидание и не менять его сигнатуру без необходимости.

При withRetry(attempts) сохранять остальные настройки, включая totalTimeoutMs и
retryExceptions. Для атрибута сохранить заданные им параметры; клиентские параметры,
которых нет в атрибуте, не терять. Runtime-опции не должны менять соседние executions.

## Приёмка и проверки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Retry не настроен; attempts=1; общие повторы выключены | Одна основная попытка, без retry-ожидания; auth проверяется отдельно |
| GET с attempts=3 и постоянным 503 | Три основных вызова, два ожидания; итог service_unavailable |
| POST/PATCH без разрешения, 503 или сетевой сбой | Один вызов; нет retry-ожидания |
| Явно разрешённый POST; явно запрещённый GET | Разрешение и запрет работают независимо от причины повтора |
| PUT/DELETE; shouldRetry; RetryableException; auth 401 | Контракт D1/D2 соблюдается без обходов и лишних попыток |
| Seekable stream, включая ненулевую позицию и multipart | Полные исходные байты одинаковы во всех попытках; потребитель читает getContents без rewind |
| Non-seekable, ошибка tell/seek, замена stream | Нет второй неполной отправки и лишнего ожидания; причина отказа доступна |
| Пустой файл и строковое тело | Пустой файл допустим; строка не меняется между попытками |
| Retry-After 429/503, дата, invalid, overflow | Проверяемое ожидание max, без реального сна, первой/финальной паузы |
| Runtime/атрибуты, enabled=false | Определённые приоритеты; totalTimeoutMs и остальные параметры сохранены |
| safeMethods клиента и safe атрибута | Отсутствующий safe и null эквивалентны; отсутствие атрибута наследует конфиг; приоритет true/false, пустой список, сохранение при overrides и применение к auth retry |
| Idempotency key и независимые executions | Стабильность внутри выполнения; отсутствие утечки ключа/настроек между вызовами |
| raw/resolved/dataOrFail, throwOnErrors, promise API, batch | Одинаковые безопасность, число отправок и смысл ошибки |

## Результат реализации — 2026-09-12

Согласованные D1–D3 реализованы. Новых обязательных настроек и runtime-переключателей
безопасности нет. Добавлены safeMethods клиента, nullable safe атрибута, общий контроль
дополнительных отправок и восстановление тела. Причина отказа доступна в контексте
ошибки как retryRefusalReason и в warning-логе. Исходный HTTP/transport failure сохраняется.

Встроенное ожидание объединяет backoff и Retry-After через максимум. Интерфейс собственного
RetryHandler не изменён; собственный handler сохраняет ответственность за свой backoff,
pipeline отдельно выдерживает серверную задержку. Это ограничение описано в guide.
Для HTTP-date добавлен подменяемый источник времени; числовое переполнение отклоняется
как некорректный Retry-After. Полный deadline не объявляется реализованным.

По регрессиям дополнительно исправлены два дефекта в пределах критериев плана:

- Multipart с вложенным файлом, уже прочитанным до ненулевой позиции, менял байты
  после перемотки общего потока. Подготовка части теперь сохраняет её начальное смещение;
  повтор передаёт тот же диапазон и соответствующую длину.
- Автоматический idempotency key вызывал отсутствующий у AbstractRequest метод toArray.
  Ключ теперь состоит из 32 случайных байт в hex, генерируется один раз на выполнение,
  сохраняется между попытками и не заменяет переданный пользователем ключ.

Проверки:

- Первые регрессии до исправления: 10 падений. Отдельный тест ненулевой позиции файла
  затем воспроизвёл различающиеся multipart-байты в двух вариантах; после исправления проходит.
- Профильный набор retry: 99 тестов, 297 assertions; 92 passed и 7 с прежними deprecation.
- `composer test -- --compact`: 942 теста, 2712 assertions; 904 passed, 38 с прежними
  deprecation, без падений, 6.17 s. Исходная версия имела 875 тестов.
- `composer dump-autoload --optimize --strict-psr`: успешно, 4894 класса.
- [Standalone retry smoke](../../tests/Support/standalone-retry-smoke.php) выполнен
  в отдельной копии с --no-dev зависимостями. Проверяет стандартный запрет POST,
  восстановление multipart с ненулевой позицией, отказ non-seekable и max ожиданий.
  Laravel и Guzzle HTTP Client отсутствуют; PSR-18, PSR-7 и promises используются из production-зависимостей.
- Синтаксис изменённых/новых PHP-файлов, относительные ссылки и `git diff --check` проверены.

Обновлены guides retry, files, requests, attributes/behavior, client-config/retry и changelog.
Зависимости, версия пакета и исходные материалы issue/001 не менялись. Выбранный объём
завершён; транспортные таймауты, полный deadline, auth refresh capability и остальные
границы этапа выше остаются открытыми для следующей работы.
