## Что требуется зафиксировать на этапе 1

| ID | Решение | Почему нельзя оставлять на усмотрение отдельных веток реализации |
| --- | --- | --- |
| R1 | Публичное подключение набора, конфликты источников и нижние defaults | После второго разбора рекомендуются конфликты вместо семи уровней; таблица параметров/defaults и публичные сигнатуры ещё требуют фиксации. |
| R2 | Strict для float, union, literal bool, mixed, nullable-элементов и результата cast; жизненный цикл и scope cast/provider | Выключить safe auto-cast недостаточно. Требуется выбрать безопасное int → float; standalone-контекст null не передаёт текущий набор повторной гидратации обработчика. |
| R3 | Object/list, проверка исходного null до нормализации/default, явное присутствие коллекции; сочетание external cast и nested-правила | У старого пути Nested сильнее Cast; явный Cast пропускает нормализацию пустой строки. Внешняя кардинальность не должна повторно угадываться по ReflectionProperty или данным. |
| R4 | Consumed paths, receiver и readonly; остатки each/Value/Key и трактовка outgoing | Кроме parent/leaf и aliases, нужно сохранить непереданные ребёнку части обёрток и определить судьбу discriminator. Запрет flatten ещё не обещает полного исключения receiver из исходящего запроса. |
| R5 | Формат и полнота source path после each, discriminator, переиндексации, missing и преобразований; отдельное безопасное представление для автоматических логов | Изменение структуры в computed/hook/cast может лишить внутренний путь соответствия исходному HTTP JSON. | R6 | Returns, пагинация, composite, continuation и cached awaitAs; конфигурация и интеграция контракта 030 | Два await-входа требуют подключения набора. Критерий Pending/Ready, исправление доставки ошибок и переход старого поведения вынесены в 030. |

Рекомендуемый минимальный результат этапа 1: конкретные сигнатуры и один сквозной

## Подтверждённые точки интеграции

- [AbstractClient](../../../src/Core/AbstractClient.php), конструктор: Hydrator
  создаётся внутри клиента; [ClientConfig](../../../src/Config/ClientConfig.php)
  вручную перечисляет поля при `with()`. Предложение о подключении через конфигурацию
  и standalone-вход сосредоточено в В01/В16
  [dsc-005](../../discussion/dsc-005-declarative-dto-contracts/dsc-005-readme.md).
- [Hydrator](../../../src/Serialization/Hydrator.php): metadata с ключом
  `<class>:hydrator` сейчас содержит атрибуты, reflection и вычисленные constructor
  defaults. Объектные defaults и args атрибутов разделяются при включённом кеше —
  общий дефект устраняется в 031, включая сериализаторы. В этом общем описании
  класса нельзя хранить результат слияния конкретного внешнего набора.
  Разрешённые правила и их кеш должны принадлежать экземпляру набора/исполнителя.
- [DtoHydrationProfileResolver](../../../src/Serialization/DtoHydrationProfileResolver.php)
  создаёт профиль и его registry при разрешении. Неизменяемость декларации сама
  по себе не изолирует mutable cast/provider; это требует явного контракта жизненного
  цикла. Отдельно проверить два набора для одного DTO при включённом metadata cache.
- [BuiltinHydrationCaster](../../../src/Serialization/BuiltinHydrationCaster.php)
  и [HydrationValueValidator](../../../src/Serialization/HydrationValueValidator.php):
  strict-путь должен отключить недопустимые неявные преобразования и проверять результат до
  reflection-вызова конструктора/присваивания. Текущую permissive-проверку сохранить
  для legacy. Допуск int → float отдельно выбирается в В05.
  У promoted-параметров и обычных свойств разные границы проверки.
- [NestedObjectTypeResolver](../../../src/Serialization/NestedObjectTypeResolver.php)
  восстанавливает кардинальность атрибутного пути из PHP-типа. Для внешнего правила
  object/list кардинальность уже известна: общая модель должна передавать её явно,
  используя существующее выполнение гидратации, а не создавать второй mapper.
- [ArrayPath](../../../src/Support/ArrayPath.php) и
  [PathResult](../../../src/Support/PathResult.php): выбранные сегменты, alias,
  исходное состояние и факт потребления нужны до потери исходных ключей.
  Общий utility используется за пределами DTO; менять его текущий публичный
  результат несовместимым образом ради гидратации не требуется.
- [RequestFlowRunner](../../../src/Pipeline/Flow/RequestFlowRunner.php) запускает
  BeforeHydrate до unwrap; Hydrator запускает computed. Для преобразованных/созданных
  значений нельзя выдавать предполагаемый source path за точный путь HTTP-источника.
- [HydrationException](../../../src/Exceptions/Serialization/HydrationException.php)
  копируется в `prependPath()`, а её `context()` используется для результата и
  автоматического лога в
  [ExecutionResultBuilder](../../../src/Pipeline/Flow/ExecutionResultBuilder.php).
  [RedactionPolicy](../../../src/Diagnostics/RedactionPolicy.php) не очищает
  произвольные сегменты строкового sourcePath. Нужно отдельно проверить результат,
  exception, previous и лог с искусственным секретом в ключе; добавления одного
  поля в исключение недостаточно.
- [ResponseHydrator](../../../src/Pipeline/Hydration/ResponseHydrator.php)
  использует `hydrate()` и `hydrateCollection()`. Проверки интеграции должны
  затронуть обе ветки и прежние контракты контейнера/withItems. Ненулевой результат
  response handler по-прежнему завершает свою обработку до Returns.
- [ContinuationService](../../../src/Continuation/ContinuationService.php) и
  [ResultHandle](../../../src/Result/ResultHandle.php) содержат отдельные вызовы
  Hydrator::default(). Первый поглощает Throwable в попытке определить готовность,
  второй теряет previous при cached awaitAs. Исправление этих ошибок относится
  к 030; в 028 проверяется интеграция правил. Это пропуски первоначального обзора,
  подтверждённые [новым probe](../../discussion/dsc-005-declarative-dto-contracts/artifacts/review-probe.php).
- [CompositeFlow](../../../src/Pipeline/Execution/CompositeFlow.php) уже принимает
  гидратор клиента; его агрегацию и ошибки всё равно нужно включить в приёмку.
- [PipelineContext](../../../src/VO/Pipeline/PipelineContext.php) передаёт config,
  но не текущий гидратор; standalone cast/provider получают null. Новые правила
  требуют явного способа продолжить гидратацию в том же наборе либо обозначенной
  границы самостоятельных default-вызовов.

## Приёмка до перехода к основному коду

- Есть единый способ подключения и пример, где SDK настраивает правила один раз.
- Указанные R1–R6 разрешены таблицами поведения, а не пометками «уточнить».
- Сквозная матрица включает два набора для одних plain readonly DTO, fallback,
  два уровня extras, одиночный объект, discriminator, scalar- и вложенные списки,
  optional-but-not-null и required collection.
- Контроль совместимости включает 029, включённый metadata cache, данные из HTTP
  cache, конечный payload рекурсивно объявленного DTO и отсутствие повторного
  конструктора в одном вызове гидратации. Метаданные циклического графа типов
  должны разрешаться с учётом уже посещённых классов.

После этого этапы 2–6 можно выполнять в рамках одного 028. План 027 не является
зависимостью. Масштаб изменений существеннее 029: добавляется публичный способ
объявления правил и происхождение данных. Для существующих потребителей новые
политики должны оставаться выключенными до явного подключения. Изменение await
принадлежит 030; общее исправление metadata — 031. Они задают базовую версию
для совместимости 028. Это критерии
будущей приёмки, а не уже проверенные гарантии нереализованного кода.
