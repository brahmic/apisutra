# Исправление существующего rate limiter

- Дата создания: 2026-09-12
- Дата обновления: 2026-09-12
- Статус: завершён

## Основание и цель

Основание — [аудит rate limiting и принятые ответы О1–О3](../audit/aud-002-rate-limit-contracts/aud-002-readme.md).
Пользователь согласовал узкую поставку: исправить существующий механизм, сохранить
необязательный PSR-16 store и перенести расширенную координацию
[в backlog до востребования](../backlog/pln-015-shared-rate-limit-coordination.md).

Цель: переносимые ключи, проверка квоты после ожидания, остановка при сбое store,
проверка параметров и корректная диагностика локального отказа без вымышленного HTTP.
План закрывает RL1, RL3, RL4, RL7 и RL8. Межпроцессная гонка RL2 остаётся известным
ограничением; весь AS-11 этой поставкой не закрывается.

## Границы и zero-config

- `ClientConfig::rateLimit = null`: лимитер по умолчанию отключён.
- `new RateLimitConfig()` сохраняет 100 запросов за 60 секунд, Wait, store=null,
  key=null. Новых обязательных полей, префиксов, адаптеров и зависимостей нет.
- Без store состояние принадлежит экземпляру лимитера, как сейчас. Разные клиенты
  автоматически не объединяются.
- С store используется существующий PSR-16 контракт. Он позволяет обмениваться
  счётчиком, но get/set не гарантируют строгое соблюдение квоты конкурентными процессами.
- Приоритет runtime-опций, атрибута и конфигурации клиента, наследование store,
  `withoutRateLimit()` и смысл custom key сохраняются.
- Очереди, worker, атомарные backend, общая память разных клиентов, новые области
  identity и несколько квот не входят в реализацию.

## Проверенная техническая основа

План подготовлен по коду HEAD `ec8d80c`; реализация ещё не изменялась.
Воспроизведения и результаты исходных тестов сохранены в аудите. Дополнительно
проверены следующие участки интеграции:

- [RateLimitApplier](../../src/Pipeline/Transport/RateLimitApplier.php) формирует
  физический ключ из custom key или baseUrl и применяет конфигурацию.
- [RateLimiter](../../src/RateLimiting/RateLimiter.php) после sleep безусловно создаёт
  окно со счётчиком 1; `set(false)` игнорируется.
- [RetrySender](../../src/Pipeline/Transport/RetrySender.php) вызывает лимитер внутри
  общего catch Throwable. Поэтому запрет HTTP retry для локальной ошибки нужно
  обеспечить явно, включая пользовательский `retryExceptions: [Throwable::class]`.
- [RateLimitException](../../src/Exceptions/Request/RateLimitException.php) наследует
  ClientException → RequestException; обязательное свойство response объявлено
  в [RequestException](../../src/Exceptions/Request/RequestException.php).
- [ExecutionResultBuilder](../../src/Pipeline/Flow/ExecutionResultBuilder.php)
  разыменовывает response у RequestException и выводит SDK-код из HTTP-статуса.
  Здесь локальная ошибка требует отдельной ветки и проверки null.
- [ErrorPolicy](../../src/Pipeline/Error/ErrorPolicy.php) создаёт RateLimitException
  для реального HTTP 429. Этот путь сохраняет настоящий ответ и существующую семантику.

## Контракт реализации

### 1. Ключи и параметры

Логический ключ остаётся `config.key ?? context.config.baseUrl`. Одинаковый custom key
в одном store продолжает объединять квоту даже при разных baseUrl. Credentials,
identity, тело, URI запроса и класс SDK не добавляются к логическому ключу.

Физический ключ, создаваемый RateLimitApplier, — 64 шестнадцатеричных символа:
`hash('sha256', 'apisutra.rate-limit.v2:' . $rawKey)`. Служебная метка входит в хеш,
пользователь её не настраивает. Алгоритм не зависит от наличия xxh3; ключ не содержит
запрещённых PSR-16 символов. Публичный `RateLimiter::acquire()` продолжает принимать
готовый ключ от вызывающего кода; второй слой хеширования в нём не вводить.

`limit` и `period` должны быть положительными. RateLimitConfig проверяет значения
при создании; атрибут проверяется не позднее преобразования в эффективный конфиг,
до ожидания, записи счётчика и HTTP. Неправильные значения дают ConfigurationException
с именем параметра и правилом, без дампа конфига.

Предусмотреть проверку представимости period вплоть до микросекунд штатного sleeper
(`period <= intdiv(PHP_INT_MAX, 1_000_000)`) и проверку сложения unixTime + period перед
созданием окна. Переполнение даёт ошибку конфигурации, а не float/TypeError или обход
лимита. Нулевое значение не служит способом отключения.

### 2. Ожидание и хранилище

В acquire использовать цикл: проверить бюджет → прочитать текущее состояние →
проверить свободное место → записать увеличенный счётчик либо применить Wait/Throw.
После каждого ожидания повторить чтение и проверку. Если другой участник занял
новое окно, ждать снова; не обнулять его счётчик. Это обычное перечитывание,
не атомарное приобретение разрешения.

Сохранить существующие ClockInterface, SleeperInterface и ExecutionBudget.
Если ожидание не помещается в остаток бюджета, завершать timeout без sleep и HTTP.
Без явно заданного общего бюджета новый предел ожидания не вводить.

При наличии store читать только его, без подстановки локальной памяти при cache miss.
Отсутствующая или истёкшая запись начинает новое окно по существующему контракту.
Исключение get/set и результат set=false означают отказ backend. Отправлять HTTP
можно только после подтверждённой записи. Сбой записи не компенсировать скрытым
переключением на память или автоматическим повтором: запись могла уже состояться.

Ввести узкий `RateLimitBackendException extends SdkException` в модуле исключений
rate limiting: безопасное сообщение, необязательный Throwable previous для ручного
разбора. В результате: `execution_error`, `reason=rate_limit_backend_error`,
`stage=rate_limit_store`; это не исчерпанная квота и не HTTP-ошибка.
Не включать ключ, конфиг и исходное сообщение backend в автоматические логи/context.

### 3. Локальная квота, исключения и retry

Сохранить класс RateLimitException, его иерархию и retryAfter в секундах.
Для локального отказа передавать `response: null`. Для этого расширить тип
RequestException::$response и соответствующего параметра до `?ProviderResponse`,
а также параметр RateLimitException. Порядок, имена и обязательность аргументов
сохранить; существующие вызовы с ProviderResponse продолжают работать.

Это осознанное изменение публичного типа базового свойства. Внутри пакета проверить
всех потребителей RequestException; нельзя ограничиваться правкой одного конструктора.
Не менять родителей исключения и не создавать фиктивный ответ для сохранения типа.

Локальный RateLimitException определяется отсутствием response; его результат:

- `code=rate_limited`, `reason=local_rate_limit_exceeded`, `stage=rate_limit`,
  `retryAfter` — целое неотрицательное число секунд до следующего окна;
- если HTTP ещё не было, result.response и error.response равны null,
  HTTP-статус отсутствует;
- если остановлен повтор после реальной HTTP-попытки, результат сохраняет последний
  фактический ответ. Код и reason остаются локальными, а httpStatus описывает именно
  сохранённый ответ; RateLimitException.response при этом остаётся null.

В ExecutionResultBuilder обрабатывать локальный RateLimitException раньше общей
ветки RequestException. Для других RequestException без response безопасно сохранять
`execution_error`, не выводить HTTP-код из null. Реальный HTTP 429 продолжает иметь
response и прежнюю обработку HTTP retry/Retry-After.

В RetrySender локальный отказ и RateLimitBackendException завершать до общей политики
retryExceptions, независимо от настроек повторов. Wait внутри лимитера не становится
новой HTTP-попыткой. Для ошибки backend также сохранять только реально полученный
предыдущий ответ, если он был; его статус не меняет код ошибки backend.

Result-first, throwOnErrors и явное извлечение/выбрасывание исключения должны передавать
одну и ту же причину. Проверить также async/batch-обёртки и ExecutionErrorFactory:
если исключение проходит через них, они не должны превращать локальную квоту или
отказ backend в connection_failed либо терять retryAfter.

## Обратная совместимость и миграция

| Изменение | Последствие для потребителя |
| --- | --- |
| Новый физический ключ | Однократный сброс накопленного окна; смешанные версии могут считать отдельно. Не читать старый ключ с запрещёнными символами и не удалять чужие записи; старые записи истекут по TTL. |
| Положительные и представимые параметры | Ранее принятые нулевые, отрицательные и чрезмерные значения станут ошибкой конфигурации. Для отключения использовать withoutRateLimit или отсутствие конфигурации. |
| Ошибка store останавливает отправку | set=false больше не разрешает HTTP. Приложение увидит отдельную ошибку исполнения. |
| Повторная проверка после Wait | Ожидание может увеличиться, если место занял другой участник; существующий deadline сохраняет силу. |
| Nullable RequestException::$response | Обработчики, включая catch ClientException/RequestException, должны проверять наличие ответа. Пользовательские наследники, повторно объявляющие это свойство, должны согласовать его тип с базовым. |
| Нет искусственного HTTP 429 | Для локального лимита использовать SDK-код, reason и retryAfter; catch RateLimitException сохраняется. |
| Локальная ошибка терминальна для HTTP retry | Пользовательский retryExceptions больше не повторяет отказ лимитера и неопределённую запись backend. |

Новых runtime-зависимостей и миграции store на специальный интерфейс нет. Поставка
не является полностью обратно совместимой; ограничения описать в публичной документации
и changelog, не скрывать их под названием внутреннего рефакторинга.

## Порядок работы и проверки

1. Добавить проверку параметров и переносимое кодирование ключей. Проверить строгий
   PSR-16 store, одинаковые/разные custom key и baseUrl, прежние приоритеты override,
   независимость клиентов без store, отсутствие ключей с исходными credentials.
2. Перестроить acquire на перечитывание. Через виртуальные часы и sleeper воспроизвести
   занятие нового окна другим участником, несколько ожиданий, истечение окна и deadline.
   Проверить get throws, set throws, set=false: нет разрешения, fallback и HTTP.
3. Изменить nullable-контракт исключения и сборку результата. Проверить локальный Throw
   до первого HTTP, после HTTP 503 при retry и после 401 при auth retry; сохранить
   фактическое число HTTP-вызовов и последний реальный ответ. Проверить backend error
   в тех же точках и запрет повторов при retryExceptions=[Throwable::class].
4. Проверить catch RateLimitException/ClientException/RequestException, retryAfter,
   result-first, throwOnErrors, явное выбрасывание, sync/async/batch. Регрессии:
   настоящий HTTP 429 и прочие HTTP-ошибки, Retry-After, replay тела и общий бюджет.
   Граничные конфиги проверить через конструктор, атрибут и runtime-опции.
5. Проверить безопасную диагностику: секреты в исключении store не попадают
   в сообщение результата, context и обычные логи; previous доступен для ручного анализа.
6. Обновить [руководство retry/rate limit](../../docs/guides/retries-rate-limit.md),
   [конфигурацию rate limit](../../docs/guides/client-config/rate-limit.md),
   [ошибки](../../docs/guides/errors.md), затронутые примеры и
   [CHANEGLOG.md](../../CHANEGLOG.md). Дать короткие примеры без store/key,
   локального отказа и необязательного store с честным ограничением атомарности.
   Публичные материалы не должны ссылаться на workflow.
7. Выполнить затронутые тесты RateLimit, Retry, Timing и сценарии результатов/ошибок,
   затем `composer test`. Проверить standalone без Laravel, ссылки и `git diff --check`.
   Сохранить результаты в плане. Существующий двухпроцессный race из аудита остаётся
   доказательством ограничения, а не тестом строгой квоты, которую эта поставка не даёт.

## Критерии завершения

Все согласованные сценарии проверены; локальный отказ не создаёт HTTP-ответ, сбой
store не разрешает отправку, Wait перечитывает квоту. Пользователь обычного клиента
не настраивает префиксы, новый backend или дополнительные политики. Документация
различает локальный лимит, ответ провайдера и отказ хранилища, явно описывает миграцию
и не обещает атомарность. Общая координация остаётся в backlog. После выполнения
обновить статус и перенести этот план в completed вместе со встречными ссылками.


## Выполнено и проверено — 2026-09-12

Реализованы переносимое кодирование ключей, валидация параметров, повторное чтение
после Wait, явный отказ backend и локальная ошибка без синтетического HTTP.
Nullable-контракт RequestException отражён в обработчиках и публичной миграции.
Defaults, смысл custom key, независимость экземпляров и существующий PSR-16 store
сохранены. Runtime-зависимости не менялись.

Уточнения по результатам реализации:

- У RateLimitException и RateLimitBackendException добавлен необязательный readonly
  lastResponse. RetrySender переносит в него фактический ответ предыдущей попытки,
  чтобы parallel batch/pool могли восстановить результат из выброшенного исключения.
  Локальный RateLimitException.response остаётся null. Существующая последовательная
  batch-стратегия при throwOnErrors продолжает выбрасывать исключение; parallel batch
  и pool упаковывают его в результат. Эта разница режимов не менялась.
- Проверка верхней границы period уточнена до микросекунд SystemSleeper, а не только
  миллисекунд ExecutionBudget: иначе последующее умножение в usleep переполнялось бы.
  Столь большие значения отклоняются до записи/HTTP; обычные периоды не меняются.
  Аналогичная проверка защищает ожидание, прочитанное из общего счётчика.
- После подтверждённой записи проверяется общий бюджет; истёкший бюджет не разрешает
  HTTP и не вызывает повторное списание.

Постоянные проверки:

  после пробуждения окно, несколько ожиданий, deadline, отсутствие fallback, get/set
  failures, диапазоны параметров и бюджет после записи.
- [Пайплайн и обёртки](../../tests/Unit/RateLimit/RateLimitExecutionTest.php):
