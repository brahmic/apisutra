# Транспортные ошибки, raw-ответы и условные повторы

- Дата создания: 2026-09-13
- Дата обновления: 2026-09-13
- Статус: завершён

Основание: [аудит пяти замечаний](../../audit/aud-005-transport-response-retry/aud-005-readme.md).
План полностью согласован пользователем и реализован 2026-09-13.
Результаты проверки и границы поставки — в [приёмке](acceptance.md).
В1, В2, В4 и В5 отвечены; В3 закрыт уточнением:
после уточнения потребности файл провайдера не требуется, D4 описывает общий
runtime-дедлайн для нескольких независимых вызовов.

## Цель и границы

Устранить неправильную классификацию сетевых сбоев, потерю данных неизвестного
формата и расхождение Retry-After. Разрешить конкретному запросу получать сырое
тело и оценивать безопасность повтора по результату попытки. Сохранить один бюджет
внутри выполнения, не объединять независимые вызовы скрытым состоянием клиента.

В ядро не входят `attachment.not.ready` и другие бизнес-коды, очереди, reconciliation,
idempotency storage, определение результата операции у провайдера, глобальный
оркестратор deadline или автоматическая отмена бизнес-сценариев.
Новых Composer-зависимостей, обязательных настроек и Laravel bindings нет.

Приложение может явно связать несколько send одним неизменяемым сроком. Это
передача ограничения, а не перенос бизнес-оркестрации в SDK. Без опции каждый
вызов остаётся независимым.

## Согласованные контракты

### D1. Классификация и диагностика отправки — В1

1. Подтверждённые cURL 55/56 → `ConnectionException` / `connection_failed`;
   28 → `TimeoutException` / `timeout`; 52 → `ConnectionException`.
   Проверка adapter-specific errno предшествует общей PSR request-ветке.
   Неизвестные Guzzle/PSR ошибки без доказательств не переклассифицируются вслепую.
2. Сохраняются `previous`, result-first, throwOnErrors, существующий ErrorCode enum
   и работоспособность PSR-18 без Guzzle. Повторная нормализация не меняет уже
   нормализованное исключение и его метаданные.
3. Ввести небольшой string-backed `TransmissionState` с `not_sent` и `unknown`.
   Состояние в нормализованном TransportException относится к попытке;
   значение по умолчанию — `unknown`. Добавление необязательного параметра в конец
   конструктора сохраняет прежние message/code/previous. Проверить наследников,
   включая ExecutionDeadlineException; новый параметр не становится обязательным.
4. `not_sent` означает доказанное отсутствие отправки текущего запроса.
   Generic PSR network exception и 28/52/55/56 всегда `unknown`. Для 6/7 без
   надёжных сведений обо всём transport call также `unknown`. Анализ текста,
   размеров upload и догадки по времени соединения запрещены как источник гарантии.
5. В RequestError.context передавать итоговый `transmissionState` для сбоя отправки
   или локального deadline. Он консервативно учитывает **все попытки текущего
   выполнения запроса**: ранний ответ/неопределённая отправка не может смениться
   на итоговое `not_sent` после следующего локального отказа. До первого возможного
   HTTP-вызова допустим `not_sent`. Другие запросы auth/dependencies имеют собственное
   состояние; это не статус всей бизнес-операции приложения.
6. Достаточно одного накопительного признака в PipelineContext, без истории попыток.
   Отмечать возможность отправки не позднее передачи управления транспорту/custom
   retry handler. Если пользовательский handler сам делает I/O, SDK консервативно
   считает исход неизвестным. Обёртка deadline сохраняет ранее накопленное состояние.
7. Эти данные не являются новым основанием retry. Сохраняются текущие safety,
   attempts, body replay, quota и deadline. После переклассификации 55/56 обычный
   retry применяется там, где он уже разрешён конфигурацией и safety.

Практический результат: приложение различает локальный отказ до отправки и сетевой
сбой с неизвестным исходом. SDK не обещает определить судьбу сообщения/платежа
после timeout и не начинает повторять небезопасный POST сам.

### D2. Auto и точечный raw — В2

Существующее поведение extension handlers сохраняется в Auto. Таблица относится
к стандартному декодеру после отказа/отсутствия подходящего обработчика:

| Ответ | Auto без DTO/пагинации | Auto с DTO/пагинацией |
| --- | --- | --- |
| JSON / `+json`, валидное тело | Декодированные данные | Текущая гидрация и проверка формы |
| JSON / `+json`, невалидное тело | `response_decoding_error` | `response_decoding_error` |
| Непустое тело без Content-Type | Строгий JSON | Строгий JSON |
| `text/plain` | Исходная строка | Ошибка неподдерживаемого формата, не `[]` |
| Другой явно указанный Content-Type | Исходная строка, даже если похожа на JSON | Ошибка неподдерживаемого формата, не `[]` |
| 204 / пустое тело / JSON null | Прежний контракт `null` | Прежняя обработка пустого DTO/пагинации |

Ошибка неподдерживаемого формата использует существующий `ResponseDecodingError`
со стабильной причиной `unsupported_response_content_type`, не новый ErrorCode.
Она появляется при обработке полученного ответа, не при создании запроса.
Для HTTP-ошибок сохраняется действующая классификация статуса и ErrorPolicy;
raw/формат не превращают 429/500 в успех.

Предлагаемый точечный API:

```php
use Brahmic\ApiSutra\Attributes\Http\Get;
use Brahmic\ApiSutra\Attributes\Response\RawResponse;
use Brahmic\ApiSutra\Core\AbstractRequest;

#[Get('/export')]
#[RawResponse]
final class ExportRequest extends AbstractRequest
{
}

// Либо опция одного исполнения через существующую цепочку запроса.
$result = $request->withRawResponse()->send()->raw();
$text = $result->data;
```

- `#[RawResponse]` — необязательный marker на классе. Для одного вызова
  `withRawResponse(?bool $enabled = true)`; `false` выбирает Auto,
  `null` снимает override и возвращает наследование атрибута.
  В RequestOptions хранится nullable boolean. Приоритет runtime → атрибут → Auto.
- Raw возвращает строку тела без JSON-декодирования, включая `''` для пустого
  тела/204 и `'null'` для JSON null. Это явный режим, в нём точность тела важнее
  нормализации пустого ответа. Не выполняет декодирование Content-Encoding
  заново: возвращает body, предоставленное транспортом.
- Явный Raw отключает response format handlers и DTO hydration. Для исключения
  конфликтующих деклараций Raw вместе с Returns/response DTO, Paginable или
  Download отклоняется как `configuration_error` до HTTP. Использование raw
  для отладки DTO возможно через уже существующий `ExecutionResult::response`.
  Валидация должна учитывать итоговый runtime override, а не только атрибут.
- BeforeHydrate для raw-строки не вызывается, как и сейчас для скалярного ответа.
  BeforeSend/AfterResponse/AfterHydrate и HTTP error policy сохраняются.
- Не менять `ResultHandle::raw()`: это по-прежнему получение ExecutionResult.
  Не переиспользовать `Returns::type` для новой, не связанной с ним семантики.
- Cache продолжает хранить HTTP-response и декодируется согласно текущему режиму.
  Новый namespace/префикс и включение raw-флага в custom key не нужны.
  Потоковые файлы не буферизуются и не кешируются.

Цена: marker, одно поле опций, metadata/accessors, небольшая ветка в hydrator,
валидация сочетаний и тесты жизненного цикла опций. Отдельный registry декодеров,
клиентская настройка и новые response wrappers не нужны.

### D3. Safety по результату попытки — В4

Добавить отдельный **необязательный** `RetrySafetyPolicyInterface`, реализуемый
запросом. Обязательные RequestInterface/TransportInterface не расширять.
Сигнатура проектируемого метода:

```php
public function isRetrySafe(
    HttpMethod $method,
    ?ProviderResponse $response,
    ?Throwable $exception,
): ?bool;
```

Request object уже содержит бизнес-параметры. Метод получает фактический HTTP-метод
и данные текущей попытки, не mutable PipelineContext и не ClientConfig.
`null` означает прежнюю политику; `true/false` — явное решение для этого исхода.
Для обычного network failure response равен null, предыдущий ответ не подставляется.
При исключении hook после ответа допустимы одновременно response и exception.

Приоритет: явный `#[Retry(safe: true/false)]` → результат опционального контракта
запроса → `RetryConfig::safeMethods`. Отсутствующий `safe` и `safe: null` равнозначны.
В примере ниже `safe: true` указывать не следует: он намеренно перекрывает условие.

```php
// Тело метода запроса, реализующего RetrySafetyPolicyInterface.
public function isRetrySafe(
    HttpMethod $method,
    ?ProviderResponse $response,
    ?Throwable $exception,
): ?bool {
    if ($method !== HttpMethod::POST) {
        return null;
    }

    return $exception === null && $response?->status === 429;
}
```

Таким образом POST после 429 разрешён, POST после timeout/503/401 запрещён,
а GET продолжает использовать прежние сетевые повторы. Считать 429 безопасным
решает SDK провайдера по своему контракту; ядро такого универсального правила
не вводит. Для `fixture.not.ready` SDK провайдера может проверить тело ответа.

Safety не инициирует retry. Сначала должна появиться причина повторять: retryOn,
retryExceptions, shouldRetry или auth recovery. Затем действуют safety, replay
тела, attempts и budget. `true` не отменяет ни один из остальных ограничителей.
Проверка применяется и перед восстановлением auth, как текущий `safe: false`.

Метод должен быть детерминированным и без I/O: это вычисление, а не место ожидания,
проверки состояния у провайдера или отправки запроса. Ошибка проверки прекращает
повторы с безопасной диагностикой (`execution_error`, причина
`retry_safety_check_failed`, исходное исключение в previous). Не проглатывать ошибку,
не считать её разрешением и не запускать retry самой проверки.

Не добавлять одновременно callback в ClientConfig, `safeOn` в атрибут и второй
контракт на клиенте. Если общая политика нужна всем запросам конкретного SDK,
он реализует этот контракт в своём базовом классе запроса.

### D4. Внешний дедлайн нескольких вызовов — согласовано, В5

Уточнение пользователя: один сценарий приложения состоит из нескольких send,
включая разные операции. Нужно передать общий срок, не превращая их во внутренний
retry. Предыдущая рекомендация только проверить провайдерский цикл заменена этим
общим контрактом; код `attachment.not.ready` в ядро не входит.

Согласованный API (2026-09-13), пример для запросов с заданным/разрешаемым клиентом:

```php
use Brahmic\ApiSutra\Timing\ExecutionDeadline;

$deadline = ExecutionDeadline::afterMs(1000);

$first = $create->withDeadline($deadline)->send()->raw();
// Приложение проверяет результат и решает, какой запрос выполнять дальше.
$second = $upload->withDeadline($deadline)->send()->raw();
$third = $confirm->withDeadline($deadline)->send()->raw();
```

**Объект и часы:**

- Небольшой final readonly `ExecutionDeadline` хранит абсолютный монотонный срок
  и источник времени. `afterMs(int $milliseconds, ?ClockInterface $clock = null)`
  фиксирует срок сразу, по умолчанию через SystemClock. Повторный send ничего
  не перезапускает. Отрицательное значение/переполнение — configuration error;
  0 — уже истёкший срок, а не снятие лимита.
- Это описание ограничения; ожидания и проверки остаются в ExecutionBudget.
  Не дублировать wait/retry/стадии выполнения в новом объекте.
- ClockInterface не расширять. Pipeline сохраняет источник времени parent/client.
  Отдельные экземпляры штатного SystemClock совместимы (один hrtime-домен текущего
  процесса). Для нестандартных часов клиент/parent и deadline должны использовать
  один и тот же объект ClockInterface. Несовместимые часы → configuration error
  до I/O; не сравнивать несвязанные числовые шкалы и не переходить на unixTime.
  В тестах один VirtualClock передаётся и клиенту, и фабрике deadline.
- Один deadline применим к разным клиентам с совместимыми часами в текущем процессе.
  Персистентность, передача в другой worker и распределённый deadline не обещаются.

**Опции и композиция:**

- Добавить nullable поле в RequestOptions и методы
  `withDeadline(ExecutionDeadline $deadline)` / `withoutDeadline()`
  в RequestOptions/RequestOptionsChainTrait. `withoutDeadline()` снимает только
  внешний срок; клиентский/родительский пределы остаются. Отсутствие опции хранится
  как null, но публичный сброс выполняется отдельным методом, как у существующих
  `withoutDelay()` и `withoutRetry()`. Копирование и снятие проверяются отдельно:
  внутренняя реализация не должна потерять сброс из-за оператора `??`.
  Цепочка возвращает новое исполнение, не мутируя исходный запрос.
  RequestInterface и ClientConfig не расширять.
- На старте выполнения: `effectiveDeadline = min(external, parent,
  startedMs + totalTimeoutMs)`, отсутствующие пределы не участвуют. Дочерний
  вызов наследует уже вычисленный parent и может его только сократить.
- Клиентский totalTimeoutMs остаётся длительностью отдельного выполнения.
  Внешний срок ограничивает всю последовательность, включая время между send.
  Более длинный external не ослабляет клиентский лимит, более короткий сокращает.
- Опция работает без RetryConfig, с `withoutRetry()` и в sync/async API.
  Её смысл не зависит от наличия автоматических повторов.
- Уже истёкший срок проверяется на стадии `started`, до HTTP, auth/cache I/O,
  execution hooks и подготовки файлов. Сборка клиентского объекта и разрешение
  опций до входа в pipeline не становятся системой принудительно отменяемого I/O.
- Та же ошибка `timeout`, `reason: execution_deadline_exceeded`, текущий stage,
  прежние result-first/throwOnErrors. Не добавлять новый ErrorCode.
- Внешний срок попадает в существующий ExecutionBudget: HTTP, delay, quota wait,
  backoff, Retry-After и auth refresh получают тот же остаток. Ожидание, равное
  остатку или превышающее его, отклоняется до sleep по существующему правилу.
- Срок не становится cache key/identity, атрибутом класса, глобальной настройкой
  клиента или ambient context. Успешный cache hit также проходит общую проверку
  срока; истёкший вызов не обслуживается из кеша. Снятие опции не меняет custom key.

**Граница гарантий:**

Для трёх операций по 400 ms при общем сроке 1000 ms третья HTTP-попытка получает
не более 200 ms. Контролируемый тестовый транспорт должен соблюдать этот timeout,
тогда итог — deadline exceeded за 1000 ms виртуального времени. Нельзя проверять
этот критерий fake-транспортом, который безусловно прибавляет ещё 400 ms, и обещать
принудительное прерывание такого кода. В реальной среде учитывается погрешность
таймеров/планировщика. SDK проверяет границы и передаёт остаток поддерживающему
таймауты транспорту; не прерывает произвольный блокирующий callback, store, hook
или работу приложения между вызовами. После возврата такого кода превышение
обнаруживается. Это та же кооперативная модель, что у существующего budget.

Цена: один небольшой объект срока на сценарий, nullable runtime-поле и композиция
в существующем budget, проверки часов/опций и интеграционные тесты. Новых I/O,
состояния на клиенте, глобального реестра часов и новой подсистемы таймеров нет.
Отдельный метод «остаток ms для этого вызова» пока не добавлять: он дублирует
возможность с менее надёжным ручным пересчётом. Встроенный retry по-прежнему
предпочтителен для подходящего повтора одной операции, но не заменяет внешний срок.

### D5. Единый Retry-After

- Переиспользовать parser из RetryAfterDelay; один раз определённая грамматика
  и защита переполнения, без второго независимого разбора в ErrorPolicy.
- Выделить доступный обоим потребителям метод разбора nullable-секунд. При этом
  текущие `RetryAfterDelay::forResponse()` и `fromSeconds()` сохраняют ms-контракт.
  Не вводить интерфейс парсера или сервисную фабрику для одного алгоритма.
- Missing/invalid/negative/overflow → `null` для исключения и отсутствие серверной
  минимальной задержки; корректный `0`/прошедшая дата → 0; будущая дата → разница
  с текущим unixTime в целых секундах. Предусмотреть все три HTTP-date формы,
  whitespace, большие значения и некорректные календарные даты.
- Pipeline передаёт единый ClockInterface в оба пути через существующую сборку.
  ClockInterface не изменяется. Прямое создание ErrorPolicy/RetryAfterDelay без
  аргументов сохраняет системные часы; дополнительные аргументы необязательны.
- Автоматическая задержка применяется к прежним статусам 429/503 и ограничивается
  ExecutionBudget. RateLimitException по HTTP 429 сообщает то же значение в секундах.
  Это не изменение исключений локального limiter и не расширение retryOn.

## Порядок реализации

### Этап A. Транспорт и Retry-After

1. Согласование завершено: ответы В1, В2, В4, В5 записаны в аудит.
2. Добавить регрессии для 55/56, PSR-only, previous и повторной нормализации.
3. Исправить классификацию, затем добавить согласованное состояние D1. Проверить
   ложный `not_sent` после предыдущего timeout/ответа, wrapper deadline,
   sendAsync и пользовательский handler. Состояние не хранить на клиенте.
4. Объединить разбор Retry-After и часы. Проверить обе публичные поверхности:
   значение исключения и реальное ожидание/отказ по бюджету.
5. Обновить гайд ошибок/retry и changelog без ссылок на внутренний workflow.
   Выполнить проверки этапа, зафиксировать отдельный результат приёмки.

### Этап B. Формат ответа

1. Сначала регрессии неизвестного Content-Type с валидным и невалидным JSON.
2. Добавить marker RawResponse и nullable runtime option в существующие
   RequestOptions/RequestOptionsChainTrait. Дополнить RequestSpec/Resolver/Accessors
   без новых обязательных параметров публичного RequestSpec; проверить копирование
   опций и корректное снятие override через null (оператор `??` его не снимает).
3. Реализовать предвалидацию конфликтов, D2 в ResponseHydrator, сохранить
   приоритеты extension handlers и существующие скалярные hooks.
4. Проверить cache miss/hit, смену режима на том же запросе, явный custom key,
   ошибочные HTTP-статусы и streaming guard.
5. Обновить справочник атрибутов, requests, response/error guide, примеры и changelog.

### Этап C. Условная safety

### Этап D. Внешний дедлайн

1. Добавить ExecutionDeadline: фабрика, монотонное время, валидация 0/negative/overflow

   сохранить; новые аргументы, если требуются, добавить необязательными в конец.

## Совместимость и цена

Полной поведенческой совместимости нет. 55/56 меняют ErrorCode/тип исключения
и начинают следовать настроенному network retry. Неизвестный Content-Type без
DTO возвращает строку вместо массива; с DTO вместо молчаливого fallback появляется
ошибка формата. Неверный Retry-After становится null вместо 0/отрицательного числа,
HTTP-date — корректным интервалом. Это отдельный обязательный раздел upgrade notes.

Auto JSON/text/null и отдельные send без внешнего срока сохраняют действующий контракт.
Новые raw, conditional safety и внешний deadline включаются только по запросу разработчика. ClientConfig
не пополняется обязательными параметрами. Цена выполнения: несколько ветвлений,
компактное состояние отправки и вызов safety только при рассмотрении повтора;
новых I/O, фоновых задач, сторонних сервисов и хранилищ нет.

Самая чувствительная часть — доставка/накопление неопределённости и взаимодействие
safety с auth/body replay. Raw затрагивает больше поверхностей API, чем одна строка
декодера. Внешний deadline переиспользует budget, но требует проверки шкал времени
и интеграции ожиданий/дочерних запросов. Retry-After и классификация локальны. Поэтому не смешивать всё в один
непроверяемый рефакторинг и не затрагивать отложенные планы 022–024.
