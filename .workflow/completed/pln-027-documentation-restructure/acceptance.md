Критерии для [плана 027](pln-027-readme.md). Реализация и результаты
D01–D17 зафиксированы в [отчёте](implementation.md); повторяемые команды приведены ниже.

По последующему [уточнению владельца](cleanup.md) сохранение старых адресов (D10)
отменено. Матрица ниже описывает первичную приёмку; текущая проверка не зависит
от ссылок и артефактов workflow.

## Что автоматизировать

1. **Навигацию:** расширить существующий `tests/Support/check-docs.py`, а не создавать
   второй постоянный проверяющий скрипт. Поддержать локальные file/fragment ссылки,
   HTML id, русские и повторные заголовки, URL encoding, изображения и применяемый
   в документах Markdown. Использованные конструкты проверить тестовыми примерами.
2. **Декларации:** явный реестр проверяемых ссылок «страница/раздел → FQCN →
   метод/параметр» в `tests/Support/docs-api.json`, без распознавания произвольного
   текста. В первую очередь ClientConfig, атрибуты, HydrationRules/descriptors и
   continuation. Reflection подтверждает имена/типы; не выполняет пользовательские
   object-default выражения ради проверки таблицы. Сложные defaults подтверждаются
   целевым тестом и редакционной сверкой.
3. **Примеры:** сохранить существующие `standalone-*.php`; привязать их к текущим
   PHP-файлам образца/отмеченным блокам. В baseline hydration-rules smoke зависел от
   двух PHP-блоков старого guide. Теперь он исполняет опубликованные PHP-файлы
   `docs/example/hydration-rules`, а не независимую копию рецепта.
4. **Размер и покрытие:** отчёт по строкам/байтам, страницам без входящих ссылок,
   сохранённым переходам и исключениям. Совпадение числа файлов не доказывает
   полноту API или отсутствие дублирования.

Проверять неблагоприятные случаи: отсутствующий файл, неверный якорь, дубликат
заголовка, кириллицу, неправильный PHP-символ/параметр, сломанный исполняемый пример,
обязательную ссылку на непоставляемый ресурс. Не вводить общий runtime-анализ
естественного языка или требование теста на каждый абзац.

## Ручная приёмка

`inventory.md` связывает описание с аудиторией и сценарием/тестом, включая отсутствие теста.
Для каждого переноса reviewer проверяет смысл и пропуски разделов, а не только diff.
`route-review.md` фиксирует путь по документам для нового SDK, добавления операции,
plain DTO с `_extra`, настройки await и диагностики strict-ошибки.
Одну пользовательскую задачу пройти через обычный и agent-вход, сравнив контракт
и результат. Отдельно проверить путь разработчика ядра из CONTRIBUTING в checkout.
Не требовать чтения внутреннего устройства для использования публичного расширения.

Сравнить «до/после»: количество конкурирующих полных описаний, размер крупнейших
страниц, обязательное чтение перед первой операцией и наличие всех нужных контрактов.
Не требуется доказать ускорение чтения универсальным числом минут.

## Команды и доказательства

База планирования воспроизводится без запуска тестов пакета:

```bash
python3 .workflow/completed/pln-027-documentation-restructure/artifacts/inventory-docs.py cddd036a0955e3379a244355fe23d3e888b1ba4a
python3 .workflow/completed/pln-027-documentation-restructure/artifacts/check-plan.py
git diff --check
```

Первая команда выводит снимок **commit**, а не текущих изменённых файлов. PHP version
в нём относится к окружению запуска. Состояние подготовки и проверки
ссылок плана после разделения аудиторий — в [audience-checks.json](artifacts/audience-checks.json).
Первоначальная [проверка](artifacts/planning-checks.json) сохранена как результат
прежней раскладки, а не как подтверждение новой.

Повторная проверка реализации:

- Для каждой порции: `composer check-docs`, `git diff --check`, связанные проверки
  API и исполняемых примеров. Проза сама по себе не требует полного `composer test`.
- Для изменённой проверяющей инфраструктуры: тесты её существенных отказов;
  PHP lint/analyse/style по области изменения. Полный тестовый набор нужен при
  влиянии на общий стенд, а не как замена ручной проверке содержания.
- Для выпуска: `composer check-package` либо
  `python3 tests/Support/check-package.py --staged --report <путь-к-отчёту>`.
  Обычная команда проверяет HEAD: явно зафиксировать проверенный commit/tree;
  не принимать предыдущую поставку за проверку ещё незакоммиченных переносов.
- Standalone запускается в установленном пакете без require-dev; Laravel-пример —
  с его реальными зависимостями отдельно. Никаких реальных запросов к API провайдера.

Сохранить в `artifacts/` результаты навигации, деклараций, примеров, размеров и
архивов; `implementation.md` связывает их с D01–D17. `inventory.md`, `moves.md`,
`route-review.md` созданы в ходе реализации; `size-exceptions.md` не потребовался.
Результат, даты, статус и индекс workflow обновлены, комплект перенесён в `completed/`.

## Повторить итоговую сверку

```bash
python3 .workflow/completed/pln-027-documentation-restructure/artifacts/verify-implementation.py
```

Команда проверяет совпадение текущей поставки с сохранённым отчётом двух архивов,
неизменность src и прежних материалов workflow, переносы, ссылки и опубликованные
примеры. Затем обновляет итоговый state с SHA-256. Она не повторяет полный Pest,
Laravel или установку архивов: их результаты и отдельные команды указаны в отчёте.
При новых изменениях поставки сначала заново выполните check-package на нужном tree.
