## Цель и текущая база

По запросу владельца от 2026-09-14 документация должна вести пользователя ApiSutra
от анализа внешнего API до проверенного SDK: конфигурация, клиент, операции, DTO,
ошибки и тесты. У каждого поддерживаемого контракта должно быть одно полное описание.
Уточнение от 2026-09-15: заранее выбрать папки, файлы, группировку и границы объёма.
Следующее уточнение: отделить разработку самого ApiSutra от использования пакета.
Разработчик SDK относится к пользователям. Человек и ИИ используют общие контракты
и маршруты; для агента предусмотрен только короткий вход подготовки задания.

База планирования — commit `cddd036a0955e3379a244355fe23d3e888b1ba4a`.
028, 029, 030 и 031 завершены; их API не проектируется повторно. Последующая
[проверка документации](../../completed/pln-028-declarative-dto/documentation-followup.md)
обновила 25 публичных документов, включая рекомендацию `_extra`, миграцию и глоссарий.
Успех её проверок не означает, что весь прежний комплект уже актуален.

Состав базы: 90 публичных Markdown-файлов, 14 329 строк; 14 файлов длиннее 300 строк,
6 — длиннее 400. Методология SDK занимает 700 строк, auth — 499, DTO — 452,
сериализация — 451, внешние правила — 351. Данные и SHA-256 — в
[baseline.json](artifacts/baseline.json); команды — в [приёмке](acceptance.md).

## Объём и границы

Входят README, `docs/`, исполняемые примеры, инструкции `AGENTS.md` / `.agents/`,
проверки документации и их подключение к существующим CI/проверкам поставки.
Пользовательский комплект — `docs/start`, guides, reference, glossary, migration,
example. Для разработчика пакета — корневые CONTRIBUTING и development, инструкции
checkout и workflow. Границы и поставка описаны в [аудиториях](audiences.md).

`src/`, публичный PHP API и продуктовые решения 028–031 сохраняются. Подтверждённые
дефекты ядра оформляются отдельно; случайный результат нельзя объявлять контрактом.
Отложенные async-first, client assembly и execution policies не возобновляются.
Сайт документации, переводы, реальные SDK провайдеров, плагин/skill и живые внешние
API не входят; учебный образец описан отдельно в маршрутах.

Старые аудиты, приёмка и манифесты остаются фактами своих commit. Их не переписывать
ради новой раскладки. `.workflow/history/` исключён из обычной инвентаризации.
Для примеров использовать нейтральный учебный API, fake и искусственные данные.

## Исходные проблемы и приоритет

Ниже зафиксированы проблемы на старте реализации. Они устранены; прежние формулировки
сохранены для связи с задачей, результаты и проверки находятся в отчёте реализации.

| Приоритет | Что проверить и исправить |
| --- | --- |
| Сначала | [Quickstart](../../../docs/guides/quickstart.md) создаёт `$config`, но получает клиент через `app()` без его передачи или binding. Сделать полностью исполняемую явную сборку и отдельный Laravel-вариант. |
| Сначала | [Глоссарий](../../../docs/glossary/requests.md) обещает non-blocking/fire-and-forget; [executeAsync()](../../../src/Pipeline/Pipeline.php) вызывает `execute()` синхронно. Развести promise API, конкурентность транспорта и provider await без изменения кода. |
| Затем | [AttributeScanner](../../../docs/glossary/attributes.md) не соответствует классу в `src/`; проверить остальные имена и публичность символов. |
| Затем | [Обзор](../../../docs/technical/architecture.md) исключает валидацию без контейнера, хотя [Validator::useFactory()](../../../src/VO/Validation/Validator.php) позволяет передать фабрику. |
| Затем | Правила `.agents/providers.md` и навигация ещё тяготеют к атрибутным профилям. Согласовать их с выбором внешних правил, не делая профиль обязательным для plain DTO. |
| Далее | Полные правила и примеры повторяются в методологии, guides, client-config, attributes и glossary. Разделить декларации, поведение, рецепты и определения по карте. |
| Сопровождение | `composer check-docs` пока проверяет существование файлов; проверка якорей из последней приёмки не стала штатной. Сигнатуры, выполнение примеров и полнота покрытия — отдельные проверки. |

## Критерий результата

Пользователь или его агент находит нужный контракт из общего маршрута, создаёт SDK
и проверяет его без чтения всего комплекта и исследования внутренних классов.
Все публичные темы учтены, каждый контракт имеет одного владельца, страницы
укладываются в заданные границы, примеры выполняются, старые ссылки продолжают вести
к актуальному описанию. Разработчик ApiSutra имеет отдельный вход в устройство и
сопровождение ядра. Проверки ссылок сами по себе этого результата не доказывают.
