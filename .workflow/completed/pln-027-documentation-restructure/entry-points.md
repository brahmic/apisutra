# Точки входа и маршрут создания SDK

Проект маршрутов **пользователя ApiSutra** для [плана 027](pln-027-readme.md).
Маршруты реализованы в `docs/`, результат их проверки — в [route-review](route-review.md).
Подробное дерево — в [структуре](structure.md).
Разработка самого ApiSutra имеет отдельный вход CONTRIBUTING и материалы development;
[граница аудиторий и выбор решения для ИИ](audiences.md).

## Выбор маршрута

| Файл | Задача читателя | Обязательный минимум | Результат |
| --- | --- | --- | --- |
| `start/README.md` | Выбрать вход | Таблица задач и возможности/ограничения в одном экране | Прямая ссылка на маршрут |
| `start/create-sdk.md` | Создать SDK внешнего API | Анализ → проектирование → первая операция → проверка → расширение → выпуск | Рабочий SDK и известные границы покрытия |
| `start/add-operation.md` | Добавить операцию в существующий SDK | Контракт операции, принятый стиль SDK, request/DTO, тест | Операция использует существующие клиент и правила |
| `start/describe-dto.md` | Описать модель ответа или запроса | Выбор входа/выхода, профиля/внешнего набора, формы и обязательности | DTO и проверенный пример данных |
| `start/use-sdk.md` | Подключить готовый SDK | Установка, конфигурация, явная сборка либо Laravel, чтение результата | Первый вызов и обработка ошибки |
| `start/diagnose.md` | Разобраться с ошибкой | ExecutionResult/исключение, стадия, safe log, причина | Воспроизведение и точный профильный контракт |

После таблицы задач — необязательная ссылка «Передать задачу ИИ-агенту» на
`start/agent.md`. Она помогает подготовить задание и выбрать один из общих маршрутов:
создание SDK, добавление операции, DTO, подключение или диагностика. Контракты,
порядок и критерии результата у человека и агента одинаковы.
В установленном пакете доступны все обязательные инструкции пользователя;
внутренние `.agents/` и workflow ApiSutra ему не требуются.

## Последовательность создания SDK

Это содержание единственного маршрута `start/create-sdk.md`; подробная работа
каждого этапа описана в соответствующем guide. В маршруте — краткая таблица и
прямые ссылки, без повторного изложения руководств.

| Шаг | Вход | Действия и приоритет | Выход | Критерий перехода |
| --- | --- | --- | --- | --- |
| 1. Факты API | Документация, схемы и допустимые примеры ответа | Зафиксировать протокол, auth, ошибки, типы, лимиты; отделить неизвестное | `api-notes.md` и вопросы с источниками | Есть достаточно фактов для одной выбранной операции |
| 2. Границы SDK | Факты и существующий код, если он есть | Выбрать простой клиент или сервисы; разместить ресурс/запрос/DTO/enum; выбрать способ гидратации | Краткая карта решений и дерево SDK | Нет обязательного механизма без причины в API |
| 3. Клиент | Base URL, auth, транспорт и зависимости | Явно передать ClientConfig/transport; общие правила собирать в factory; подключить Laravel только при необходимости | Собираемый клиент и конфигурация | Клиент создаётся без скрытых binding и credentials в исходниках |
| 4. Одна операция | Проверенные request/response примеры | Request → DTO → Returns/результат; выбрать правильные входные типы и формат запроса | Работающий вертикальный пример | Fake подтверждает запрос, DTO и ошибку |
| 5. Граничные случаи | Контракт и примеры шага 4 | Missing/null, типы, вложенность, mapping, `_extra`, shape/sourcePath по используемым правилам | Контрактные тесты операции | Ошибки не становятся успешным DTO; исходящий payload проверен отдельно |
| 6. Расширение | Проверенный образец и список операций | Переиспользовать механизмы; подключать pagination/files/continuation и прочее по условиям | Покрытие операций и список ограничений | Поддержка подтверждена тестом, неподдержанное явно отмечено |
| 7. Документация и выпуск | Рабочий SDK | Описать установку, настройку, примеры, зависимости и совместимость | README SDK, документация и проверенная поставка | Потребитель повторяет пример без чтения внутреннего workflow |

Приоритеты для любого исполнителя: исправность первой операции → верность данных/ошибок →
покрытие нужных пользователю операций → удобство и дополнительная инфраструктура.
Ни мегаклиент, ни live-стенд, ни каталоги не обязательны для первой операции.
Задача «добавить метод» начинается с принятой структуры SDK, а не с её перепроектирования.

Общий guide анализа API определяет, как помечать предположение и неизвестные
условия. Endpoint, коды, лимиты и формат данных должны иметь источник. Без внешнего
API можно проверить сборку и сериализацию на искусственных данных.
`agent.md` даёт компактный шаблон задания и передачи результата, ссылаясь на эти
общие требования. Правила разработки и таблицы контрактов туда не копируются.

## Развилка DTO

`start/describe-dto.md` начинает с четырёх вопросов выбора, а не с обязательного
наследования от AbstractDto:

1. Это входящий ответ, модель исходящего запроса или DX-представление?
2. Есть ли уже принятые атрибуты/профили или нужны plain-модели с HydrationRules?
3. Какие реальные типы/формы приходят; нужно ли требовать ключ и запрещать explicit null?
4. Нужно ли сохранять неизвестные данные и будет ли этот объект отправляться клиентом?

Plain-путь ведёт к `guides/dto/plain-models.md`, атрибутный — к `attribute-models.md`.
Полные таблицы strict, конфликтов и defaults остаются в reference.
Приёмник по рекомендации называется `_extra`, но его имя явно задаётся в правилах.
Standalone с внешним набором использует `forRules()`; `from()` и `toArray()` его
автоматически не наследуют. Проверка входа не заменяет проверку wire-сериализации.

## Условные ветви

| Признак API или приложения | Куда перейти | Что должно быть установлено |
| --- | --- | --- |
| Несколько сервисов/версий | `guides/integration/multi-service.md` | Разные границы клиента и правила явного выбора версии |
| Token refresh и 401 | `reference/auth/tokens.md` | Фактический refresh-протокол, изоляция и безопасный повтор |
| Пагинация | `guides/recipes/pagination.md` | Путь элементов/меты, тип элемента и правило окончания |
| Отложенная готовность | `guides/recipes/continuation.md` | Ready/Pending/Failed, token/poll, финальный тип и ошибка |
| Файлы/архивы | `guides/recipes/files.md` | Формат тела, владение потоками и место хранения |
| Квоты между workers | `reference/execution/rate-limit.md`, `reference/integrations/redis.md` | Нужна ли общая атомарная квота; Redis не обязателен для ядра |
| Laravel/validation | `guides/integration/laravel.md`, `reference/client/validation.md` | Необходимые bindings и фабрика валидации |
| Каталоги и большой список операций | `guides/sdk/coverage.md` | Отличие read-only описаний от runtime meta |
| Проверка реального API | `guides/testing/live.md` | Отдельный opt-in, окружение, стоимость и разрешённые операции |

## Учебный SDK и повторное использование примеров

Сохранить `docs/example/` и добавить небольшой самодостаточный пример:

```text
docs/example/sdk/
  README.md
  bootstrap.php
  run.php
  fixtures/
    record.json
    error.json
  src/
    DemoClient.php
    Config/
      ClientConfigFactory.php
      HydrationRulesFactory.php
    Resources/
      Records/
        RecordsResource.php
        Get/
          GetRecordRequest.php
          GetRecordResponseDto.php
```

`bootstrap.php` подключает Composer autoload пакета и namespace примера без
require-dev. `run.php` использует MockTransport, читает только локальные фикстуры
и показывает успех и ошибку. Это образец SDK, а не второй HTTP-клиент.

По умолчанию пример показывает plain DTO и набор; компактный атрибутный пример
в companion-файле демонстрирует альтернативу без копирования целого SDK.
Если для сценария действительно нужен общий тип, его размещение определяется
областью использования: запрос → ресурс → Domain. Пустой Domain заранее не создаётся.

Guide ссылается на конкретные исходники и объясняет значимые строки. Один большой
PHP-блок не копируется в README, quickstart, методологию и тест. При переносе
исполняемые snippets и проверяющие их smoke меняются одновременно.

## Проверка понятности

Проверить одну пользовательскую задачу двумя способами: человек идёт по общему
маршруту, агент получает задание через agent-вход и тот же маршрут. Достаточно ли
материалов dist, виден ли следующий шаг, одинаковы ли контракт и критерии результата;
можно ли найти тип/политику без чтения внутреннего устройства ядра. Зафиксировать переходы и результат
в `route-review.md`; не выдавать проверку ссылок за проверку понятности.
Этот просмотр не требует привлечения отдельного агента или внешнего рецензента.
