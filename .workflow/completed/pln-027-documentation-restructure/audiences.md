# Аудитории: пользователь пакета и разработчик ApiSutra

Уточнение [плана 027](pln-027-readme.md) от 2026-09-15 по запросу владельца.
Разделяем материалы по тому, что человек изменяет. Использование ИИ не создаёт
третью предметную область и не меняет контракт пакета.

## Две области работы

| Аудитория | Задача | Вход и материалы | Окружение |
| --- | --- | --- | --- |
| Пользователь ApiSutra, в том числе разработчик SDK | Создать API-клиент, добавить операцию/DTO, настроить или расширить SDK через публичный API | `docs/README.md` → `docs/start/`; guides, reference, glossary, migration, example | Достаточно установленного пакета; исходники ядра изучать не требуется |
| Разработчик ApiSutra | Изменить `src/`, исправить механизм, поддержать тесты/сборку/документацию и выпустить сам пакет | `CONTRIBUTING.md` → `development/`; `AGENTS.md` / `.agents/` для правил, `.workflow/` для рабочих решений | Checkout ApiSutra, require-dev и инфраструктура проверки пакета |

Разработчик SDK провайдера — пользователь ApiSutra, даже если он пишет сложный код.
Реализация CastInterface, hook, extension, транспорта или фабрики через поддержанный
контракт также относится к использованию пакета. Изменение реализации Hydrator,
pipeline или механизма регистрации относится к разработке ApiSutra.

Практическая граница: «как подключить своё поведение» описывается в публичном
reference; «как устроен и изменяется механизм подключения» — в development.
Публичные семантика, ограничения и зависимости всегда остаются в docs, даже если
для их объяснения полезна схема жизненного цикла.

## Разделение файлов и навигации

- `README.md` прежде всего ведёт пользователя в docs. Разработка самого ApiSutra
  обозначена отдельной ссылкой на CONTRIBUTING в репозитории.
- `docs/start/` содержит только задачи пользователя. Маршрут `start/contribute.md`
  убирается из проекта; он смешивал две аудитории в одном списке.
- `CONTRIBUTING.md` — вход в разработку пакета; `development/` — архитектура
  внутренней реализации, тестирование ядра и сопровождение документации.
- Текущие `docs/technical/*` разделяются по содержанию: внутреннее устройство
  переходит в development, публичные гарантии — к владельцам в reference.
- `docs/glossary/` объясняет термины и поддержанные точки расширения пользователя.
  Внутренние помощники из прежних описаний переносятся в development либо удаляются
  как устаревшие; сам модификатор PHP `public` не доказывает пользовательский контракт.
- `.agents/` остаётся краткими инструкциями для работы в репозитории ApiSutra.
  Полные правила/примеры создания SDK имеют владельца в docs; внутренние инструкции
  не навязываются проекту пользователя. `.workflow/` не заменяет постоянный dev-guide.

У сопровождающего пакета также один источник публичного контракта — docs/reference.
В development не создаётся вторая спецификация поведения для внутреннего употребления.

CONTRIBUTING объясняет подготовку checkout и порядок внесения изменения. Индекс
development ведёт к устройству модулей, потокам выполнения, тестированию ядра и
сопровождению документации. `development/testing.md` описывает стенды и CI ApiSutra;
пользовательский `docs/guides/testing/` — проверку собственного SDK. Аналогично
`development/documentation.md` посвящён комплекту ApiSutra, а `docs/guides/sdk/release.md`
— документации и выпуску SDK пользователя. Короткие `.agents/` ссылаются на владельцев
этих правил и не копируют руководства целиком.

## Нужна ли отдельная документация для ИИ

Выбран общий комплект для человека и агента с коротким необязательным входом
`docs/start/agent.md`. Основной выбор — задача пользователя: новый SDK, операция,
DTO, подключение или диагностика. Agent-вход помогает передать эту задачу исполнителю.

| Вариант | Оценка |
| --- | --- |
| Полная отдельная ветка документации для ИИ | Дублирует правила и примеры; версии неизбежно расходятся. Не использовать. |
| Только общие страницы, без входа для агента | Сохраняет один источник, но не объясняет, какие сведения передать и какой результат ждать. |
| Общие страницы плюс короткий agent-вход | Сохраняет контракты и порядок в одном месте; помогает ограничить чтение конкретной задачей. Выбран. |

Agent-вход содержит только:

1. Формат задания: репозиторий SDK, новая или существующая реализация, цель,
   источники внешнего API, окружение и принятые ограничения.
2. Выбор **общего** маршрута по задаче и необходимые разделы для начала.
3. Короткий шаблон передачи результата: изменённые части SDK, проверенные примеры,
   выполненные команды и оставшиеся неизвестные условия API.

Порядок создания SDK, приоритеты, правила проверки фактов и критерии готовности
относятся ко всем исполнителям и живут в общих маршрутах/руководствах. Agent-вход
ссылается на них. Он не дублирует таблицы DTO, API и тестовый минимум, не добавляет
своих defaults и не становится обязательной главой для человека.

В `docs/start/README.md` сначала перечисляются пользовательские задачи, затем
предлагается необязательная ссылка «Передать задачу ИИ-агенту». Специальные правила
под конкретную модель, генерация копии всего комплекта и отдельный `docs/ai/`
в этот план не входят. Страница — читаемый документ, а не автоматически исполняемая
инструкция; пользователь может передать её своему агенту ссылкой.

Агент, который изменяет ApiSutra, работает в другой области: CONTRIBUTING,
AGENTS и правила checkout. Создание SDK через пакет само по себе не поручает ему
изменять пакет или его vendor-копию.

## Поставка и старые адреса

В Composer/Git dist остаётся весь пользовательский комплект, включая agent-вход
и примеры. `development/` и `CONTRIBUTING.md` исключаются из обоих архивов при
реализации вместе с уже исключёнными `.agents/`, `.workflow/` и AGENTS.

Ссылки из поставляемых страниц на разработку ведут в репозиторий по полному URL;
локальных ссылок на исключённые файлы быть не должно. Старые адреса `docs/technical/*`
сохраняются короткими переходами: публичная тема — по относительной ссылке на
reference, внутреннее устройство — по ссылке в репозиторий. В общем пользовательском
индексе эти переходы больше не образуют раздел «разработка ядра».

Приёмка отдельно проверяет комплект пользователя из dist и комплект разработчика
из checkout. Человек и агент проходят одинаковую предметную задачу по одному
контракту; различается только начальная подготовка задания.
