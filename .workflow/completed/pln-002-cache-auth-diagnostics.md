## Цель и основание

Устранить смешение ответов разных учётных записей, сохранение прежнего auth scope
после его сброса и раскрытие credentials в штатной диагностике. Это первый,
самостоятельно принимаемый этап выбранных частей AS-04/09/10 из
[ТЗ issue/001](../issue/001/technical-specification.md), а не реализация всего ТЗ.
Пользователь согласовал выбор приоритетного объёма и подготовку плана в обсуждении
2026-09-11. На момент создания плана реализация не была начата; поставка завершена 2026-09-12.
Фактический результат и проверки приведены в конце документа.

Уточнение от 2026-09-12: обязательный prefix и правила автоматической identity
пересмотрены в [pln-003](pln-003-automatic-cache-identity.md). Ниже сохранён объём
и результат первой поставки; актуальный контракт описан в профильных guides.

Основания: [аудит aud-001](../audit/aud-001-architecture-code-2026-09-11/aud-001-readme.md),
[пробы R02/R11/R12/R13/R15/R17](../issue/001/evidence/contract-probes.php) и

## Проверенные места и технические решения

### 1. Auth scope: исправить сброс без общей смены nullable-семантики

[RequestOptions::with()](../../src/Request/RequestOptions.php) использует `??`,
поэтому null, переданный из withAuth/withoutAuth/forceAuth, не очищает scope.
В том же копировании находятся необязательные TTL и connect timeout: безусловная
замена всех `??` изменит поведение несвязанных публичных методов.

- Для authScopeOverride различать отсутствие ключа и явно переданный null через
  проверку наличия ключа. Изменение ограничить необходимым полем; остальные опции
  не менять механически.
- Сброс удаляет runtime scope. Далее действует обычное разрешение авторизации:
  атрибут AuthScope, если он есть, сохраняет силу; без атрибута выбирается default.
  Сценарий R11 без атрибута должен вернуться к credentials A.
- В [AuthHandler](../../src/Pipeline/Auth/AuthHandler.php) проверить fallback
  от context options к исходному request: явно очищенный scope execution-копии
  не должен восстанавливать прежний runtime scope исходного объекта.
- Сохранить правила NoAuth, AuthPolicy и forceAuth, а также независимость копий.
  Несоответствия комментариев фактическому приоритету исправлять по существующим
  контрактным тестам, не вводя новый порядок авторизации в рамках этой задачи.

### 2. Кеш: явный контекст и один алгоритм идентичности

[RequestFlowRunner](../../src/Pipeline/Flow/RequestFlowRunner.php) читает кеш после
BeforeSend stages, auth и hooks. Однако
[CacheManager::clearCache()](../../src/Pipeline/Cache/CacheManager.php) выполняет
только сериализацию и overrides. Ключ сейчас исключает headers, отбрасывает query
из URL и сортирует элементы списков; явный ключ атрибута обходит расчётный ключ.

Выбранный подход для первой реализации:

- Использовать явный, несекретный контекст кеша. Переиспользовать
  CacheConfig::prefix как пространство provider/identity/tenant; для смены
  identity в одном клиенте добавить runtime `withCacheScope(string $scope)`
  через существующие options/execution adapters. Пустое значение этого override
  отклонять как ошибку конфигурации; отсутствие override использует prefix клиента.
- Не выводить identity из имени класса аутентификатора или названия scope:
  одинаковый scope `default` у двух клиентов не означает одну учётную запись.
- Без заданного пространства кеш не читать и не записывать; запрос выполняется
  обычным способом, причина пропуска доступна в безопасной диагностике.
  Это консервативный default и для анонимных запросов: общий публичный кеш
  включается явным пространством. Решение не зависит от угадывания произвольных
  provider credentials. Для R02 допустимы два HTTP-вызова без общего кеша;
  R17 подтверждает кеширование при явно разделённых пространствах.
- Фактический ключ строить после применимых преобразований из версии алгоритма,
  пространства, метода, полного URI, тела и headers. Сохранять порядок query,
  повторяющиеся параметры, значения и отсутствие тела. Имена headers сравнивать
  без учёта регистра. На первом этапе учитывать все headers: возможный лишний
  cache miss безопаснее объединения разных ответов. Исключение изменчивых headers
  и оптимизацию hit rate вынести отдельно.
- В store передавать только ограниченный по длине ключ с хешем; prefix, credentials,
  URI и пользовательский ключ не конкатенировать открытым текстом. По уточнению
  пользователя в ходе реализации `#[Cache(key: ...)]` сохраняет намеренное
  объединение URI/тела/headers внутри обязательного пространства identity/tenant.
  Автоматические ключи учитывают полные HTTP-данные. Это заменяет первоначальное
  предложение считать custom key только дополнительной меткой. Старые записи
  не читать новым алгоритмом; они истекают по прежнему TTL.
- Зафиксировать идентичность попытки до обращения к transport. Ответ после смены
  credentials при auth retry нельзя сохранить под ключом прежних credentials.
  Если точный ключ успешной попытки недоступен, пропустить запись с диагностикой.

Для очистки разделить точный ключ ответа и стабильную группу инвалидирования.
Группа определяется пространством и исходным запросом с runtime/pagination
options до auth refresh и BeforeSend hooks; точный ключ дополнительно учитывает
конечное HTTP-представление. Очистка запроса инвалидирует его варианты внутри
этой группы без выполнения auth refresh или пользовательских hooks.
В группу входят только настройки идентичности запроса; traceId, TTL и режим
чтения/записи не создают отдельные группы. Результаты двух клиентов с одинаковым
явным пространством и одинаковыми HTTP-данными должны переиспользоваться.
Это намеренное уточнение прежнего обещания удаления одной записи: оно позволяет
очистить ответы с меняющимся токеном или заголовком без повторения сетевых эффектов.

Реализованное инвалидирование — непрозрачная смена поколения группы,
входящего в точные ключи. Поколение сохраняется до отправки, чтобы начатый до
очистки запрос не записал старый ответ в новое поколение. До основной реализации
проверить на выбранном PSR-16 store создание поколения, его срок жизни и гонку
clear/write; не использовать сбрасываемый числовой счётчик, способный вновь
сделать старые записи доступными. Физическое удаление старых вариантов выполняется
их TTL. Это ограниченная внутренняя часть CacheManager, без нового общего cache backend.
Поколение пространства сохраняется без TTL; поколение группы — на `max(60, TTL)`
секунд. Новое случайное поколение после вытеснения/истечения исключает возврат
старых записей. Возможен дополнительный cache miss, срок жизни ответов не продлевается.
ReadOnly не создаёт служебных записей; WriteOnly читает только служебные поколения.
Для очистки всего пространства аналогично учитывать поколение пространства.
Ошибки записи служебного поколения не должны приводить к ложному успешному
кешированию или очистке; использовать существующий механизм сигнализации ошибок.

Отдельно изменить [AbstractClient::clearCache()](../../src/Core/AbstractClient.php):
сейчас он вызывает `store->clear()` и очищает всё общее хранилище. Целевой метод
инвалидирует только настроенное пространство клиента; без пространства является
no-op. Полная очистка backend остаётся явным действием его владельца.
Клиенты, намеренно использующие одно пространство, разделяют и инвалидирование;
разным identities нужно назначать разные пространства.

### 3. Допустимость кеширования и TTL

- Глобальная конфигурация автоматически допускает GET (политика также допускает
  HEAD, но новый HTTP-метод в enum этой поставкой не добавляется).
  Для остальных методов требуется opt-in на запросе: существующий `#[Cache]`
  либо runtime withCache/withCacheReadOnly/withCacheWriteOnly.
  Disabled запрещает чтение и запись независимо от метода.
  Проверять запрет обычного POST и его opt-in с заданным пространством, чтобы
  bypass из-за отсутствия prefix не маскировал ошибку политики HTTP-метода.
- Сохранить ограничения upload/download: uploads с файлами не кешировать,
  download допускается только существующим явным opt-in. Потоки не читать
  ради расчёта ключа. Полноценную потоковую обработку не добавлять.
- Записывать только успешный свежий ответ, прошедший штатную обработку результата.
  Cache hit не вызывает повторную запись и не продлевает TTL. Ошибки не кешировать.
- Сохранить runtime TTL, приоритеты настроек и режимы доступа. Имеющиеся тесты,
  закрепляющие одинаковый ключ для переставленных значений списка, заменить
  проверками различного наблюдаемого результата через публичный API.

### 4. Диагностика: общая политика на границе экспорта

[ExecutionResult::requestDebug()](../../src/Result/ExecutionResult.php) имеет
собственное маскирование, но возвращает URL без изменений.
[AuditLogger](../../src/Pipeline/Diagnostics/AuditLogger.php) передаёт context
как есть. [RecordingTransport](../../src/Transport/RecordingTransport.php)
применяет [FixtureRedactor](../../src/Testing/FixtureRedactor.php) только при
пользовательском Fixture. Поэтому настройки Fixture не закрывают остальные пути.

- Вынести переиспользуемую политику маскирования из отдельных потребителей
  в подходящий общий модуль; production logger не должен зависеть от Testing.
  Предусмотреть явную передачу дополнительных правил через конфигурацию,
  без глобального mutable registry.
- Базовые правила включены всегда для безопасного экспорта: Authorization,
  Proxy-Authorization, Cookie/Set-Cookie, стандартные API-key headers,
  известные token/password/secret-поля, URL userinfo и query credentials.
  Расширения добавляют provider headers, имена и пути полей.
- Обрабатывать регистр headers, вложенные JSON/form-поля, повторяющиеся query
  и percent-encoded имена. URL маскировать без потери повторяющихся параметров.
  Использовать metadata credentials enrichment для известных секретных полей.
- Recorder применяет базовые правила без Fixture; существующий Fixture добавляет
  правила и замены. Согласовать порядок так, чтобы расширение не отключало базовую
  защиту и сохраняло допустимые пользовательские replacement values.
- Маскировать копии. HTTP-данные, cache identity и исходные request/response
  остаются неизменными; stream не читать и не перематывать. Существующий явный
  `requestDebug(false)` сохраняет raw-доступ.
- Для неразбираемого структурированного тела безопасный экспорт не должен
  возвращать потенциальные credentials через fallback raw: использовать маркер
  пропуска. Произвольный текст ошибок и нестандартные форматы не объявлять
  автоматически очищенными; точные гарантии описать по поддерживаемым полям.
- Audit payload и прямой доступ к DebugInfo/response остаются raw-объектами;
  не объявлять их безопасным экспортом и не менять данные результата ради redaction.
  Новое общее API сериализации audit/debug относится к следующему этапу AS-10.

- фиксированный TTL, базовое маскирование recorder и границы raw debug;

Не предоставлять неявный legacy-режим смешения identities или раскрытия секретов.
Изменения публичного поведения отражать в документации вместе с реализацией,
не описывать целевой контракт как уже доступный до прохождения тестов.

## Критерии завершения

- Пройдены сценарии всех трёх шагов и общий набор тестов; команды, окружение
  и результаты записаны в плане, а не заменены ссылкой на старый baseline.
- Нет смешения identities в кеше, восстановления сброшенного runtime scope
  и утечек известных/настроенных credentials через перечисленные safe exports.
- Очистка изолирована и не вызывает auth refresh; чтение не продлевает TTL.
- Обновлены guides и migration notes, проверены ссылки и исполняемые примеры
  затронутого API; новое поведение работает без Laravel.
- В итоговом отчёте перечислены именно выполненные части AS-04/09/10.
  Остальные требования ТЗ сохраняют статус будущих работ.

После выполнения критериев перенести весь план в `completed/`, изменить статус
на `завершён`, дату обновления и ссылку в индексе workflow. Публикация релиза
и изменение статуса отложенного async-плана в эту работу не входят.
