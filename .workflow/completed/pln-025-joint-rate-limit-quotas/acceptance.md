# Приёмка и ожидаемое поведение

Матрица реализации [025](pln-025-readme.md) выполнена;
[итоги и привязка к проверкам](implementation.md). Baseline описывает прежнее поведение. Основные backend-сценарии выполнить одним
контрактным набором для локального backend и настоящего Redis, где применимо.

Критерии соответствуют подтверждённым 2026-09-13 [В1/В2](peer-review.md): один
клиентский rateLimit как общая квота и полное отключение через withoutRateLimit.

## Конфигурация и совместимость

| ID | Сценарий | Проверяемый результат |
| --- | --- | --- |
| C1 | Старые named/positional constructors, клиентский лимит с атрибутом/runtime | Синтаксис прежних вызовов сохранён; поведение теперь совместное. Отдельный regression на согласованное изменение; несвязанные контракты ошибок/результата не меняются |
| C2 | Нет применимых квот / backend=null при одной или двух квотах без store | Без квот нет backend calls/I/O; без внешнего backend квоты работают локально. Обычная установка не требует redis |
| C3 | with(), изменение другого поля, замена/null и fromLaravel | Два новых поля и rateLimit сохраняют значения, backend сохраняет identity; null действительно отключает optional компонент |
| C4 | Полная пара атрибута / include-only / пустой атрибут | Собственная пара либо отсутствие квоты от атрибута, корректное участие; request/runtime сохраняется, общий rateLimit не копируется в собственную квоту |
| C5 | Половина пары, неположительное/переполнение, key/Throw без пары | Configuration error до списания и HTTP |
| C6 | Пользовательский extension/подкласс/reflection consumer атрибута | Встроенные consumers поддерживают nullable; реальные ограничения типовой BC записаны в миграции |
| C7 | Одна применимая квота со store, backend=null; прямой acquire | Прежний одиночный storage/key path, наследование store, контракт ошибок; без обещания межпроцессной атомарности |
| C8 | Store + явный backend / две квоты хотя бы с одним применимым store | Configuration error до чтения/записи store и HTTP; конфликт backend/store конфига — при создании клиента, совместного набора — при разрешении |
| C9 | withoutRateLimit, затем withRateLimit; request/options wrappers | Полное отключение/повторное включение по контракту, без потерянных overrides |
| C10 | InvalidRateLimitRequest и новые неполные пары: metadata/spec/inventory, затем send | Чтение метаданных не добавляет value-validation exception; применение даёт configuration_error до store/HTTP; прежний execution test сохраняется |
| C11 | period=60 секунд, нормализация для стороннего backend; границы чисел | periodMs=60000; timeoutMs/retryAfterMs явно в ms, retryAfter исключения в секундах; переполнение отвергается до acquire |
| C12 | Миграция существующего клиента на совместные квоты | Проверяемый пример до/после, изменённый расход, конфликт store, граница окна и отсутствие обещания переноса счётчиков; сценарий соответствует ответу В1 |
| C13 | Laravel-рецепт с именованным phpredis connection и сборкой в ServiceProvider (этап B) | Адаптер получает исходный клиент, поддерживает документированные options; config:cache работает без объектов соединения в config; наличие Laravel/Redis само не включает backend, обычное соединение кеша не перенастраивается |
| C14 | Общая квота со store + собственная без store; include=false; явный собственный store | Совместный набор отвергается из-за store общей квоты; одиночная собственная наследует store только без backend; явный собственный store имеет приоритет; нет скрытого fallback в атомарном наборе |

## Совместные квоты и ключи

| ID | Сценарий | Проверяемый результат |
| --- | --- | --- |
| Q1 | Client=100/min, reports=5/min | Пять отчётов расходуют пять единиц обоих счётчиков; шестой не списывает ни один |
| Q2 | Уже 98 других запросов, reports ещё пуст | Разрешены два отчёта, третий отклонён общей квотой без расхода квоты reports |
| Q3 | include=false на отчёте | Расходуется только reports, общая квота неизменна |
| Q4 | include-only=false при общем rateLimit; без/с собственным request/runtime override | Без собственного override набор пуст; с override действует только он. Общий лимит не становится собственным |
| Q5 | client include=false / request true; rateLimit клиента отсутствует | Явное участие действует только для существующего определения |
| Q6 | Два request класса без custom key; два экземпляра одного класса | Разные operation counters; одинаковый класс делит свой counter |
| Q7 | Одинаковый custom key у двух операций | Одна operation group, только при согласованных limit/period |
| Q8 | Одинаковый текст custom key у client и operation | Разные kind, нет случайного двойного расхода одного счётчика |
| Q9 | Один active ID, несовместимые limit/period; повтор ID в наборе | Конфликт не сбрасывает окно и не списывает; идентичный дубль списывается один раз |
| Q10 | Разные scope / одинаковый scope двух клиентов | Изоляция / явное объединение в Redis; локальные clients не объединяются автоматически |
| Q11 | Разные периоды, граница окна, истечение TTL | Корректное создание новых окон только при grant; deny не сдвигает reset |
| Q12 | Локальный clock: wall time скачет вперёд/назад, monotonic движется независимо | Окно зависит только от monotonicMs; за 1 ms до reset — deny с retryAfterMs=1, в reset — grant; ClockInterface не расширен, PSR-16 формат Unix секунд сохранён |

## Ожидание, попытки и ошибки

| ID | Сценарий | Проверяемый результат |
| --- | --- | --- |
| E1 | Заблокированы два Wait лимита с разными reset | Ожидание максимума, затем повторная проверка всего набора, без частичного резервирования |
| E2 | Блокирующий Throw / неблокирующий Throw + блокирующий Wait | Немедленный отказ / разрешённое ожидание соответственно; при нескольких blockers retryAfter — максимум всех окон с округлением вверх в секунды (1200/9100 ms → 10 s) |
| E3 | Ожидание равно или больше remaining budget | Timeout без sleep и без HTTP, как в существующем ExecutionBudget |
| E4 | Backend медленный, успех/ошибка после deadline | HTTP не отправлен, корректный stage и previous, нет повторного списания |
| E5 | Retry 503, успешный auth recovery/401 repeat | Каждая фактическая HTTP-попытка получает свежий набор разрешений; safety/replay контракт не меняется |
| E6 | Auth refresh и depends-on, операция исключена из общей квоты | Каждое HTTP учитывается по правилам своего класса и фактически исполняющего клиента |
| E7 | Cache hit, composite без HTTP | Нет quota acquire; реальные дочерние HTTP учитываются |
| E8 | Batch/pool sync/async, страницы paginator | Проверка перед каждой попыткой, без обещания реального parallel I/O или нового execution scope |
| E9 | Неподдерживаемый transport/timeout/destination/body в обоих режимах, включая исчерпанную квоту | Доступные локальные проверки отказывают до acquire; backend не вызван; единый порядок, новая приоритетная локальная ошибка явно записана в миграции/changelog |
| E10 | Grant, затем deadline/worker failure/HTTP exception | Refund не происходит; нет второго HTTP/acquire от автоматического backend retry |
| E11 | Backend failure / malformed decision / secret in previous | Терминальная локальная ошибка, безопасная диагностика; result-first/throw/Promise сохраняют контракт |
| E12 | fake/record/playback на частично израсходованной квоте | Сохраняются limiter/backend identity и счётчики, меняется только путь transport |
| E13 | Acquire ждёт, затем retry backoff дополнительно тратит budget | HTTP получает актуальный effective timeout после обоих ожиданий; preliminary capability check не публикует options в preparedRequest, отказ до acquire не расходует квоту |
| E14 | Одинаковая последовательность denied/granted локального и внешнего backend, включая Wait/Throw и deadline | Одинаковое поведение общего RateLimiter; sleeper вызывается организатором, backend не ждёт квоту и не повторяет acquire самостоятельно |

## Реальные конкурентные процессы Redis

Запускать несколько отдельных PHP workers с независимыми соединениями и одним
test scope; координация старта барьером, не надеждой на случайную гонку. Тестовые
scope уникальны для запуска, очищать только их ключи. Не выполнять FLUSHDB общего
пользовательского Redis. Для SCRIPT FLUSH использовать отдельный тестовый сервер.

| ID | Проверка | Ожидание |
| --- | --- | --- |
| R1 | Два workers, один слот общей квоты | Ровно один granted, второй denied, расход соответствует одному разрешению |
| R2 | Разные операции конкурируют за общий остаток | Сумма grants не превышает общий остаток, каждая операция соблюдает свой предел |
| R3 | Одна квота исчерпана, другая свободна | Ни один worker не изменяет свободную квоту при deny |
| R4 | Повторный concurrent acquire после границы окна | Новое окно общее; гонка не создаёт несколько независимых окон |
| R5 | Разные часы PHP workers | Решение общей квоты определяется временем Redis, local budget остаётся корректным |
| R6 | NOSCRIPT после очистки script cache | Script восстановлен, одна успешная выдача, не двойное списание |
| R7 | Разрыв соединения после отправки команды | Счётчик может быть списан, HTTP не отправлен; автоматического acquire retry нет |
| R8 | Некорректное состояние/ACL/OOM/недоступный Redis | Нет allow/fallback; при отказе до commit счётчики неизменны |
| R9 | Ошибка после общей MSET, например TTL | Нет HTTP, счётчики либо все списаны, либо не изменены до commit; частичное списание не допускается |
| R10 | Опции auto retry/pipeline/serializer, отсутствующий ext-redis | Адаптер либо приводит выделенное соединение к документированному режиму, либо отклоняет конфигурацию; не выполняет скрытые повторные записи |

Fault injection для R7–R9 должна реально контролировать момент сбоя (прокси/тестовый
script/ACL на изолированном сервере); простое исключение до вызова не доказывает
поведение после commit. Начать с минимального стенда: ACL для проверяемых ошибок
команд, изолированный script для границы commit; для R7 — небольшой тестовый прокси,
подавляющий ответ после подтверждённой отправки команды. Не создавать универсальную
chaos-платформу и не добавлять её зависимости в SDK. Искусственная ошибка Lua доказывает
только соответствующий сценарий, а не автоматически произвольный OOM/падение Redis.
Production script и фактический протокол также проходят
обычные concurrency tests; тестовый сценарий не подменяет их.

## Стоимость и хранение

Зафиксировать воспроизводимый локальный benchmark для: лимиты выключены; одиночный PSR-16;
одна/две локальные квоты; Redis с тёплым/холодным script cache и отказом. Считать
backend calls, Redis round trips, число созданных объектов/память и время на попытку.
Для объектов достаточно проверить отсутствие создания соединения/backend на каждую
попытку и измерить память; отдельный profiler для точного подсчёта всех аллокаций не нужен.
Числа сохранять с версиями PHP/Redis/phpredis и условиями; не назначать произвольный
процент допустимой просадки и не превращать шумный wall-time benchmark в CI assertion.

Структурные обязательные проверки: ноль backend calls без квот; одно tryAcquire на
набор; без новых checks/pings/locks/connection на каждый запрос; без загрузки всего
аккаунта при одной операции. Локальная очистка истёкшего состояния и Redis TTL
не должны оставлять неограниченную историю окон; при ошибке TTL диагностировать сбой,
не объявлять гарантированную очистку исправной.

## Команды, CI и документация

Этап A можно слить после C1–C12/C14/Q/E, локальной части измерений, общих composer-проверок,
документации и changelog реализованного поведения. R-критерии помечены «ещё не выполнены»;
межпроцессное решение не объявляется готовым. Этап B требует R1–R10 на настоящем Redis, C13,
Redis CI, installed-package smoke с ресурсом Lua и обновлённых примеров адаптера.
Каждый этап самостоятелен для ревью; завершение A не закрывает план 025.

После целевых тестов новых contracts/backend/RateLimit/Retry/Timing/Config:

```bash
composer test
composer lint
composer analyse
composer check-docs
composer check-package
```

Отдельный CI job включает Redis service и phpredis: нижний заявленный профиль и
актуальный поддерживаемый, PHP 8.4/8.5. Обычные jobs продолжают проверять пакет без
redis. Интеграционные tests могут явно пропускаться локально без backend, но не
должны молча пропускаться в обязательном Redis job. Проверить Lua resource в архиве
и smoke установленного пакета, не расширять PHPStan baseline ради новых неточных типов.

Обновить docs/guides/client-config/rate-limit.md, docs/guides/attributes/behavior.md,
docs/guides/retries-rate-limit.md и ссылки индексов. Отдельно описать миграцию прежнего замещения
к совместным квотам, участие, withoutRateLimit, nullable attribute migration, fixed
window, scope и переход namespace. В Redis guide показать подготовку соединения,
отключение auto retry, timeouts, требования к состоянию сервера и потери разрешений
при неизвестном исходе. Пользователь не должен сочинять Lua или алгоритм ожидания.
Дать рецепт миграции с отказом от несовместимого rate-limit store и согласованным
переключением окон/workers. Явно описать fail-closed при недоступности Redis, noeviction,
сеть и разницу HTTP timeout/общего budget. Это не новая обязательная инфраструктура
для локального пользователя. Inspect/остатки не входят в критерии первой поставки.

Готовность означает выполнение всех применимых C/Q/E/R критериев, а не только
успешный локальный unit suite. Обновлены документация/changelog, записаны ограничения
совместимости и измерения. Только после этого план переводится в completed.
