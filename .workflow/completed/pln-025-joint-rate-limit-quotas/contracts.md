# Контракты совместных квот

Все новые типы/параметры — проект реализации [025](pln-025-readme.md). Примеры не
описывают доступные сегодня возможности. Это настройка квот, без системы профилей
или административного источника политик в SDK.

Владелец 2026-09-13 подтвердил [В1/В2](peer-review.md): один rateLimit клиента задаёт
суммарную квоту, атрибут/request/runtime — собственную квоту операции, withoutRateLimit
отключает весь набор. Исходный проект отдельного поля clientQuota заменён этим контрактом.

## Настройки клиента

| Поле | Default | Значение |
| --- | --- | --- |
| rateLimit | null, как сейчас | Суммарная квота клиента; существующий RateLimitConfig с новым назначением |
| includeClientQuota | true | Участие операций в общей квоте, если атрибут не уточнил его; без rateLimit эффекта нет |
| rateLimitBackend | null | Атомарный backend для всего набора; null выбирает локальную реализацию, кроме явного совместимого PSR-16 пути одной квоты |

Новые аргументы добавляются в конец ClientConfig. Конфиг не содержит Redis DSN,
паролей, closures источников настроек и registry адаптеров: передаётся готовый объект.
Один RateLimiter на клиент владеет локальным состоянием и использует выбранный backend.

```php
use Brahmic\ApiSutra\Config\ClientConfig;
use Brahmic\ApiSutra\Config\RateLimitConfig;

// Проект API: локальная суммарная квота, без дополнительной инфраструктуры.
$config = new ClientConfig(
    baseUrl: 'https://provider.example',
    rateLimit: new RateLimitConfig(limit: 100, period: 60),
);
```

```php
use Brahmic\ApiSutra\Config\ClientConfig;
use Brahmic\ApiSutra\Config\RateLimitConfig;
use Brahmic\ApiSutra\RateLimiting\Backends\PhpRedisRateLimitBackend;

// Проект API: соединение уже подготовлено приложением для адаптера.
$config = new ClientConfig(
    baseUrl: 'https://provider.example',
    rateLimit: new RateLimitConfig(limit: 100, period: 60),
    rateLimitBackend: new PhpRedisRateLimitBackend(
        redis: $redis,
        scope: 'provider-example/account-42',
    ),
);
```

scope — непрозрачный стабильный идентификатор совместного учёта. Один scope для
одного набора общих квот на одном Redis backend; разные подключения/аккаунты — разные
scope, если внешний API не задаёт иного. SDK провайдера может формировать его при
создании клиента. Ядро не извлекает его из credentials автоматически и не требует
scope для обычного локального режима. Это не ручная настройка технического префикса:
namespace/key hashing автоматические, scope определяет продуктовое объединение.

Приложение вправе явно разделять один backend между клиентами одной группы; это
объединяет их квоты. Просто создать несколько локальных клиентов — не объединение.
Смена/ротация credentials сама по себе не должна сбрасывать stable scope общего счётчика.

## Атрибут

Проект сигнатуры, остальные параметры сохраняют порядок и defaults:

```php
public function __construct(
    public ?int $limit = null,
    public ?int $period = null,
    public RateLimitBehavior $behavior = RateLimitBehavior::Wait,
    public ?string $key = null,
    public ?bool $includeClientQuota = null,
) {
    // Атрибут хранит объявление; применимые значения проверяет resolver при выполнении.
}
```

```php
#[RateLimit(limit: 5, period: 60)]
#[RateLimit(limit: 5, period: 60, includeClientQuota: true)]
#[RateLimit(limit: 5, period: 60, includeClientQuota: false)]
#[RateLimit(includeClientQuota: false)]
```

Выше четыре альтернативы для разных классов запросов, не повторяемый атрибут на одном
классе. Одна попытка расходует одну единицу каждого выбранного лимита; limit=5 не
означает стоимость запроса в пять единиц общей квоты.

- Оба limit/period заданы: атрибут определяет собственный лимит операции.
- Оба отсутствуют: атрибут не создаёт собственного лимита. Собственный request/runtime
  override, если есть, сохраняется; общий rateLimit действует только по правилу участия.
- Задана только половина пары, неположительное/непредставимое значение: configuration_error
  при применении атрибута в выполнении, до backend/HTTP. Валидация не должна раскрывать
  исходные секретные значения. Конструктор атрибута не переносит эти проверки в metadata
  discovery: создание RequestSpec/operationInventory само по себе не применяет лимиты.
- null includeClientQuota наследует bool клиента, true/false задают участие явно.
- Пустой RateLimit() эквивалентен отсутствию overrides. key без собственной пары
  либо behavior, отличный от default Wait, без пары отклонять: не игнорировать параметры.
  Изменение поведения общей квоты задаётся её конфигом клиента, не этим полем атрибута.

### Совместимость атрибута

Старые записи с limit/period синтаксически сохраняются и задают собственный лимит;
при наличии общего rateLimit они теперь дополняют его, а не заменяют. Это согласованное
изменение поведения. Кроме того, int → ?int у публичных
readonly свойств — расширение контракта, а не абсолютно прозрачная типовая правка.
Сторонние обработчики, подклассы с переобъявлением свойств, metadata exporters и reflection
проверки могут потребовать адаптации. Все встроенные consumers должны различать
«собственная пара отсутствует» и конкретное значение; null не превращается в 0.

До выпуска проверить extension scenarios и требования версии пакета. Документировать
миграцию для прямых потребителей атрибута; не обещать им строгую типовую BC лишь потому,
что старые attribute declarations продолжают работать. Не заменять null фиктивным int
и не менять старые limit/period defaults молча ради формального сохранения типа.

Встроенный путь: RequestSpecResolver создаёт атрибут, RequestSpec его хранит,
RequestSpecAccessorsTrait отдаёт, RateLimitApplier применяет. Проверить все четыре
места и inventory через resolver. Существующий InvalidRateLimitRequest должен по-прежнему
давать configuration_error через send(), а не новое исключение при чтении каталога.
Строгая PHP-проверка типов аргументов остаётся; это правило о валидации значений/пары.

## Разрешение правил перед попыткой

1. Определить полное runtime withoutRateLimit. Если включено — набор пуст и backend
   не вызывается. withRateLimit после него снова включает rate limiting по существующей
   семантике; участие в общей квоте определяется клиентом/атрибутом.
2. Разрешить собственный лимит: options override → request override → атрибут с полной
   парой → отсутствие собственной квоты. ClientConfig.rateLimit больше не служит fallback
   собственной квоты. Атрибут только с участием этот выбор не заменяет. Унаследованный
   PSR-16 store, если нужен прежнему одиночному пути, разрешается отдельно от чисел лимита.
3. Определить includeClientQuota: атрибут ?? клиент. При наличии rateLimit и true
   добавить суммарную квоту, независимо от наличия собственного лимита.
4. Построить идентификаторы и валидировать набор; получить разрешение один раз на
   весь набор. Для пустого набора не создавать backend, не читать store.

| Условия | Применяемые квоты |
| --- | --- |
| Нет настроек | Ни одной |
| Только rateLimit клиента | Суммарная |
| Только атрибут/request/runtime с парой | Собственная операции |
| rateLimit клиента + атрибут/request/runtime с парой | Суммарная + собственная операции |
| То же, includeClientQuota=false | Только собственная |
| rateLimit клиента + атрибут только include=false, собственного override нет | Ни одной; из общего числа не создаётся собственная квота |
| То же, собственный request/runtime override задан | Только собственная из override |
| Клиент include=false, атрибут include=true | Суммарная включается при наличии её определения |
| include=true, но rateLimit клиента=null | Общая квота не создаётся; применяется собственный лимит, если есть |
| withoutRateLimit | Ни одной; это явный полный override, не обход неизвестного запрета SDK |

Отдельные runtime-методы для участия не добавляются в первую поставку. Атрибут
поддерживается существующим request metadata path; произвольный RequestInterface
не получает новую магию introspection атрибутов, которой раньше не было.
Для RequestInterface вне AbstractRequest сохраняется отсутствие request/options
overrides rate limiting; применяется только rateLimit клиента с клиентским флагом участия.

## Выбор backend и сохранённый PSR-16 путь

Сначала разрешается один набор по новой семантике. Отдельного opt-in совместных квот
или режима прежнего замещения нет. При отсутствии применимых квот backend не вызывается.
При построении набора сохранить происхождение явных store, не подмешивать клиентский
store в каждую операционную квоту заранее. Наследование относится только к кандидату
на одиночный PSR-16 путь: одна квота, rateLimitBackend=null. Для него после определения
состава набора разрешается fallback store и выбирается PSR-16 либо локальная реализация.

При заданном rateLimitBackend весь набор использует этот backend. При null и отсутствии
store используется локальный атомарный backend, в том числе для единственной квоты.
Локальная память остаётся per-instance, межпроцессной гарантии у неё нет.

PSR-16 поддерживается только для одной применимой квоты, если rateLimitBackend=null.
Для собственной квоты store определяется по прежнему правилу: собственный override.store
либо клиентский rateLimit.store; атрибут может наследовать только store, не числа общей
квоты. Этот путь использует прежний RateLimiter::acquire и прежний key, не обещает
атомарности между workers. Сам публичный прямой acquire также сохраняется.

Две применимые квоты с ненулевым store либо явный backend вместе с применимым store —
configuration_error до учёта/HTTP. Не игнорировать store и не выполнять половину acquire
в Redis, а половину в PSR-16. CacheConfig.store для HTTP/auth остаётся независимым.
Явный конфликт ClientConfig.rateLimit.store и rateLimitBackend проверяется при создании
клиента; request-level/совместные конфликты — при разрешении набора. Полное runtime
отключение не обращается к store и не разрешает квоты, но не отменяет уже выполненную
валидацию конструктора конфига. Рецепт миграции обязан раскрывать эту границу совместимости.
Пример: общая квота со store + атрибут операции — настоящий несовместимый набор,
даже если собственный store операции не задан. Отсутствие наследования не разрешает
игнорировать store самой общей квоты. При include=false и одной собственной квоте
без явного backend fallback к клиентскому store, наоборот, сохраняется.

## Идентичность и определения

Только в сохранённом одиночном PSR-16 пути используется прежний pipeline key
`hash('sha256', 'apisutra.rate-limit.v2:' . rawKey)` с fallback rawKey=baseUrl;
прямому acquire готовый key передаёт вызывающий код. Для атомарных backend, включая
локальный default, используется новый версионированный namespace:

- Суммарная квота: kind=client + ClientConfig.rateLimit.key либо постоянная группа client.
- Квота операции: kind=operation + effective custom key либо class-string фактически
  исполняемого запроса. Два экземпляра одного request class расходуют одну квоту.
- Оба key помещаются в scope выбранного backend; kind предотвращает коллизию общей
  и собственной квоты при одинаковом тексте custom key. Идентификаторы хешируются.
- Не включать query/body/traceId/случайный ID/limit/period в ключ автоматически.
  Явный custom key может объединить несколько request classes; это ответственность SDK
  провайдера/приложения. У разных классов по умолчанию раздельные счётчики объявленных
  собственных квот; без определения собственная квота не создаётся.

Правило для одной активной logical quota атомарного backend должно иметь одинаковые
limit/period во всех workers. Конфликт определения — configuration_error без списания. Это
относится и к разным runtime overrides одного ключа в действующем окне: их нельзя
использовать для сброса счётчика. После окончания окна можно начать новое с новым
определением; согласованное развёртывание конфигурации обеспечивает приложение.
behavior не часть identity/счётчика: он определяет реакцию конкретного выполнения.

Переход на новый backend/namespace не переносит старое состояние автоматически.
Документировать переключение после завершения прежнего окна либо контролируемую
паузу приложения; не обещать непрерывную квоту при смешанной работе legacy/new workers.
Не менять scope произвольно при каждом запросе: это создаёт независимые счётчики.

### Миграция существующего клиента

Назначение rateLimit меняется без переименования поля. Это проект upgrade notes
будущего выпуска, не описание уже реализованного поведения.

```php
use Brahmic\ApiSutra\Config\ClientConfig;
use Brahmic\ApiSutra\Config\RateLimitConfig;

// Объявление клиента остаётся прежним; rateLimit теперь задаёт общую квоту.
$config = new ClientConfig(
    baseUrl: 'https://provider.example',
    rateLimit: new RateLimitConfig(limit: 100, period: 60),
);

```

1. Проверить назначение прежнего rateLimit. Если нужен общий предел, оставить определение
   клиента и проверить атрибуты/overrides. Если нужен только заменяемый default, прежнюю
   схему нельзя считать сохранённой: явные лимиты операций задаёт SDK провайдера, ненужный
   общий rateLimit убирается. Не вводить второе клиентское поле взамен отвергнутого default.
2. Атрибут отчёта 5/60 теперь расходует и общий 100/60, и собственный 5/60; остальные
   операции без собственного лимита расходуют только общий. Исключения объявить явно.
3. Ненулевой прежний rate-limit store убрать из совместного набора. Для одного клиента
   можно выбрать локальный backend; для нескольких workers подключить Redis/phpredis
   с одним согласованным scope. Кеш HTTP/auth из-за этого не менять. Оставленный store
   в совместном наборе должен дать configuration_error, а не тихо перестать использоваться.
   Одиночный PSR-16 путь без явного backend остаётся доступен с прежними ограничениями.
4. Не переносить старые счётчики механически: прежде могли смешиваться разные правила
   одного ключа. Приложение останавливает новые попытки старых workers, завершает текущие,
   дожидается окончания соответствующих старых окон и затем запускает новый режим.
   Не смешивать два namespace в расчёте на единый общий предел. SDK не управляет этим rollout.
5. Проверить свой лимит и key каждой операции, общий расход и ошибки до включения
   реальной отправки. Новые счётчики стартуют пустыми; это причина согласования границы окна.

До изменения отчёт с атрибутом 5/60 применял только это правило (возможно к тому же
ключу, что и default). После — два независимых правила 100/60 и 5/60. Для исключения
отчёта из общей квоты используется includeClientQuota=false; для отключения обеих —
withoutRateLimit(). Это не обещание точного восстановления старой группировки счётчиков.

## Контракт backend и ожидание

```php
interface RateLimitBackendInterface
{
    /** @param list<RateLimitQuota> $quotas */
    public function tryAcquire(array $quotas, ?int $timeoutMs = null): RateLimitDecision;
}
```

RateLimitQuota — immutable нормализованный key/limit/periodMs; limit — число разрешений,
periodMs — положительная длительность окна в миллисекундах. Публичные RateLimitConfig.period
и RateLimit.period остаются в секундах: resolver переводит их в ms один раз с проверкой
переполнения. timeoutMs — доступная длительность одного tryAcquire, null означает отсутствие
внешнего budget, но не отменяет конечный I/O timeout адаптера. Соответствующий behavior
хранит организатор набора. RateLimitDecision — granted либо denied с непустым списком
blocked quota IDs и положительным retryAfterMs. Granted не содержит blocked IDs/ожидания.
Результат проверяется: неизвестные IDs/отрицательное ожидание/неверные типы — ошибка
backend, а не allow или busy-loop. Повтор одного ID с одинаковым правилом нормализуется
в одно списание, противоречивый дубль отклоняется. Core строит максимум две квоты;
контракт работает со списком, без новой публичной системы конфигурации произвольных деревьев.

Backend не спит, не выполняет HTTP и не делает retry после неопределённого исхода.
Он проверяет все правила и либо расходует единицу каждого, либо возвращает deny
без изменения счётчиков. Источники времени различаются без расширения ClockInterface:

- Локальный атомарный backend: monotonicMs() clock, переданного при создании backend.
  Окна и очистка его per-instance состояния используют одну шкалу; unixTime не влияет
  на reset. Не менять clock этого состояния на clock очередного родительского budget.
- Сохранённый одиночный PSR-16 путь и прямой RateLimiter::acquire: прежний unixTime()
  в секундах. Значения состояния могут разделяться процессами; формат не меняется.
- Redis: серверный TIME, перевод в ms внутри script. Внешний backend не получает
  абсолютный monotonic deadline другого процесса.

retryAfterMs всегда относительный. Budget отдельно считает оставшуюся длительность
по своему clock. Локальный reset = monotonicMs + periodMs проверяется на переполнение;
монотонная отметка не экспортируется как Unix timestamp. Новый публичный метод часов,
синхронизация часов workers или дополнительный clock adapter не нужны.

RateLimiter передаёт оставшийся budget как timeoutMs, проверяет budget до/после acquire.
Если среди блокирующих квот есть Throw — немедленный RateLimitException с retryAfter,
равным округлённому вверх в секунды максимуму retryAfterMs всех блокирующих квот,
включая Wait. Например, Throw освободится через 1200 ms, Wait через 9100 ms: retryAfter=10.
Это оценка по снимку; другой worker может занять место, гарантии будущего allow нет. Иначе ждёт
максимальный срок среди блокирующих окон через ExecutionBudget.wait и повторяет проверку
всего набора. Неблокирующая квота с Throw не запрещает ждать другую. Ожидание не держит
распределённую блокировку или частичное разрешение. Порядок/справедливость workers не обещаются.
Для локального и Redis backend существует один общий цикл acquireAll в RateLimiter:
tryAcquire → проверка budget/decision → Throw либо ExecutionBudget.wait → повтор всего
набора. Backend не содержит собственного quota wait/retry loop. Существующий прямой
legacy acquire сохраняет контракт; не создавать универсальный callback-framework
ради принудительного объединения старого секундного и нового миллисекундного storage API.

## Окна, ошибки и пределы гарантий

Алгоритм остаётся fixed window, начинающимся с первого успешного расхода после
отсутствующего/истёкшего состояния. Разные квоты могут иметь разные периоды/границы.
Не добавлять token bucket, sliding window, weighted costs или распределённый semaphore.

Сохранить существующую доставку:

- Исчерпание без ожидания: rate_limited, reason=local_rate_limit_exceeded, собственный response исключения=null,
  retryAfter в прежних секундах (округлять вверх из ms). Это не реальный HTTP 429 сервиса.
- Backend failure: существующий RateLimitBackendException/классификация execution_error,
  reason=rate_limit_backend_error, stage=rate_limit_store; previous доступен явно.
- Deadline: существующий timeout и соответствующий stage rate_limit_wait/store/before_http.
- Ошибка конфигурации/определения: configuration_error до HTTP, без автоматического retry.

После предыдущей HTTP-попытки ExecutionResult может сохранять её реальный response
через lastResponse; response=null выше означает отсутствие ответа на новый локально
запрещённый вызов, а не удаление диагностического ответа предыдущей попытки.

Не логировать Redis connection/credentials/raw scope, значение ключа или сырой текст
backend exception. Результат/throwOnErrors/Promise/parent lastResponse не должны терять
реальную предыдущую HTTP-ошибку или приписывать её запрещённой новой попытке.

При обычном deny ни одна квота не списана. После успешного grant, неизвестного сетевого
исхода или остановки worker возможен расход без HTTP; автоматического refund нет.
Между grant и фактической отправкой нет транзакции с внешним API. Не обещать точное
совпадение счётчика SDK с биллингом сервиса, exactly-once доставку и сохранность квоты
при потере/очистке состояния backend.

Read-only inspect(), полный остаток/reset по всем квотам и планировщик очередей
отложены до отдельной подтверждённой потребности. Текущего blocked IDs/retryAfterMs
достаточно для решения acquire/Wait/Throw; это не обещание будущего разрешения.
