# Первый готовый атомарный backend: Redis через phpredis

Выбор backend подтверждён владельцем 2026-09-13. Алгоритм и настройки ниже реализованы в
[025](pln-025-readme.md); [результаты конкурентных тестов](implementation.md).

## Почему этот вариант

Использовать один готовый PhpRedisRateLimitBackend со встроенным параметризованным Lua
script. Приложение передаёт выделенное соединение и stable scope, не пишет Lua/locks.
Ядро переиспользует существующий RateLimiter/ExecutionBudget; альтернативный полный
RateLimiter, общий DI registry и система lock lease не требуются.

Redis выполняет Lua script без вмешательства других команд в середину исполнения.
Один EVALSHA позволяет проверить связанные ключи и решить вопрос в одном обращении;
script cache может исчезать, поэтому требуется обработка NOSCRIPT. Это подтверждается
[официальным описанием Lua scripting](https://redis.io/docs/latest/develop/programmability/eval-intro/).

Начальный целевой профиль: Redis standalone 7.0+ и phpredis 6.2+. Нижние версии должны
реально пройти CI перед объявлением поддержки; это целевая матрица, не результат
проверки в текущем окружении. RedisCluster, active-active, Sentinel orchestration,
Predis/Laravel adapters не входят в первую поставку. Сервером и отказоустойчивостью
управляет приложение; ядро не устанавливает и не запускает Redis.

## Ключи, состояние и часы

Key: постоянный namespace версии + hash(scope) + kind + hash(logical quota ID).
Redis не получает raw scope, credentials и полное описание HTTP. У каждой квоты
свой string key со state `{version, limit, periodMs, count, resetAtMs}`.

Отдельные ключи сохраняют ограниченную работу на один acquire: читаются только
применимые квоты. Не читать/переписывать весь аккаунт со всеми операциями на каждой
попытке; не делать SCAN для разрешения запроса. Schema version отделена от пользовательского
scope. Limit/period хранятся в состоянии для проверки конфликтующих определений.

Время окна определяется Redis TIME внутри script, единицы — ms. Клиентский monotonic
clock отвечает за ExecutionBudget, серверный — за общие окна workers. Ответ содержит
относительный retryAfterMs. После сетевого ожидания SDK перепроверяет собственный budget.
Скачки серверных часов и потеря состояния не превращаются в обещание идеального
соответствия внешней квоте; выбор fixed window сохраняется явно.

Входы проверяются до записи: положительность, типы, форматы состояния, уникальность
keys и представимость арифметики. Для Lua/JSON нельзя молча округлять PHP_INT_MAX:
ограничить Redis-входы точным диапазоном целых используемого представления и проверить
сложение текущего времени с periodMs. Это ограничение адаптера, не изменение старого
локального API. Неподдерживаемое значение отклоняется до HTTP.

## Алгоритм одной попытки получения

1. Проверить оставшийся timeout и готовность выделенного соединения.
2. Передать script все key через KEYS и параметры через ARGV. Источник script постоянный.
3. В script получить серверное время, прочитать выбранные состояния. Отсутствующее/
   истёкшее состояние моделировать новым окном, пока без записи.
4. Проверить schema, limit/period для активных окон и все числовые границы.
   Повреждённое состояние/конфликт — ошибка, не сброс счётчика.
5. Если хотя бы одна квота исчерпана — вернуть blocked IDs и максимум времени до
   доступности; **не записывать ни один счётчик и не продлевать окна**.
6. Вычислить и сериализовать все новые состояния до первой записи. Выполнить одну
   MSET для всего набора, затем установить абсолютные TTL по resetAtMs.
7. Вернуть granted только после успешного завершения предусмотренных команд.

Выбор одной MSET для счётчиков важен: команда записывает все переданные значения
атомарно, что отдельно описано в [документации MSET](https://redis.io/docs/latest/commands/mset/).
Последовательные INCR для разных квот с возможной ошибкой посередине не подходят.
По той же причине Z4 не принимается как эквивалентная замена на несколько SET PXAT:
каждый SET объединяет значение и TTL одного ключа, но ошибка между SET оставляет
разный расход квот. MSET объединяет именно запись счётчиков, хотя TTL остаются отдельными.
Для двух квот это три команды записи вместо двух внутри одного EVALSHA, без дополнительного
сетевого round trip. Это осознанный небольшой расход, а не основание добавлять rollback.
Устанавливать TTL на абсолютный конец окна, не сдвигать конец на period от каждого
запроса. Состояние само содержит resetAtMs, TTL служит также освобождению памяти.

Атомарное выполнение не следует выдавать за универсальный rollback. Redis не
предоставляет rollback уже выполненных команд Lua при последующей ошибке. Основание:
[redis.call и ошибки](https://redis.io/docs/latest/develop/programmability/lua-api/)
и обработка результата lua_pcall в
[исходнике Redis 7.0](https://github.com/redis/redis/blob/7.0/src/script_lua.c).
Это вывод по протоколу/исходнику, не выполненный здесь Redis integration test.
Поэтому в проекте весь проверяемый расчёт выполняется до одной записи счётчиков.
Ошибка после MSET, например при TTL, может оставить все разрешения списанными;
операция завершается backend failure без HTTP, обратного списания нет. Такие ошибки
проверить отдельно; они не должны оставлять только половину счётчиков обновлённой.
При нарушенных ACL TTL может не очистить ключ; это неисправность инфраструктуры,
а не основание проигнорировать ошибку или объявить acquire успешным.

## Выполнение script и сбои

- Обычный путь — EVALSHA, без отдельного EXISTS/INFO перед каждым вызовом.
- Только достоверный NOSCRIPT разрешает загрузку script/повтор EVALSHA либо EVAL
  с теми же аргументами: исходная команда не исполнила списание. Перед каждым
  дополнительным I/O пересчитать остаток timeout.
- Timeout/разрыв соединения после отправки команды — **неизвестный исход**. Возможно,
  Redis уже списал обе квоты. Не повторять acquire, не отправлять HTTP, вернуть
  RateLimitBackendException. Повторные попытки заданий остаются решением приложения.
- Redis busy, OOM, wrong type, повреждённое состояние, ACL error и недопустимый ответ
  также не превращаются в allow или локальный fallback.
- При недоступности Redis не использовать память как незаметную замену: workers
  получили бы независимые квоты. Legacy PSR-16 путь не выбирается автоматически.
- Script cache flush обрабатывается отдельно от потери данных. Очистка квот, eviction,
  restart без сохранённого состояния либо откат реплики могут обнулить ограничения.
  Гарантия — атомарный учёт при сохранном согласованном состоянии одного Redis primary,
  а не строгая квота при любой потере данных/failover. Настройки хранения/eviction
  входят в эксплуатационную документацию приложения.

Подключение Redis делает его доступность условием отправки HTTP даже при свободных
квотах. Сбой Redis заканчивает этот вызов локальной ошибкой; SDK не переключается в
память и не пробует списание повторно. В руководстве это отдельный явный абзац.
Для ключей квот требуется отсутствие eviction; практический профиль — отдельный Redis
с maxmemory-policy=noeviction и контролем памяти. Noeviction сохраняет ключи при давлении
на память, но допускает отказ записи: это также fail-closed. Redis с вытесняемым кешем
не становится пригодным для квот от одного выбора другой logical DB. Основание —
[официальное описание eviction](https://redis.io/docs/latest/develop/reference/eviction/).

## Соединение, deadline и требования пользователю

Переданный Redis объект предназначен для этого адаптера: не shared соединение, на
котором приложение одновременно меняет MULTI/pipeline/options. Передать его в другие
клиенты одной группы через тот же backend можно в последовательном процессе;
каждый worker создаёт собственное соединение к общему Redis.

Проверить отключение автоматических повторов модифицирующей команды в phpredis
(OPT_MAX_RETRIES), режим обычных команд, совместимые serializer/compression/prefix.
Не копировать secret connection options в сообщения. Возможности retry/timeout
описаны в [документации phpredis](https://github.com/phpredis/phpredis); конкретные
options и поведение минимальной версии закрепить интеграционными тестами адаптера.

Адаптер имеет конечный ioTimeoutMs, предлагаемый default 1000 ms; пользователь может
изменить его под инфраструктуру. На операцию применяется минимум собственного timeout
и переданного remaining budget. Использовать настройки чтения/доступных сетевых
таймаутов phpredis на принадлежащем адаптеру соединении, корректно восстанавливая их
после вызова. Не ждать освобождения квоты внутри backend и не запускать бессрочный
цикл reconnect. Создание соединения приложением происходит вне выполнения SDK.

Redis желательно располагать близко по сети. Его задержка и ожидание квоты входят
в общий RetryConfig.totalTimeoutMs, если он задан; ClientConfig.timeout — таймаут
HTTP-попытки и не заменяет общий budget. Нельзя обещать «до 3 s из timeout=30 s»:
это разные настройки, а первый backend timeout прекращает вызов без retry. Три
успешных медленных acquire при трёх HTTP-попытках действительно суммируют задержку.

Проверки budget до/после вызова не являются принудительным прерыванием произвольного
блокирующего кода. Адаптер обязан применять поддерживаемые I/O timeouts и после
задержки не разрешать HTTP с истёкшим budget. Не обещать жёсткое real-time завершение
ровно в миллисекунду при остановке процесса/системных задержках; это тот же практический
предел, что у существующих blocking transport. Отдельный subprocess/thread ради отмены
Redis-команды не вводится.

## Подключение в Laravel

Согласовано владельцем 2026-09-13: использовать тот же PhpRedisRateLimitBackend,
собирая его при регистрации SDK-клиента в ServiceProvider/контейнере приложения.
Отдельные LaravelRateLimitBackend, facade или фабрика ради сокращения конструктора
в первую поставку не добавляются. Ядро не обращается к Laravel-контейнеру за Redis.

Проект примера после реализации адаптера:

```php
use Brahmic\ApiSutra\RateLimiting\Backends\PhpRedisRateLimitBackend;
use Illuminate\Support\Facades\Redis;

// Фрагмент сборки SDK-клиента в ServiceProvider, не содержимое config-файла.
$backend = new PhpRedisRateLimitBackend(
    redis: Redis::connection('apisutra')->client(),
    scope: $quotaScope,
);
```

`apisutra` — настроенное приложением именованное соединение в config/database.php.
Для этого примера требуется драйвер phpredis, не Predis/RedisCluster. Метод client()
возвращает исходный клиент из Laravel-обёртки: см.
[Laravel Connection::client](https://api.laravel.com/docs/12.x/Illuminate/Redis/Connections/Connection.html#method_client).
Параметры соединения, включая max_retries/read_timeout, задаются штатным способом:
[Laravel Redis](https://laravel.com/docs/12.x/redis).

Рекомендуется выделенное для адаптера соединение с контролируемыми options и
отключёнными автоматическими повторами; оно может вести на тот же подходящий Redis-сервер.
Не менять незаметно настройки общего соединения кеша/очередей. Совместимость prefix,
serializer и timeout с реальным Laravel/phpredis подключением проверить в этапе B.
Scope задаёт приложение или SDK провайдера: это группа совместного учёта, а не имя
соединения. Не регистрировать один общий backend для всех независимых групп автоматически.

В ClientConfig передаётся готовый backend. Объекты/соединения не помещать в Laravel
config-файлы: там остаются сериализуемые значения для config:cache. Рецепт дополнит
[существующий гайд Laravel](../../../docs/guides/laravel.md) при поставке адаптера.
SDK провайдера может скрыть эту сборку от конечного приложения.

Наличие Laravel или настроенного Redis не включает shared rate limiting автоматически.
Локальный режим остаётся стандартным; Laravel/phpredis не добавляются в обязательные
Composer-зависимости ядра. Само приложение обеспечивает Redis-интеграцию Laravel.

## Поставка и цена

- Никакого ext-redis в обязательном require всего SDK. Можно добавить composer suggest
  с объяснением, для какого адаптера нужна версия расширения.
- Без ext-redis ядро и локальные tests работают. Использование выбранного Redis-адаптера
  без расширения диагностируется как configuration_error, не произвольный class-not-found.
- Lua resource включён в composer archive и проверяется installed-package smoke.
- Scope выбирается один раз; пользователь не пишет технические prefixes, Lua, locks
  или код retry. В руководстве — точный пример подготовки соединения с нужными options.
- Нет lock acquire/release на каждый HTTP. Обычно один backend round trip на попытку
  получения набора. Отказ/ожидание не держат ресурсы резервирования; стоимость связана
  с числом попыток и сетевой задержкой Redis.

Оптимизации script caching и ограниченных чтений нужны сразу. Более сложные протоколы
reservation ID, гарантированный refund, автоматические failover retries и rollback
между разными backend не входят в эту поставку: они изменили бы цену и контракт задачи.
