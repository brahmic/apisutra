# Проверка замечаний коллеги к плану 025

Проверка 2026-09-13. Это приложение к [плану](pln-025-readme.md), не поручение
реализовать альтернативу. Ниже отделены факты, технические уточнения и решения владельца.
После ревью владелец принял В1/В2: актуальный контракт с одним rateLimit зафиксирован
в contracts. Рассуждения о двух полях ниже сохранены как история рассмотренного варианта.

## Что подтверждено, а что поправлено

Повторно выполнена команда из [baseline](artifacts/baseline.json): **133 passed,
798 assertions**, 0.33 s. HEAD f92e7c9; git describe: v0.1.0-alpha.1-27-gf92e7c9.
Следовательно, alpha-тег есть, но текущий checkout уже на 27 коммитов дальше.
В composer.json собственной фиксированной версии нет. Redis/phpredis integration
в этой проверке не запускалась; утверждения об адаптере остаются проектными.
Результат повторного запуска и совпадение всех 22 исходных хешей сохранены в
[peer-check.json](artifacts/peer-check.json); команда повторения находится там же.

Приоритет правил, get/set PSR-16, per-instance память, обязательная пара атрибута
и сохранение limiter при смене транспорта подтверждаются исходниками. Однако фраза
«все отчёты уходят в другой счётчик» неверна в общем случае:
[RateLimitApplier](../../../src/Pipeline/Transport/RateLimitApplier.php) использует
config.key либо baseUrl. Без custom key атрибут и default читают тот же счётчик
с разными применяемыми параметрами. Отдельные ключи появляются при соответствующем
custom key. Двух независимых одновременных ограничений всё равно нет.

Текущее замещение описано в [публичном контракте](../../../docs/guides/client-config/rate-limit.md).
Поэтому основание задачи: SDK пока не выражает совместные общую и операционную квоты,
а привычная комбинация настроек может не соответствовать ограничениям провайдера.
Нельзя безусловно объявлять каждый существующий override семантическим дефектом
или писать в changelog, что исправление гарантированно нужно всем пользователям.

## Почему Z1 — реальный выбор, а не бесплатная чистка

Исходный вариант D1 сохранял два разных назначения: default, заменяемый запросом,
и дополнительный общий предел. Это не два названия одного значения. Но отдельная
потребность сохранить клиентский default одновременно с общим пределом здесь не
предъявлена; именно BC сейчас является главным доводом за оба поля.

Принятая после ревью альтернатива: ClientConfig.rateLimit задаёт общий предел; атрибут либо
request/runtime override задаёт собственный лимит операции. Они действуют совместно,
includeClientQuota управляет участием. Атрибут без пары меняет только участие и не
создаёт лимита операции. Без лимитов SDK по-прежнему не создаёт I/O/инфраструктуру.

Что действительно сокращается: дополнительное поле clientQuota и необходимость
объяснять два клиентских определения. **Флаг участия остаётся** — он нужен согласованным
исключениям, а не только BC. Поддержка старого PSR-16 store тоже не исчезает магически:
совместный acquire всё равно несовместим с последовательным get/set. Alpha позволяет
обсудить миграцию раньше, но не доказывает отсутствие внешних пользователей.

Цена альтернативы: существующее сочетание client rateLimit + атрибут/runtime больше
не заменяет общий предел; оно расходует две квоты. Меняются ключи и active-window
поведение; сочетание со store требует миграции на единый backend. Потеря прежнего
client default — сознательное изменение публичного назначения поля. Старую схему
нельзя в общем случае восстановить одним include=false: ещё различаются default,
группировка ключей и storage. Нужны upgrade notes и сценарии миграции, а не обещание
«только один абзац и всё обратно совместимо».

Рассмотренная, но не выбранная альтернатива: сохранить два поля ради BC. В таком случае
новое поле лучше назвать totalRateLimit, согласовав ссылки флага, и прямо описать
rateLimit как overrideable default. Не вводить скрытый режим по версии и не обещать
неизбежное удаление поля в 1.0 без решения. После ответа В1 этот вариант не входит в план.

## Почему не менять смысл withoutRateLimit

Пример: клиент ограничен 100/min, отчёты — 5/min. withoutRateLimit явно означает
отключение rate limiting для запуска; includeClientQuota=false исключает только
общий счётчик, оставляя лимит операции. Это две понятные, различные операции.

Если лимит аккаунта должен быть неотключаемой административной политикой, это другой
контракт. Владелец ранее согласовал опциональное участие. SDK не должен запрещать
приложению распоряжаться собственными настройками или добавлять систему caps в эту задачу.
Не добавлять новые runtime-флаги/методы только ради гипотетического использования.

## Технические уточнения без лишнего механизма

Z3: destination/body уже проверяются в RetrySender до acquire; проблема конкретнее —
TimeoutResolver и TransportCapabilities идут после него. Переносим доступные проверки
перед acquire для обоих режимов; после ожидания пересчитываем оставшийся budget и
эффективные timeout. Предварительная проверка не заменяет окончательную. Встроенный
RetryHandler дополнительно ждёт backoff/Retry-After и проверяет budget/transport перед
send; Z3 не является разрешением переписать публичный RetryHandlerInterface или убрать
его финальные guards. Не обещать отсутствие любого расхода без отправки: D12 сохраняется.

Z4: [SET PXAT](https://redis.io/docs/latest/commands/set/) объединяет значение и срок
одного ключа. Lua исключает вмешательство конкурента, но ошибка выполнения прекращает
script без отката предыдущих команд: это следует из redis.call и luaCallFunction в
[Redis 7.0](https://github.com/redis/redis/blob/7.0/src/script_lua.c).
Одна [MSET](https://redis.io/docs/latest/commands/mset/) оставляет одну границу записи
всех счётчиков. Она не гарантирует успешный TTL, сохранность при crash или rollback
всего script. Цена для двух квот — одна дополнительная команда внутри того же сетевого
обращения. Собирать всю группу операций в один большой ключ ради единственного SET
не нужно: это увеличит объём работы при каждой операции. Реальные сбои проверить в B;
вывод по исходнику не выдавать за выполненную Redis-приёмку.

Z8: Redis выбирается приложением и становится зависимостью доступности только этого
режима. Ошибка acquire прекращает HTTP даже при свободной квоте. Нельзя выводить
численную вероятность отказа SDK из вероятности Redis без модели нагрузки/сбоев.
ioTimeoutMs ограничивает I/O; RetryConfig.totalTimeoutMs — всё выполнение, включая
ожидание. ClientConfig.timeout ограничивает HTTP-попытку. Поэтому пример коллеги
«три Redis timeout съели три секунды из HTTP timeout=30 s» некорректен: первый
backend timeout уже терминален. Три медленных успешных acquire могут суммировать
задержки. Эксплуатационные требования описаны в [Redis-дизайне](redis-backend.md).

Z10: snapshot остатка сам по себе не разрешает отправку, между inspect и acquire
его могут потратить другие workers. Remaining/reset для всех квот расширили бы
RateLimitDecision и контракт сторонних адаптеров, а inspect добавил бы отдельный I/O.
Это допустимое будущее расширение по потребности, не обязательная часть текущего решения.

## Поставка и цена проверок

Принято разбиение на A (контракт + локальные совместные квоты) и B (Redis + workers/CI).
Они отдельно пригодны для слияния; 025 завершён только после обоих. Новые обязательные
зависимости для обычного пользователя не появляются. Нельзя объявить атомарный shared
режим готовым после одних mock/unit tests.

R7–R9 нужны для заявленных гарантий, но не требуют универсальной chaos-платформы.
Использовать минимальные изолированные сценарии, различая ошибки до записи, после
записи и потерю ответа; не добавлять production hooks исключительно ради стенда.
Не пытаться тестами SDK доказать любую внутреннюю аварийную ситуацию Redis.
Benchmark — воспроизводимые измерения выбранных путей и числа обращений; подсчёт каждого
временного объекта с отдельным profiler не является обязательным выпускным требованием.

## Дополнительная проверка часов и границ реализации

Повторный отзыв проверен по исходникам 2026-09-13 после принятия В1/В2. Это техническая
конкретизация утверждённого контракта, без новых пользовательских настроек.

1. **Часы — принять.** [ClockInterface](../../../src/Contracts/Interfaces/Timing/ClockInterface.php)
   уже имеет monotonicMs(), поэтому нового метода не нужно. Только unixTime возвращает
   секунды; [SystemClock](../../../src/Timing/SystemClock.php) реализует их через time(),
   monotonicMs — через hrtime. Локальный атомарный backend использует monotonicMs своего
   постоянного clock; скачки wall time не меняют его окна. Сохранённый PSR-16/direct
   acquire продолжает использовать unixTime, Redis — TIME. Внешний результат содержит
   относительное ожидание, а не сравнимую с другим backend абсолютную отметку.
   Это уточняет реализацию C11; сам C11 не считается пройденным до написания и проверки
   backend. Добавлен Q12 на скачки wall time и миллисекундную границу.
2. **Наследование store — принять порядок, уточнить вывод об ошибке.**
   [RateLimitApplier](../../../src/Pipeline/Transport/RateLimitApplier.php) действительно
   подмешивает клиентский store в три ветки. Новый resolver сначала определяет состав
   набора и сохраняет явные store. Fallback нужен только кандидату на одиночный PSR-16
   путь без явного backend. Но при двух квотах клиентский store уже принадлежит общей:
   configuration_error в сочетании «общая со store + атрибут» является ожидаемым,
   а не ложным. Удалять/игнорировать его ради прохождения вызова нельзя. При исключении
   общей квоты одиночная операция по-прежнему может наследовать store. Добавлен C14.
3. **Таймауты — два resolve не обязательны.**
   [TimeoutResolver](../../../src/Pipeline/Preparation/TimeoutResolver.php) разрешает
   настройки и сохраняет ссылку на budget. Остаток времени вычисляет
   [TransportOptions::effective](../../../src/VO/Http/TransportOptions.php), а не resolve.
   Достаточно локального options для preflight, effective до/после ожидания и записи
   в preparedRequest после допуска. Ранее созданный базовый options сам по себе не
   содержит застывшего remaining timeout. Нельзя сохранять раннюю effective-копию
   как окончательный расчёт либо удалять effective перед фактическим HTTP после backoff.
   Принята последовательность без предварительной записи options в context, но
   число вызовов resolve не превращено в обязательный тест реализации. Добавлен E13.
4. **Ожидание — подтвердить существующую границу.** Один acquireAll в RateLimiter
   организует Wait/Throw для обоих новых backend; backend возвращает решение и
   относительный retryAfterMs. Не копировать loop в Local/Redis и не передавать им sleeper.
   Сохранённый прямой acquire со старым storage API не требует универсальной новой
   абстракции ради физического объединения всех циклов. Добавлен E14 на одинаковое
   наблюдаемое поведение организатора. Восстановление NOSCRIPT остаётся отдельным
   безопасным протокольным случаем, не повтором после deny/неизвестного списания.

Разделение A/B сохранено. Новые проверки добавлены к критериям будущей реализации;
они не являются уже выполненными тестами. Источники времени, store selection и
финальная подготовка timeout уточнены в contracts/основном плане.
