# Совместные квоты и атомарный учёт rate limit

- Дата создания: 2026-09-13
- Дата обновления: 2026-09-13
- Статус: завершён

## Цель и основание

Перед каждой HTTP-попыткой учитывать совместно суммарную квоту подключения и лимит
операции. Для нескольких workers предоставить готовый атомарный механизм учёта,
сохранив ожидание, общий deadline и самостоятельность ядра.

Основание — конкретная потребность разработчика и диалог владельца 2026-09-13.
Владелец поддержал атрибут с необязательным includeClientQuota, форму без limit/period,
локальный стандартный механизм, подключаемый атомарный backend и готовый первый
адаптер **Redis через phpredis**, необязательный для остальных пользователей SDK.

Это конкретизация части [отложенного 015](../../backlog/pln-015-shared-rate-limit-coordination.md),
а не возобновление всего его объёма. Планы 022–024 остаются отложенными и не являются
зависимостями. Пример аккаунта и отчётов иллюстрирует независимые квоты, не задаёт
ядру модель аккаунтов, количество интеграций или обязательную админку.

## Проверенное исходное состояние до реализации

- RateLimitApplier разрешает один RateLimitConfig: runtime → запрос → атрибут → клиент.
  Настройка операции заменяет default, отдельного суммарного ограничения нет.
- RateLimiter читает и пишет PSR-16 store через get/set; это не атомарный acquire.
  Без store используется память экземпляра. Текущие ключи — hash от custom key/baseUrl.
  Без custom key атрибут и клиент используют один ключ с заменёнными параметрами,
  а не обязательно два разных счётчика. Поэтому задача закрывает отсутствие совместных
  независимых квот; прежний документированный override не объявляется универсальным багом.
- RetrySender вызывает limiter внутри цикла попыток перед HTTP, включая повтор после
  auth recovery. ExecutionBudget уже учитывает ожидание; это переиспользуется.
- Атрибут RateLimit имеет обязательные int limit/period. Поля придётся расширить для
  согласованной формы, задающей только участие. RateLimiter создаётся клиентом один раз
  и сохраняется при fake/record/playback.
- Локальные auth locks не объединяют процессы. Общий lock вокруг отдельных get/set
  не заменяет доказательство совместного атомарного списания нескольких квот.

## Решения и аргументация

Согласованное направление отделено от конкретизации, выбранной при подготовке плана.
Новые имена типов/полей ниже — проект API, а не описание существующего релиза.

| ID | Решение | Основание / последствия |
| --- | --- | --- |
| D1 | rateLimit клиента задаёт общую квоту; атрибут/request/runtime задаёт дополнительную квоту операции | Подтверждено владельцем 2026-09-13, В1. Отдельного clientQuota нет; принято изменение alpha-контракта с миграцией, без режима прежнего замещения |
| D2 | Атрибут includeClientQuota: ?bool = null; null наследует клиентский bool, по умолчанию true | Квота включается для обычных операций автоматически, исключения явные. Без rateLimit клиента флаг ничего не создаёт. Согласовано |
| D3 | limit/period задаются вместе или оба отсутствуют | Можно менять только участие, без дублирования общей цифры и фиктивного лимита. Согласовано; влияние nullable на публичные потребители раскрыто в contracts |
| D4 | Один RateLimiter организует ожидание, один backend получает весь набор разрешений | Приложение не пишет алгоритм; не нужна смена полного executor или система политик 024. Согласованное направление |
| D5 | Стандартная реализация локальна, первый внешний backend — Redis/phpredis | Ядро не требует Redis/Laravel, shared режим подключается один раз. Redis/phpredis прямо подтверждён владельцем |
| D6 | При обычном отказе хотя бы одной квоты ни одна не списывается | Исключает потери общей квоты из-за исчерпанной квоты операции. Backend выполняет один tryAcquire для набора; не несколько независимых acquire |
| D7 | Одна HTTP-попытка стоит по единице каждой применимой квоты | Достаточно для поставленной задачи. Вес, денежные балансы, reservation/refund API не вводятся |
| D8 | withoutRateLimit отключает все SDK-квоты вызова | Подтверждено владельцем 2026-09-13, В2. includeClientQuota=false отключает только общую, не собственный лимит |
| D9 | Локальный default per-client; для Redis явный scope общей группы | Ядро не угадывает аккаунт по URL/секрету. SDK провайдера может скрыть настройку scope при создании клиента. Автоматическое объединение всех локальных клиентов не включено |
| D10 | PSR-16 остаётся для одной применимой квоты без явного backend; для совместного набора несовместим | Не игнорировать store. Новая семантика квот действует всегда; storage-путь не возвращает прежнее замещение. Direct acquire сохранён |
| D11 | Отказ/ожидание — только по блокирующим квотам; backend failure не повторяется SDK | Истёкший общий budget имеет приоритет. При неизвестном результате списания повтор способен расходовать ещё одну квоту |
| D12 | Квота учитывает выданные разрешения, не гарантированно доставленные HTTP | После acquire может истечь deadline/упасть transport/worker. Автоматического возврата нет: SDK не знает, дошёл ли HTTP до сервиса |
| D13 | Атомарные backend используют новый namespace и раздельные client/operation keys | Применяется и к локальному default. Прежний key остаётся только одиночному PSR-16 пути; миграция учитывает новые счётчики и смешанные workers |
| D14 | В Laravel тот же phpredis backend собирается в ServiceProvider через именованное Laravel-соединение | Подтверждено владельцем 2026-09-13: готовый рецепт без отдельной Laravel-фабрики/адаптера и без автоматического включения Redis; scope определяет приложение/SDK провайдера |

D6–D13 конкретизируют реализацию и границы гарантий; последствия раскрыты в контрактах
и приёмке. Согласование плана само по себе не является поручением изменить runtime.

сохранена в peer-review; нормативный будущий контракт находится в contracts.

## Границы ответственности и стоимость

Приложение выбирает квоты/участие, связывает клиентов с общей группой, предоставляет
Redis connection и эксплуатацию сервера. SDK провайдера может объявить ограничения
операций и подготовить настройки подключения. Ядро разрешает правила, вызывает backend,
ожидает и доставляет результат. Backend атомарно принимает/отклоняет набор; не управляет
очередями, retry HTTP или политиками приложения.

Реализация ограничена resolver квот, коротким контрактом backend, локальным алгоритмом,
одним Redis-адаптером и тестами. Не нужны DI registry, динамические профили, mutex для
каждого запроса, распределённые транзакции между разными хранилищами и новые обязательные
Composer-зависимости. Самое затратное место — проверка поведения Redis при гонках/сбоях
и совместимости атрибута; число строк resolver не отражает эту цену.

Без лимитов: ранний выход, без backend/I/O. Одиночный PSR-16: сохранённый storage-путь.
Локальный набор: проверка и обновление максимум двух применимых правил в памяти.
Redis: обычно один сетевой EVALSHA на попытку получения набора; ожидание вызывает новую
проверку, холодный script cache требует дополнительного обращения. Source script один,
не генерируется на каждый запрос. Это ожидаемая модель стоимости, не измеренный benchmark.

## Шаги реализации

### Поставка двумя законченными этапами

Этап A: шаги 1–4, 6 и относящиеся к ним тесты/документация шага 7 — совместные квоты,
контракт и локальный backend. Этап B: шаг 5 и Redis-часть шага 7 — готовый адаптер,
реальные workers, проверяемые сбои и CI. У этапов отдельные критерии в acceptance.
Этап A можно слить отдельно; весь 025 остаётся незавершённым до B. Публичная документация
этапа A не обещает поставленный Redis или межпроцессную атомарность локального backend.
Контракт A сверить с дизайном Redis заранее, не ждать полной инфраструктуры fault injection
ради локального результата. Новые универсальные стенды/прокси в production SDK не входят.

### 1. Зафиксировать контракт и regression baseline

- Применить согласованные В1/В2 и проверить D8–D13: полный disable, scope, несовместимое смешение store/backend,
  namespace, конфликт определений и отсутствие refund после выдачи разрешения.
- Повторить целевые существующие тесты из baseline перед правкой; сохранить результаты.
- Защитить неизменяемые контракты ошибок, direct RateLimiter::acquire и одиночного
  PSR-16 пути. Для согласованных изменений добавить явные before/after сценарии
  приоритетов/ключей; проверить типичных потребителей атрибута. Не переписывать
  несвязанные ожидания старых tests под новую модель.

### 2. Расширить конфиг и атрибут

- В ClientConfig добавить в конец includeClientQuota=true и rateLimitBackend=null
  по [контракту](contracts.md); rateLimit получает назначение общей квоты. Отдельное
  поле clientQuota не добавлять. Обновить with/fromLaravel для двух новых полей.
- В RateLimit добавить optional includeClientQuota, сделать пару limit/period
  необязательной с точной валидацией при применении resolver, а не в конструкторе
  атрибута. Проверить metadata/spec/inventory consumers и прежнюю доставку ошибки send().
- Не добавлять runtime-методы участия без отдельной потребности. Существующие
  withRateLimit/withoutRateLimit сохраняются с явно описанной семантикой набора.
- Проверить named/positional старые вызовы и отсутствие обязательных дополнительных полей.

### 3. Разрешать набор квот

- Разрешать единый набор: ноль, одна или две квоты, без ветки прежнего замещения.
  Собственный лимит: options → request → атрибут → отсутствует; общий — rateLimit
  клиента с правилом участия. Для одиночного PSR-16 отдельно сохранить выбор store/key.
- В атомарных backend разделить client/operation keys, обеспечить стабильную
  автоматическую группу операции и явные custom groups.
- Проверить коллизии, одинаковые идентификаторы с разными limit/period, отсутствие
  секрета в ключах/логах. Не включать limit/period в identity ради обхода конфликтов.
- Отклонять store вместе с явным backend или двумя применимыми квотами до списания/HTTP.
  Одиночную квоту со store без backend направлять в сохранённый PSR-16 путь.
  Не наследовать store при построении всех квот: fallback применяется только после
  выделения кандидата на одиночный путь. Явный store общей квоты при этом не теряется.

### 4. Добавить контракт и локальный backend

- Ввести RateLimitBackendInterface::tryAcquire(list<RateLimitQuota>, ?int timeoutMs)
  и immutable RateLimitQuota/RateLimitDecision с проверяемыми инвариантами;
  в нормализованной квоте поле periodMs, перевод секунд выполняет resolver.
- Локальный backend использует monotonicMs существующего ClockInterface и per-instance
  state lifetime; выполняет проверку всего набора до commit. PSR-16/direct acquire
  остаётся на unixTime, Redis — на TIME. Не расширять публичный интерфейс часов.
- Сохранить публичный acquire одного legacy лимита; добавить отдельный внутренний
  путь acquireAll, переиспользующий общую логику ожидания/deadline там, где это совместимо.
- Весь Wait/Throw цикл acquireAll общий для локального и Redis backend и принадлежит
  RateLimiter; backend только принимает или отклоняет набор и сообщает относительное ожидание.
- Ошибки backend/result validation классифицировать существующими SDK-ошибками.

### 5. Реализовать готовый Redis/phpredis backend

- Поставить PhpRedisRateLimitBackend и один версионированный Lua resource в пакет.
- Выполнить протокол и проверки из [дизайна Redis](redis-backend.md), включая
  совместную запись, серверное время, TTL, NOSCRIPT и неоднозначный сетевой сбой.
- Не писать сетевой Redis-клиент; использовать phpredis и отдельное соединение
  приложения с отключёнными автоматическими повторами изменяющих команд.
- Добавить согласованный Laravel-рецепт сборки в ServiceProvider через
  Redis::connection('apisutra')->client(); проверить его в этапе B. Новые объекты
  не размещать в config-файлах, Laravel-интеграцию не делать зависимостью ядра.
- Адаптер соблюдает доступный I/O timeout, не спит внутри tryAcquire и не создаёт
  Redis connection на каждый запрос. Отсутствующее расширение даёт понятную ошибку
  только при попытке использовать этот адаптер.

### 6. Встроить перед HTTP-попыткой

- Для обоих режимов выполнить доступные локальные проверки тела/destination и
  TimeoutResolver/transport capability перед acquire. Основание исправления legacy:
  сейчас неподдерживаемый timeout может расходовать квоту перед локальным отказом.
  Не поддерживать два порядка эффектов. Изменение приоритета ошибок при одновременно
  неисправном transport и исчерпанной квоте записать в changelog и проверить.
- Для предварительной проверки получить TransportOptions в локальную переменную,
  вызвать effective() и проверить capability без записи в context.preparedRequest.
  После acquire проверить budget и снова effective()/capability, затем записать options
  в preparedRequest. TimeoutResolver разрешает настройки, а remaining budget читает
  effective(): повторный resolve только ради прошедшего времени не нужен. Сохранить
  ссылку на budget и финальный effective() после backoff в транспортном пути.
  Не выполнять acquire дважды для одной попытки и не фиксировать ранний remaining timeout.
- Retry/auth recovery/зависимые HTTP/страницы учитываются по фактическим попыткам.
  Composite-обёртка без HTTP не списывает квоту, cache hit — тоже.
- Смена fake/record/playback сохраняет limiter/backend/state. Внутренняя фабрика 022,
  scope допуска 023 и динамические политики 024 для этого не требуются.

### 7. Провести приёмку и обновить документацию

- Выполнить [матрицу](acceptance.md), включая отдельные конкурентные PHP-процессы
  с настоящим Redis. Mock backend не доказывает межпроцессную атомарность.
- Добавить отдельный CI job Redis, сохранив обычные jobs без расширения redis;
  проверить минимальную заявленную и актуальную поддерживаемую версии адаптера.
- Проверить runtime без Redis/Laravel, PHP 8.4/8.5, качество и distribution.
- Обновить гайды rate-limit/client-config/attributes/errors/testing и техническую
  схему. Примеры показывают локальный/Redis backend, исключение из общей квоты,
  сохранённый одиночный PSR-16 путь и миграцию прежнего замещения.
- Обновить changelog без ссылок на workflow. Зафиксировать результаты, переносить
  план в completed только после выполнения критериев; commit реализации — по поручению.

## Финальные ожидания

1. Пользователь без лимитов ничего не меняет. Для существующих лимитов описана
   согласованная миграция: rateLimit стал общим, операция добавляет свою квоту,
   namespace атомарных backend меняется. Полная BC не обещается.
2. Пользователь нового локального режима задаёт суммарную квоту и при необходимости
   атрибут операции; инфраструктура/префиксы/обязательные identifiers не нужны.
3. Пользователь нескольких workers подключает готовый Redis backend с соединением
   и scope общей группы. Он не пишет Lua, locks, цикл ожидания или собственный limiter.
4. При одном оставшемся разрешении конкурентные процессы не получают два allow;
   при отказе одной квоты остальные не расходуются. Границы сбоев описаны честно.
5. Retry не обходит квоты; ожидание не начинает HTTP после deadline; ошибки имеют
   существующий result-first/throwOnErrors контракт и безопасную диагностику.
6. Расходы измерены и объяснены: никаких скрытых I/O в выключенном/локальном режиме,
   переиспользование backend и нерастущая история завершённых окон.

Реализация завершена 2026-09-13. Этапы A/B приняты по локальной проверке;
[результаты и ограничения](implementation.md). Удалённый CI не запускался. Детальная типовая совместимость
расширенного атрибута, ограничения эксплуатации Redis и правила перехода между
namespace являются частью приёмки, а не обещанием абсолютной обратной совместимости.
Открытых продуктовых вопросов нет; ответы на В1/В2 сохранены в peer-review.
