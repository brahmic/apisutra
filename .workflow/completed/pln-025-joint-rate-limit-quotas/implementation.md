## Цена решения

Воспроизводимый скрипт: `php tests/Support/benchmark-rate-limit.php`.
Для Redis добавить APISUTRA_TEST_REDIS=1 и адрес выделенного тестового сервера;
холодный сценарий выполняет SCRIPT FLUSH. Измеряется RateLimitApplier без HTTP,
логов и повторной сборки клиента; это не end-to-end latency или SLA.

На локальном PHP 8.5.4: выключено 0.37 µs, одиночный PSR-16 1.98 µs, одна локальная
квота 2.46 µs, две 3.70 µs за попытку. В Docker Redis 8.2.9: тёплый набор около
105 µs, холодный около 233 µs, отказ около 108 µs. Сеть и окружение меняют эти числа.
[Локальный замер](artifacts/benchmark-local.json), [Redis](artifacts/benchmark-redis.json).

Без квот — ноль backend calls. Набор из двух — один tryAcquire. Тёплый Redis:
500 попыток = 500 EVALSHA и 0 EVAL; холодный: 20 EVALSHA + 20 EVAL после NOSCRIPT.
Соединение/backend не создаются на попытку; локальная память не растёт на серии
разрешений, истёкшие окна удаляются. Точный profiler аллокаций не добавлялся.

## Уточнения реализации

TimeoutResolver вызывается один раз за попытку: effective() читает живой budget
перед acquire, после ожидания и после backoff. Повторный resolve не нужен.
ClockInterface не менялся: local использует monotonicMs, одиночный PSR-16 — Unix
секунды, Redis — TIME. Встроенный script использует точные десятичные строки,
поскольку JSON-кодирование Lua могло бы потерять точность больших счётчиков.

Для phpredis 6.2 воспроизведён сбой следующего чтения при восстановлении нулевого
READ_TIMEOUT. На выделенном соединении адаптер сначала задаёт конечный default;
положительный исходный timeout восстанавливает. Это не перенастройка общего
Laravel cache connection. Обход и ограничения описаны в публичном Redis guide.

Разрешение не равно доставленному HTTP. Redis fail-closed, отсутствие refund,
неизвестный исход, noeviction и возможность утраты TTL после общей записи явно
документированы. Динамическая админка, отмена операций и планы 022–024 не возобновлялись.
