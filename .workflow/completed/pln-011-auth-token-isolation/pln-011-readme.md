# Изоляция токенов и корректные auth-блокировки

## Цель и основание

Закрыть приоритетную часть AS-09: изоляцию сохранённых токенов, состояние встроенного
TokenAuthenticator между клиентами и корректное освобождение refresh lock.
Основания: [AS-09](../../issue/001/technical-specification.md#12-as-09--runtime-опции-и-авторизация),
[F05/F06 исходного аудита](../../audit/aud-001-architecture-code-2026-09-11/aud-001-readme.md#f05-authrefreshlock-освобождает-не-тот-backend),
[границы первой поставки](../../completed/pln-002-cache-auth-diagnostics.md) и
[завершённый контракт тела](../../completed/pln-010-prepared-request-body-transitions.md).

Пользователь поручил точечную проверку и план. Проверена версия `17d9f4c` на PHP 8.5.4.
Рабочий production-код, публичная документация и changelog при подготовке не изменялись.
D1–D3 подтверждены пользователем 2026-09-12 с обязательным сохранением zero-config.
План согласован; порученная реализация завершена и проверена.

Для обычного клиента решение должно оставаться zero-config: без обязательных
префиксов, account ID, lock key, новых контейнерных binding или подключения Redis.
Общее хранилище не должно подменять credentials другого клиента.

Под «аккаунтом» в результатах проверки понимается набор credentials, под «сервером» —
base URL клиента. Это описание сценариев, а не новые доменные сущности ядра.
SDK остаётся агностичным: область определяется конфигурацией клиента и непрозрачной
identity authenticator, без знания модели пользователей или tenant внешнего API.

Обязательные условия zero-config, повторно подтверждённые пользователем:

- Существующего ClientConfig с auth достаточно для безопасного обычного выполнения.
- Встроенный TokenAuthenticator сам предоставляет identity; пользователь не задаёт
  новые prefix, account ID, lock key или обязательный backend.
- Уже выбранный store с объявленной атомарной capability используется автоматически.
  Без неё работает локальная блокировка; подключать Redis или Laravel не требуется.
- Явное расширение требуется только для дополнительных гарантий между процессами
  или специфичного контекста собственного authenticator, который ядру неизвестен.
- Регрессия должна проверять минимальную конфигурацию без новых аргументов и работу
  без cache store; пример основного сценария в документации остаётся минимальным.

## Объём первой реализации

1. Автоматическая область хранения токенов и lock, безопасные ключи.
2. Изоляция состояния встроенного TokenAuthenticator между контекстами клиента.
3. Симметричные acquire/release; явная capability атомарной блокировки вместо add duck typing.
4. Повторная загрузка токена после ожидания и явное завершение при исчерпании lock wait.
5. Регрессии, документация поведения и миграция.

Не включены: распределённый rate-limit, общий рефакторинг Laravel bindings,
универсальное клонирование произвольных authenticators, все состояния долгоживущего
worker, настоящий async, renewal/fencing для неограниченно долгого внешнего refresh,
новый OAuth-протокол и политика ротации конкретного провайдера. AS-09 целиком не закрывается.

## D1 — автоматическая область токенов и изоляция памяти

**Согласованное решение.** Использовать стабильную identity, доступную до auth/refresh,
и контекст SDK-клиента. Не строить ключ только по username, имени scope или классу.

Для встроенного TokenAuthenticator входы области:

- версия схемы и назначение записи (`token` / `refresh-lock`);
- класс SDK-клиента и его настроенный base URL, включая base path;
- класс authenticator и `getCacheIdentity(null)` — уже учитывает username, password
  и refreshRequestClass; не включать текущий выданный access token;
- выбранный auth scope, если он есть, как дополнительная консервативная граница;
- объявленная tenant identity из существующего CacheConfig.identity, если задана.

Использовать ту же трактовку identity подключения, что принята для HTTP-кеша,
но отдельную версию и назначение ключей. Не переиспользовать HTTP response cache key:
URI ресурса, body, custom key и access token не должны менять область refresh.
Одинаковый контекст в разных процессах получает одинаковую область. Разные пароли,
серверы, scope или объявленные tenant — разные области. Опциональный cache prefix
не становится обязательным и не является заменой identity.

Origin policy не меняется: разрешённая пользователем передача auth на внешний URL
не начинает автоматически обновлять токен на этом URL. Область относится к контексту
настроенного клиента/выбранной auth, а не к подписанному адресу скачиваемого ресурса.
Не добавлять сетевое определение tenant; если провайдер различает аккаунты скрытым
контекстом, SDK провайдера должен объявить его существующей identity.

Физический ключ — 64 шестнадцатеричных символа digest от версионированной структуры,
с разными purpose для token/lock. Username, password, URL и namespace класса не
попадают в открытый ключ. Digest здесь разделяет записи; это не шифрование и не
обещание защиты слабого пароля от перебора. Значения токенов не выводятся в логи.

### Способ внедрения

- Ввести внутренний resolver auth-области; передать недостающий контекст класса
  клиента из сборки pipeline. Существующие способы выбора default/scope/auth policy сохранить.
- Привязать экземпляр встроенного TokenAuthenticator к этой области до внедрения store,
  shouldRefresh и authenticate. Для разных областей получать отдельные экземпляры
  с отдельным token/expiresAt, а не переключать mutable поля исходного объекта.
  Повторное использование внутри одного AuthHandler/области сохраняет состояние.
- Копии создаются явно встроенным TokenAuthenticator из исходных credentials;
  произвольный пользовательский authenticator через reflection/clone не копируется.
  Реестр привязок ограничен сроком жизни клиента/pipeline, без process-global map
  токенов и credentials. Не хранить отдельную копию на каждый HTTP URI.
- Разделённый PSR-16 view переводит логические token keys в физическую область.
  Его bulk-операции не выходят из области; `clear()` не должен очищать чужой store.
  Если clear не нужен для поддерживаемого контракта, отклонять его явно, а не
  делегировать глобальное удаление. Это требуется проверить отдельным тестом.
- `getCacheKey()` остаётся логическим ключом. У встроенного TokenAuthenticator
  заменить username-only значение безопасным digest credentials identity также
  для прямого использования вне pipeline. В pipeline дополнительно действует
  контекст клиента; low-level auth без клиента не может автоматически знать сервер.

### Пользовательские authenticators

Существующий CacheAwareInterface сохраняется. Для общей области использовать
CacheIdentityProviderInterface с ненулевой стабильной identity. Если её нет,
рекомендуется давать отдельный локальный token store в пределах клиента и auth-объекта,
не подставлять общий backend на основании одного getCacheKey(). Это сохраняет работу
обычного auth, но убирает неявное межклиентское разделение токенов.

Отсутствие identity явно описать в диагностике без секретов и инструкции миграции.
Для custom authenticator собственное mutable состояние и безопасное повторное
использование одного объекта между клиентами остаются ответственностью его автора.
Полная автоматическая изоляция памяти в этой поставке гарантируется встроенному
TokenAuthenticator; нельзя обещать её через одно переименование cache keys.

### Перечитывание и миграция

При смене store/context старое in-memory состояние не переносится в новую область.
В прежней области cache miss сам по себе не должен уничтожать ещё действующий
локальный токен после отказа записи в store; различать rebind и обычный reload.

Старые `auth_token_<username>` и старые lock keys **не читать как fallback** и не
мигрировать вслепую: по ним нельзя восстановить владельца/сервер. Старый общий
backend не очищать. После обновления допустим одноразовый refresh при первом обращении.
Предзаполненные вручную старые записи потребуют безопасного повторного получения токена.
Передача заранее заполненного unbound TokenAuthenticator в pipeline не должна
переносить токен неизвестного серверного контекста в новые привязки.

## D2 — capability атомарной блокировки

**Согласованное решение.** Убрать выбор backend через `method_exists('add')`.
Добавить небольшой независимый от Laravel контракт, например AuthLockProviderInterface:

```text
acquire(key, ttlSeconds) -> lease | null
lease.release() -> bool
```

Provider гарантирует атомарный захват отсутствующей/истёкшей записи и атомарное
освобождение только владельцем. Lease удерживает backend, key и owner token;
release не выбирает backend заново. Owner token не является токеном API и не логируется.
Повторное освобождение безопасно; потерявший lease владелец не удаляет новую запись.

Порядок выбора:

1. Необязательный `CacheConfig::locks` с реализацией контракта — если явно задан.
2. Уже выбранный cache store, если он сам реализует контракт — автоматически.
3. Иначе локальный backend, без попытки изображать распределённый lock через PSR-16.

Ошибка явно выбранного lock backend не включает тихий fallback к локальному:
иначе исполнение потеряет запрошенную межпроцессную гарантию.
Все новые параметры необязательны и добавляются совместимо к конструкторам/with.
При обычном `ClientConfig(baseUrl: ..., auth: ...)` настройка не нужна. PSR-16 store
можно продолжать использовать для токенов; отсутствие lock capability не делает
сам token store недопустимым. Наличие add без контракта больше не включает общий lock.

Локальная блокировка гарантирует взаимное исключение только для общей локальной
службы блокировок, используемой данным клиентом/pipeline. Она не объявляется
межпроцессной или общей между независимо созданными клиентами. Если пользователь
нуждается в такой гарантии, требуется backend с capability. Автоматическое подключение
Redis, скрытые подключения к Laravel или новая обязательная зависимость исключаются.

В первой поставке не обещать поддержку всех Laravel lock drivers. Адаптер конкретного
backend включать только с проверкой атомарного owner release; иначе оставить
расширение через контракт и честное ограничение в документации. Это отдельная
возможность интеграции, а не основание блокировать безопасный локальный режим.

TTL существующего ожидания 5–30 секунд сохранить для первой поставки; пользоваться
ClockInterface для локального срока lease и существующим Sleeper для ожидания.
Истечение lease не даёт старому владельцу права удалить нового. Само наличие lease
не гарантирует единственный refresh после истечения TTL: renewal/fencing и защита
от поздней записи внешнего ответа в эту поставку не входят. Не обещать exactly-once
для ротации токенов между процессами при refresh, который пережил TTL.

## D3 — ожидание нового токена и исчерпание lock wait

**Согласованное решение.** Если refresh нужен, но lock за отведённое время не получен
и пригодный обновлённый токен не появился, завершать исполнение с `timeout`,
причиной `auth_refresh_lock_timeout` и stage `auth_lock_wait`. Основной HTTP не отправлять.
Не выдавать успешный результат и не продолжать с пустым/заведомо устаревшим токеном.
Общий deadline имеет приоритет и сохраняет `execution_deadline_exceeded`.

Для встроенного TokenAuthenticator:

- До ожидания сохранить непрозрачный признак версии токена, не его значение в debug.
- После ожидания/перед refresh под полученным lease перечитать cache в той же области.
- При обычном refresh использовать появившийся действующий токен без второй выдачи.
- При force refresh после 401 новый действующий токен, отличный от отправленного,
  может удовлетворить ожидание; тот же отвергнутый токен не считается обновлением.
- Если новый токен отсутствует, выполнять refresh только после приобретения lease.
- Если refresh не удался, освобождать lease в finally и сохранять существующую
  классификацию ошибки refresh. Ошибка release не должна затереть первичный deadline
  или HTTP-сбой. Если refresh успешен, а release завершился исключением backend,
  вернуть execution_error с причиной auth_lock_backend_error до основного HTTP;
  при существующей первичной ошибке сохранить её, а вторичную записать без секретов.
  Результат release=false из-за утраты владельца отличать от исключения backend.

Произвольный CacheAwareInterface не обещает reload/version check. Не предполагать,
что каждый setter reload-ит токен. Для custom auth без такого контракта сохранять
консервативное выполнение refresh после получения lease; оптимизацию пропуска
повторной выдачи гарантировать встроенному TokenAuthenticator.

При auth retry после 401 сохранять исходный HTTP-контекст в ошибочном результате.
`throwOnErrors`, sendAsync/result-first и прежние лимиты authRetryAttempts остаются.
Не отключать общий бюджет и не использовать реальные sleep в тестах ожидания.

## Совместимость и согласование

Обычная настройка клиента остаётся прежней, но изменения поведения существенны:

| Решение | Последствие | Согласованный выбор |
| --- | --- | --- |
| D1 | Старые token keys становятся cache miss; один username больше не объединяет разные credentials/серверы. Custom auth без identity теряет общий token cache. | Принять безопасную область и холодную миграцию без чтения старых записей. |
| D2 | Cache с одним add больше не означает распределённую блокировку. Без capability используется локальная служба; отдельный lock backend — опционален. | Принять явный атомарный контракт и локальный zero-config режим. |
| D3 | Исчерпание lock wait вместо продолжения запроса даёт timeout; новый токен другого владельца используется после reload. | Принять явный отказ без отправки исходящего запроса. |

D1–D3 подтверждены пользователем 2026-09-12 в чате после пояснения агностичности SDK.
Дополнительно подтверждена обязательность zero-config. Имена новых внутренних
компонентов и детали реализации можно уточнять без повторного согласования,
пока сохраняются описанные гарантии, ограничения и публичные точки расширения.

## Приёмка

- ArrayCache без add больше не оставляет собственную блокировку после release;
  повторный refresh не ждёт TTL завершённого предыдущего refresh.
- На общем store одинаковый username с разными password/base URL/scope/tenant
  не читает чужой токен. Одинаковый объявленный контекст разделяет новый token key.
- Физические ключи проходят StrictCache, не содержат исходных username/секретов;
  старые записи не читаются и не удаляются. Bulk/clear не выходит из auth-области.
- Повторное использование встроенного auth между A → B → A, разными/отсутствующими
  store и worker-подобными последовательностями не переносит token/expiresAt.
- Custom auth с identity получает scoped shared store; без identity работает локально.
  Собственное mutable состояние пользовательских реализаций не объявляется изолированным.
- Занятый lease блокирует refresh, освобождение проверяет владельца атомарно;
  старый владелец после истечения TTL не удаляет новый lease. Add-only store выбирает
  локальный режим. Блокировка никогда не выдаётся за глобальную без capability.
- Новый пригодный токен после ожидания используется без лишнего refresh; тот же
  токен после 401 не считается новым. Проверены пустой cache и истёкший токен.
- При исчерпании ожидания основной HTTP не вызывается, результат timeout; при
  исчерпании общего бюджета сохраняется deadline и исходный 401, если он был.
- Ошибки refresh/исключения/release освобождают только свой lease и не маскируют
  исходную причину; custom backend failure имеет явный тестируемый результат.
- Остальные auth/runtime/body/stream/origin/cache контракты проходят регрессию;
  новые обязательные настройки отсутствуют, standalone работает.

Следующий предметный блок после этой поставки — строгий unwrap и сохранение
точности больших целых (остаток AS-07). Этот документ не поручает его реализацию.


## Результаты реализации — 2026-09-12

D1–D3 реализованы с сохранением согласованных границ zero-config. Новых обязательных
аргументов ClientConfig/TokenAuthenticator нет. CacheConfig::locks — опциональный
AuthLockProviderInterface; поддерживающий контракт cache store выбирается автоматически.
Без capability используется локальная служба, без add duck typing и скрытых зависимостей.

### Основные изменения

- [AuthBindingResolver](../../../src/Pipeline/Auth/AuthBindingResolver.php) определяет
  область по конфигурации, исходной credentials identity, выбранному scope и tenant
  подключения. [AuthBinding](../../../src/Pipeline/Auth/AuthBinding.php) хранит отдельный
  экземпляр встроенного TokenAuthenticator и scoped cache в пределах pipeline.
- [AuthTokenCache](../../../src/Pipeline/Auth/AuthTokenCache.php) переводит логические
  ключи в digest, изолирует bulk/delete и отклоняет глобальный clear. Для неизвестной
  identity используется локальное хранение; диагностическая причина не содержит секретов.
- [TokenAuthenticator](../../../src/Auth/TokenAuthenticator.php) разделяет credentials
  уже в прямом cache key, очищает память при смене store и создаёт свежую привязку
  для pipeline. Старые username-only records не читаются и не удаляются.
- [AuthRefreshLock](../../../src/Pipeline/Auth/AuthRefreshLock.php) сохраняет совместимый
  acquire/release фасад, но освобождает тот же lease/backend. Новый lease-контракт
  не позволяет выбирать другой backend на release. Локальная реализация проверяет
  владельца и монотонный TTL без process-global состояния.
- [AuthHandler](../../../src/Pipeline/Auth/AuthHandler.php) перечитывает токен после
  ожидания/под lease, отличает новый token после 401, возвращает lock timeout без
  основного HTTP и сохраняет deadline/первичный отказ при ошибке release.
- Ошибки auth lock исключены из общего HTTP retry даже при retryExceptions=Throwable;
  это предотвращает повторную отправку после неудавшегося обновления токена.

### Доказательства и проверки

A1–A4 закреплены падающими тестами до исправления. A6 проверен управляемым истечением
lease и попыткой старого владельца удалить нового. A7 покрыт начальными вызовами,
auth retry после 401, общим deadline, throwOnErrors и async.

A8 дополнительно воспроизведён на извлечённом снимке исходного `src` из `17d9f4c`
[отдельной пробой](artifacts/reload-probe.php): store_updated=true,
sent_updated_token=false, wait_ms=5000, refresh_calls=0. Текущий рабочий src при этом
не заменялся. Для повторения извлечь `git archive 17d9f4c src` в отдельный временный
каталог и передать его первым аргументом скрипта. Новый regression test проверяет
reload как при обычном ожидании, так и после 401; прежний отвергнутый token не принимается.

Основные регрессии:

- [TokenIsolationTest](../../../tests/Unit/Auth/TokenIsolationTest.php): разные
  credentials/base URL/base path/scope/tenant, общий контекст, A → B → A с одним
  исходным auth-объектом, отсутствие store, cold migration, cache write miss,
  custom auth с identity и без неё, reload после ожидания.
- [AuthLeaseContractTest](../../../tests/Unit/Auth/AuthLeaseContractTest.php): смена
  владельца, add-only fallback, автоматическая capability/явный приоритет locks,
  исчерпание ожидания, сохранение 401/deadline, acquire/release failure, async.
- [AuthTokenCacheTest](../../../tests/Unit/Auth/AuthTokenCacheTest.php): scoped bulk,
  delete/clear и локальный TTL. Старые lock-тесты переведены на capability-контракт;
  реальный sleep для TTL заменён управляемыми часами.
