# Строгий Returns::unwrap и сохранение больших целых

## Основание и цель

Продолжение [AS-07, требования 5–7](../../issue/001/technical-specification.md#10-as-07--json-и-типы-данных).
Разбор malformed JSON и result-first классификация уже поставлены в
[pln-004](../../completed/pln-004-json-error-contracts.md). Здесь устраняются две
оставшиеся причины успешного результата с неверными данными: подстановка внешнего
документа при ошибочном unwrap и потеря точности целочисленного идентификатора.

Проверена версия `341a72e`. Пользователь поручил проверку и подготовку плана;
реализация начата по поручению пользователя 2026-09-12. Решения D1–D3 согласованы пользователем

Zero-config: не добавлять обязательных параметров, префиксов, глобальных режимов
JSON или настроек SDK-клиента. Обычный потребитель получает безопасное поведение

## Согласованные решения

### D1. Отсутствующий Returns::unwrap — ошибка по умолчанию

Принято: указанный путь обязателен. Missing → HydrationException и
`hydration_error` с сохранённым HTTP-ответом; не подставлять корень документа.
До выбора пути сохраняется существующий порядок BeforeHydrate hooks.
`unwrap: null` по-прежнему означает отсутствие извлечения. Строка пути, включая
пустую строку как ключ, использует текущую dot-нотацию ArrayPath; не вводить
скрытое trim/новый синтаксис или wildcard.

Не добавлять permissive-флаг или глобальную политику: подтверждённой потребности
для обычного Returns нет. Провайдер с несколькими формами envelope может явно
нормализовать их через существующий BeforeHydrate hook либо ResponseHandler.
Если нужен DTO корня, нужно убрать unwrap.

### D2. Null в выбранном пути сохраняет своё значение

Принято: найденный null — не Missing и не повод взять корень/пустой массив.
Текущий Returns обязательно объявляет response DTO, nullable-контракт корневого
DTO отсутствует. Поэтому null в пути для Returns → `hydration_error` о несовпадении
формы: ожидаются данные DTO, получен null. То же относится к scalar вместо DTO.
Это отличается от Missing и должно быть видно по безопасной диагностике.

Нового флага nullable DTO в этой поставке не вводить. API с допустимым отсутствием
объекта можно представить DTO-обёрткой с nullable вложенным полем; существующую
гидратацию такого поля сохранить. Корневой JSON null без DTO остаётся успешным null.
Прежнюю нормализацию корневого null/204/пустого тела при DTO без unwrap не менять.
Вложенный пустой массив передавать обычному Hydrator: не считать его missing/null.
Различение JSON `{}` и `[]` не вводится — текущее associative-декодирование их объединяет.

### D3. Большие целые сохраняются строками автоматически

Принято: целочисленные JSON-литералы вне диапазона PHP int декодировать с
JSON_BIGINT_AS_STRING. В диапазоне остаётся int; JSON-строки остаются строками;
дроби/экспоненциальная запись остаются обычными float. Это не arbitrary-precision
поддержка всех чисел и не восстановление значения, ранее округлённого сервером/пользователем.

DTO `string`, `int|string`, mixed и массив сохраняют точные цифры большого ID.
DTO `int` не может вместить такой ID: автоматическая гидратация обязана вернуть
`hydration_error` вместо ограничения значением MAX/MIN, округления или приведения
через reflection. Nullable int меняет допустимость null, но не диапазон int.
Проверять положительную и отрицательную границы без промежуточного float для
целочисленных строк; сохранить допустимые ведущие нули и обычные преобразования.

Та же защита от численного переполнения нужна встроенному IntegerCast при hydrate
и serialize; в исходящем запросе это `serialization_error` до HTTP. Не превращать
это в общий пересмотр всех permissive-преобразований IntegerCast. Числовые строки
с экспонентой и float вне диапазона также не должны обходить защиту диапазона.
Явный тип float/FloatCast означает выбранную провайдером приблизительную арифметику.
Пользовательские casts сохраняют свой приоритет и ответственность за результат.

Добавить флаг сохранения больших целых в поддерживаемые SDK точки JSON-декодирования:
ProviderResponse::json/jsonStrict/errorMessage, JsonCast::hydrate, RedactionPolicy::body,
RecordingTransport::normalizeBody и оба пути чтения JSON-фикстур MockTransport.
Существующую строгость malformed JSON каждой точки не менять в рамках D3:
jsonStrict бросает ошибку, permissive json и JsonCast сохраняют прежний контракт.
Не нужен универсальный decoder service только ради одного флага.

Запись диагностического/fixture JSON может представить большой целочисленный
литерал JSON-строкой; гарантируются точные цифры и маскирование секретов,
а не байтовое равенство с raw response. Сам raw response не пересобирать.
В уже испорченных старых fixture значения автоматически не восстановятся.

## Объём и ограничения

Входит: Returns::unwrap, сохранение больших целых по D3, предотвращение встроенного
переполнения int, безопасная диагностика **новых** ошибок, тесты и публичные документы.
Не менять порядок кеша, hooks, расширений, retries и существующие политики результата.
Проверить числа на HTTP cache hit и в sync/async интерфейсах без обещания нового I/O.

Не входит:

- ContinuationResult::unwrap, правила polling, преобразование continuation token;
- PaginationConfig.itemsPath (свои fallback-правила); Returns на DTO-контейнере пагинации входит;
- новый nullable-контракт корневого DTO, общая строгость null/missing всех DTO-полей;
- строгий malformed JSON для JsonCast, полная переработка ошибок вложенной гидратации;
- точная decimal/exponent арифметика, bigint VO, изменения формата JSON-запросов
  для автоматической отправки строк как числовых литералов;
- закрытие всего AS-07 или остальных задач issue.

   затем передать найденное значение, включая null, в проверку формы DTO.

3. Для новых ошибок добавить безопасные reason/path/expected/actual сведения в
   HydrationException и error context, сохранив совместимость первых трёх аргументов
   конструктора Exception. Предлагаемые reason: `unwrap_path_missing`,
   `unexpected_response_shape`, `integer_out_of_range`. Фактическая форма — тип/state,
   без значения, тела или перечня внешних ключей. Вложенный путь поля/индекс коллекции
   передавать для ошибок диапазона, не собирать из содержимого ответа.
4. Включить JSON_BIGINT_AS_STRING в перечисленных точках. Сохранить исключения,

5. Переиспользовать одну проверку диапазона в автоматическом int-преобразовании и
   IntegerCast. Guard выполняется до потери цифр и reflection; ошибка гидратации
   дополняется путём DTO, исходящей сериализации — классифицируется отдельно.
   Проверить union selection и приоритет явных пользовательских casts.
6. Обновить документацию, выполнить targeted и полный composer test, standalone

7. Внести фактические результаты и ограничения, обновить changelog без ссылок на

## Совместимость и документация

Изменение **не полностью обратно совместимо по поведению**:

- Missing/null при Returns::unwrap больше не возвращают DTO из корня.
  Миграция: верный путь, DTO-обёртка или явная нормализация провайдером.
- Большой JSON integer станет string вместо float, включая json() для пользовательских
  обработчиков ошибок/auth. Миграция: string/int|string для идентификаторов;
  приблизительные вычисления должны явно выбирать float.
- Переполнение int больше не возвращает MAX/MIN; IntegerCast::serialize также откажет
  до отправки. Передавать точный ID строкой, если это соответствует протоколу провайдера.
- JSON в новых fixtures/диагностике может содержать строку вместо числового литерала.

Конструкторы клиентского конфига и атрибутов не требуют новых аргументов.
Гарантий байтового round trip JSON не добавляется. Зависимостей от Laravel/внешних
сервисов нет; решение агностично к моделям конкретных API.

Публичные изменения описать в [Returns](../../../docs/guides/attributes/response.md),
