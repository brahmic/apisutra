# Потоковые upload и download с ограниченным расходом памяти

- Дата создания: 2026-09-12
- Дата обновления: 2026-09-12
- Статус: завершён

## Цель и основание

Оставшаяся часть AS-08 из [issue/001](../issue/001/technical-specification.md):
передавать большие файлы без создания строки размером со весь файл, определить
владение потоками и безопасное сохранение результата скачивания.
Продолжение [retry/replay](../completed/pln-005-safe-retries-stream-replay.md)
и [внешних URL](../completed/pln-008-external-signed-urls-origin-policy.md).
Исходная версия — `da4794f`.

Пользователь поручил реализацию 2026-09-12: «Если вопросов нет и всё готово —
приступай к реализации». Продуктовые решения обсуждены и согласованы в чате;
запись ответов приведена ниже. Технические детали D1–D3 остаются проектным
предложением для реализации в рамках согласованного поведения.

### Согласованные решения

- Отказ от HTTP-кеширования файловых операций: глобальный кеш их пропускает,
  явное включение возвращает ошибку до HTTP. Пользователь предложил отказаться
  от кеширования файлов; контракт уточнён в обсуждении пункта 2 и D1.7.
- Потоковый raw body download с сохранением `FileResponse` и его методов,
  отправка binary с текущей позиции и запрет повтора non-seekable binary
  подтверждены ответом пользователя «Подтверждаю» на перечисленные три изменения.
- Безопасное сохранение из D2 принято ответом «перечисленное вроде как норм»
  после объяснения: новый `withDownloadTo()` не заменяет существующий файл без
  `overwrite: true`; временный файл публикуется после успешного завершения и
  проверок; неудачные HTTP-попытки не смешиваются; пользовательский поток остаётся
  открытым и может содержать часть данных при ошибке финального копирования.
- Существующий `FileResponse::saveTo()` сохраняет разрешённую перезапись.
  Новые обязательные настройки для обычного файлового сценария не вводятся.

Открытых продуктовых вопросов по обсуждённому контракту нет. Если при реализации
понадобится изменить согласованное поведение, новое решение следует обсудить
отдельно; повторное согласование уже принятых пунктов не требуется.

Zero-config: существующие `FileInput`, `#[File]` и `#[Download]` должны выбирать
потоковую передачу автоматически. Пользователь указывает источник и, при
необходимости, назначение файла. Обязательные `FileConfig`, размер буфера,
временный каталог и флаги перемотки не вводятся.

## Подтверждённое исходное состояние

Проведены чтение кода, проверка существующих тестовых контрактов и две небольшие
локальные пробы. Это точечная подготовка, не повторный аудит всего SDK.

| Наблюдение | Основание и следствие |
| --- | --- |
| Binary upload превращает файл в строку | `prepareBinaryBody()` в [FilePayloadPreparer](../../src/Serialization/FilePayloadPreparer.php) выполняет `(string) $fileItem->stream`. [SerializerFilesTest](../../tests/Unit/Serialization/SerializerFilesTest.php) закрепляет `body = 'PDF'`, `stream = null`. |
| Ненулевая позиция binary теряется | Проба с `prefix:payload`, `seek(7)` вернула `binary_body = 'prefix:payload'`, `has_stream = false`, позицию 14. Требуется изменение байтов для этого случая, а не только оптимизация памяти. |
| Multipart уже использует поток | `buildMultipartStream()` сохраняет начальную позицию частей через `LimitStream`. [RequestBodyReplay](../../src/Retry/RequestBodyReplay.php) восстанавливает позицию одного выполнения, не закрывает и не буферизует поток. |
| Ответ материализуется до гидрации | [HttpTransport](../../src/Transport/HttpTransport.php) приводит PSR body к строке. [ProviderResponse](../../src/VO/Http/ProviderResponse.php) имеет обязательное `string $body`. |
| Download заново создаёт поток из строки | [ResponseHydrator](../../src/Pipeline/Hydration/ResponseHydrator.php) сначала вызывает `json()` даже для download, затем `streamFor($response->body)` и `strlen()`. Простого изменения `FileResponse` недостаточно. |
| Кеш download явно поддерживается | [CacheManagerDownloadTest](../../tests/Unit/Cache/CacheManagerDownloadTest.php) проверяет `withCache()` и `#[Cache]`. [CacheManager](../../src/Pipeline/Cache/CacheManager.php) сохраняет строковое тело; по умолчанию download уже исключён из кеша. Upload с файлами также исключён. |
| Recorder сериализует всё тело ответа | [RecordingTransport](../../src/Transport/RecordingTransport.php) разбирает его как JSON либо пишет строку в fixture. [MockTransport](../../src/Transport/MockTransport.php) считает отсутствие тела обычной фикстурой; метаданные потока нельзя выдать за полноценную запись для playback. |
| Сохранение файла требует усиления | [FileResponse](../../src/VO/Files/FileResponse.php)::saveTo() открывает конечный путь через `wb`, безусловно перематывает источник, не проверяет короткую запись и не гарантирует `finally`. `content()` и `asArchive()` явно создают строку. |
| Нулевой размер определяется неодинаково | Проба пустого временного файла: [FileInput](../../src/VO/Files/FileInput.php)::fromPath()->size = null, tryFromPath()->size = 0; причина — `filesize() ?: null`. |
| PSR-18 сам по себе не доказывает расход памяти | [GuzzleHttpClient](../../src/Transport/GuzzleHttpClient.php) использует известный cURL handler. Установленный `CurlFactory` пишет ответ в sink, но может перематывать upload и преобразовывать маленькие тела в строку. Воспроизведение пробы позиции из корня репозитория, без HTTP:

```bash
php <<'PHP'
<?php
require 'vendor/autoload.php';
use Brahmic\ApiSutra\Enums\Http\FileFormat;
use Brahmic\ApiSutra\Serialization\FilePayloadPreparer;
use Brahmic\ApiSutra\VO\Files\FileInput;
use GuzzleHttp\Psr7\Utils;
$stream = Utils::streamFor('prefix:payload');
$stream->seek(7);
$file = FileInput::fromStream($stream, 'fixture.bin');
$prepared = (new FilePayloadPreparer())->prepareBodyAndStream(
    FileFormat::Binary, [['name' => 'file', 'file' => $file]], [], false, [],
);
var_export([$prepared['body'], $prepared['stream'] !== null, $stream->tell()]);
PHP
```

Предыдущие 1101 тест и результаты plan-008 относятся к `da4794f`, а не к будущей
потоковой реализации. Проверка 128 MiB под 64 MiB пока не выполнена.

## D1 — потоковый режим и представление ответа

Рекомендуется автоматический потоковый binary/multipart upload и download для
`#[Download]`, без переключателя в конфиге клиента.

1. Binary передаёт `StreamInterface` через существующий `PreparedRequest.stream`,
   `body = null`. Отдельное представление ограничивает начало текущей позицией:
   перемотка HTTP-адаптером не открывает байты до неё. MIME сохраняется; длина
   определяется по передаваемому диапазону, а не по полному размеру исходника.
   Неизвестная длина остаётся неизвестной, пустой файл имеет длину 0.
2. Каждая HTTP-попытка download пишет в собственный временный файл на диске.
   Это синхронная передача с ограниченным расходом RAM: результат появляется
   после завершения HTTP. Ленивое чтение из сокета пользователем не вводится.
3. Рекомендуемое расширение `ProviderResponse`: `?string $body` и добавленный
   необязательный `?StreamInterface $stream`. Ровно одно представление тела:
   обычные ответы сохраняют строку, download получает `body = null` и поток.
   Пустой download — валидный пустой поток, а не отсутствующее тело.
   Не подставлять `''` вместо не прочитанного файла и не делать скрытый lazy cast.
4. `FileResponse` получает уже существующий поток, позицию 0 и фактическое число
   записанных байтов. Не доверять `Content-Length` как фактическому размеру:
   возможны неизвестная длина и декомпрессия. `content()` остаётся явным чтением
   целиком в память; `asArchive()` сохраняет такое же ограничение.
5. Для download убрать неявный JSON decode и автоматический archive handler.
   Вызов `json()`/`jsonStrict()` на потоковом `ProviderResponse` даёт понятный
   `configuration_error`, а не скрытое чтение или ложный null. Миграция custom
   hooks: проверять форму ответа и читать поток явно, когда это действительно нужно.
6. Для HTTP-ошибок download сохранять полный raw-поток. `errorMessage()` может
   разобрать JSON лишь если всё тело укладывается в фиксированный предел 64 KiB;
   чтение ограничено и восстанавливает позицию. Для большего/не-JSON тела —
   `HTTP <status>`. Это предел автоматического извлечения сообщения, не предел файла.
7. Отказаться от HTTP-кеширования файловых операций в ядре: download и upload
   с файлами не читают и не записывают кеш. Глобальная настройка автоматически
   пропускает их. Поведение явного активного `withCache()`/`#[Cache]` —
   `configuration_error` до auth/HTTP независимо от наличия cache store;
   `withoutCache()` снимает конфликт. Для upload это делает явную несовместимую
   настройку видимой вместо нынешнего молчаливого пропуска. Распознавать upload
   по потоку/файловым метаданным, включая `FileInput` в Base64, без чтения содержимого;
   обычные JSON-строки не классифицировать как файлы по предположению.
   Дисковый кеш файлов и режим совместимости с полной материализацией не вводить.
   Временный download-файл принадлежит одному выполнению и не используется между
   запросами: это рабочее хранилище передачи, а не кеш.

Причина выбора: сохраняются привычные файловые операции, а гарантия памяти не
зависит от случайного размера ответа. Цена — временный диск и точечная несовместимость
raw body/явного кеширования, указанная ниже.

## D2 — сохранение в путь или пользовательский поток

Рекомендуемый новый API на `RequestOptions` и chain trait:
`withDownloadTo(string|StreamInterface $target, bool $overwrite = false)` и
`withoutDownloadTo()`. Это предложение сигнатуры, не существующий API.
Операция применима к запросу с `#[Download]`; на другом запросе — ошибка до HTTP.
`withoutDownloadTo()` очищает цель, оставляя обычный download во временный файл.

### Путь

- Поддержать локальный файловый путь. Пустые пути, stream wrappers, каталог вместо
  файла и конечную символьную ссылку отклонять. Каталоги автоматически не создавать.
  Имя из `Content-Disposition` — метаданные; оно не выбирает путь на диске.
- По умолчанию существующий файл не перезаписывается. `overwrite: true` явно
  разрешает замену обычного файла. Проверка перед HTTP не заменяет повторную
  проверку при публикации: появившийся в промежутке файл также нужно защитить.
- Получать тело во временный файл рядом с назначением; конечное имя публиковать
  только после последнего принятого 2xx, гидрации, hooks и проверки бюджета.
  Каждый retry использует новый staging-файл. 3xx не публикуется как файл;
  политика redirect из plan-008 сохраняется.
- Публикация без overwrite должна использовать атомарную операцию без замены
  существующего имени; `exists()` + обычный `rename()` этого не гарантируют.
  При overwrite — атомарная замена в той же файловой системе. Если файловая система
  этого не поддерживает, вернуть явную ошибку, не переходить к неатомарной записи.
- До публикации любая HTTP/локальная ошибка, отказ hook или deadline сохраняет
  прежний конечный файл. После атомарной публикации не выполнять новые SDK-шаги,
  способные объявить операцию неуспешной. Публикация — последняя стадия с эффектом;
  это не гарантия сохранности при аппаратном сбое или транзакция с внешними hooks.

### Пользовательский StreamInterface

- Проверить `isWritable()` до HTTP. `overwrite: true` к потоку неприменим и ошибочен.
  Принимаются в том числе write-only и non-seekable приёмники.
- HTTP пишет во внутренний staging-файл. В пользовательский поток копировать
  только окончательный принятый результат, после hooks и проверок, порциями.
  Такой порядок предотвращает попадание в приёмник тела 401/503 или нескольких retry.
- Писать с текущей позиции приёмника, не перематывать, не усекать хвост и не закрывать
  его. За append/позицию и дальнейшее использование отвечает вызывающий код.
  Рекомендуемый обычный случай — открытый пустой поток.
- При короткой записи продолжать с остатком; `false`, отсутствие прогресса и
  исключение превращать в ошибку, а не бесконечный цикл или успех.
  Если ошибка/deadline возникли во время копирования, приёмник может содержать
  часть данных. Произвольный внешний поток не поддерживает гарантированный rollback;
  вернуть `bytesWritten` и признак частичной записи, не запускать HTTP заново.
- Результат остаётся `FileResponse` с внутренним читаемым потоком и позицией 0,
  даже если конечный приёмник write-only. Это требует временного диска и копирования,
  но сохраняет тип результата и возможность `content()`/`stream()`.

Существующий `FileResponse::saveTo($path)` сохранить с прежней семантикой разрешённой
перезаписи. Исправить обработку коротких записей, cleanup и использовать безопасную
публикацию. Новый `withDownloadTo()` по умолчанию защищает существующий файл;
разницу явно описать. Для non-seekable FileResponse сохранение возможно с текущей
позиции; методы проверки magic bytes не должны незаметно съедать начало потока.

## D3 — владение, повторы, диагностика и поддержка транспорта

### Владение и повторы

- `FileInput::fromStream()` заимствует поток: SDK его не закрывает и не передаёт
  адаптеру право закрыть исходник. То же правило действует для переданного sink.
- Поток, созданный `fromPath()`/`fromContent()`, принадлежит `FileInput`; не закрывать
  его после `send()`, пока объект остаётся доступен. Добавить явный `close()`;
  для заимствованного потока он не закрывает исходник. Копии `withMimeType()`
  разделяют владельца: его закрытие делает общую файловую ручку недоступной всем.
- Начало upload фиксировать при подготовке одного выполнения. Автоматически
  восстанавливать его перед повторной попыткой. После завершения не обещать возврат
  позиции исходника: повторный `send()` — новое выполнение с текущей позицией.
  Immutable request не даёт независимую копию файла; параллельное использование
  одной ручки и изменение исходника во время передачи не поддерживаются.
- Сохранить `Retry.safe`, auth retry, причины `body_not_replayable`,
  `body_rewind_failed`, `body_changed`, исходную ошибку и общий deadline.
  Non-seekable upload отправляется один раз. Не вводить скрытый upload spool
  или фабрики повторяемого тела в этой поставке.
- SDK владеет временными download-файлами. Неуспешные/заменённые попытки освобождаются
  при исчезновении владельцев; сохраняемый в результате raw-ответ остаётся читаемым.
  Успешный владелец передаётся `FileResponse` и raw response совместно.
  Добавить явный `FileResponse::close()` с документированной инвалидизацией общего
  потока; последний владелец освобождает временный файл. Сохранённый конечный файл
  при `close()` не удаляется. Cleanup проверять и при исключениях, а не только через GC.

### Диагностика и кеш

- Upload/download потоки не читать ради debug, audit, ключа кеша или redaction.
  Показывать доступные метаданные: признак потока, MIME, известный/фактический размер;
  `requestDebug(false)` также не должен неявно превращать поток в строку.
- Recorder записывает для потока метаданные и явный признак `bodyOmitted`, не
  содержимое. Такая fixture непригодна для полного playback: loader выдаёт понятную
  ошибку вместо успешного пустого ответа. Добавить ручные stream/file fixtures для
  тестирования download, с новой ручкой на каждый ответ; старые JSON fixtures работают.
- Сохранить маскирование signed URL и credentials; не помещать локальные пути,
  файловые дескрипторы или содержимое файла в безопасные ошибки и журнал.
- Обычные JSON/text ответы, их кеш и archive extension вне `#[Download]` сохраняются.
  Общий лимит JSON, потоковые архивы и Base64 JSON в этот план не входят.

### Транспорт и ошибки

- Добавить небольшой контракт capability для файловой передачи с проверкой режима
  upload/download. Общие `TransportInterface`/PSR-18 не расширять обязательными
  методами. Штатный транспорт поддерживает capability автоматически; проверка
  стороннего транспорта, PSR-клиента и custom retry handler — до auth и HTTP.
- Передавать режим download и управляемый sink через типизированные данные
  отдельного выполнения/попытки, а не общий Guzzle config. Сохранять их при copy,
  effective timeout и подготовке retries. Child-запрос не наследует sink родителя.
- Guzzle обязан писать прямо в SDK sink. Не допускать скрытый default sink/debug
  или принудительное преобразование большого upload в строку. Проверить нормальный
  и изолированный клиент, не ослабляя origin policy и точное сохранение URL.
- Неподдерживаемый адаптер выдаёт `configuration_error`, без молчаливого fallback
  к полной строке. Standalone поддерживается через явный адаптер без Laravel и
  без обязательного Guzzle HTTP Client; зависимости пакета не расширяются.
- Ошибки локального чтения/записи оформить отдельным `FileTransferException`
  с предлагаемым `file_transfer_error`, стадией и счётчиком байтов. Их нельзя
  классифицировать как сетевой сбой и автоматически повторять HTTP. Некорректная
  конфигурация цели — `configuration_error`; исчерпание бюджета сохраняет `timeout`.
  Сохранять доступный HTTP-статус и исходную причину; соблюдать result-first/throwOnErrors.
- Чтение HTTP ограничивается текущими transport timeout, копирование и финализация
  проверяют общий бюджет между порциями и перед публикацией. Отдельная блокирующая
  операция произвольного пользовательского StreamInterface не становится прерываемой;
  этот предел гарантии описать, не обещать новый неблокирующий I/O.

## Совместимость

Полная обратная совместимость не заявляется.

| Сценарий | После изменения / миграция |
| --- | --- |
| Обычные JSON/text запросы | Прежние строковые ответы и конфигурация. |
| Upload из начала файла | Прежние HTTP-байты; binary находится в `PreparedRequest.stream`, а не `body`. Hooks/адаптерам нужно учитывать поток. |
| Binary с ненулевой позицией | Передаётся остаток с указанной позиции, как multipart; раньше передавался весь файл. Для всего файла явно rewind до вызова. |
| Non-seekable binary с retry | После перехода со строки на поток повтор запрещён; прежде строковая копия могла повторяться. Это существенное изменение. |
| `#[Download]` → `FileResponse` | Прежний тип результата и методы; по умолчанию требуется временный диск. |
| Прямой `ProviderResponse.body`, json/hooks для download | Теперь `body = null`, данные в потоке. Нужна адаптация; строковые конструкторы старого кода остаются валидными. |
| Явный HTTP cache download | Ошибка до HTTP. Убрать `withCache()`/`#[Cache]` либо отключить runtime; отдельный файловый кеш — задача приложения. |
| Явный HTTP cache upload с файлами | Ошибка до HTTP вместо молчаливого пропуска. Глобальный cache по-прежнему не применяется; формат Base64 сам по себе не разрешает кеширование файловой операции. |
| Recorder/playback файлов | Автоматическая запись метаданных не воспроизводит файл. Для playback предоставить явную файловую fixture. |
| Сторонние адаптеры | Подтвердить capability и реализовать потоковую передачу; обычные нефайловые запросы работают как раньше. |
| `saveTo()` и `content()` | Перезапись в saveTo сохраняется; content по явному запросу использует память пропорционально файлу. |

## Порядок реализации

1. После поручения реализации выполнять согласованный контракт D1–D3 с учётом
   таблицы совместимости. Начать с failing-сценариев binary position, streaming response,
   запрета cache, ошибок записи и владения; не переписывать тесты только под типы.
2. Ввести модель владельца ресурса, потоковую форму ответа, опции цели и capability.
   Проверить copy/reset, child context, low-level transport и контракты ошибок.
3. Перевести binary на поток, защитить начальную позицию от rewind адаптера,
   сохранить multipart/replay; исправить размер пустого файла и lifecycle.
4. Провести download intent до фактического транспорта, реализовать sink каждой
   попытки и передачу потока в FileResponse. Устранить неявный JSON decode.
5. Реализовать финальную доставку в путь/поток, атомарную публикацию, cleanup,
   failure/result-first, закрытие ресурсов и проверки бюджета. Учесть hook failure

6. Обновить кеш, debug/recorder, mock fixtures и capability wrappers. Проверить
   signed URL, retries, auth refresh, mode/target reset и отсутствие наследования sink.
7. Добавить сценарии локального HTTP и отдельные процессы с ограничением памяти.

## Критерии приёмки

- В отдельных PHP-процессах с `memory_limit=64M` файл 128 MiB проходит binary,
  multipart, обычный download, download-to-path и download-to-stream. Размер и
  потоковый hash совпадают; генератор и локальный сервер тоже не держат весь файл
  в строке. Проверить debug + RecordingTransport и включённый глобальный cache.
- Повтор seekable upload передаёт те же байты: маленькое/большое тело, позиция 0
  и ненулевая, multipart boundary. Non-seekable не получает второй отправки.
- Download 503 → 200 и 401 → refresh → 200 не смешивает попытки и пишет в цель
  только окончательные байты. Обрыв передачи, усечённый HTTP body и deadline не
  создают успешный файл. Политика повторов операций сохраняется.
- Пустой файл upload/download имеет фактический размер 0. Неизвестная длина,
  декомпрессия, маленький JSON error и большой error body не нарушают память/статус.
- Проверены существующий путь, overwrite, гонка создания цели, symlink, запрет
  wrappers, невозможность атомарной публикации, недоступный каталог, заполненный
  диск через fault injection. До commit point старый файл сохраняется.
- Короткая запись, нулевой прогресс, ошибка чтения, отказ hook и истечение бюджета
  возвращают явную ошибку. Для пользовательского sink корректны bytesWritten и
  partial state; нет повторного HTTP из-за локальной ошибки.
- Заимствованные upload/sink остаются открыты; внутренние временные файлы имеют
  проверяемый lifecycle. FileResponse/raw response не закрывают поток друг друга
  при обычном освобождении одной ссылки; явный close описан и проверен.
- Потоковый debug/recorder не читают и не меняют позицию. Метаданные fixture не
  воспроизводятся как пустой успех; ручная файловая fixture воспроизводится повторно.
- Глобальный cache не читает и не пишет файловые операции. Явное включение cache
  для binary/multipart/Base64 upload с FileInput и для download отклоняется до
  auth/HTTP даже без cache store; runtime withoutCache снимает конфликт.
- Конфликты target и неподдерживаемый транспорт выявляются до auth/HTTP.
  Default transport работает без дополнительных настроек; signed URL сохраняются,
  credentials не утекают, redirects не включаются.
- Общая регрессия и standalone проходят; проверки, команды и измерения сохраняются
  в репозитории. План переносится в completed только после реализации и приёмки.

## Границы поставки

Это ограниченная по памяти синхронная файловая передача с временным диском.
Не входят: async-first, socket streaming пользователю до завершения запроса,
resume/range download, автоматический redirect, DNS/SSRF policy, общий JSON size
limit, потоковая обработка Base64/архивов, файловый кеш, фабрики upload replay,
автоматическое создание каталогов и гарантия транзакции для произвольного sink.
Не заявлять закрытие всех требований AS-08 до проверки оставшихся пунктов issue.

### Воспроизводимая проверка памяти

[streaming-memory-smoke](../../tests/Support/streaming-memory-smoke.php) создаёт
файл порциями и проверяет размер/hash результата. Каждый режим запускается
отдельным PHP-процессом; локальный сервер также ограничен 64 MiB.
Включены debug, RecordingTransport и глобальный cache.

```bash
php -d memory_limit=64M tests/Support/streaming-memory-smoke.php binary
php -d memory_limit=64M tests/Support/streaming-memory-smoke.php multipart
php -d memory_limit=64M tests/Support/streaming-memory-smoke.php download
php -d memory_limit=64M tests/Support/streaming-memory-smoke.php path
php -d memory_limit=64M tests/Support/streaming-memory-smoke.php sink
```

| Режим | Размер файла | Пик memory_get_peak_usage(true) |
| --- | --- | --- |
| binary | 134217728 | 15745024 |
| multipart | 134217728 | 15745024 |
| download | 134217728 | 8388608 |
| path | 134217728 | 8388608 |
| sink | 134217728 | 8388608 |

Это измерение PHP RAM, не лимит временного диска или общей памяти всех процессов.
Внешняя сеть не используется. [HTTP-стенд](../../tests/Support/file-http-server.php)
сохраняется вместе с тестами; временные файлы проверки удаляются.

### Standalone и уточнения реализации

[standalone-streaming-smoke](../../tests/Support/standalone-streaming-smoke.php)
проверяет upload, download, sink и async с production-зависимостями, без Laravel
и Guzzle HTTP Client. Использует явные PSR-адаптеры; команда указана в шапке скрипта.
Повторно прошёл также standalone внешних URL.

Файл назначения публикуется после hooks и проверок бюджета. Итоговый logger
вызывается после публикации; его исключение в этом случае не превращает уже
сохранённый файл в неуспех. До публикации обычные ошибки logger сохраняют прежнее
поведение. Это уточнение обеспечивает согласованную границу сохранения.

Ошибки файловой записи проверены через короткую запись/нулевой прогресс; ошибка
атомарной публикации воспроизведена удалением staging-файла перед её выполнением.
Реальный диск не заполнялся. Гарантии ограничены контрактом файловой системы и
пользовательского StreamInterface; аппаратный сбой, аварийное завершение процесса
и блокирующий пользовательский I/O не превращены в транзакционную систему.

Оставшиеся вне объёма вопросы AS-08 не объявлены решёнными. Исходные issue/001
и параллельные изменения README/логотипа не изменялись.
