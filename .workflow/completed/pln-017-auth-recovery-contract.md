# Auth retry только после доступного восстановления авторизации

- Дата создания: 2026-09-12
- Дата обновления: 2026-09-12
- Статус: завершён

## Основание и цель

[Аудит A1–A4](../audit/aud-003-remaining-work/aud-003-readme.md), требования AS-03/AS-09
и сохранения реальных ошибок AS-02. Завершённый
[план изоляции токенов](pln-011-auth-token-isolation/pln-011-readme.md)
не закрывал availability auth refresh.

Цель — убрать бесполезную автоматическую повторную отправку после 401, сохранить
работающий refresh, исходные HTTP-ответы и executing-client context.

Сейчас фиксированный Bearer и отсутствие auth дают два основных HTTP-вызова после
401 без refresh. Ошибка refresh 503 заменяется искусственным 401. Вызов
`client->send(new Request())` с refresh требует незаявленного предварительного setClient.
Привязанный request с успешным refresh работает и должен продолжать работать.

## Согласованный контракт

В1 принят пользователем 2026-09-12 — О1 в
[ответах аудита](../audit/aud-003-remaining-work/aud-003-readme.md#ответы).

1. Автоматический auth retry разрешается после успешного refresh с обработкой
   типизированного ответа либо после подтверждённого обновления TokenAuthenticator
   другим владельцем lock. Отсутствие auth/refresh-request не разрешает auth retry.
2. Не требовать нового флага в ClientConfig или обязательного метода от всех
   пользовательских AuthenticatorInterface. Использовать существующий nullable
   getRefreshRequest и имеющийся tokenVersion у TokenAuthenticator. Не требовать
   изменения байтов токена после успешного refresh: провайдер может вернуть то же
   значение; SDK не знает серверной семантики credentials.
3. При отсутствии восстановления по умолчанию вернуть настоящий исходный 401.
   Если приложение явно настроило обычный retryOn=[401] или собственное правило,
   оно проходит обычную политику retry/безопасности/бюджета. Это отдельная настройка,
   не основание для безусловного auth retry.
4. При неудачном refresh после основного 401: оставить основной 401 с его headers/body,
   добавить reason=auth_refresh_failed и диагностический результат зависимости
   (фактический HTTP 503, timeout, decoding error и т. п.). При initial refresh до
   первого основного HTTP — вернуть фактическую ошибку зависимости, без фиктивного 401.
   Если истёк общий deadline, сохранить принятый приоритет timeout.

Пример: постоянный API key отвергнут → один основной HTTP и 401. Обновляемый токен
отвергнут → refresh → одна разрешённая повторная попытка. Refresh недоступен с 503 →
повтор основной операции не выполняется, оба фактических ответа доступны для разбора.

## Границы и zero-config

Сохранить authRetryOn401/authRetryAttempts, NoAuth/forceAuth/scope и origin policy,
общий deadline, безопасный replay тела и отдельный лимит auth-попыток.
Для обычного пользователя дополнительных обязательных настроек и зависимостей нет.
Не добавлять OAuth-протоколы, универсальное сравнение credentials, очереди,
атомарную координацию сторонних AuthenticatorInterface и переустройство token store.

## Подход

- Разделить применение credentials и попытку восстановления после 401 в
  [AuthHandler](../../src/Pipeline/Auth/AuthHandler.php). Сохранить публичный void
  handleAuthentication; результат восстановления передавать отдельным внутренним
  методом/результатом со значениями «недоступно» и «готово к повтору». Ошибка остаётся
  ошибкой, не ещё одним видом разрешения.
- Не считать успешный возврат void handleAuthentication доказательством refresh.
  Наличие refresh определять один раз; не вызывать фабрику дважды ради проверки и
  выполнения. Для отсутствующего refresh не ждать бесполезную auth-блокировку.
- При TokenAuthenticator сохранить повторное чтение кеша после lock и пропуск
  собственного refresh, если другой участник уже обновил токен. Освобождение lease
  остаётся обязательным при любом исходе.
- Привязывать dependency refresh к реально выполняющему клиенту. Не вызывать
  request->getClient() ради автоматического глобального resolve, если client->send
  уже задал контекст. Сверить точки сборки AuthHandler/Pipeline, передать нужную
  зависимость через существующую сборку; не вводить глобальный «текущий клиент».
- В [RetrySender](../../src/Pipeline/Transport/RetrySender.php) увеличивать auth-счётчик
  и разрешать повтор только по результату восстановления. Проверки безопасности
  операции и восстановления тела должны предшествовать refresh с побочными эффектами.
- Заменить synthetic UnauthorizedException из refreshToken диагностикой с реальными
  ответами. Для compatibility сохранить catch UnauthorizedException при отказе после
  основного 401 через специализированный AuthRefreshFailedException; response содержит
  основной реальный 401, отдельное поле — результат зависимости. До основного HTTP
  использовать причину зависимости. В автоматический context не экспортировать токены,
  credentials, полный объект dependency result или unsafe previous.
- Обеспечить terminal-обработку отказа восстановления на уровне основного auth retry:
  retryExceptions=[Throwable::class] не должен перезапускать весь auth refresh вслепую.
  Собственная политика выполнения dependency остаётся ограничена её конфигом/бюджетом.

## Совместимость и завершение

Иерархия базовых auth-интерфейсов не меняется. Изменятся число лишних HTTP-вызовов,
содержимое ответа при refresh failure и поведение custom authenticator, который
раньше использовал повторный authenticate без getRefreshRequest для неявной ротации.
Такой сценарий надо явно обозначить в migration, не возвращать бесполезный retry
для всех клиентов ради него. Новая capability для такого расширения — только при
подтверждённой необходимости, вне автоматической части этого плана.

Готовность: В1 согласован, нет бесполезного автоматического auth retry, реальный ответ
не подменяется, успешный refresh и изоляция сохранены, тесты и документация обновлены.
Реализация завершена; результаты приёмки записаны ниже.
