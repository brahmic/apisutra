# Техническое задание на доработку ApiSutra

**Дата:** 11 сентября 2026 года.  
**Редакция документа:** 1.0.  
**Пакет:** `brahmic/apisutra`.  
**Проверенная версия:** `v0.1.0-alpha.1`.  
**Базовый commit:** `96e8c4071f2cc517cb39dfca36101671259ab317`.  
**Назначение:** передача разработчику пакета для планирования, реализации и приёмки изменений.

## 1. Цель и границы работ

Обеспечить предсказуемую работу ApiSutra как основы типизированных SDK: корректную отправку данных, изоляцию учётных записей, управляемые таймауты и повторы, фактическую асинхронность, безопасную диагностику и подключение к Laravel.

Целевое окружение — PHP 8.4 и новее; Laravel-интеграция — начиная с Laravel 12. Ядро должно сохранять возможность работы без Laravel. Поддержку последующих major-версий зависимостей необходимо подтверждать отдельной строкой CI-матрицы.

Работы выполняются в ApiSutra. Конкретные внешние API, их предметные модели, маршруты и бизнес-процессы в ядро не включаются. Все домены `example.test`, токены и идентификаторы в этом документе вымышлены.

Нужно доработать существующие механизмы, сохранив оправданные границы между request, сериализацией, transport, execution, result и Laravel-адаптацией. Новые контракты вводятся для реальных точек расширения; дублирующие слои DTO, транспорта и конфигурации не требуются.

## 2. Основание и статус утверждений

Проверка выполнена на PHP 8.5.4 с зависимостями из `composer.lock` указанного commit. Полный набор тестов пакета завершился без падений: 723 теста, 1733 assertions. Pest отметил 43 теста с deprecation-предупреждениями. Запуск на PHP 8.4 и проверки в полноценном Laravel-приложении в исходную проверку не входили.

Дополнительно выполнены 17 изолированных проб. HTTP-ответы подменялись; внешние сервисы не вызывались. Это проверка поведения SDK, а не подтверждение совместимости с каким-либо провайдером.

В документе используются три статуса:

- **Воспроизведено:** поведение получено исполняемой пробой через публичный API пакета.
- **По исходникам:** установлен конкретный путь выполнения; отдельная исполняемая проба для этого пункта не проводилась.
- **Целевое требование:** предлагаемое расширение либо уточнение контракта. Само по себе не означает, что текущая реализация содержит дефект.

Рабочие возможности вынесены в регрессионные требования. Наличие нескольких проблем не является основанием переписывать исправные подсистемы.

После исправлений значения должны измениться согласно критериям приёмки. Сохранённый JSON описывает только базовую версию.

## 4. AS-01 — таймауты

**Текущее поведение.** В R01 заданы `ClientConfig(timeout: 77, connectTimeout: 11)` и runtime `withTimeout(42, 7)`. Guzzle получает собственные исходные значения `timeout=9`, `connect_timeout=3`. Значения SDK не применяются. В `PreparedRequest` отсутствует типизированный контракт транспортных опций; стандартный `HttpTransport` вызывает только PSR-18 `sendRequest()`.

**Требования.**

1. Определить единое разрешение настроек: runtime override → атрибут запроса → `ClientConfig` → документированное значение по умолчанию. Отсутствие override и значение 0 должны различаться.
2. Передавать итоговые настройки в transport явным контрактом, например отдельным immutable VO. Конкретное имя класса выбирает разработчик. Транспорт не должен читать приватное состояние request или контейнер приложения.
3. Реализовать применение общего таймаута запроса и таймаута соединения хотя бы в одном штатном транспорте. Не менять глобальный Guzzle-клиент ради одного запроса.
4. Для транспорта, не поддерживающего выбранную настройку, предусмотреть явную проверку возможности и понятную ошибку конфигурации. Молчаливое игнорирование недопустимо. PSR-18 сам по себе не предоставляет per-request timeout options.
5. Зафиксировать единицы измерения. Неположительные и отсутствующие значения должны иметь однозначную семантику: отрицательные запрещены; 0 означает отсутствие соответствующего ограничения только там, где это явно поддерживается. Безлимитный запрос всё равно ограничивается общим deadline, если он задан.
6. Совместить per-attempt timeout с оставшимся общим бюджетом AS-03. Не допускать округления оставшихся миллисекунд до 0 с последующим отключением ограничения.

**Пример.** `GET /reports/next` допускает ожидание ответа 45 секунд. Отдельный `GET /profile` должен завершаться за 5 секунд. Последовательное выполнение одним клиентом не переносит настройки между запросами.

**Приёмка.**

- В R01 транспорт получает 42 и 7; без runtime override — значения атрибута, затем конфигурации.
- Интеграционный тест с управляемым локальным HTTP-сервером подтверждает фактическое прерывание медленного ответа. Проверки одних полей конфигурации недостаточно.
- Проверены отдельный connect timeout и два одновременных запроса с разными настройками.

Исходники: [HttpTransport](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Transport/HttpTransport.php), [PreparedRequest](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/VO/Http/PreparedRequest.php), [RequestPreparer](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Preparation/RequestPreparer.php). Ограничения стандарта и адаптера: [PSR-18](https://www.php-fig.org/psr/psr-18/), [Guzzle timeout options](https://docs.guzzlephp.org/en/stable/request-options.html#timeout).

## 5. AS-02 — ошибки и последний HTTP-ответ

**Текущее поведение.** В R04 первая попытка выбрасывает Guzzle `ConnectException`, следующая могла бы завершиться успешно. При настроенных двух попытках SDK делает одну: проверка retry видит исходное исключение, тогда как по умолчанию ожидает собственный `ConnectionException`. Обёртка создаётся позже.

В R05 сервер дважды возвращает 503. Последний `ProviderResponse` сохраняется в результате, но основной код ошибки становится `connection_failed`, а сообщение — «Не удалось выполнить запрос». HTTP-ошибка ошибочно классифицируется как отсутствие соединения.

**Требования.**

1. Нормализовать ошибки конкретного транспорта **до** решения о повторе. Сохранять исходное исключение как `previous`.
2. Различать сетевой сбой, подтверждённый timeout, некорректный HTTP-запрос, HTTP-ответ 4xx/5xx, ошибку JSON, ошибку гидратации, конфигурации и пользовательского hook. Не превращать произвольный `Throwable` в сетевую ошибку.
3. Не определять DNS/timeout по тексту сообщения. Использовать доступные типы, коды и transport metadata; при отсутствии достоверного признака возвращать общий сетевой тип.
4. После исчерпания повторов HTTP-ответ должен проходить штатный error mapping с исходными status, headers, body и provider message. Для последовательности «сетевая ошибка → HTTP 503» итог описывает последнюю попытку; предыдущие попытки доступны как история.
5. Сохранить согласованность `ExecutionResult`, `resolved()`, `dataOrFail()`, `throwOnErrors`, batch и async. Отличаться может форма доставки ошибки, но не её смысл и контекст.
6. Ошибочный non-JSON ответ должен сохранять HTTP-статус и raw body. Не маскировать HTTP 503 ошибкой разбора JSON.

**Приёмка.** R04: две попытки и успешный результат при разрешённом повторе GET. R05: код `service_unavailable` или согласованный эквивалент, status 503 и исходное provider message. Отдельные тесты покрывают 400/401/403/404/422/429/500/502/503/504, сетевой сбой без ответа, ошибку hook и неверную DTO. Для ошибок 4xx нельзя использовать общий `server_error`, если он утверждает, что проблема находится на стороне сервера.

Исходники: [RetrySender](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Transport/RetrySender.php), [RetryConfig](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Config/RetryConfig.php), [ExecutionResultBuilder](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Flow/ExecutionResultBuilder.php), [ResultFactory](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Result/ResultFactory.php).

## 6. AS-03 — управляемые повторы

**Текущее поведение.** Повторы по умолчанию выключены — это поведение сохранить. После включения общей retry-конфигурации POST повторяется по статусу без проверки семантики операции: R06 выполняет `POST /resources` дважды.

По исходникам: backoff применяется и перед первой попыткой; использует прямой `usleep()`. `totalTimeoutMs` проверяется перед циклом, но не ограничивает всё последующее ожидание и HTTP-вызов. `RetryConfigResolver` теряет `totalTimeoutMs` при создании конфигурации из некоторых overrides. `Retry-After` может вызвать ожидание даже после последней разрешённой попытки.

**Требования.**

1. Разделить решение «есть причина повторить» и «эту операцию разрешено повторить». Предусмотреть расширяемую политику с доступом к запросу, результату/исключению, номеру попытки и оставшемуся времени.
2. Общая настройка retry не должна автоматически разрешать повтор POST/PATCH. Для операций изменения требуется явное заявление о допустимости повтора. GET разрешается стандартной политикой; PUT/DELETE — согласно документированному контракту идемпотентности с возможностью запрета для конкретной операции.
3. Наличие `Idempotency-Key` само по себе не доказывает, что сервер поддерживает дедупликацию. Поддержка сервером задаётся отдельно в provider SDK. Один логический вызов использует одинаковый ключ во всех попытках; независимые вызовы получают разные ключи, если пользователь не передал свой.
4. Определить `attempts` как общее максимальное число основных HTTP-попыток, включая первую. Повторные auth-попытки иметь отдельно ограниченными, но включать в общий бюджет времени и общий диагностический счётчик HTTP-вызовов.
5. Не делать backoff перед первой попыткой. Явный `delay` остаётся отдельной настройкой. После последней попытки ожидание не выполняется.
6. `Retry-After` поддерживает целое число секунд и HTTP-date. Некорректные и отрицательные значения обрабатываются определённым правилом. Для применимых ответов использовать максимум серверного ожидания и backoff, а не безусловную сумму. Если серверное ожидание превышает оставшийся бюджет, прекратить выполнение, не отправляя запрос раньше разрешённого срока.
7. Общий бюджет должен учитывать HTTP, request delay, rate-limit wait, retry wait и auth refresh. Использовать монотонные часы; для тестов — подменяемые часы и ожидание. Не сохранять прямые `sleep/usleep` в разных компонентах.
8. Изменение `attempts` через runtime или атрибут не сбрасывает остальные настройки: deadline, классы исключений, backoff, jitter и политику безопасности.
9. Повторы потоковых тел разрешены только при возможности восстановить исходные байты — AS-08.
10. При 401 повторять запрос только если доступен механизм обновления/смены credentials. Повтор с тем же неизменяемым API key не должен расходовать лишний запрос. Это целевое уточнение текущего auth retry.

**Приёмка.**

- POST создания ресурса без явного разрешения не повторяется при 503; GET с `attempts=3` имеет не более трёх попыток.
- При явно включённой серверной идемпотентности проверяются стабильный ключ, одинаковое тело и ограничение попыток.
- `attempts=1` не вызывает retry sleep; `withoutRetry()` исключает общие повторы согласно документированной политике auth retry.
- Подменяемые часы подтверждают соблюдение deadline, в том числе при `Retry-After`, rate limiting и runtime `withRetry()`.
- Sync и async имеют одинаковую политику. Async-ожидания не блокируют независимые операции.

Исходники: [RetryDecisionMaker](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Transport/RetryDecisionMaker.php), [RetryHandler](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Retry/RetryHandler.php), [RetryConfigResolver](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Transport/RetryConfigResolver.php).

## 7. AS-04 — HTTP-кеш

**Текущее поведение.** R02: клиенты с credentials A и B выполняют `GET /profile` через одно хранилище; B получает ответ A. R17 подтверждает, что разные `CacheConfig::prefix` устраняют эту коллизию. R15: глобальное включение кеша превращает два одинаковых POST создания ресурса в один HTTP-вызов.

По исходникам ключ не учитывает заголовки и авторизацию, использует query из `meta` вместо полного фактического URI, а значения query-массивов сортируются. Это может объединять запросы с разным смыслом, например `sort[]=name&sort[]=date` и обратный порядок.

**Требования.**

1. Добавить явный контекст изоляции: credentials/identity, tenant и необходимые provider-specific измерения. Разрешить переиспользовать существующий prefix либо предоставить отдельную стратегию ключей.
2. Для авторизованных запросов без достоверного контекста нельзя незаметно использовать общий кеш. Допустимы автоматический непрозрачный fingerprint или обязательный явный scope с понятной ошибкой/отключением кеша. Сырые секреты не включать в ключи и логи.
3. Учитывать фактический URI и параметры после применимых преобразований. Не терять query, заданный прямо в endpoint/URL или авторизацией. Сохранять порядок списков и повторяющихся параметров; сортировку допускается включать только для явно объявленных множеств.
4. Учитывать заголовки, меняющие представление ответа: например `Accept`, `Accept-Language` и настроенные tenant/version headers. Предоставить контролируемый список таких заголовков.
5. Глобальный cache store сам по себе не разрешает кеширование POST/PUT/PATCH/DELETE. Для таких операций требуется отдельный opt-in на операции. Потоковые загрузки не кешируются как обычный HTTP-ответ.
6. Ошибочные результаты не кешировать по умолчанию. Поведение `no-store`, `Vary` и режима явного application cache должно быть документировано; HTTP cache, учитывающий `Vary: *`, не должен сохранять такой ответ.
7. `clearCache()` использует тот же контекст и алгоритм, что чтение/запись; очистка A не затрагивает B. Не инициировать сетевой auth refresh только ради вычисления ключа очистки.
8. Сохранить режимы read-only/write-only/disabled и TTL. Ротация credentials не должна неожиданно открывать кеш другой учётной записи.

**Приёмка.** B получает только свой профиль; одинаковые GET в одном scope дают cache hit. Два обычных POST приводят к двум HTTP-вызовам. Проверены различия URI, порядка query-массива, языка ответа, credentials и tenant; корректная очистка и истечение TTL. Для общего хранилища использовать два независимых экземпляра клиента.

Исходники: [CacheManager](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Cache/CacheManager.php), [CacheConfig](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Config/CacheConfig.php).

## 8. AS-05 — фактическая асинхронность

**Текущее поведение.** R03 показывает `syncCalls=1`, `asyncCalls=0` при вызове клиентского `sendAsync()`. `Pipeline::executeAsync()` синхронно вызывает `execute()`. Дополнительно `HttpTransport::sendAsync()` и `RecordingTransport::sendAsync()` вызывают `send()` и оборачивают результат в Promise. Замены только HTTP-транспорта недостаточно.

**Требования.**

1. Асинхронное выполнение должно проходить через асинхронный pipeline и асинхронный транспорт. Возврат Promise после завершённого блокирующего HTTP-вызова не соответствует этому контракту.
2. Общую логику разрешения настроек, подготовки, политик и обработки результата переиспользовать между sync/async. Не поддерживать две расходящиеся реализации бизнес-правил.
3. Реализовать штатный async-адаптер. PSR-18 адаптер, который умеет только sync, должен явно сообщать об отсутствии async-возможности. Допустимый fallback именуется и включается явно.
4. `pool(concurrency: N)` должен допускать не более N активных HTTP-попыток, запускать независимые запросы параллельно и освобождать слот после завершения/ошибки. Подготовка iterable остаётся ограниченной, без предварительной материализации всего набора.
5. Определить порядок результатов, обработку частичных ошибок, отмену и поведение при исключении одного элемента. Отмена должна останавливать запланированные повторы; если активный транспорт не умеет отмену, это ограничение сообщается явно.
6. Retry, rate limiting и request delay в async-режиме не должны блокировать весь пул. Декораторы, включая RecordingTransport, сохраняют async-семантику.
7. Для cursor pagination страницы одной цепочки могут выполняться последовательно. При этом разные цепочки не блокируют друг друга; возврат async API не должен ждать загрузки всех страниц.

**Приёмка.** R03 вызывает async-метод транспорта. Детерминированный транспорт с отложенным завершением показывает запуск двух запросов до завершения первого при `concurrency=2` и отсутствие третьего активного. Локальный HTTP-тест отдельно подтверждает перекрытие реальных запросов. Проверка только типа Promise недостаточна.

Исходники: [Pipeline](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Pipeline.php), [HttpTransport](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Transport/HttpTransport.php), [PoolExecutor](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Execution/PoolExecutor.php), [RecordingTransport](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Transport/RecordingTransport.php).

## 9. AS-06 — URI и query

**Текущее поведение.** R07: `false` становится `enabled=`, тогда как 0 сохраняется. Пустая строка является допустимым URL-представлением, но без явной политики её нельзя считать универсальным представлением boolean. R08: endpoint `/resources?fixed=1` и `#[Query] page=2` дают `/resources?fixed=1?page=2`.

**Требования.**

1. Собирать URI с учётом существующего query, base path и относительного endpoint. Результат R08 должен содержать `fixed=1&page=2`.
2. Ввести документированную политику boolean для query/form: как минимум `true/false` и `1/0`; настройка клиента и точечный override/cast. Не преобразовывать `false` в пустую строку без явного выбора такой схемы.
3. Сохранять различие между отсутствующим параметром, null, `false`, 0, `"0"`, пустой строкой и пустым списком. Отсутствие собственного представления null или пустого списка в query разрешается документированной политикой, а не случайным приведением типов.
4. Сохранить array formats, порядок значений и повторяющиеся ключи. Не терять вложенные/ассоциативные ключи молча: поддерживать согласованный формат либо отклонять неподдерживаемую форму.
5. Path-параметры кодировать как сегменты пути. Неразрешённый placeholder выявлять до HTTP-вызова. Проверить Unicode, пробел, `/`, `+`, `%` и отсутствие двойного кодирования при выбранном контракте.
6. Явно определить поддержку абсолютного URL для одного запроса и правила совместного использования с base URL. Подписанные URL должны иметь режим передачи без пересборки query; дополнительные query-параметры в таком режиме отклоняются либо требуют явного согласованного преобразования.
7. Одинаково применять правила для GET/POST/PUT/PATCH/DELETE. URI не должен содержать fragment в отправляемом HTTP request target.

**Приёмка.** Табличные тесты сравнивают фактический URI на границе транспорта. Для boolean выбранная политика даёт `enabled=false` или `enabled=0`. Подписанный URL с повторяющимися ключами, `%2F` и `+` передаётся без изменения подписываемых байтов.

Исходники: [RequestUrlBuilder](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Serialization/RequestUrlBuilder.php), [ApiKeyAuthenticator](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Auth/ApiKeyAuthenticator.php).

## 10. AS-07 — JSON и типы данных

**Текущее поведение.** R09: невалидная UTF-8 строка в JSON-поле приводит к отправке пустого тела; ошибка сериализации не возвращается. R10: HTTP 200 с `Content-Type: application/json` и телом `{broken` превращается в успешный результат с `[]`.

R16 подтверждает исправное сохранение `false` и пустого списка в JSON, а также отделение query от body. Это поведение сохранить.

**Требования.**

1. Ошибки `json_encode` должны прекращать выполнение до HTTP-вызова и возвращать типизированную ошибку сериализации. Проверить UTF-8, рекурсивные структуры, INF/NAN и неподдерживаемые значения. Подстановка/исправление данных допустимы только отдельной явной политикой.
2. Для JSON-ответов использовать строгий разбор. Невалидный JSON не должен становиться `null`/`[]` с успешным статусом. Сохранять HTTP-контекст и причину разбора.
3. Определить отдельные контракты JSON, raw/text, download и пустого ответа. 204 и явно объявленный пустой ответ — нормальный результат; JSON `null`, пустая строка, `{}` и `[]` различаются там, где это имеет значение для контракта операции.
4. Для необязательных полей обеспечить явное различие «не передавать» и «передать null». Разрешается использовать существующие политики и типы, если они покрывают задачу. DTO-сериализация для пользователя и фактическое HTTP-тело должны иметь документированные различия.
5. Строгий `unwrap` должен различать отсутствие пути и значение null. При обязательном пути не подставлять весь исходный документ. Если совместимость требует permissive-режима, сделать его явным.
6. Ошибки гидратации должны указывать путь поля, ожидаемый тип и фактическую форму без утечки чувствительных значений; классифицироваться как hydration error.
7. Зафиксировать политику больших целых. Значения вне диапазона PHP int не должны молча терять точность через float. Provider SDK должен иметь возможность сохранять такие идентификаторы строками.

**Приёмка.** В R09 HTTP-вызовов 0, возвращена serialization error. В R10 результат ошибочный с сохранённым HTTP 200. Матрица: malformed JSON, валидный JSON null, объект, список, scalar при соответствующем контракте, 204, text/plain, вложенный nullable DTO и отсутствующий обязательный `unwrap`.

Исходники: [FilePayloadPreparer](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Serialization/FilePayloadPreparer.php), [ProviderResponse](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/VO/Http/ProviderResponse.php), [RequestFlowRunner](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Flow/RequestFlowRunner.php), [ResponseHydrator](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Hydration/ResponseHydrator.php).

## 11. AS-08 — файлы, потоки и внешние URL

**Текущее поведение.** В R14 поток multipart содержит 229 байт в первой попытке и 0 во второй. Подменённый HTTP handler читает поток через `getContents()`, как потребитель потока, и не перематывает его за SDK. Байты повторной попытки зависят от поведения конкретного HTTP-адаптера.

По исходникам binary upload превращает stream в строку; `HttpTransport` полностью читает response body в строку, после чего download создаёт новый stream из этой строки. Потоковая обработка больших файлов таким путём не обеспечивается.

**Требования.**

1. Определить владение потоком, начальную позицию, ответственность за закрытие и возможность повторного использования. Immutable request не делает переданный stream неизменяемым.
2. Для разрешённого повтора seekable-тело восстанавливается к начальной позиции либо заново создаётся фабрикой. Повтор должен передавать те же байты. Нельзя рассчитывать, что HTTP-клиент автоматически сделает rewind.
3. Для non-seekable тела повтор запрещён с явной причиной либо обеспечивается отдельной воспроизводимой фабрикой/контролируемым временным буфером. Молчаливая отправка пустого/частичного тела запрещена.
4. Потоковые multipart, binary upload и download не должны требовать загрузки всего файла в строку. Base64 JSON закономерно требует другого профиля ресурсов; его ограничения описываются отдельно.
5. Предоставить download-to-stream/file или sink с явным контролем жизненного цикла. Чтение JSON может иметь ограничение размера; кеш, debug и recorder не должны незаметно материализовать большой файл.
6. Поддержать нейтральный сценарий: `POST /upload-sessions` возвращает URL, затем файл отправляется на `https://storage.example.test/...` с собственными полями/заголовками. Это композиция provider SDK, не зашитый workflow ядра.
7. Вызов по внешнему URL должен явно выбирать auth policy. Credentials исходного origin не переносятся автоматически на другой origin или через redirect. Одного `forceAuth()` недостаточно для отмены проверки допустимого origin: междоменная передача credentials разрешается отдельной настройкой.
8. При переходе с PSR-18 на другой адаптер сохранить явную redirect policy; не включить автоматические redirects побочным эффектом доработки async/таймаутов. Подписанные URL обрабатываются по AS-06.
9. Multipart boolean/null/списки сериализуются по объявленной политике, с корректным boundary, filename и MIME type. Пустой файл размером 0 остаётся валидным файлом.

**Приёмка.** R14 после явного разрешения безопасного повтора имеет одинаковое непустое тело в обеих попытках. Non-seekable тест не отправляет вторую неполную копию. Для большого локального файла, например 128 MiB, потоковый сценарий завершается в отдельном PHP-процессе с `memory_limit=64M`; источник/приёмник не держат весь файл в памяти. Внешний URL получает только разрешённые credentials; исходный клиент сохраняет свои настройки для следующего вызова.

Исходники: [FilePayloadPreparer](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Serialization/FilePayloadPreparer.php), [FileInput](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/VO/Files/FileInput.php), [HttpTransport](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Transport/HttpTransport.php), [ResponseHydrator](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Hydration/ResponseHydrator.php).

## 12. AS-09 — runtime-опции и авторизация

**Текущее поведение.** R11: цепочка `withAuthScope('secondary')->withoutAuth()->withAuth()` сохраняет scope `secondary` и отправляет credentials B вместо default credentials A. Методы передают null для сброса scope, но внутреннее копирование через `??` оставляет старое значение. Аналогичная невозможность очистить nullable поле присутствует в `PreparedRequest::with()`.

**Требования.**

1. В immutable-копировании различать отсутствие изменения и явный сброс. Применить единое решение: проверка наличия ключа, sentinel либо явные методы очистки.
2. Сброс auth scope должен возвращать выбор к default, а не сохранять предыдущий scope. Зафиксировать порядок `withAuth`, `withoutAuth`, `forceAuth`, атрибута `NoAuth`, auth policy и origin policy.
3. Проверить все опции с nullable состоянием: auth scope, timeout overrides, rate-limit override, idempotency key, pagination, body/stream. Для необходимых операций очистки предоставить публичный способ; не менять существующую семантику null без migration note.
4. Последующие цепочки не должны изменять исходный request/config или другие execution-объекты. Параллельные вызовы с разными credentials/traceId/headers не обмениваются состоянием.
5. Auth refresh и lock при совместном хранилище должны иметь контекст учётной записи. Метаданные классов можно кешировать глобально; credentials, request context и runtime overrides — только в подходящем scope.

**Приёмка.** В R11 scope сброшен, используется A. Проверены последовательности A → B → A, force/no-auth, очистка тела/потока и независимые execution-копии. Повторные задания в одном worker не наследуют credentials и traceId предыдущего задания.

Исходники: [RequestOptions](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Request/RequestOptions.php), [PreparedRequest](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/VO/Http/PreparedRequest.php), [AuthHandler](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Auth/AuthHandler.php).

## 13. AS-10 — диагностика и запись фикстур

**Текущее поведение.** R12: `requestDebug()` маскирует `query.access_token`, но оставляет тот же секрет в поле `url`. R13: `RecordingTransport` без пользовательского Fixture сохраняет `Authorization` в открытом виде. По исходникам стандартный debug log также может содержать URI целиком.

**Требования.**

1. Применить общую расширяемую политику redaction ко всем экспортируемым диагностическим представлениям: logger context, requestDebug/JSON, audit/debug export, записанным request/response fixtures.
2. По умолчанию маскировать стандартные credential headers, cookies, token/password/secret-поля, URL userinfo и соответствующие query-параметры. Обрабатывать заголовки без учёта регистра, вложенные JSON-поля, повторяющиеся и percent-encoded query-параметры.
3. Позволить provider SDK добавить собственные имена заголовков/полей и пути. Пользовательский Fixture расширяет базовую политику, а не является условием её включения.
4. Маскирование выполняется на копии. Фактический HTTP-запрос, подпись URL, кеш-идентичность и тело не изменяются.
5. Raw доступ для осознанной отладки может сохраняться как явный opt-in; безопасный экспорт остаётся режимом по умолчанию. Не требовать недостижимого поиска любых произвольных секретов: гарантии формулируются для известных и настроенных полей.
6. Ограничивать размер диагностических тел; не потреблять/перематывать пользовательский поток ради лога. Recorder должен сообщать об ошибке записи согласно явной политике и не повреждать основной ответ.
7. Единообразно показывать traceId, номер попытки, статус, длительность и факт cache hit. Согласовать единицы duration: в текущем VO комментарий о секундах расходится с вычислением миллисекунд в транспорте.

**Приёмка.** Фиктивный секрет отсутствует в сериализованных safe debug, logger records и fixture-файлах; присутствует в фактически отправленном запросе. R12 маскирует URL, R13 — Authorization без дополнительной конфигурации. Отдельно проверены response Set-Cookie, нестандартный credential header и большой поток.

Исходники: [ExecutionResult](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Result/ExecutionResult.php), [RecordingTransport](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Transport/RecordingTransport.php), [RequestPreparationStep](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Flow/RequestPreparationStep.php), [FixtureRedactor](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Testing/FixtureRedactor.php).

## 14. AS-11 — rate limiting

**Основание.** По исходникам shared limiter обновляет состояние последовательностью PSR-16 `get` → изменение → `set`; атомарность между процессами не обеспечена. Ожидание использует `sleep()`. Статический ключ задаётся конфигурацией, по умолчанию основан на base URL. Соревнование реальных процессов в исходной проверке не воспроизводилось.

**Требования.**

1. Явно разделить внутрипроцессный limiter и limiter с распределёнными гарантиями. PSR-16 store без атомарной операции не должен объявляться достаточным для строгого общего лимита.
2. Предоставить контракт атомарного приобретения разрешения и как минимум один Laravel-совместимый адаптер с общей блокировкой/атомарной операцией. Зависимость конкретного backend не переносить в ядро.
3. Поддержать вычисляемый ключ из identity, группы операций и ресурса. Пример: общий лимит учётной записи и дополнительный лимит записей для `project_id=42`.
4. При нескольких ограничениях определить порядок приобретения, учёт уже полученных разрешений и поведение отказа. Не допускать обхода общего лимита созданием новых клиентов.
5. Ожидание использует общие часы/deadline и async-совместимый механизм. Предоставить режим немедленного отказа с доступным временем следующей попытки, чтобы очередь приложения могла перепланировать задание.

**Приёмка.** При лимите 2 одновременное приобретение из нескольких процессов через общий backend разрешает не более двух операций в выбранном окне. Ключи A и B независимы; несколько клиентов A разделяют общий лимит. Проверены ожидание, отказ, граница окна и исчерпание deadline.

Исходники: [RateLimiter](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/RateLimiting/RateLimiter.php), [RateLimitApplier](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Pipeline/Transport/RateLimitApplier.php).

## 15. AS-12 — Laravel-интеграция

**Основание.** `SdkServiceProvider` существует. В базовом `composer.json` отсутствует `extra.laravel.providers`; Illuminate-компоненты находятся в require-dev. Провайдер при разрешении любого `AbstractRequest` из контейнера заполняет его из текущего `Illuminate\Http\Request`. Это документированная возможность, а не скрытый доказанный дефект; требуется сделать её применение явным.

**Требования.**

1. Обеспечить один документированный способ подключения в Laravel 12: package discovery либо явная регистрация provider. Проверить выбранный путь в чистом приложении после установки пакета с `--no-dev`.
2. Сохранить работу ядра без Illuminate. Если отдельные возможности, например Laravel validation, требуют Illuminate, отсутствие зависимости обнаруживается только при их использовании и объясняется понятной ошибкой.
3. Отделить базовую регистрацию клиента/транспорта от заполнения SDK request из входящего HTTP-запроса. Последнее сделать отдельным opt-in, провайдером или явной фабрикой. Явно переданные значения исходящего запроса не перезаписываются входящими параметрами по умолчанию.
4. Пользовательская transport/logger/cache/auth binding должна иметь предсказуемый приоритет. Provider не должен незаметно заменять уже зарегистрированный адаптер.
5. Проверить HTTP request, Artisan command и queue worker без входящего HTTP-контекста. Пример регистрации нескольких клиентов должен однозначно выбирать экземпляр и credentials без глобального «последнего клиента».
6. Конфигурация должна работать с `config:cache`: без сохранения closures/живых соединений в публикуемом config. Runtime-объекты собираются в контейнере.
7. Проверить последовательную работу нескольких tenant context в долгоживущем worker. Если заявляется Octane, добавить соответствующий lifecycle-тест либо явно ограничить поддержку до его появления.
8. Для тестов документировать подмену ApiSutra transport. Не обещать действие `Http::fake()` на прямой Guzzle/PSR transport, если отдельная интеграция не реализована.

**Приёмка.** Минимальное Laravel-приложение запускает типизированный GET из HTTP-контроллера, Artisan и job; сохраняет явные входные данные request и пользовательские bindings; проходит `config:cache`. Отдельная установка ядра без Laravel выполняет тот же GET с явно переданным транспортом.

Исходники: [SdkServiceProvider](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Laravel/SdkServiceProvider.php), [composer.json](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/composer.json), [Laravel guide](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/docs/guides/laravel.md).

## 16. AS-13 — существующие расширения и регрессионные контракты

Ниже перечислены возможности, для которых не требуется заранее разрабатывать новую подсистему. Нужно подтвердить их сквозными тестами и дополнить документацию; изменение кода требуется только при обнаруженном несоответствии.

| Контракт | Нейтральный пример и критерий |
|---|---|
| Разделение частей запроса | `POST /resources?workspace_id=10` отправляет title/enabled/labels в JSON, credentials — в настроенном заголовке. R16 сохраняется |
| HTTP-методы | GET/POST/PUT/PATCH/DELETE корректно совмещают path/query/body согласно описанию конкретного запроса |
| Readonly DTO и mapping | `account_id` преобразуется в `accountId`; вложенные объекты/списки и enum сохраняют типы |
| Полиморфные данные | `{type: "document", ...}` и `{type: "image", ...}` выбирают нужные DTO по discriminator |
| Неизвестный вариант | Режимы error/keep-raw/skip работают явно; keep-raw сохраняет неизвестный discriminator и исходные поля |
| Необязательные данные | Отсутствующее поле, null, false, 0 и пустой список соответствуют объявленной политике; отсутствие поля не превращается в ложное значение |
| Cursor pagination | Ответ `{items: [...], next: "cursor-b"}`; последующий запрос использует `cursor=cursor-b` через штатный custom meta resolver |
| Завершение пагинации | Null/отсутствие следующего cursor завершают обход; повторяющийся cursor и maxPages не вызывают бесконечного цикла; cursor `"0"` не теряется |
| Изменяемый page size | Размер страницы конфигурируется провайдером, без привязки ядра к конкретным именам полей |
| Подмена зависимостей | Транспорт, cache, logger, clock/sleeper и error mapper заменяются для теста без реального API |

Не добавлять отдельный механизм cursor pagination только ради нового имени параметра: в пакете уже есть `PaginationMetaResolverInterface`. Аналогично переиспользовать Nested/discriminator и существующие DTO-политики.

Примеры: [PaginationMetaResolverInterface](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/src/Contracts/Interfaces/Pagination/PaginationMetaResolverInterface.php), [Nested discriminator tests](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/tests/Unit/Serialization/NestedDiscriminatorModeTest.php), [DTO guide](https://github.com/brahmic/apisutra/blob/96e8c4071f2cc517cb39dfca36101671259ab317/docs/guides/dto.md).

## 17. AS-14 — проверка качества и поставка

**Требования.**

1. Для каждого исправления добавить регрессионный тест наблюдаемого поведения. Не ограничиваться вызовом приватного метода или проверкой полей конфигурации.
2. Сохранить полный набор unit/integration-тестов; тесты, закрепляющие ошибочное поведение, изменить с пояснением целевого контракта. Простое сохранение числа зелёных тестов не является приёмкой.
3. Настроить CI как минимум на PHP 8.4 и 8.5; Laravel 12 проверить через полноценный integration harness. Проверить установку ядра без require-dev и Laravel-приложения с пакетом без dev-зависимостей самого пакета.
4. Устранить deprecation из кода ApiSutra. Предупреждения зависимостей разбирать отдельно: обновлением совместимых версий или документированным ограничением; не скрывать весь класс предупреждений.
5. Ввести воспроизводимые проверки стиля, статического анализа и Composer metadata. Новые публичные API должны иметь понятные типы результата для IDE/анализатора, в том числе для DTO, коллекций, resolved result и Promise. Выбранные инструменты и уровень анализа фиксируются в репозитории.
6. Проверить минимально заявленные версии зависимостей и актуальный совместимый набор. Если код требует более новой версии, исправить constraint и документировать изменение.
7. Обновить guides по transport, timeout, retry, cache, async, files, auth, Laravel и troubleshooting. Удалить обещания, не выполняемые стандартной конфигурацией. Исполняемые примеры проверять в CI.
8. Для каждого изменённого публичного поведения приложить migration note: прежнее поведение → новое → способ явного включения допустимого legacy-режима. Не сохранять небезопасное поведение как неявный default ради совместимости.
9. Зафиксировать границы публичного API и внутренних классов. Закрепить поддерживаемые extension points; потребитель не должен наследоваться от внутреннего pipeline ради настройки таймаута, кеша или авторизации.
10. Подготовить changelog и новую версию после прохождения приёмки. Этот документ не задаёт автоматическую публикацию релиза.

## 18. Порядок реализации и общая приёмка

Рекомендуемая последовательность:

1. Зафиксировать целевые контракты transport options, ошибок, времени, retry, identity scope, stream replay и очистки nullable overrides. Описать выбранные публичные изменения короткими design notes.
2. Исправить AS-01/02/04/06/07/09/10 с регрессионными тестами. AS-03 и AS-08 реализовать согласованно: нельзя включать повторы потоков до решения replay.
3. Реализовать AS-05 на общих контрактах; проверить AS-03/08/10 повторно в async-сценариях.
4. Выполнить AS-11/12, затем общую матрицу AS-13 и поставку AS-14.

Результат передаётся с перечнем закрытых AS-ID, ссылками на изменения и тесты, описанием изменённого публичного API и фактической матрицей окружений. Для пункта, уже удовлетворённого существующим механизмом, достаточно исполняемого доказательства и документации; фиктивная доработка не нужна.

Общие критерии завершения:

- Все P1 и P2 выполнены либо явно вынесены в согласованный следующий этап с указанным ограничением публичного контракта.
- Не происходит смешения credentials/кеша между учётными записями, потери тела запроса или молчаливого принятия malformed JSON.
- Таймауты, retry budget и concurrency проверены по фактическому исполнению.
- Публичные sync/async API имеют согласованные результаты и типы ошибок.
- Проверки не требуют production credentials и не вызывают внешние API; сетевые сценарии используют управляемые локальные сервисы.
- Примеры, migration notes и команды проверок позволяют воспроизвести результат из чистого checkout.
