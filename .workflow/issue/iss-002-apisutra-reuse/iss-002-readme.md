## Задача и вывод

Найти возможности ApiSutra, которые уменьшают собственный код MaxSutra,
сохраняя выразительный публичный API и проверенные правила протокола.
Основание — обсуждение пользователя о DTO и декларациях запросов после этапа 5.

ApiSutra уже умеет существенно больше, чем использует наш адаптер: Returns/unwrap,
гидратация обычных readonly-классов, вложенные варианты, структурированные ошибки,
форматы query/body и совместные квоты. Собственное преобразование ответов нельзя
обосновать только требованием чистых моделей: самостоятельный DTO не обязан
наследоваться от ApiSutra. При этом механическая замена декодеров на Returns
изменила бы текущий контракт. Рекомендуется использовать штатные возможности,
закрыв конкретные разрывы, а не строить второй общий mapper или зеркальные DTO.

Результаты разделены на [агностичные требования разработчику](upstream-requirements.md)
и план изменений MaxSutra (`../../current/pln-007-apisutra-reuse.md` в исходном SDK).
Аудит не запускает реализацию этого плана и не меняет принятые архитектурные границы.

## Находки

### A01 — P1: общее построение моделей реализовано повторно

**Статус:** подтверждённое наблюдение и рекомендация; текущие декодеры работают.

GetMeRequest (`../../../src/Core/Internal/ApiSutra/Bots/GetMeRequest.php` в исходном SDK) не содержит
Returns; адаптер отправки (`../../../src/Core/Internal/ApiSutra/Messages/ApiSutraMessagesApi.php` в исходном SDK)
извлекает message через Payload. Три декодера и Payload занимают 278 строк
в исходном состоянии; эта цифра показывает объём сопровождения, а не обещание
удалить их все. Отдельные правила MAX и фабрики raw-вариантов всё равно нужны.

[ResponseHydrator](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Pipeline/Hydration/ResponseHydrator.php)
и [Hydrator](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Serialization/Hydrator.php)
уже выполняют unwrap, построение через конструктор, проверку обязательных полей
и вложенных типов. `send()->raw()` возвращает ExecutionResult и не отключает DTO.

**Проверка:** P01–P02, P05, P09–P16. **Действие:** переход по модели целиком после
A02–A05, через один mapping для standalone и HTTP. Внешние публичные классы
и лаконичный API остаются; generic reflection/hydration в MaxSutra не добавляется.

### A02 — P1: scalar-приведения и политика присутствия расходятся с контрактом SDK

**Статус:** воспроизведённая несовместимость default-поведения, не дефект ApiSutra.

P03: `"123" → 123`, `"false" → false`, `0 → "0"`.
Наш Payload (`../../../src/Core/Internal/Protocol/Payload.php` в исходном SDK) требует native-типы.
Строгость здесь — действующий контракт SDK и средство обнаружения изменения
протокола; это не утверждение, что всякий сторонний API обязан отвергать строки.

P05 подтверждает, что обязательность и null ApiSutra уже различает. Но P06/P08
показывают другой случай: `?int $count = null` принимает и отсутствие, и явный null;
property Cast для null не вызывается. У нас last_activity_time и avatar_url
разрешают отсутствие, но запрещают явный null. Это нельзя выразить только
текущим PHP-типом и default. P07 доказывает существующий обход scalar-кастования
через явный Cast; отсутствие этой возможности не заявляется.

**Основание:** [SafeScalarHydrationCaster](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Serialization/SafeScalarHydrationCaster.php),
[BuiltinHydrationCaster](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Serialization/BuiltinHydrationCaster.php),
уточнения MAX (`../../../resources/core/schema/README.md` в исходном SDK).
**Действие:** AS-1 и AS-4; не ослаблять текущие проверки молча.

### A03 — P1: дополнительные поля и raw-варианты требуют явного решения

**Статус:** воспроизведённое поведение.

P04: неизвестное поле не попадает в extra само. Встроенная гидратация заполняет
объявленные свойства; extra остаётся default. computed/BeforeHydrate позволяют
подготовить массив вручную, но копирование правил consumed-полей по всем DTO
снова создаёт собственный общий mapper.

P10: Nested умеет сохранить неизвестный вариант целиком, однако возвращает массив,
а не наш RawAttachment/RawButton. P11: повреждённый **известный** вариант корректно
завершает гидратацию ошибкой. Это полезное существующее поведение нужно сохранить.

**Действие:** AS-2 для сбора дополнительных полей. Для raw-моделей — минимальная
явная фабрика на границе; не просить ApiSutra знать типы вложений MAX и не выдавать
массив вместо обещанной модели. Для двухмерных рядов клавиатуры проверить итоговый
mapping или локальный cast, не создавать DTO-копию каждого ряда только ради обёртки.

### A04 — P1: чистым моделям нужна внешняя декларация преобразования

**Статус:** ограничение просмотренного штатного пути; предлагается точка расширения.

Обычный класс без наследования гидратируется, когда имена/типы подходят. Но наши
snake_case-поля, вложенные модели, дополнительные данные и строгие правила требуют
metadata. Штатные From/Nested/Cast и привязки профилей находятся на DTO.
[DtoHydrationProfileResolver](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Serialization/DtoHydrationProfileResolver.php)
находит профиль по атрибуту класса;
[AbstractClient](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Core/AbstractClient.php)
собирает Hydrator внутри. В просмотренных публичных контрактах не найден внешний
реестр правил для графа чистых DTO, единый для request и standalone hydration.

Это не утверждение о невозможности написать произвольный extension/hook. Такой
код может вызвать наши декодеры и вернуть DTO, но сам по себе не уменьшает
собственное преобразование. Подмена внутренних массивов metadata cache также
не является подходящим контрактом интеграции.

**Действие:** AS-3. Предпочтение — правила внутри Internal/ApiSutra, обычные публичные
Input/Model. Если разработчик предложит существующий поддерживаемый способ,
проверить его вместо требования нового API. Две полные иерархии DTO не вводить.

### A05 — P1: списки и диагностические пути нельзя потерять при замене

**Статус:** воспроизведённые различия.

P13: ассоциативный набор Nested принимает и переиндексирует; наши декодеры проверяют
list-форму. P12: path после From содержит `data.batchId`, а исходный ключ — batch_id.
P20: текущий ApiSutraExecutor превращает любой неуспех при 2xx в ProtocolException
с `$`, теряя уже доступную подробную диагностику гидратации.

**Действие:** AS-4 для формы контейнера; AS-3 включает доступ к source path.
В MaxSutra адаптировать перевод structured error, не прикрепляя наружу raw response,
PipelineContext или исходное исключение с чувствительными данными. После POST
гидратационная ошибка остаётся OutcomeUnknown, не превращается в локальную
ValidationException и не запускает повтор. P11/P16 подтверждают сохранение HTTP
в ExecutionResult, необходимое для такой классификации.

### A06 — P2: есть немедленное упрощение формата query

**Статус:** подтверждённая возможность без обновления зависимости.

SendMessageRequest вручную хранит строку disableLinkPreview. ApiSutra поддерживает
`ClientConfig::textBooleanFormat = BooleanFormat::Literal`; локально подтверждены
false и правила пропуска nullable query (P17). JSON boolean при этом не меняется.
Альтернатива — property BooleanCast с явным форматом, если конкретному запросу
нужен override. При текущем едином формате предпочтительна конфигурация адаптера.

P18 подтверждает Body и wire policy для null/false/`"0"`. Но перевод четырёх
существующих ключей body в отдельные свойства не обязательно уменьшает код.
Сохранять текущий BodyRoot допустимо. KeyboardEncoder кодирует также envelope
и допустимые поля варианта; его удаление требует полного эквивалентного mapping,
а не автоматической сериализации всех публичных свойств Input.

**Основание:** [настройки serialization](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/docs/guides/client-config/serialization.md),
[RequestPartsCollector](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Serialization/RequestPartsCollector.php).
**Действие:** часть A плана; body и encoder переписывать только при уменьшении
суммарной сложности и сохранении точного JSON.

### A07 — P2: старое ограничение одной квоты уже устранено

**Статус:** подтверждено по коду и локальному сценарию, не полная приёмка лимитов.

[RateLimitApplier](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/Pipeline/Transport/RateLimitApplier.php)
собирает client/operation quotas и вызывает acquireAll; есть подключаемый
[RateLimitBackendInterface](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/src/RateLimiting/RateLimitBackendInterface.php).
P21 подтверждает совместное применение локально и отсутствие частичного расхода
общей квоты при отказе собственной. Ранее переданное задание повторять не нужно.

Сценарии разных workers, Redis, ключей ботов/адресатов, ожиданий/deadline и каждой
повторной попытки этим запуском не проверены. Limiter не включается в текущий
send автоматически. Архитектурная заметка об одной квоте уточнена со ссылкой
на этот аудит, историческое задание сохранено.

### A08 — P2: tooling полезен выборочно

**Статус:** P19 и просмотр API/документации.

Native fake проходит гидратацию, но обходит настоящий HttpTransport и PSR-18
границу. Он не заменяет наши wire-проверки auth/query/body. Публичный Max fake
не должен заставлять пользователя импортировать внутренние request-классы ApiSutra.

[OperationInventory](https://github.com/brahmic/apisutra/blob/6857dc054648bd079f4e9ebf7d1511116f3ff17e/docs/guides/operation-inventory.md)
может дать декларативные method/path/responseType. Автовосстановление sdkCallPaths
рассчитано на методы, возвращающие request; наши terminal methods возвращают
модели. Реестр из двух строк пока проще сопровождать вручную. Генерация юзкейсов,
каталогов и дублирующих описаний не входит в план.

## Рекомендуемое направление архитектуры

Публичная поверхность ADR-002 сохраняется: Messages, MessageTarget, PendingMessage,
build, Input/Model и исключения MaxSutra. ApiSutra обслуживает исполнение и общий
алгоритм преобразования; MaxSutra задаёт контракты MAX и свои пользовательские имена.

Предпочтительный путь после AS-1–AS-4:

1. Внутренний request декларирует Returns и unwrap, а metadata связывает чистую модель
   с wire-данными. Публичная модель не получает HTTP-атрибутов или DTO-базового класса.
2. Один набор правил и один способ вызова гидратора работают для HTTP-ответа и
   самостоятельного payload. Будущий webhook не должен создавать второй decoder.
3. Специфичные значения/фабрики raw-вариантов и инварианты исходящих Input остаются
   нашими. Generic обход свойств, scalar-касты, constructor binding и общая обработка
   missing/null не дублируются в MaxSutra.
4. Текущий запрет зависимости Internal/Protocol от ApiSutra не обходится скрыто.
   Перед переносом общего преобразования нужен ADR: mapping в Internal/ApiSutra,
   чистые специфичные правила в Protocol, совместная точка сборки в Bootstrap.
   Новый публичный интерфейс mapper и инфраструктура webhook заранее не нужны.

## Выводы и границы решения

Самый большой потенциальный выигрыш — гидратация результатов и её декларации.
Самый маленький доказанный немедленный шаг — штатный формат boolean query.
Наличие расширений не означает, что любое оборачивание старого кода становится
упрощением. До приёмки DTO-контракта рабочие декодеры остаются на месте.

Создан план pln-007 (`../../current/pln-007-apisutra-reuse.md` в исходном SDK), со статусом новый,
с независимой первой частью и явными условиями второй. Пользовательский docs,
production-код, зависимости и HTTP-покрытие этим аудитом не изменены.
