# ApiSutra: требования к декларативному преобразованию DTO

Документ для передачи разработчику. Требования агностичны к провайдеру API,
фреймворку и предметным сущностям. Имена будущих классов, атрибутов и методов
намеренно не предписаны: важен контракт поведения и поддерживаемый способ его задать.

Исследована **v0.2.0-alpha.1**, commit
`6857dc054648bd079f4e9ebf7d1511116f3ff17e`. Отдельные пожелания ниже могут решаться
существующими расширениями; если есть штатный способ без повторения общего mapper,
достаточно указать его и подтвердить критерии. Текущие defaults не называются
ошибками и не должны меняться глобально ради одного SDK.

## Контекст

Клиент внешнего API использует собственные обычные `final readonly` DTO.
Их имена и PHP-типы образуют публичный контракт. Нужны одни правила преобразования
для DTO, полученного через Returns, и для payload, пришедшего другим способом.
Пользователь SDK не должен настраивать гидратор для первого вызова.

ApiSutra уже поддерживает Returns/unwrap, constructor-first hydration,
From/Nested/discriminator, обязательные nullable-аргументы, casts и структурированные
ошибки. Эти возможности не требуется создавать повторно.

## AS-1. Необязательная строгая политика scalar-типов

**Зачем:** некоторые контракты API требуют сохранять типы JSON и обнаруживать
дрейф схемы, а не нормализовать его незаметно. У других API преобразования полезны;
текущее поведение должно оставаться доступным.

**Сейчас:** стандартный hydrator преобразует `"123"` в int, `"false"` в bool,
число в string. Property Cast уже может запретить конкретное преобразование,
но массовая установка одинаковых casts на каждом поле увеличивает сопровождение.

**Требуется:** опциональная общая политика без неявных scalar-приведений,
применимая к графу DTO, с явным override там, где преобразование действительно нужно.
Явный cast остаётся осознанным преобразованием; после него результат проверяется
по типу. Включение политики для одного набора правил не влияет на другой клиент
или независимый standalone-вызов.

| Целевой тип в строгом режиме | Вход | Ожидание |
| --- | --- | --- |
| int | `123`, `0`, минимальный/максимальный поддерживаемый int | Принять без изменения |
| int | `"123"`, `123.0`, true | Ошибка типа, не приведение |
| bool | false / true | Принять |
| bool | `"false"`, `"true"`, `0`, `1` | Ошибка типа |
| string | `"0"`, `""` | Сохранить строку; отдельные ограничения длины независимы |
| string | `0`, `1.5`, false | Ошибка типа |

Переполнение int уже диагностируется; эту гарантию сохранить. Не требуется
обязательный strict-флаг для каждого DTO, Laravel validator или новая глобальная
настройка PHP. Проверки применяются и к вложенным объектам/элементам списков.

## AS-2. Сбор дополнительных полей ответа

**Зачем:** частично моделируемые API должны сохранять полученные данные,
которым пока не соответствует типизированное свойство. Это касается не только
полей, неизвестных внешней схеме, но и известных схеме, ещё не описанных DTO.

**Сейчас:** свойство DTO `extra = []` остаётся пустым; неизвестные ключи источника
автоматически туда не переносятся. computed/BeforeHydrate позволяют написать
сбор вручную, однако он повторяется для каждого типа и его mappings.

**Требуется:** декларативно назначить свойство-приёмник оставшихся данных
для конкретного DTO. Название свойства произвольное. Сбор выполняется штатным
преобразованием с учётом реально использованных source mappings.

Критерии:

1. Источник `{"record_id":7,"active":false,"future":null}` при mapping
   record_id → id и active → active даёт id=7, active=false, extras с future=null.
   Типизированные поля не копируются в extras.
2. false, ноль, пустая строка, пустой список и вложенные данные не теряются.
   У каждого вложенного DTO — собственный приёмник дополнительных полей.
3. Учитываются переименование, dot-path и fallback. Если использовано
   `profile.id`, соседний `profile.future` остаётся доступен; нельзя выбрасывать
   весь profile только из-за потреблённого листового пути. Приоритет нескольких
   source aliases должен быть определён, включая судьбу неиспользованного alias.
4. Источник с ключом, совпадающим с именем свойства-приёмника, не может молча
   перезаписать весь мешок. Правило коллизии явно определено; исходное значение
   можно сохранить как обычный дополнительный ключ.
5. Отсутствие приёмника сохраняет текущее поведение. Сбор данных при чтении
   не означает автоматическое добавление этих ключей в исходящие payload.

Не требуется знать названия сущностей провайдера, генерировать DTO из схемы
или проверять структуру неизвестного поля как будто она уже описана моделью.

## AS-3. Внешние правила для графа чистых DTO

**Зачем:** DTO может принадлежать потребителю, оставаться независимым от библиотеки
и использоваться вне HTTP. Запрос, metadata и адаптер принадлежат SDK и могут
зависеть от ApiSutra. Нежелательно вводить зеркальный класс каждой публичной модели
только для нанесения атрибутов и последующего копирования значений.

**Сейчас:** plain readonly-класс гидратируется при подходящих именах/типах.
Переименования и вложенные правила обычно задаются атрибутами DTO; hydration profile
также привязан атрибутом. В исследованном штатном пути не найден внешний реестр
правил с одинаковым применением внутри Returns и при standalone hydrate.

**Требуется:** поддерживаемый способ привязать правила к целевому PHP-классу
снаружи, не требуя от него наследования, интерфейса, атрибутов ApiSutra или
зависимости от Laravel. Это может быть декларативное описание или иной компактный
контракт; конкретный дизайн остаётся за библиотекой.

Критерии:

1. Одна декларация управляет переименованием source-поля, отдельным вложенным
   объектом, списком объектов и выбором известного типа по discriminator.
   Вложенные целевые классы также могут быть обычными readonly DTO.
2. Те же правила доступны при Returns и при явном преобразовании массива/объекта
   без HTTP, PipelineContext и глобального контейнера. Результаты, ошибки,
   политики AS-1/AS-2/AS-4 совпадают. Внутренняя реализация может использовать
   контекст, но вызвавший standalone-преобразование не обязан его конструировать.
3. Конструктор вызывается один раз, обязательность и native-типы проверяются.
   Преобразование не выполняет HTTP или иные скрытые операции ввода-вывода.
4. Правила изолированы между клиентами/наборами правил. Установка одного профиля
   не меняет поведение уже созданного другого клиента или глобального default.
5. Существующие атрибуты продолжают работать. При их сочетании с внешними правилами
   есть документированный приоритет либо явная ошибка конфигурации.
6. Ошибка сохраняет структурированный reason и путь. Должен быть доступен путь
   в исходных данных с учётом mapping, вложенности, индексов и unwrap; DTO path
   можно сохранять дополнительно. Например, ошибка batch_id не теряет связь
   с исходным ключом после преобразования имени в batchId.

Публичный API не должен требовать записи во внутренний reflection cache,
собственного рекурсивного обхода DTO или регистрации отдельного hook на каждую
операцию ради одинаковых правил. Standalone-вход нужен для тех же объектов,
получаемых через другой envelope или входящий транспорт.

## AS-4. Явное присутствие поля и форма контейнера

**Зачем:** nullability PHP-свойства описывает итоговое значение, но не всегда
полностью описывает допустимые входные данные. Дополнительные правила нужны
точечно, где контракт источника строже PHP-представления.

### Отсутствие и null

Обязательные nullable-поля уже поддерживаются; изменить нужно не их default,
а дать выразить оставшийся сценарий:

| Вход для optional count, запрещающего явный null | Ожидание |
| --- | --- |
| `{}` | Применить объявленный default, например null |
| `{"count":7}` | Принять 7 |
| `{"count":null}` | Ошибка присутствующего недопустимого null |
| `{"count":"7"}` | Определяется AS-1/явным cast; missing/default не вмешиваются |

Поле можно представить как `?int $count = null`, но правило входа отдельно запрещает
явный null. Сейчас такой null принимается и пропускает property Cast.
Нужен способ проверить состояние источника до применения default/кастов.
Не требуется обязать все nullable-поля использовать новую декларацию.

### Списки

Для поля, объявленного списком, допустимы последовательные элементы и пустой список
по его контракту. Ассоциативный или разреженный массив должен завершаться ошибкой,
если не объявлена политика нормализации. По умолчанию совместимость существующих
коллекций сохранить: строгая форма включается явно для нужных полей/правил.

Вложенные списки используют ту же проверку на каждом объявленном уровне.
Нельзя превращать отсутствующее обязательное поле в пустую коллекцию, если это
не предусмотрено его декларацией. Object, list, missing и null — разные состояния.
Для декодированного PHP-массива не требуется восстанавливать сведения, которые
ранее потерял JSON decoder; важна проверка доступной формы без угадывания.

## Общая приёмка и объём

- Текущие defaults существующих пользователей не меняются без отдельного решения.
- Новые правила работают без Laravel и без сети; одна установка правил при сборке
  SDK достаточна, конечному пользователю дополнительных настроек не требуется.
- Ошибки конфигурации отделены от неверных данных. Гидратационная ошибка в запросе
  сохраняет HTTP-ответ и машинно-читаемые детали. Диагностика правил не включает
  значения полей, токены или исходные payload; нынешнюю обработку ошибок сохранить.
- Известный повреждённый discriminator-вариант остаётся ошибкой; неизвестный
  вариант может сохраняться raw. Уже существующие механизмы не заменяются новым
  общим pipeline.
- Нужны версия/commit и способ запуска критериев. При наличии существующего
  решения предпочтительнее пример его применения, чем дополнительный API.

Этот запрос не касается лимитирования, транспорта, очередей, генерации документации
или публичного fluent API клиентских пакетов. Сохранение raw-варианта в конкретный
пользовательский тип может остаться небольшой фабрикой SDK.

[P01–P21](artifacts/observations.json). Пользователь намерен передать документ
разработчику; факт передачи или согласования требований пока не подтверждён.
