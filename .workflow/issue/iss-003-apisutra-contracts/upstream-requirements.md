# ApiSutra: оставшиеся требования к построению DTO и копированию конфигурации

Подготовлено 2026-09-15 для передачи разработчику. Проверенная версия:
**v0.3.0-alpha.1**, reference **`6a649f5e247adba3ecc0c82f1ba68cb74c018aba`**,
PHP 8.5.4. Формулировки агностичны к провайдеру API и фреймворку.

Внешние HydrationRules, строгие scalar-типы, extras, list-shape и source paths
уже работают в проверенных сценариях. Прежние AS-1–AS-4 не предлагается реализовать
повторно. Ниже продолжается нумерация: AS-5 и AS-6.

Примеры воспроизводятся в [upstream-probe.php](artifacts/upstream-probe.php),
результаты — [upstream-observations.json](artifacts/upstream-observations.json).
Скрипт не использует классы SDK-потребителя и не загружает Laravel-приложение.
[Запуск и состав комплекта](artifacts/README.md). Проверки выполняются без сети.

## AS-5. Построение DTO со свойствами, инициализированными конструктором

**Приоритет: P1. Тип: воспроизведённое ограничение интеграции.**

### Сценарий и текущее поведение

Обычный DTO самостоятельно устанавливает неизменяемый признак своего варианта:

```php
final readonly class ConstructorOwned
{
    public string $kind;

    public function __construct(public int $id, public array $extra = [])
    {
        $this->kind = 'known';
    }
}
```

Для класса зарегистрированы внешние правила, включая extras. Преобразование
`['id' => 7, 'kind' => 'known']` вызывает конструктор, а затем завершается:

```text
ConfigurationException:
DTO hydration property already initialized before fallback assignment: ConstructorOwned::$kind
```

Это воспроизводится самостоятельно, в элементе списка и через Returns/unwrap
после HTTP 200: U15–U17. При `kind = 'other'` получается та же ошибка заполнения,
а отсутствие kind даёт required_field_missing: U18–U19.

Основание —
[Hydrator::assignPropertyValues](https://github.com/brahmic/apisutra/blob/6a649f5e247adba3ecc0c82f1ba68cb74c018aba/src/Serialization/Hydrator.php).

### Требуемый контракт

Нужен поддерживаемый способ внешне описать построение и проверку такого класса,
сохранив ответственность конструктора за его инварианты. Целевой DTO не должен
получать наследование, интерфейсы или атрибуты библиотеки только ради этого случая.

Допустима явная политика для свойства или другой компактный контракт библиотеки.
Названия новых методов не предписываются. Если существующее средство уже решает
сценарий без повторного mapper и копии DTO, достаточно показать его и подтвердить
критерии ниже. Переход на небезопасную инициализацию без конструктора не подходит.

### Критерии приёмки

1. При настроенном контракте корректный вход создаёт DTO с id=7 и kind=known;
   конструктор вызывается ровно один раз. Повторной записи readonly-свойства нет.
2. Значение источника, объявленное частью контракта, проверяется. Несовпадение
   `kind = 'other'` не игнорируется и не перезаписывает результат конструктора.
   Это ошибка входных данных с reason и путём, а не ConfigurationException
   от попытки повторной записи. Строгие scalar-типы продолжают действовать.
3. Обязательность определяется явно объявленными правилами. Сам факт назначения
   свойства конструктором не делает отсутствующее поле автоматически допустимым.
   Обязательный missing и запрещённый null сохраняют свои ошибки; допустимое
   отсутствие при соответствующей политике должно иметь описанную семантику.
4. Работают переименование и dot-path. Проверенное поле учитывается как
   потреблённое при сборе extras; соседние и неизвестные данные сохраняются.
5. Один набор правил применяется самостоятельно, во вложенном DTO/списке
   и через Returns с unwrap. Ошибка конфликта сохраняет расположение в источнике,
   например `/data/items/0/kind`, без утечки значения в стандартную диагностику.
6. Некорректная декларация по-прежнему даёт ошибку конфигурации; корректная
   декларация с плохим ответом — ошибку гидратации. При HTTP-выполнении сохраняются
   ответ и статус для классификации результата вызывающим SDK.
7. Не нарушается обычное заполнение ещё не инициализированных свойств, работа
   promoted parameters и изоляция наборов правил разных клиентов. Явная opt-in
   семантика допустима; глобально менять правила всех DTO не требуется.

**Не требуется:** универсальная проверка бизнес-инвариантов, знание конкретного
discriminator провайдера или молчаливый пропуск всех свойств, заполненных конструктором.

## AS-6. Корректное копирование и переопределение конфигурации кеша

**Приоритет: P2. Тип: воспроизведённые дефекты копирования и уточнение контракта null.**

### Сценарии и текущее поведение

`$store` ниже — обычное PSR-16 хранилище. Сначала задаются хранилище и параметры
двумя аргументами:

```php
$config = new ClientConfig(
    baseUrl: 'https://example.invalid',
    cache: $store,
    cacheConfig: new CacheConfig(ttl: 60),
);

$copy = $config->with(timeout: 7);
$anotherCopy = $config->with();
```

Оригинал кеширует повторный GET. Обе копии теряют хранилище; повторный GET снова
доходит до транспорта. **U13–U14.**

Другой поддерживаемый способ задания кеша:

```php
$config = new ClientConfig(
    baseUrl: 'https://example.invalid',
    cache: new CacheConfig(store: $store, ttl: 60),
);

$copy = $config->with(cacheConfig: new CacheConfig(store: $otherStore, ttl: 10));
```

В копии остаётся прежний CacheConfig с TTL 60. **U06.**

Наконец, `with(cache: null)` оставляет кеширование через прежний cacheConfig:
поле cache становится null, но повторный запрос всё ещё берётся из кеша. **U07.**
Замена через `with(cache: $newCacheConfig)` и очистка обоих параметров работают:
**U08–U09**. Эти обходы не исправляют копирование с несвязанным override.

Причина по коду: нормализация конструктора и аргументы, формируемые `with()`,
по-разному трактуют пару cache/cacheConfig.
[ClientConfig](https://github.com/brahmic/apisutra/blob/6a649f5e247adba3ecc0c82f1ba68cb74c018aba/src/Config/ClientConfig.php),
[применение кеша](https://github.com/brahmic/apisutra/blob/6a649f5e247adba3ecc0c82f1ba68cb74c018aba/src/Pipeline/Cache/CacheManager.php).

### Требуемый контракт и критерии приёмки

1. `with()` без overrides сохраняет эффективную конфигурацию кеша для каждого
   поддерживаемого способа её задания. Сохраняется тот же экземпляр хранилища,
   TTL, prefix, mode, identity и locks; глубокое клонирование сервисов не требуется.
2. Изменение несвязанного параметра, например timeout, не меняет кеширование.
   Проверка выполняется и по свойствам конфигурации, и двумя одинаковыми GET:
   при разрешённом кешировании до транспорта доходит только первый.
3. Явная замена поддерживаемого блока применяется. Новый cacheConfig не может
   быть молча проигнорирован из-за восстановленного старого аргумента cache.
   Если комбинация новых аргументов противоречива, есть однозначное правило
   приоритета либо явная ошибка конфигурации, а не скрытый выбор старого значения.
4. Различаются отсутствие override и явно переданный null. Нужно документировать,
   что очищает каждый параметр и как отключить HTTP-кеширование. Если cache=null
   означает отключение, прежний блок не должен сохранять активный кеш. Если это
   только очистка одного источника store, пример отключения должен явно показывать
   полный поддерживаемый способ; изменение этой семантики не навязывается молча.
5. Исходный ClientConfig и уже созданный с ним клиент сохраняют прежнее поведение.
   Копия не очищает и не модифицирует общие данные хранилища как побочный эффект.
6. Нормализация кеша согласована у его потребителей. HTTP cache и auth, если они
   используют конфигурацию store, не должны расходиться из-за того, какой алиас
   заполнил with(). Политику отключения HTTP-кеша и хранения auth следует различать.
7. Задокументировать формы конструктора, замену и отключение; покрыть U06–U09,
   U13–U14. Не требуется менять семантику замены всех вложенных объектов на
   глубокое слияние или вводить общий новый ConfigBuilder.

## Что не запрашивается повторно

- Внешний реестр правил, строгие scalar-типы, extras, list-shape и исходные пути:
  соответствующие механизмы уже появились.
- Несколько extras receivers, специальный тип неизвестного варианта или изменение
  sourcePath после произвольного cast: сначала используются и оцениваются
  существующие точки расширения; доказанного нового общего требования пока нет.
- Автоматическое подключение logger/cache/transport в fromLaravel, включение
  retry по умолчанию или перенос предметных исключений SDK в ApiSutra.
- Новые обещания параллельности, распределённые backend и интеграции с провайдерами:
  эти сценарии не являются условием текущих AS-5/AS-6.

После ответа разработчика следует указать точный release/reference и пример
декларации AS-5, повторить воспроизведение и отдельно принять требуемое поведение.
Совпадение со старым снимком фиксирует старые ограничения, а не успешное исправление.
