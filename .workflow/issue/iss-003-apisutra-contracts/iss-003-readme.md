# ApiSutra 0.3: повторная проверка DTO, конфигурации и оставшихся ограничений

- Дата создания: 2026-09-15
- Дата обновления: 2026-09-15

## Результат и границы

ApiSutra уже предоставляет основные механизмы, ради которых были сформулированы
AS-1–AS-4: внешние правила для чистых DTO, строгие scalar-типы, сбор дополнительных
полей, формы списков и пути исходных данных. Повторять прежнее задание целиком
не требуется. Полная эквивалентность всего графа моделей MaxSutra пока не принята.

Остались два конкретных предмета доработки:

- **F01 / AS-5, P1:** поддерживаемое построение DTO со свойством, которое уже
  инициализировал конструктор; сейчас корректный вход заканчивается исключением.
- **F02 / AS-6, P2:** корректное копирование и переопределение настроек кеша;
  `with()` может потерять хранилище или проигнорировать новый блок настроек.

[Требования разработчику](upstream-requirements.md) сформулированы отдельно,
без сущностей MAX, зависимости от Laravel и навязывания названий будущего API.
Наличие этого документа не означает его передачу разработчику или согласование
конкретной реализации. Аудит не начинает [план 007](../../current/pln-007-apisutra-reuse.md)
и не меняет архитектурные границы пакета.

## Объект и методика

- MaxSutra: `9681b288d602394756a93d346dc1ea483f0fc9f8`.
- Установленная ApiSutra: **v0.3.0-alpha.1**, reference
  **`6a649f5e247adba3ecc0c82f1ba68cb74c018aba`**.
- PHP 8.5.4; одна принятая среда. Версия зависимости не обновлялась.
- Прочитаны исходники, декларации запросов, hydration rules, ClientConfig,
  применение настроек в pipeline и документация зависимости на этом reference.
- Сохранены **58 наблюдений**: P01–P39 о преобразовании/интеграции и U01–U19
  о конфигурации/агностичном воспроизведении. Все повторно выполнены из каталога
  аудита. [Инструкции и результаты](artifacts/README.md).

Скрипты используют синтетические данные и искусственный PSR-18 клиент под настоящим
HttpTransport ApiSutra. Сети, токенов ботов, Redis и загрузки Laravel-приложения нет.
`upstream-probe.php` не зависит от классов MaxSutra. Это воспроизводимый аудит,
а не новый постоянный набор тестов Composer. Успешное сравнение со снимком означает
повторение наблюдений, включая обнаруженные ограничения.

Историческая база — [aud-001 на версии 0.2](../aud-001-apisutra-reuse/aud-001-readme.md).
Её результаты не выдаются за проверку новой версии. Этот аудит не проверяет каждую
функцию зависимости, производительность и распределённое исполнение.

Политики входящих DTO, исходящего body и параметров запроса независимы.
`ClientConfig::casts` не заменяет hydration rules, а входной naming не задаёт
исходящий JSON автоматически. P19 подтверждает исключение receiver из body,
но не симметричное преобразование остальных имён. Отправка целого SendMessage
как body по-прежнему неверна: часть полей относится к query.

## Находки

### F01 — P1: конструктор уже заполнил readonly-свойство

**Статус:** воспроизведённое ограничение штатного построения DTO.

У CallbackButton и InlineKeyboardAttachment конструктор назначает `type`.
Гидратор сначала вызывает конструктор, затем пытается заполнить это свойство
через fallback и получает ConfigurationException. Тот же результат получен
на нейтральном ConstructorOwned с `kind = 'known'`, без типов MaxSutra.

P22–P23 и P27–P28; U15–U19 воспроизводят самостоятельный вызов, элемент списка,
`Returns` после HTTP 200, конфликтующее и отсутствующее значение. В HTTP-проверке
статус сохраняется, но построение неуспешно.

Основание: проверка `isInitialized()` в
[Hydrator::assignPropertyValues](https://github.com/brahmic/apisutra/blob/6a649f5e247adba3ecc0c82f1ba68cb74c018aba/src/Serialization/Hydrator.php).
Нельзя исправлять это слепым пропуском всех уже заполненных свойств: тогда
конфликтующее значение ответа может остаться непроверенным.

**Действие:** [AS-5](upstream-requirements.md#as-5-построение-dto-со-свойствами-инициализированными-конструктором).
Это блокирует прямой перенос известных вариантов вложений, но не отдельный BotInfo.
Изменять публичные модели или вводить их зеркальные копии ради обхода не рекомендуется.

### F02 — P2: with() не сохраняет и не всегда заменяет кеш

**Статус:** два воспроизведённых дефекта копирования и неоднозначность отключения.

1. При `cache: $store, cacheConfig: new CacheConfig(ttl: 60)` конфигурация работает.
   После `with(timeout: 7)` или даже `with()` хранилище теряется: два одинаковых GET
   выполняют два HTTP-вызова вместо одного. U13–U14.
2. После `cache: new CacheConfig(...)` вызов `with(cacheConfig: $replacement)`
   оставляет старые параметры. В U06 остаётся TTL 60 вместо переданного TTL 10.
3. `with(cache: null)` сохраняет действующий `cacheConfig`; повторный GET берётся
   из кеша. U07. Это требует однозначного публичного контракта отключения.

Причина по коду: `with()` передаёт `$this->cacheConfig ?? $this->cache` как `cache`,
а конструктор при таком CacheConfig выбирает его вместо отдельного `cacheConfig`.
[ClientConfig](https://github.com/brahmic/apisutra/blob/6a649f5e247adba3ecc0c82f1ba68cb74c018aba/src/Config/ClientConfig.php),
[CacheManager](https://github.com/brahmic/apisutra/blob/6a649f5e247adba3ecc0c82f1ba68cb74c018aba/src/Pipeline/Cache/CacheManager.php).

Проверенные обходы: заменять блок через `with(cache: $newCacheConfig)`;
для полного удаления конфигурации кеша передавать `cache: null, cacheConfig: null`.
U08–U09. **Действие:** [AS-6](upstream-requirements.md#as-6-корректное-копирование-и-переопределение-конфигурации-кеша).
В MaxSutra кеш пока не включён, поэтому это не блокер текущего переноса DTO.

### F03 — P1: остаточные правила моделей ещё требуют приёмки

**Статус:** подтверждённые различия контрактов и работа интегратора;
не доказательство отсутствия нужных точек расширения ApiSutra.

- KeepRaw сохраняет неизвестный вариант массивом, а наш API обещает RawAttachment /
  RawButton. Нужна небольшая явная фабрика. P21.
- Один DTO имеет один extras receiver; повторная декларация отклоняется. P34.
  Для плоской модели с отдельными `extra` и `payloadExtra` ещё нужно подтвердить
  компактное преобразование без повторного generic mapper.
- Текущий Payload требует строковые ключи объекта. ApiSutra принимает проверенный
  словарь с числовым дополнительным ключом. P35. Это различие локальной политики:
  числовое имя ключа допустимо в JSON-объекте, поэтому само по себе не дефект ApiSutra.
- Scoped cast использует тот же строгий набор, но происхождение после произвольного
  преобразования ограничено границей cast: `/rows/0`, kind=boundary. P29.
  Это документированная точность, а не ошибка, которую надо исправлять выдуманным путём.

**Действие:** проверить небольшой cast/фабрику для этих случаев в части B плана.
Не отправлять требования о нескольких receivers или специальном raw-типе upstream
до демонстрации, почему существующего расширения недостаточно. Не объявлять весь
граф Message принятым после одного успешного BotInfo.

### F04 — P1: перевод ошибок должен учитывать новое выполнение

**Статус:** рекомендация по интеграции, основанная на коде и P17/U17.

[ApiSutraExecutor](../../../src/Core/Internal/ApiSutra/ApiSutraExecutor.php) сейчас
обобщает неуспех при 2xx и использует прежнюю классификацию исключений.
После подключения Returns появятся ошибки гидратации и конфигурации, которые
нельзя все считать транспортным сбоем или повреждённым ответом провайдера.

**Действие:** переводить категории ExecutionResult в собственные Errors,
сохранять безопасный путь и HTTP-контекст; после изменяющего запроса сохранять
OutcomeUnknown там, где исход неизвестен. Это работа MaxSutra, не требование
добавить его исключения в ApiSutra. Готовый `errorMapper` зависимости не заменяет
такую политику автоматически.

## Конфигурация: подтверждённые особенности без новых требований

- `with()` неизменяем относительно исходной конфигурации и не перенастраивает
  уже созданный клиент. Объекты зависимостей остаются общими по ссылке. U01.
- Вложенные RetryConfig и массивы заменяются целиком; глубокого слияния нет.
  U02 показывает возврат attempts=3 и потерю прежнего totalTimeoutMs после замены.
- `fromLaravel()` автоматически получает только debug/environment. Логгер,
  кеш, auth и транспорт не подключаются. U03–U04. В Core сохраняется явная сборка
  с NullContainerProvider; зависимости приложения предоставляет Integration/Laravel.
- Retry=null и attempts=1 в проверенном GET дают одну попытку; attempts=2 — две.
  U10–U12. Повтор после 401 управляется отдельно. Не менять нынешнюю политику
  отправки при сокращении конфигурации; клиентский default не запрещает все
  возможные переопределения конкретного запроса.
- OriginPolicy, правила redaction, logger и расширения уже доступны. Включать
  кеш, лимиты и распределённый backend следует при соответствующем сценарии,
  а не только ради использования всех настроек.
- Транспорт отдельно от ClientConfig; штатный createDefault не заменяет наши
  настройки CA bundle и запрета редиректов.
- Fake гидратирует DTO, но обходит PSR-транспорт. P32. Один `preventStrayRequests()`
  без fake не блокирует транспорт; `fake([])` вместе с ним блокирует. P33/P36.
  В проверках использовать документированную последовательность, не считать fake
  проверкой конечного HTTP-запроса. Новое upstream-требование здесь не выставляется.
- Наличие Promise само по себе не гарантирует параллельное HTTP I/O:
  текущий HttpTransport::sendAsync вызывает синхронный send. Это наблюдение по коду,
  не измерение производительности и не блокер реализованных операций.

Рекомендация по структуре: общие технические правила собирает существующий
Bootstrap/ClientFactory; Laravel-интеграция передаёт зависимости приложения;
пользователь настраивает бота и нужные эксплуатационные параметры. Публичные
Model/Input, сервисы и fluent-цепочки сохраняют принятую независимость от ApiSutra.
Второй универсальный конфигуратор и зеркало всех его параметров не требуются.

## Выводы

Основной путь упрощения подтверждён: декларативные запросы и общий набор правил
ApiSutra вместо собственного обхода DTO. Существующие механизмы AS-1–AS-4 уже
пригодны для проверенных случаев. Удалять все декодеры пока рано: остаются F01,
приёмка F03 и корректный перевод ошибок F04.

Разработчику подготовлены только AS-5 и AS-6. Конкретные особенности MAX остаются
в адаптере и не превращаются в требования к предметной модели ApiSutra.
План 007 остаётся новым; реализация, ADR о перемещении mapping и изменение docs
этим аудитом не выполнялись.
