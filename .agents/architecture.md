# Архитектура и порядок реализации

## Когда применять

При изменении поведения, контрактов, зависимостей или структуры модулей.
Основа — [AGENTS.md](../AGENTS.md) и описание затронутого механизма в
[документации](../docs/README.md). Для SDK конкретного API дополнительно действуют
[правила провайдеров](providers.md); их раскладка не переносится на ядро.

## Обязательно

- В ядре оставляйте общие механизмы и контракты. Особенности внешнего API принадлежат
  провайдеру; зависимости Laravel — соответствующей интеграции. Не вводите циклы
  между модулями и скрытые зависимости ядра от приложения.
- Сохраняйте опциональность контейнера. Передавайте зависимости явно; существующие
  механизмы auto-resolve используйте в предусмотренных точках интеграции.
  Не добавляйте обращения к глобальному контейнеру внутрь вычислений.
- Сохраняйте публичные контракты и поведение при рефакторинге. Если задача меняет
  поведение или совместимость, явно описывайте это и проверяйте затронутые сценарии.
  Общие рекомендации ниже не являются основанием для массовой переделки API.
- Соблюдайте действующий контракт результатов и ошибок: result-first поведение,
  режимы выбрасывания исключений и управляющие исключения пайплайна.
  Не превращайте ошибки в видимый успех и не раскрывайте чувствительные данные.
  Подробности — в [руководстве по ошибкам](../docs/reference/results/handles.md).
- Различайте асинхронный интерфейс и параллельное выполнение I/O. Синхронный вызов
  внутри `sendAsync()` допустим: так устроен текущий
  [HttpTransport](../src/Transport/HttpTransport.php). Наличие promise не гарантирует
  неблокирующий транспорт; смена этой семантики должна входить в задачу.

## Рекомендации по проектированию

- Начинайте с существующего механизма. Ясность, одна ответственность, подстановка
  реализаций по контракту и небольшие интерфейсы важнее формального числа слоёв.
  Предпочитайте композицию; наследование подходит реальной связи базового
  и специализированного типов с сохранением контракта.
- Обязательные зависимости передавайте через конструктор, данные конкретного
  вызова — через параметры метода. Общие ключи и значимые значения именуйте явно,
  не создавая константу для каждого локального литерала.
- Отделяйте вычисления и построение данных от HTTP, хранения и других эффектов.
  Оркестратор задаёт порядок шагов; самостоятельные правила остаются в профильных
  компонентах. Объект результата может сообщать следующий шаг, если решение
  о способе исполнения принадлежит вызывающему коду.
- Выделяйте компонент при отдельной причине изменения, повторяющемся правиле,
  вариативности поведения или необходимости изолированной проверки. Длина метода
  и несколько похожих строк — повод оценить читаемость, а не обязательство
  создавать класс, интерфейс или вспомогательный метод.
- Нормализуйте вход на границе, сохраняйте разрешённые метаданные в подходящем
  контексте, делайте приоритеты обработчиков явными. Переиспользуйте собранные
  зависимости только в пределах их срока жизни и области действия.
- DTO передаёт данные, VO выражает значение и его инварианты. Не помещайте в них
  I/O или оркестрацию; отсутствие бизнес-логики в DTO само по себе не недостаток.
  Коллекция оправдана общими правилами, типами и повторными вычислениями над набором;
  для простой локальной передачи данных достаточно массива.

Выбирайте паттерн под конкретную потребность:

| Потребность | Подход |
| --- | --- |
| Сложная сборка или много вариантов настройки | Фабрика или builder; сначала проверьте, достаточно ли конструктора и существующей конфигурации |
| Общий каталог реализаций | Registry с явной областью действия и жизненным циклом |
| Внешний интерфейс или сложная подсистема | Adapter или обычный фасад; это не требование использовать Laravel Facade |
| Варианты алгоритма, последовательная обработка | Strategy или pipeline/цепочка с явным порядком |
| Независимые реакции на событие | Observer/события, если они не скрывают обязательный поток выполнения |

## Порядок работы

Для существенного изменения:

1. Опишите цель, границы, критерии готовности и значимые ограничения: совместимость,
   производительность, ресурсы и безопасность. Используйте уже известный контекст задачи.
2. Найдите существующие реализации, термины и тесты. Определите основные, граничные
   и ошибочные сценарии, инварианты данных и ожидаемые результаты.
3. Наметьте минимальный поток: компоненты, зависимости, входы/выходы, ошибки
   и побочные эффекты. Новые абстракции вводите при подтверждённой необходимости.
4. Реализуйте контракты и типы, порядок шагов, сами шаги, адаптеры и сборку зависимостей
   в удобном для проверки порядке; переиспользуйте существующее.
5. Проверьте поведение по [правилам тестирования](testing.md), обновите затронутую
   документацию. Убедитесь, что нет лишних абстракций, циклов и скрытых эффектов.

Глубина проработки соответствует масштабу задачи: небольшая правка не требует
полного проектного документа. Планы, аудиты и решения, когда они нужны, храните
в [.workflow](../.workflow/README.md); не дублируйте их в правилах.

## Повторное выполнение

Детерминированность — одинаковый результат при одинаковых входных данных и условиях.
Идемпотентность — повторное выполнение операции не добавляет эффектов относительно
однократного выполнения. Работа с сетью или состоянием сама по себе её не исключает.
Retry допустим при подтверждённой безопасности повтора по контракту операции;
подробности — в [Retry и Rate Limit](../docs/reference/execution/README.md).
