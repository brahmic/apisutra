# Правила тестирования

## Когда применять

При изменении поведения пакета, тестов, фикстур или тестовой инфраструктуры.
Стиль PHP — в [правилах кода](code-style.md); команды установки и запуска —
в [AGENTS.md](../AGENTS.md#проверка-изменений). Тесты используют локальные зависимости
пакета; внешнее приложение и база данных не нужны.

## Обязательно

- Проверяйте наблюдаемое поведение и контракты, включая значимые ошибки и границы.
  Для исправления дефекта воспроизводите затронутый сценарий. Не закрепляйте
  внутреннее устройство класса проверками приватных методов.
- Изолируйте обычные тесты от реального HTTP и внешних сервисов. Используйте fake
  или тестовый транспорт; случайный запрос должен выявляться настройками стенда.
  Настоящие запросы относятся к отдельным live-сценариям.
- Обеспечивайте независимость от порядка запуска. Контролируйте время, случайность,
  ожидания и изменяемое глобальное состояние; используйте существующий сброс из
  [tests/Pest.php](../tests/Pest.php) и дополняйте его при появлении нового состояния.
- Соблюдайте размещение и автозагрузку тестовых типов из таблицы ниже. При изменении
  namespace или пути обновляйте локальный `autoload-dev` и затронутые ссылки.
- Не сохраняйте реальные секреты в фикстурах и ожидаемых результатах. Для сценариев
  аутентификации используйте искусственные значения.

## Структура и данные

| Место | Назначение |
| --- | --- |
| `tests/Unit/` | Тесты по механизмам пакета; здесь также есть проверки взаимодействия компонентов |
| `tests/Stubs/` | Именованные тестовые реализации и модельные провайдеры |
| `tests/Support/` | Общие инструменты стенда, helper-классы, fake-транспорт и сброс состояния |
| `tests/Fixtures/` | Файловые данные и ответы для сценариев |
| `tests/Fixtures/Acme/` | PHP-фикстуры внешних пакетов для discovery с отдельными namespace `Acme` |
| `src/Testing/` | Публичные инструменты тестирования для потребителей SDK; это часть поставляемого API |

Именованные вспомогательные типы выносите из файлов тестов в подходящий каталог.
Для небольшого одноразового double допустим анонимный класс. Pest-файлы с функциями
`describe()`/`it()` не требуют namespace только из-за своего пути; именованные типы
следуют [настройкам автозагрузки](../composer.json).
Для примеров в документации действуют [отдельные правила](documentation.md):
там используются именованные классы.

## Рекомендации

- Чистые вычисления и инварианты проверяйте изолированно; взаимодействие пайплайна,
  транспорта, сериализации и результатов — интеграционными сценариями. Laravel-
  интеграцию проверяйте отдельно от поведения ядра. Соотношение уровней определяйте
  рисками, а не фиксированной квотой.
- Используйте реальные DTO и VO. Подменяйте прежде всего внешние зависимости
  через их контракты; глубокие цепочки моков — повод пересмотреть границу теста.
  Не перепроверяйте внутреннюю реализацию фреймворка или сторонней библиотеки,
  но проверяйте собственную интеграцию с ними. Тривиальные getter/setter требуют
  отдельных тестов, только если за ними стоит поведение или инвариант.
- Для устойчивых сложных ответов используйте фикстуры, для вариантов данных —
  фабрики и datasets с воспроизводимыми значениями.
- Пишите понятные описания сценариев в `describe()`/`it()`/`test()` и сохраняйте
  порядок Arrange → Act → Assert. Связанные утверждения удобно объединять через
  `expect(...)->and(...)`, пока это не мешает чтению и диагностике.
- Для идемпотентной операции проверяйте отсутствие дополнительных эффектов
  после повтора; совпадения двух возвращённых значений недостаточно.
  Для retry проверяйте число попыток и безопасность повторяемой операции.
- Не вводите универсальные лимиты длительности теста и проценты покрытия.
  Выбирайте проверки по риску изменения; производительность измеряйте отдельным
  воспроизводимым сценарием, когда она входит в требования.

## Проверка изменений

Сначала запускайте затронутые тесты, затем расширяйте проверку с учётом общих
зависимостей и риска регрессий. При сбое воспроизведите его и проверьте гипотезу;
не меняйте инфраструктуру без признаков, что причина в ней.
После изменения автозагрузки выполните `composer dump-autoload --optimize --strict-psr`.
Для правок только в документации проверяйте ссылки и точность описания API;
запуск PHP-тестов ради текста не требуется.

Возможности fake, record/playback и проверок контрактов описаны в
[гайде тестирования](../docs/guides/testing/unit.md). Live-тесты требуют условий
конкретного провайдера и отдельного запуска; см.
[live-тестирование](../docs/reference/testing/live.md) и [правила провайдеров](providers.md).
