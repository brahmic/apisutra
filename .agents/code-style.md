# Стиль PHP-кода

## Когда применять

При изменении PHP-кода, тестов и примеров. Базовые требования к версии PHP,
PSR-12, strict types, типизации, импортам и языку комментариев — в
[AGENTS.md](../AGENTS.md). Для публичных примеров дополнительно действуют
[правила документации](documentation.md).

## Обязательно

- Имена классов, интерфейсов, трейтов и enum — PascalCase; методов и свойств —
  camelCase; констант — UPPER_SNAKE_CASE. Сохраняйте совместимость публичных имён.
- Новые именованные типы размещайте по одному в файле с namespace и путём,
  соответствующими автозагрузке в [composer.json](../composer.json).
  Размещение тестовых типов описано в [правилах тестирования](testing.md).
- Уточняйте содержимое массивов в PHPDoc: тип элементов, ключей или форму данных.
  Используйте `mixed`, когда контракт допускает произвольное значение, например
  при сериализации; для известного набора типов задавайте конкретный или union-тип.
- Различайте отсутствие значения, допустимый `null` и ошибку. Значения по умолчанию
  и null-safe доступ не должны скрывать нарушение контракта.
- Для API неизменяемых объектов методы `withX()` возвращают новый объект,
  сохраняя исходный. Property hooks и ограничение записи сами по себе этого
  не обеспечивают. Изменение переданных объектов допустимо, если предусмотрено
  контрактом, например при работе с `PipelineContext`.

## Рекомендации

- Предпочитайте `readonly` для VO, DTO и дескрипторов, которые после создания
  не меняются. Учитывайте назначение объекта, а не только имя или каталог;
  состояние исполнения может быть изменяемым. Базовые типы оставляйте расширяемыми.
- Используйте constructor promotion, именованные аргументы, типизированные
  константы и возможности поддерживаемой версии PHP, когда они упрощают чтение.
  `match` удобен для выбора значения; ранние возвраты уменьшают вложенность.
  Выбор конструкции определяется смыслом, а не числом ветвей.
- Enum подходит замкнутому набору вариантов, константа — устойчивому значению,
  конфигурация — настраиваемой политике. Не заменяйте одно другим механически.
- Применяйте `Override`, `Deprecated` и `SensitiveParameter` по назначению,
  с импортами `use`. Маскирование параметров в стеке не заменяет очистку
  чувствительных данных в логах, результатах и фикстурах.
- Используйте `??`, `?->` и Null Object, если они точно отражают семантику
  отсутствующего значения. Не создавайте отдельный тип ради устранения одной проверки.

Декомпозиция, обработка ошибок и выбор паттернов — в
[архитектурных правилах](architecture.md).
